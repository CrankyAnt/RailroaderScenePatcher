# Apply fixed placement through the core engine

The core library exposes `RailroaderScenePatcher.Core.PatchEngine` over an `IScene` adapter. The engine owns scene patch file parsing, map-context matching, dependency ordering, target uniqueness checks, preflight, snapshot, mutation, and failure handling. `SceneCapabilities` assembles the scene of a load from independent capability adapters: `LocationSigns` for location signs, over the native `BoardScene` port, `BridgeScene` for the Ela bridge, `TrackMarkerScene` for Generic track markers, `CrossingPadScene` for crossing pads, `StarterPlacementScene` for starter placement markers and `StationMapIconScene` for station map icons. It reports the active map definition identifier and its resolved map layers. An isolated native test on Railroader 0.6.2 build 26335745 verified fixed placement, origin conversion, culler and mask updates, settled terrain work and declarative restoration. The core tests use controlled scenes for failure injection; native mutation-failure rollback and live multiplayer behavior remain unproven.

## Implement the scene adapter

`LocationSigns` in the core library implements `IScene` for the location-sign pattern. It holds the capability's rules and talks to the game only through `IBoardWorld`, which the native `BoardScene` implements with reflection on the game's members. The core tests drive `LocationSigns` through a controlled `IBoardWorld` that models the culler, mask and terrain lifecycle.

- `MapIds` returns the selected map definition identifier and identifiers for its resolved map layers.
- `Capability` remains `Unchecked`. `BoardScene` checks the required native types, methods, fields and events when it is constructed; missing prerequisites prevent initialization.
- `Resolve` matches the scene name, full hierarchy path and culler component, and accepts no other `structure` than `location-sign-v1`. `Refusal` names why an object does not match the pattern: a missing or disabled culler, other than exactly one enabled circle mask, an inactive parent, or another dependency in the hierarchy (`Track.*`, another culler, mask component or culling handler, a missing script). A mask that flattens the terrain height is no refusal: the location sign's own rebuild and terrain tracking cover it (`BoardFacts.FlattensHeight` stays observed). `Preflight` throws with that reason. The location sign itself may be inactive through an explicit disable. The inventory uses the same `Refusal` for its problems.
- `Read` returns the complete current state: position in map coordinates, rotation, and activity. `Apply` takes an `ObjectState`; a null placement or activity leaves that part untouched. `BoardScene` converts map coordinates with `Helpers.WorldTransformer` and checks the round trip. For an active location sign `Apply` requests `RequestUpdateCullingPosition` and calls the circle map mask's `Rebuild` method. Enabling and disabling rely on the `OnEnable` and `OnDisable` of the culler and mask; an inactive location sign gets no culling or mask call.
- After every application `Apply` verifies the placement, the activity and the registrations: `BoardScene.Registration` reads the culler's culling-sphere center and the location sign's mask keys in the terrain system's modifier storage. An active location sign must have its sphere and every mask descriptor at its position, with no key missing from storage; a disabled location sign must hold neither. A mismatch throws, so the engine or session restores the captured state.
- `Capture` and `Restore` handle position, rotation, parent, and active state. `Restore` reapplies the snapshot with the same verification.

### Dependent output

`IDependentOutputScene` describes native writes that follow a mutation asynchronously. `Output(target)` returns a `DependentOutput` with the completed and outstanding writes and an error when they stopped; `RetryOutput(target)` requests the outstanding writes again. `LocationSigns` implements it for generated terrain output through `TerrainOutput`, the tracker that the scene ground masks share (see [scene ground masks](#scene-ground-masks)):

- Each mask change records the location sign's old and new positions. A position whose tile `ITerrainWorld.TileLoaded` reports unbuilt is complete at once, because the game builds that tile later from the current masks.
- `Poll`, called every frame by the entry point, completes a position after an `OnTileBuilt` notification covering it, once terrain work is idle with no pending invalidations. A position whose tile unloads completes for the same reason. A position still outstanding 30 seconds after the last mask change sets the error. `Failures` lists the edited objects whose output stopped.
- `RetryOutput` invalidates the tiles of the outstanding positions through the game's public `MapManager.Invalidate(Vector2Int)` and restarts the timer.

The engine uses the output to guard retries. After a mutation fails and `Restore` verifies, the target stays guarded while its restored output is outstanding, and the guard lifts once that output completes. Output that stops turns the guard into unverified cleanup. `PatchEditingSession` exposes `Output` and `RetryOutput` for the Scene Patcher window, applies the same guard to a failed edit, and `Recheck` requests stopped output again. Generated terrain output is not a Save participant: Save does not write the output generated from location sign masks, and the game regenerates it from the saved placement on load. Native edited terrain tiles are a separate native Save concern; the location sign capability does not change them.

### Scene ground masks

`GroundMasks` in the core library holds the rules of the scene ground masks of complexes, of bridges, mileposts, crossing pads, station map icons and spawn points, and of Generic track marker objects such as Hemingway flagstopstation. It talks to the game through `IGroundMaskWorld`, which extends `ITerrainWorld`. `Masks(target)` returns a copied `GroundMaskState` for each mask at or below a top scene object, child object or marker object: its holder's name, whether it is enabled, whether it flattens the height, its center and axis in map coordinates, its modifier count, its registrations and its missing keys. `Rebuild(target, id)` calls the game's `MaskComponentBase.Rebuild`. `GroundMaskWorld` implements both with reflection on the mask components (`Map.Runtime.MaskComponents.MaskComponentBase`, its `_modifierKeys`, the `flattenHeightmap` field of the shaped masks, and the `sizeX`, `sizeZ` and `degrees` fields of `RectangleMapMask`) and on the terrain access of `BoardScene` (`StoredModifier`, the tile functions and the tile events). Objects the game builds while it runs, marked `HideFlags.DontSave`, count as no mask. A mask follows its holder whichever edit moves it: `GroundMaskWorld.Components` reads every mask at and below the edited object, a location sign carried along below it included, and leaves out only a mask on the edited object itself when that object is a location sign (`GroundMasks.MovedByEdit`, with `GroundMasks.HeldByBoard`: a renderer culler and a circle mask without a `Track.*` component, such as a Loc: location sign). The location sign family rebuilds that mask itself, so each mask is handled once. The members are checked at construction, and the world that passed the check owns `GroundMaskWorld.Available` (a `WorldOwnedFlag`): a map context change builds the next host before Unity destroys the earlier one, and the earlier host's teardown leaves the next world's availability standing. `PatcherBehaviour.Release` acts only once, so that the `OnDestroy` release at the end of the frame touches nothing the next host set up. The members checked are: the mask components and their fields, and the fields `kind`, `biomeCode` and `maskName` of the mask target type, which is the element of `maskTargets`. A missing one leaves `GroundMaskWorld.Available` false, and `GroupWorld.MaskProblem` then refuses a top scene object that holds a mask. The adapter's model of the game follows `Map.Runtime.dll` of Railroader 0.6.3, as the comments in `GroundMaskWorld` cite it: `MapMaskBase.ApplyModifiers` and `TryCreateModifier` for the modifier count, and `RectangleMapMask.MakeMaskDescriptor`, `RectangleMaskDescriptor` and `MaskRotation.YawDegrees` for the center and direction. The model was read from the decompiled `Map.Runtime.dll` of that version, which is not part of the repository; a Railroader run remains the check of the running game.

A mask that flattens the terrain height takes the same route as any other: no placement is refused for it. The game builds a terrain tile from its base heights and the masks registered on it (Railroader 0.6.3, `Map.Runtime.dll`: `MapMaskBase.ApplyModifiers` adds a `HeightmapModifier` for `flattenHeightmap`, `MaskComponentBase.OnDisable` and `Rebuild` remove the stored modifiers, and `TerrainBuilder.TerraformCore` builds the heights of a tile from the base heights and the stored modifiers), so a rebuild at the new place leaves the old place at its height without the mask. `GroundMaskState.Flattens` stays observed for the inspector's dependency line. A native journey compares the terrain height at the old and the new place with the [terrain height readout](terrain-height-readout.md).

`MaskFollowing` wraps `GroundMasks` for a capability whose holder is one object: `BridgeScene`, `MilepostScene`, `CrossingPadScene`, `StationMapIconScene`, `SpawnPointScene` and `TrackMarkerScene`. `Write(target, change)` observes the masks at and below the object, runs the change and calls `Follow(target, target, before)`; `Restore(target, restore)` runs the capability's own restoration and then `Follow`, and reports false when either fails. Each of these capabilities implements `IDependentOutputScene` through it, so the **Changes** tab shows the terrain output. `Use` gives a capability built before the world's masks existed, the marker and spawn point capabilities that a new game's start prepares, those masks.

`GroundMasks.Follow(target, scope, before)` runs after the apply and after the restoration of a top scene object, child object or marker. It judges and rebuilds only the masks that the edit changed, which `Same` decides from the activity, the missing keys, the registration count and each registration's center and direction. A mask the edit left as it was, such as the station's mask when a sign is disabled, is neither rebuilt nor judged. For each changed mask that is enabled and stale, it calls `Rebuild` and tracks the old registration centers and the new center under `target`. A mask whose activity changed, and so gained or lost its registrations, is tracked at those centers. Afterwards each changed mask must be free of staleness, and `Follow` throws otherwise, so an apply fails and a restoration reports false. A mask is stale when a registration key is missing from the terrain system, its registration count differs from its modifier count, a center lies more than 0.1 from its holder in the ground plane, or its direction differs by more than 0.1 degrees (`Turn`, where opposite directions agree). A disabled mask must hold no registration. Enabling and disabling run through the component's own `OnEnable` and `OnDisable`; the patcher only rebuilds. In `SceneObjects` and `ChildObjects`, `Apply` observes the masks before it changes the placement and follows them after the culling and placement checks. `Restore` follows them inside its verification, so a mask that does not follow fails the restoration.

`TerrainOutput` is the tracker of both `LocationSigns` and `GroundMasks`, over `ITerrainWorld`. `Track(target, position)` records a position under the edited object, or completes it at once with a note when its tile is not built. `TileBuilt` marks the positions that a built tile covers, `Poll` completes them once terrain work is idle, and a target outstanding for longer than `TerrainOutput.Timeout` (30 seconds) gets an error. `Output`, `RetryOutput`, `Failures`, `Stopped` and `Outstanding` read or request it. `EntryPoint` polls the single `GroundMasks` instance of a scene each frame, which the scene object and child object capabilities and `TrackMarkerScene` share, and reports each failure with the object's path.

### Patcher version per target

`IVersionedScene.MinimumPatcherVersion(target)` returns the patcher version required by a target, or null. `PatchEditingSession.MinimumPatcherVersion` takes the highest of the scene patch file's format requirements and these values. Fixed placement requires `0.1.0`, and generic `active` requires `0.2.0`; target-specific capabilities can raise that base minimum. `LocationSigns` returns `0.5.0` for location signs that match the pattern, other than the legacy Sylva location sign. The Sylva target still uses the pattern checks, but does not raise the pattern-based location sign dependency minimum. Bridge, track-marker relationship and target/group activity, crossing coverage, track-following, scene object and child object capability gates remain `0.5.0`. Runtime reporting adds no scene patch file, schema or capability requirement.

### Objects that stand in a moving frame

A child object of a complex stands in the object directly above it, its top scene object or a child object: without a modification of its own it moves with that object. `ChildObjects.Read` marks the placement of such a child object with `Placement.Frame`, that object's map placement at that moment (`PartObservation.ParentPlacement`). `PatchEngine.Underlying` evaluates a placement with a frame at the frame's placement now, through `IFramedScene.FramePlacement`, which `SceneCapabilities` forwards to the adapter that resolved the object. A removal, an activity-only edit, a revert to the underlying value and the Changes lines therefore use the child object's place in its parent wherever the parent stands. Applied back, a placement with a frame releases the child object; any other placement is a fixed placement that holds it.

`PartHolds` records the fixed placements of child objects and is shared by `SceneObjects` and `ChildObjects`. After a top scene object or a child object moves, every held child object below it is placed again at its fixed placement, each after the held child objects above it, and `IGroupWorld.RefreshCulling` moves the culling spheres and applies the group's `CullingPlan`. Restoration, gizmo previews and repeated application run through the same step, so the result does not depend on key order, load order or a preview. A child object that no longer stands under its identity releases its hold and its own culling (`IRetainedScene.Release`), and holds of destroyed child objects are dropped. A child object that a game-object culler switches reads no activity, so neither the underlying nor a desired state holds one, and `ChildObjects.Apply` never sets it.

A storage pile (`Scenery.Pile`, a `Scenery.BulkScenery`) has no saved renderer or collider, so `SceneObjectRules.Present` counts the pile component itself as physical presence, and the storage displays Andrews Snowbird Paper, Sylva Paperboard and Connelly are complexes with their piles as child objects. The pile computes its logs in map space when it lays them out and keeps a culling sphere of its own in `CullingManager.Scenery`, outside the culler kinds of `GroupObservation`. `GroupWorld` keeps, per pile, the map placement at which it last laid out its logs: read when its group is first observed and after each refresh. `GroupWorld.RefreshCulling` acts only on a pile that stands elsewhere now, so a gizmo drag rebuilds the piles it moves and no other. For such an enabled pile whose sphere is registered and not removed, it calls `RequestUpdateCullingPosition`, then `Rebuild` while the sphere shows (`_cullingVisible`), and destroys the collider mesh the rebuild replaced (`Pile._colliderObject`), which the game leaves. The sphere must then stand at the pile's new map placement with the radius `GetCullingRadius` gives; otherwise the refresh fails with the pile's name and the edit is restored. A disabled pile, or one without a sphere, registers and lays out at its place when it starts again. `GroupWorld.Presence` counts a pile with the cube around its culling radius and leaves out what the game builds while it runs, such as the pile's collider. `GroupWorld.Problem` refuses a top scene object with a pile when one of these members is missing. The storage a pile shows comes from the `Scenery.BulkIndustryStorageSynchronizer` that names it (`NativeInventory.PileStorage`): the industry component and load IDs are a binding, and the storage's name is presentation metadata outside the fingerprint (`SceneObservation.Storage`), so names that resolve after the first discovery never make the inventory stale. A top scene object or child object with piles below it carries `CommandBand.PilesBinding`; `CommandBand.UseInGame` builds the Use in the game text from these.

A log pond (`Scenery.LogPond`) is a `Scenery.BulkScenery` too: `SceneObjectRules.Present` counts the component as physical presence, so the `Whittier Log Pond` complex lists its `LogPond` as a child object beside its lake surface, and `GroupWorld.RefreshCulling` refreshes it as it refreshes a pile. A log pond builds no collider, so the refresh reads the collider field of `Scenery.Pile` only from a pile, and refusal and failure texts name the kind (`SceneObjectRules.BulkKind`, `BulkMembersRefusal`). A lake surface (`LakePolygon`) has no Unity lifecycle method; its water mesh is a mesh renderer on its own object, which the patcher moves through that object's transform. In Railroader 0.6.3 build 26740326 the drawn water followed a moved complex and lake, and none of the base-game map's lake surfaces was statically batched (patcher `ec871d4`). A mesh renderer that is part of a static batch is drawn where the scene had it, so `GroupWorld.PlacementRefusal` refuses the placement of a top scene object or child object with such a lake surface (`GroupWorld.BatchedLake`, `SceneObjectRules.StaticBatchRefusal`). `SceneObjects` and `ChildObjects` ask for it in `CheckRelationships`, which the engine runs before any mutation, and `PlacementGesture` runs that check when a gizmo gesture starts; activity stays editable. The log pond carries the fixed binding `Log pond=this object` and, as a pile does, its storage binding only while a loaded synchronizer names it; a top scene object or child object above it carries `Log ponds below=<count>` (`CommandBand.LogPondBindings`). `CommandBand.UseInGame(part, category, storage, bindings)` chooses the Use in the game text from the bindings alone; the storage's name stays presentation metadata. A lake surface's inspection names `CommandBand.LakeSurfaceDependency`, which says whether its water is part of a static batch. `WorldSelectionOverlay` frames a log pond with the box it lays its logs out in (`SceneObjectRules.LogPondBox`), as it frames a pile.

A car loader (`RollingStock.CarContentSwapper`) has no rule of its own: a top scene object that holds one follows the ordinary scene object and child object rules. The Robinson Gap Mine Coal Loader is such a top scene object; a loader that fills cars is an industry building, so it stands under Industry building, and the game loads Robinson Gap coal by teleport between the industry's native track spans, not at the loader. An object with a `KeyValueBoolAnimator`, one of `SceneObjectRules.Animators`, is animated: the child object rule (`SceneObjectRules.Animates`) and `GroupWorld.AddDriven` both treat such an object and everything below it as animated, so it is no child object and `GroupChecks.Layout` checks only its identity and activity.

A rail bridge outside Ela is a complex; the track it carries stays native map data with its own trestle or steel flags. For such a complex, `GroupWorld.Observe` adds one `ColliderState` per collider the scene saves at and below the root, as the Ela bridge observes its colliders, and a description of the generated trestles within 250 m of the root, selected at its first observation (`BridgeWorld.TrestlesNear`, `DescribeTrestles`). `GroupChecks.Colliders` checks after every top scene object or child object edit and every restore that each collider keeps its identity, shape and enabled state, that the physics bounds of a box, sphere or capsule collider follow its transform, and that the trestle description is unchanged. A difference fails the edit, which restores the captured placement, activity and culling; a restore that cannot verify them reports incomplete cleanup and blocks the retry. `IGroupWorld.FollowingRefusal` refuses a track-following placement of a rail bridge or one of its child objects in `CheckRelationships`, before any mutation (`SceneObjectRules.RailBridgeNoFollowing`).

The construction controller (`Game.Mow.TrackConstructionScenery`) sets the activity of the objects its entries name whenever the construction state of its segments changes. A progression controller (`Game.Progression.ProgressionEntityObjectController`) and a map feature (`Game.Progression.MapFeature`, `gameObjectsEnableOnUnlock`) do the same for the objects of their lists; `GameSwitch` names the three switches. `GameSwitchActivity` in the core shares that activity with the patcher through `IGameSwitchHost`, one instance per loaded world. An explicit disable (`GroupWorld.Switch` for a top scene object or child object; `GameSwitchActivity.SetActivity` and `HoldFollower` through `GroupWorld` from `MapIconWorld.SetActive`, `TrackMarkerWorld.SetActive` and `TrackMarkerWorld.HoldDisabled`) diverts the switches' writes for the object: `GroupWorld.SwitchHost` points every list entry that names the object (`GroupWorld.SwitchLists`) at a hidden stand-in object through `SwitchSlots.Divert`, and the stand-in's `SwitchStandIn` reports each write. The object then stays off, and Enable returns it to the switch's latest choice and puts the entries back (`SwitchSlots.Restore`). Enabling an object whose writes are not diverted makes no stand-in. `SwitchSlots.Divert` puts back every entry it already changed when a write fails part way, and `GameSwitchActivity` records an object only after the host diverted it, so a failed diversion leaves no entry that no record names. Only an object a list names directly is switched; a switch of a folder above it is not. `GameSwitchActivity.HeldAgainst` gives the switches an explicit disable holds the object against, and `GameSwitchActivity.HoldWarning` its amber warning, which `ScenePatcherLayout` shows on the Object tab and in the footer through `GroupWorld.HoldWarning`; for a track-group follower, whose Enable is refused, the warning names Clear activity alone. A station map icon, a track marker that follows no track group and a top scene object that progression or a map feature switches read the mod value of activity (`GameSwitchActivity.ReadActivity`, `GroupWorld.ProgressionEnabled`), so an enabled object that the switch keeps off verifies. A track-group follower reads its own activity; its hold (`HoldDisabled`) also holds it against progression and map features. While an object is held, the reference scan of `NativeInventory` names the switch that holds its stand-in as a referrer of the object (`GroupWorld.HeldThrough`), so its dependencies and the inventory do not change by the hold. `GroupWorld.DisableProblem`, which the station map icon, track marker, scene object and existing crossing equipment capabilities read through `IDisableRefusal`, refuses `active: false` before any change when the disable could not hold: for an object that progression or a map feature switches while the shared activity of the load is unavailable, and for an object that a progression controller or map feature names in any list field while their known members are missing. `GroupWorld` also logs `SwitchMembersProblem` once in that case. The loaded switch components are read again only when the loaded scenes change. After `PartCullingController.Apply`, `GroupWorld.RefreshCulling` calls `GameSwitchActivity.Settle` for every controller target at or below the top scene object. A target that own culling switches, as a moved child object outside its culler's sphere or a node above one, stays diverted, so each controller write reaches own culling through `SetDesired` instead of being frozen at the activity the plan read. A target own culling lets go of goes back to its controller with the controller's current choice. `GroupWorld.Authored` reads a diverted target's activity as the controller's choice unless held, and `GroupWorld.Enabled` reads the mod value of Enabled. Disposing the group world gives every object back to its controller. A segment the track graph no longer holds makes the game's own visibility update fail (`Graph.GetSegment` returns null); the patcher reads the IDs without resolving them and reports no problem for them.
The buildings with pickable toggles (`RollingStock.Controls.KeyValuePickableToggle`), Bryson Section House, Bryson Tower Chance Clayton, Bryson Turntable and Roundhouse 3, are listed complexes with child objects. A toggle holds no position: it is picked through a collider at or below its object (`ObjectPicker`, `GetComponentInParent<IPickable>`), looks up the nearest `KeyValue.Runtime.KeyValueObject` above it when it is first used, and writes its Boolean key through `StateManager` under that object's registered ID. `RollingStock.Controls.GlobalKeyValueObject` registers the key-value object under its serialized `globalObjectId` in `OnEnable` and unregisters it in `OnDisable`; `PropertyObjectManager` saves the values by that ID. A move therefore needs no refresh beyond the complex's culling, and the toggle works at its new place. A lantern's `Effects.LanternController` stands on the toggle's object and observes the same key; a stall's toggle stands on the object with the `KeyValueBoolAnimator` that opens its doors, which the child object rule leaves out with everything below it, so the stall above it is the child object that moves the doors. The lantern's flame, the transform its `LanternController.filamentRenderer` names, is turned to the camera every frame, so `SceneObjectRules.DrivenFields` and `GroupWorld.AddDriven` mark it animated and it is no child object. `GroupWorld.Verdicts` records once per hierarchy change which top scene objects hold a toggle (`GroupWorld.HoldsToggles`). `NativeInventory.InteractiveBindings` reads, only for such a complex, what each top scene object or child object owns: its own object and the objects below it down to the next child object. It adds `CommandBand.ToggleBinding` per toggle with its kind (`CommandBand.ToggleKind`: lantern switch, door toggle or toggle) and key (`CommandBand.ToggleKeyOf`), `CommandBand.KeyObjectBinding` with the global ID (`CommandBand.GlobalIdOf`), `CommandBand.NameTextBinding` with the text of a `TMPro.TextMeshPro`, `CommandBand.KeyObjectsBelowBinding` with the count of key-value objects in the child objects below, whose Use in the game warns that disabling the entry disables them too, and `CommandBand.TogglesBelowBinding` with the count of toggles in the child objects below. These bindings are inside the fingerprint and stay the same while the scene stays. `CommandBand.UseInGame` builds the Use in the game text from them before the decorative text.

### Scene spawn points

`SpawnPointScene` places and enables or disables a scene spawn point (`Character.SpawnPoint`) under `spawn-point-v1`, through `ISpawnPointWorld`; `SpawnPointWorld` is the native adapter. A spawn point has no renderer, collider or culling, and the game reads its transform each time it uses it: `SpawnPoint.All` (`FindObjectsByType`, so active spawn points only, sorted by `priority`) for the default start in `GlobalGameManager.InitializeDefaultSpawnIfNeeded` when the map provides no native spawns (`MapSpawns.Shared` is empty), for the rescue in `PlayerController` through `SpawnPoint.TryClosestTo`, and for `TeleportCommand`; `StateManager.ApplyNewGameSetup` reads `SetupDescriptor.spawnPoint.transform` whatever its activity, for the setup `GetSetupDescriptor` finds among active setups, and only for a company with no cars and a zero balance. In Railroader 0.6.3, a new company game started at the moved spawn point its setup names on a map without native spawns, and `TeleportCommand` used a moved spawn point; the default start without a setup, the rescue and the precedence between native spawns and a setup are not observed. A move therefore writes the transform alone, and `Apply` and `Restore` verify placement and activity. `SpawnPoints.Uses` builds the Object tab's Use in the game lines from the bindings `SpawnPointWorld.Bindings` writes, the native spawn count and a `SpawnRank`. `SpawnPoints.Rank` gives that rank from the inventory: the spawn point's own activity and the other active spawn points, by path, whose priority is the same, higher or unread. `Uses` names the default start here only for an active spawn point with a priority binding, no active spawn point of a higher priority and no native spawns, which is `SpawnPoint.Default`. In a tie it gives one line saying the game starts at one of the tied spawn points, without naming this one as the start, and another active spawn point's unread priority hedges the line. With native spawns, the start setup line names the setup without claiming the start, because the precedence is not settled. The core tests are `SpawnPointTests.RankCountsTheOtherActiveSpawnPoints` and `SpawnPointTests.NewGameStartIsNamedOnlyWhereTheGameStartsThere`.

Both new-game reads run before the mods' `OnWorldLoad`: `GlobalGameManager.LoadMap` ends with `ApplyNewGameSetup`, and `HandleClientDidReceiveSnapshot` calls `InitializeDefaultSpawnIfNeeded` right after `LoadMap` and before `ExecuteMainScriptsOnWorldLoad`. `NewGameStartHook` therefore patches `StateManager.ApplyNewGameSetup` with a prefix that never skips the original. The prefix opens the load attempt through `LocalWorldBinding.Prepare`, as the early marker repair does, and calls `PatchRuntime.BeforeNewGameStart` for each applicable scene patch file. `PatchEngine.BeforeNewGameStart` checks the complete envelope and then runs, through the same `Execute` as the world load, only the spawn point modifications without `dependsOn`, without a track-following placement or relationship, and whose target is unique, not guarded and passes preflight now; any other modification is left untouched without a recorded failure. `Underlying` is captured before that first mutation, so removal still returns the map's placement. The world-load apply runs every modification again. A failed hook install, a missing binding or any exception leaves the game's own start. Because the runtime is now prepared before `Initialize` builds the ground masks, `Initialize` hands them to the marker capability through `TrackMarkerScene.UseMasks`. The core tests are `SpawnPointTests.NewGameStartPlacesSpawnPointsFirst`, `SpawnPointTests.NewGameStartLeavesOtherWorkForTheWorldLoad` and `GroundMaskTests.MarkerSceneBuiltBeforeTheMasksGainsThem`.

### Own culling spheres for moved child objects

No edit changes a culler's radius. A child object that a move takes out of the sphere of a culler above it gets a culling sphere of its own, so the child object shows at any distance and the rest of the group keeps the culler's sphere.

`CullingPlan.Compute` is pure. Its input is the complex observation, the moved child objects and their bounds. `PartHolds.Moved` names the moved child objects: the held child objects whose placement in the object above them differs from the placement recorded before the first hold. An unedited child object is never in the plan. For each moved child object the plan takes the spheres above it, nearest first, and the child object follows the first one that encloses every corner of its bounds within `CullingPlan.Tolerance`. When none encloses it, the plan adds a `PlannedRegion` centered on the bounds. The bounds of a child object leave out the moved child objects below it. `IGroupWorld.Presence` returns no corners for an object without a renderer, collider, light or storage pile at or below it, outside the named child objects. A renderer or collider whose bounds cannot be read, such as a renderer without a mesh on an inactive object or a non-primitive collider that is off, counts as one point at its object, so content the game can switch on later is never taken for an empty object; a moved child object without presence takes `IGroupWorld.Anchor`, its map position, as its bounds, so it gets a sphere of radius zero at its place. The plan handles the three culler kinds separately:

- Simple culler. It switches its whole object. The plan lists a `PlannedNode` for each object whose activity must follow other spheres than its parent's. An object is on while its desired value is on and one of its needed spheres is visible, or the own sphere of a moved child object below it is visible (`CullingActivity.Active`, `PlannedNode.Below`). A child object that a nearer sphere encloses still gets its own sphere when it left the sphere of a simple culler further up. The culler's object and each object between it and the moved child object need the culler's sphere and the child object's own sphere. An object with no moved child object below it needs only the sphere it followed before. A `PlannedHook` names each simple culler whose visibility the plan needs. With `Replace`, the controller's handler takes the place of the game's handler on the culling group. Without it, the game's handler runs first, which is the case for a moved child object with a simple culler of its own.
- Renderer culler. `PlannedHandOver.Follows` names the moved child objects below it. The renderers at and below a child object that left the sphere leave the culler's `_cullRenderers` and follow the own sphere by the culler's rule. A renderer culler on the moved child object itself moves with the child object and keeps its renderers and its radius.
- Game-object culler. A listed object that a move separates from the culler's sphere leaves `gameObjects` and enters the controller's registry. A listed object that stayed inside, with a moved child object below it that follows another sphere, is handed over like a child object that only carries a simple culler. A stand-in sphere with the culler's center, radius and rule takes the object, which is then on while the stand-in or the moved child object's own sphere shows. A listed object whose `Presence` is empty outside its moved child objects, such as the object above a crossing mast, gets no stand-in while every moved child object below it follows an own sphere (a `PlannedRegion`). The first of those spheres takes the object, which is then on while any of them shows, so no sphere stays in the culler's place. Components without presence on that object, such as scripts or audio, then follow the moved child objects' spheres instead of the culler's. When a moved child object below it follows the game's sphere of a simple culler or another stand-in, including the stand-in of a listed object above it, the object keeps the stand-in; the plan reads the own spheres before it plans any stand-in, so the order of the listed objects does not matter. When the sphere that holds a handed-over object changes, for example after one of two moved child objects returns, the controller moves the hand-over to the new sphere. The controller never sets a listed object that it did not take over. `ListedObjects.Union` gives readers the list and the registry together, so `GroupWorld.Switches`, `ActivityRefusal`, `Authored`, the `CullerSwitched` value and the inventory still see the object as listed. The controller puts back only objects it took out, each once, with the culler's current state.

`PartCullingController` applies a plan through `ICullingHost` and keeps what it registered per complex. `Apply` adds, moves and releases spheres, hands renderers and listed objects over and back, and sets the planned objects. `Tick` runs every frame from `PatcherBehaviour.Update`. It installs what waited for a game culler to start, repairs a complex after a failed callback, and drops complexes that no longer exist. A waiting complex keeps the cullers it waits for, and `Tick` applies its plan again only when one of them has started or a sphere that found no culling manager can be registered. `ReleaseAll` gives everything back to the game as if every plan were empty. `GroupWorld.Dispose` calls it through `SceneObjects.Dispose` when the patcher's state for a world ends while the scene stays loaded, and the `GroupWorld` constructor calls it for an earlier controller. `Unload` forgets everything without a host call, and `Apply` does nothing while `ICullingHost.Available` is false, so nothing reads a culling manager while the map unloads. A callback for a released registration, a destroyed manager, child object or culler returns without writing. `Desired` gives the activity that the modder or the scene set for an object the controller switches. `GroupWorld.Observe`, `GroupWorld.Authored` and the inventory report that value, so camera-driven activity is neither an edit nor a reason for a stale inventory.

`PartCullingHost` is the native side. Its constructor checks the private fields it uses and fails with the name of a missing one: `SimpleCuller._cullingGroup`, `RendererCuller._cullRenderers`, `cullingManagerName` and `_cullingState` on both manager-based cullers, `GameObjectCuller.cullingMode` and `CullingManager._spheres`. An own sphere is a `CullingManager.ICullingEventHandler` registered in `CullingManager.Scenery` for a simple culler, or in the culler's own manager with its `visibleDistanceBand` and mode. It keeps its center as an offset in the child object, so `RequestUpdateCullingPosition` keeps it at the child object after a floating-origin shift. The host sets itself unavailable on `MapWillUnloadEvent`. A handler on a simple culler calls the game's handler in its own place once the controller no longer owns the hook, so a handler that stays after an unload only passes events on.

`GroupChecks.Culling` verifies that every culler has the radius the scene gives it, that every planned sphere stands at its child object and encloses it, that no other own sphere remains, and that a disabled complex holds none. A sphere that waits for a game culler to start passes. A handler that the controller could not take out because other code replaced it stays as a pass-through, and `PartCullingController.Report` writes one debug line per such culler through `PatcherLog.Debug`, so it reaches the Player log only while Debug logging is on.

## Implement a relationship capability

`ObjectState.Marker` carries the track-marker relationship: `MarkerBinding.At(TrackLocation)` sets or replaces it, `MarkerBinding.Detached` clears it, and null leaves it untouched. `PatchEngine.Parse` reads it from `relationships.trackMarker`. `Desired` overlays it like placement and activity, so removal recomputes the underlying relationship plus the remaining contributions, and `PatchEditingSession` verifies it with the placement after every change, restoration and `Recheck`.

An adapter that supports relationships implements `IRelationshipScene.CheckRelationships(target, state)`. The engine and `SceneCapabilities` call it for every state of an implementing adapter, not only for states with a relationship, so an adapter can also refuse a setting its relationships make unsupported. The engine calls it after `Preflight` and before capture; `PatchEditingSession` calls it for the modification before its mutation guard, so the underlying relationship may be the broken one being repaired. A scene without `IRelationshipScene` refuses any relationship, and `SceneCapabilities` refuses a relationship on an object whose adapter lacks it.

`TrackMarkerScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ITrackMarkerWorld`, which `TrackMarkerWorld` implements with reflection on `Track.TrackMarker` and `Track.Graph`:

- `PatternProblem` refuses everything except one Generic marker without milepost, crossing pad, crossing parent, location-change listener, `TrackRelativePosition` with group-driven activity that targets another object or whose `_setTargetActive` another component replaced, new-game car placement (`SetupDescriptor.placements[].marker`) or direct reference from any loaded component other than the colocated `TrackRelativePosition._marker`. `TrackMarkerWorld.Problem` is the same check for the inventory, which passes the reference scan and the setup index of its discovery; the adapter scans at most once per frame and builds a setup index per check. `NativeInventory.Discover` walks the fields once, one owner at a time through `ReferenceScan.Begin` so that the stepped discovery can pause between owners: the walk, like `ReferenceScan.Of` with an observer, reads every field of every owner once and hands each value or failure to the dependency strings, while the marker scan applies its own relevance and errors to the same reads. The setup index is a core `HolderIndex`: it walks the setup placements in their original order once, at the first marker that reaches the setup check, holds every marker found before the walk's first read failure and passes that failure to any other marker. Field descriptors and their relevance are cached per type; values are read afresh in every scan, and no scan result, value or error outlives its discovery. The scan is a core `ReferenceScan` over `ReferenceField` values: `ReferenceScan.CanHold` counts a field whose declared type can hold a component, directly or as the element of a non-generic `IList`, an array or a generic `IList<T>`, and the scan enumerates values of those list kinds. A relevant field that cannot be read, a list that cannot be enumerated or an owner whose fields cannot be listed makes the scan incomplete. `Refusal` then refuses every marker, because an unread field may hold any of them.
- `RefreshDependents` and `DependentProblem` hold the consumer state that caches the location. `MapBuilder.Add(MapLabel)` caches the track group from `TrackGroupIdFor(label)`, so the adapter removes and adds every registered label in the hierarchy and compares `_mapLabels` with `TrackGroupIdFor` afterwards. The group subscription has its own members, below.
- `Location` reads the serialized `_location`; `SetLocation` uses the native `Location` setter, which clears the cached pose and does not change the registration.
- `Registrations` reads every entry under the marker ID from `Graph._namedLocationsBySegmentId`; `Unregister` and `Register` call `RemoveNamedLocation` and `AddNamedLocation` as the marker's `OnDisable` and `OnEnable` do.
- `Resolve` starts from the loaded marker components and builds the hierarchy path only for their objects; an object with several markers counts once, so a missing, ambiguous or duplicate identity resolves as before.
- `SegmentLengths` resolves a segment through `Graph.GetSegment`. The graph keys segments by ID, so the native world returns zero or one length.

Sources for the consumers: `Game.Scripting.Modules.Railroader.NativeTrack.GetMarkerLocation` (graph lookup, then the stored location), `UI.Map.MapBuilder.Add` and `TrackGroupIdFor`, `Game.State.CompanyModeSetup.Setup` reading `SetupDescriptor.CarPlacement.marker`, `Game.FlareManager.NearbyFlares` and `Model.AI.AutoEngineerPlanner`, which filter registrations by their own marker types through `Track.NamedLocationExtensions` and `TrackMarkerType`, and `TrackRelativePosition.ConfigureAndApply`, called only from `MapObjectSpawner`, `ObjectsEditor` and `TrackAnchorReposer` for map objects.

- `GroupActivity` reads a `TrackRelativePosition` with group-driven activity: whether the hold is installed, `_observing`, `_observedGroupId`, its `OnGraphGroupEnabledDidChange` handlers on `Graph.GroupEnabledDidChange`, whether the marker location resolves, the segment's `groupId` and whether `Graph.enabledGroupIds` contains it. It returns null for any other object. `ObserveGroup` calls the relative position's private `UnsubscribeFromGroupEvents` and `ObserveTrackGroup`, which subscribe once for the current location's group and set the object's activity from the group. `HoldDisabled` installs or removes the explicit-disable hold: a delegate in `_setTargetActive`, which the native `SetTargetActive` calls instead of `SetActive`, and which keeps the object inactive. `TrackMarkerWorld` keeps the delegate per relative position so it can recognise and release its own hold; the pattern refuses a callback it did not install.

`Preflight` requires the registration rule: one owned registration at the stored location for an enabled, active marker with a resolvable location, none otherwise. `Preflight` and `PreflightPlacement` leave out the marker's own entries under a segment the graph no longer has: a native track edit that removes a segment, such as Dissolve, leaves them until the marker is enabled again, and `Apply` removes them with `Unregister`. The verification after `Apply` counts every entry. `Apply` rewrites the registration and refreshes the dependents when the relationship changes or either disagrees, then applies activity and placement, and verifies location, placement, activity, the registration rule and `DependentProblem`. `Restore` writes the captured location, placement and activity the same way and returns true only when they verify. For a group follower, `Read` reports activity as null (group-driven) unless the hold is installed, so `Desired` keeps group-driven activity when no mod sets `active`, and removal returns to it. A null `Active` therefore has two meanings for a follower, and `ObjectState.LeavesActivity` tells them apart. A complete desired state, as `Desired`, `Restore` and the scene patch editing session's commit, clearing and removal pass it, has the flag unset, and a null `Active` releases the hold. One modification's own state has the flag set through `LeavingActivity()`, and a null `Active` keeps an installed hold; the runtime's `Execute` and `PlacementGesture.Preview` apply such a state. `CheckRelationships` refuses `active: true` on a follower; the engine and `SceneCapabilities` call it for every state of an adapter that implements `IRelationshipScene`, not only for states with a relationship. `Apply` installs the hold and deactivates the object before the relationship step when `active` is false, runs `ObserveGroup` after a rebinding, a release of the hold or a subscription that disagrees with the location, and verifies the subscription and activity with `GroupProblem` beside the registration rule. `Capture` records whether the hold was installed; `Restore` reinstalls or releases it with the captured location. The adapter's capability minimum is `0.5.0` for `track-marker-v1`. `PatchEditingSession.Bind(target, binding, inspected)` sets, replaces or detaches this mod's relationship; a null binding clears it and removes a modification left without content.

## Implement the starter placement capability

`ObjectState.Starter` carries a starter placement: a `StarterSetting` with the `Setup` whose new-game car placement reads the marker, the `Track` location as a `MarkerBinding` and the `Wreck` setting as a `bool?`, where null leaves that setting untouched. `PatchEngine.Parse` reads it from the `starterPlacement` member and reads a `{ "detach": true }` track as `MarkerBinding.Detached`, so the capability refuses it with its reason. `PatchEngine.Overlay` lays it over the underlying state like the other members, so removal recomputes the underlying location plus the remaining contributions. `StarterSetting.Same` compares the track location and the wreck setting; the setup identifies the car placement. Every other capability, and a scene without relationships, refuses a starter placement with `StarterPlacements.NotAStarter`.

`StarterPlacementScene` implements `IScene`, `IRelationshipScene`, `IVersionedScene` and `ITargetConfirmation` over `IStarterPlacementWorld`, which extends `ITrackMarkerWorld` and `IStarterTrack`. It reuses `MarkerRelationship` for the location, the registration rule, capture and restoration, and resolves only identities whose `structure` is `starter-placement-v1`. `Read` returns the object's placement and activity, which it never writes, and a `StarterSetting` with the reader's setup, the current location and the reader's wreck setting. `Apply` writes the wreck setting through `IStarterPlacementWorld.SetWreck` when the state sets one and differs, then the location when the state sets one. `Capture` keeps the marker's snapshot with the reader's wreck setting, and `Restore` returns the wreck setting before the location and verifies both. `CheckRelationships` refuses placement, activity, `trackMarker` and coverage, then asks `StarterSetups.Reader` for the one car placement of an active setup that reads the marker and refuses none, several, unreadable setups and another `setup`. For a track location it refuses a detach, a missing or ambiguous segment and a distance outside the segment, then runs the whole-cut check. The capability minimum is `0.5.0`.

`StarterCutRule` is the game's placement rule from `TrainController.CanPlaceAt` over `IStarterTrack`: `Checked` gives the front, a location every 1.5 m back while the walked distance stays below the cut's length, and the back end, as the game walks them; `Move` throws `StarterTrackException` with the game's reason at the end of the track or a switch lined against the movement, and `Unplaceable` gives the reason for a location that is not on available track. `Body` gives the positions of a placed cut every half metre. `Problem` checks the setup's cuts in placement order, each against the bodies of the cuts before it that passed, with the game's check radius of 0.75 m beside a body half a car wide; it returns the failure of the marker's own cut, or of a later cut that runs into it, and ignores a failure that this cut does not cause. `StarterPlacementScene` implements `IPlannedStateScene`: before a scene patch file's modifications are checked, `PatchEngine.Plan` resolves every modification with `starterPlacement` and passes the desired states, and the whole-cut check judges those markers' cuts at their desired locations instead of their current ones; `ApplyScenePatchFile` and the session's `Commit` call it and clear it again afterwards, and `SceneCapabilities` hands each adapter the states of the objects it resolved. A cut that the rule passed but whose body cannot be followed fails with that reason, and `StarterPlacementWorld` turns every native failure of the walk into a `StarterTrackException` with the reason. `StarterPlacementScene.CutPath` returns the body of the marker's cut at a location, which `PatchEditingSession.StarterCut` exposes for the world marking.

`StarterPlacementWorld` implements `IStarterPlacementWorld` by deriving from `TrackMarkerWorld`. `Belongs` claims a marker that `StarterSetups.Use` reports as used, which `TrackMarkerWorld.Consumers` refuses for the Generic-marker capability; `PatternProblem` checks the marker shape, its ID, location listeners, group-driven activity and direct holders other than the colocated `TrackRelativePosition`. `Setups` reads `TrackMarkerWorld.StarterSetups` once per frame and turns a read failure into `StarterSetups.Unreadable`. `CutLength` invokes `StateManager.DescriptorsForIdentifiers`, which adds each steam locomotive's tender, and `ConsistLength.OfDescriptors`, which adds the drawbar gaps. `Move` invokes `Graph.LocationByMoving` with the switch check and maps `EndOfTrack` and `SwitchAgainstMovement` to the game's reasons. `Unplaceable` reads `TrackSegment.Available` without the sandbox exception, because a new company game is no sandbox. `Position` reads `Graph.GetPosition`. `SetWreck` writes `SetupDescriptor.CarPlacement.wreck` on the native placement that `StarterCarPlacement.Handle` holds and makes the next `Setups` read again.

`PatchEditingSession.PlaceStarter(target, location, inspected)` writes `starterPlacement` with the reader's setup and the location, keeping other members of an existing modification; a new modification's key starts with `starter-`. `ClearStarterTrack` removes the track and the member with it when only `setup` remains. `Normalised` removes a track equal to the underlying one, so placing the marker back on the map's location reverts the setting. `SetStarterWreck(target, wreck, inspected)` writes `wreck` with the reader's setup the same way, and `Normalised` removes a wreck equal to the underlying one, so setting the checkbox back reverts the setting. `StarterWreck` returns the effective setting the checkbox shows, or null when not exactly one car placement reads the marker. `HasStarterTrack` and `HasStarterWreck` read the scene patch file alone. `MinimumPatcherVersion` returns at least `0.5.0` for a modification with `starterPlacement` or a `starter-placement-v1` target.

Timing: `GlobalGameManager` calls `ExecuteMainScriptsOnWorldLoad`, which invokes every mod's `OnWorldLoad` and so the patcher's application, before `StateManager.SessionDidBecomeActive`, which runs `CompanyModeSetup.Setup` for a pending new company game. `CompanyModeSetup.Setup` reads `placement.marker.Location.Value` for each placement in order and calls `TrainController.PlaceTrain`; `HandlePlaceTrain` throws when `CanPlaceAt` fails, and the setup's catch around all placements stops the remaining placements, the initial track conditions and the initial industry storage. The source is Railroader 0.6.2 build 26335745; whether a patched location reaches a new company game is a Railroader journey's evidence, not this reading's.

## Implement the replacement ID

`ObjectState.MarkerId` carries the `markerId` member, a string or null. `PatchEngine.Parse` reads it through `ParseMarkerId`, which refuses a non-string, an empty or whitespace-only value, a value that begins or ends with a space (`ReplacementMarkerIds.Problem`) and a value that begins with a prefix in `ReplacementMarkerIds.ReservedPrefixes`. `ObjectState.WithMarkerId` sets it. `PatchEngine.Overlay` lays it over the underlying state with `mod.MarkerId ?? under.MarkerId`, so `Desired` and removal recompute the effective ID from the underlying state and the remaining modifications. `PatchEngine.CheckRelationships` refuses an ID for a scene that does not implement `IMarkerIdScene`, with `ReplacementMarkerIds.NotSupported`. `SceneCapabilities` implements `IMarkerIdScene` by delegating to the adapter that resolved the object, and its `CheckRelationships` applies the same refusal to that adapter.

`TrackMarkerScene` is the only adapter that implements `IMarkerIdScene`. It builds `MarkerRelationship` with `replaceable` set, which gives the relationship the `IMarkerIdWorld` of its world. `TrackMarkerWorld` implements `IMarkerIdWorld` over the marker's `id` field and the graph:

- `MarkerId` and `SetMarkerId` read and write the `id` field. `SetMarkerId` writes the field only; the caller owns the registration.
- `UnregisterOwn` removes only the marker's own graph entries under its ID. The native `RemoveNamedLocation` would remove the entries of every holder.
- `IdUsers(id, except)` lists the other scene markers that hold the ID, each named `scene/path`, then the owners of graph entries under the ID that no listed scene marker owns, named `ReplacementMarkerIds.ForeignOwner`.
- `MapObjectIds` lists the keys of the map object manager's `Shared.Objects` for the loaded map context. It returns null while the manager is not loaded. `Bindings` then refuses every replacement ID with `ReplacementMarkerIds.MapObjectsUnknown`, so the patcher fails closed and does not treat an unchecked ID as free.

`MarkerRelationship.CheckRelationships` checks the ID before mutation whenever it differs from the current ID. `Unavailable` returns the first of an invalid value, a user from `IdUsers`, a map object ID or the unloaded map object list, as a `ReplacementMarkerIds` message. When the modification changes the marker's ID, `renames` is set and the duplicate-ID refusal of its activity, binding and track-following changes is skipped. A marker that already holds its own ID has no duplicate to refuse for. Holders of a duplicate ID that do not change their ID keep that refusal.

`MarkerRelationship.Write` orders the rename by the holders. When the marker leaves a duplicate ID, `Rename` runs first: `UnregisterOwn`, `SetMarkerId`, then `Register` when the marker is active and its binding resolves. The activity, location and track-following writes then touch only the marker's own registration under the new ID. Otherwise the rename runs last, after the activity and location changed under the ID the marker holds alone. Restoration and removal use that second order to return a duplicate ID. `Verify` compares the ID after the write, and `Capture` and `Restore` keep it in the snapshot.

The shared-ID rule goes through `PatchEngine.AdditionIds`. A modification with a non-blank `markerId` contributes the key `marker ID <id>`, next to the detection-addition and equipment keys. `SharedAdditionIds` collects every key that more than one modification uses, and `SharedAddition` turns a `marker ID` key into `ReplacementMarkerIds.Shared`. A replacement ID therefore fails every modification of its file that uses it.

`ScenePatchFile` writes `markerId` after `target` in the canonical modification order. `PatchEditing.MinimumPatcherVersion` raises the minimum to `ReplacementMarkerIds.RequiredVersion` (`0.5.0`) for any modification with `markerId`, whether or not the build has the capability. `PatchEditingSession.SetMarkerId(target, id, inspected)` writes or clears the member under the key prefix `marker-id-`. Clearing is refused with `ReplacementMarkerIds.ClearRefusal` while the modification still sets activity, a binding or track following and another scene marker holds the underlying ID. `PatchEditingSession.WithIdDependencies` runs for every edit of a holder. It adds entries when the modification sets no `markerId` of its own and `IMarkerIdScene.RewritesRegistration` holds: the modification sets activity, `relationships.trackMarker` or track following, or a dependent cache such as a map label's track group disagrees with the holder's location. The session remembers a holder whose cache disagreed, because the first edit corrects that cache in the loaded world only and a load starts from the stale cache again. It adds to `dependsOn` the keys of the file's other modifications that set `markerId` on a holder of the same underlying ID, found with `Items` and `ResolveUnique`, and sorts the result by ordinal key. Otherwise, including for a holder whose modification gives it a replacement ID of its own, it removes only those keys from `dependsOn` again and keeps the modification's other entries. `Change` refuses to remove a modification that another one names (`Dependents`), and `SetMarkerId` with a null ID, or with the underlying ID while the modification sets `markerId`, clears the member and refuses first with `ReplacementMarkerIds.DependentRefusal`, then with `ClearRefusal`. The core tests are `ReplacementMarkerIdTests` and `DuplicateMarkerIdTests`; the test world covers an ID applied before track following and the save and reload of dependent binding and track-following edits.

## Evaluate track-following placement

`Placement.Following` holds a `TrackFollowing`: a `TrackAnchor` (a `TrackLocation` on a segment, or an endpoint node ID), an offset in the track's frame and a rotation applied after the track's rotation. `PatchEngine.Parse` reads it from `placement.mode = "trackFollowing"` with a null position and rotation. `PatchEngine.Evaluate` asks the scene, which must implement `ITrackPoseScene`, for the anchor's current `TrackPose` in map coordinates and replaces the placement with its absolute evaluation, keeping `Following` set. `Execute` evaluates after `Preflight` and before the relationship check and capture, so an anchor that does not resolve fails the modification without mutation; `Desired` evaluates the effective state. Adapters receive an ordinary absolute placement and need no change. `TrackFollowing.Relative` computes the offset and rotation that keep a given absolute placement at the anchor's current pose.

`SceneCapabilities.Tracks` supplies the poses for every capability; `EntryPoint` sets it to `NativeTrackPoses`, which reads `Graph.GetPositionRotation` for a segment location (forward axis away from the measured end) and `TrackNode.Position` and `Rotation` for an endpoint, and refuses a missing segment or node and a distance beyond the segment's length.

`PatchEditingSession.Follow(target, anchor, inspected)` stores the current placement relative to the anchor, `StopFollowing` stores the current placement as fixed placement, and `Edit` with a placement keeps a following object's anchor and stores the new relative values. `ReconcileTrackFollowing` re-evaluates every following modification of the active scene patch file and applies the ones whose object differs from its evaluation, without changing the scene patch file or the history. It reports each moved or failed object by modification ID, restores the prior state on failure, and marks the object unsafe when that restoration does not verify; an unsafe object is skipped until `Recheck`. `EntryPoint` calls it four times a second while the native map editor is attached, no gizmo is active and `HasTrackFollowing` is true. Each pass first tries a check that does no scene-wide work: it holds the target each following modification last resolved to while that modification object stays in the scene patch file, and skips the modification when `ITargetConfirmation.StillIdentifies` confirms the held object, no other modification names the same target, and the object's state and `IDerivedStateScene.DerivedProblem` already agree with the modification evaluated from `PatchEngine.Underlying` at the anchor's current pose. That check mutates nothing, so it needs no preflight. When the check finds a difference in placement or derived state only, a held update follows: the scene confirms the held object, `IPlacementPreflight.PreflightPlacement` checks the object's own pattern and registration through `IPlacementPattern.PlacementProblem`, without the setup-placement index and the direct-reference scan, and the relationship, activity and coverage must already agree. It applies through `IFollowUpdateScene.ApplyFollowUpdate`, which skips `ITrackMarkerDiagnostics.AfterVerifiedState` and its search of every marker unless the binding or activity changed; explicit edits, history steps and removal always reconcile the warning. Any other difference, a missing confirmation or an exception takes the full path, which resolves, preflights, applies and verifies as before. `TrackMarkerWorld.StillIdentifies` reads the held object only: it is loaded in the identity's scene, at its path, with its marker and capability; uniqueness is checked again by the next resolution. `PatchEditingSession.MinimumPatcherVersion` returns `0.5.0` for a `trackFollowing` placement and for an `active` value on a `track-marker-v1` target, from the scene patch file alone. `ClearActivity` removes the mod value of `active`.

Both marker capabilities share the internal `MarkerRelationship`, which holds the location, registration, placement, activity and group-activity rules above. The crossing-pad capability refuses pads with group-driven activity in `PadProblem`, so its objects never take the group-activity path. `CrossingPadWorld` inherits `TrackMarkerWorld.AfterVerifiedState`, so a verified pad state reconciles the native not-on-the-track warning of its marker like a Generic marker, and `EntryPoint.ReconcileMarkerWarning` retracts an exactly attributed warning after a verified pad repair. The early repair before `TrackMarker.OnEnable` resolves only `track-marker-v1` targets, so pads are repaired when their scene patch files apply. A capability whose objects derive state from the marker location passes an `IMarkerConsumer`: `Capture` with the snapshot, `Refresh` after every write, `Problem` in the verification after `Apply` and `Restore`, and `Restored` to compare the restored state with the captured one.

## Implement the crossing-pad capability

`CrossingPadScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingPadWorld`, which extends `ITrackMarkerWorld` with `Geometry` and `Generate`. `CrossingPadWorld` implements it by deriving from `TrackMarkerWorld`:

- `Resolve` returns only marker objects with a `Track.TrackCurveMeshBuilder`; `TrackMarkerWorld.Resolve` returns only those without one, so the two capabilities never claim the same object. `PadProblem` is the pattern check shared with the inventory; it uses `TrackMarkerWorld.Consumers` for the ID, listener, group-driven activity, setup-placement and reference rules, and also allows the builder's `_marker` reference.
- `Generate` calls `CurveMeshBuilderBase.Generate()`, which reads the marker's graph curves, replaces the mesh container's children, offsets the mesh by the pad's map position and moves the culling token to the new bounds. The new renderer starts enabled, so the adapter adds the token to `CullingManager._needsUpdate`; the manager's next `Update` calls `CullingSphereStateChanged`, which sets the renderer visibility. The adapter records the location, map position and signature it generated from in a weak table.
- `Geometry` returns the signature of the current `_renderers` (vertex count, FNV-1a hash of the local vertex positions, local bounds and mesh map position), the recorded source while the signature still matches, and whether the culling sphere equals the pad position plus `_boundsCenterLocal` with `_boundsRadius`. A pad without a live token, such as a disabled pad, has nothing to align.

For a track-following pad, `MarkerRelationship.Apply` passes `following` to the consumer, which also regenerates when `PadGeometry.Curves`, the `ICrossingPadWorld.SourceCurves` fingerprint recorded at generation, is unknown or differs from the current one. `CrossingPadWorld.SourceCurves` invokes `TrackCurveMeshBuilder.GetCurves()` for a resolvable location and joins every curve's `P0` to `P3`, `_up0` and `_up3`, rounded to millimetres. `MarkerRelationship.Apply` also passes `explicitApply`, so an applied edit, history step or removal regenerates any pad whose recorded `Curves` differ from the current ones; reconciliation (`DerivedProblem`) and `Restore` do not. An unknown token, on either side, never confirms the recorded curves. `Track.TrackSegment` and `Track.TrackNode` are plain graph objects, not Unity objects, so the token checks them against null. The consumer builds those curves only when `ICrossingPadWorld.CurveToken` differs from the token recorded with them. `CrossingPadWorld.CurveToken` reads the cached `TrackSegment.Curve` of every segment within half the pad width plus one metre of the marker location and the segment IDs `Graph.SegmentsConnectedTo` returns at each node it reaches, which decide the builder's next segment; it builds no curve. When built curves match the recorded ones under a changed token, the adapter records the new token. `Geometry` reuses the signature of a builder's renderer array until generation assigns a new array. `CrossingPadScene.DerivedProblem` reports a curve-only change once the changed curves have held still between two reconciliation checks, so a native drag regenerates the pad once, on its final curve; an applied edit regenerates at once. `CrossingPadScene` and `SceneCapabilities` implement `IDerivedStateScene.DerivedProblem`, and `PatchEditingSession.ReconcileTrackFollowing` applies the desired state when the placement differs or `DerivedProblem` reports a difference. The core consumer regenerates when the pad holds no geometry for a resolvable location, geometry for an unresolvable one, geometry of unknown or other source, geometry generated at another position, or a misaligned culling sphere. A restoration requires the regenerated signature to equal the captured one when the pad held geometry at capture. `CheckRelationships` refuses a detach: with no marker location, `TrackCurveMeshBuilder.GetCurves` logs "Track marker is not set or invalid" and returns no curves, so `Generate` leaves no renderer and `CullingSphereStateChanged` calls `Generate` again, with the same error, whenever the sphere becomes visible or near. `MinimumPatcherVersion` returns `0.5.0` for `crossing-pad-v1`, and `PatchEditingSession.MinimumPatcherVersion` returns at least `0.5.0` for a modification naming that structure. The inventory describes a pad's generated `DontSave` mesh objects with one dependency line instead of per component, because culling toggles their renderers and generation replaces them; otherwise an inspected pad would become stale with every camera move. `HierarchyDependencies.Describe` holds that rule without Unity, and the core tests run it through `SceneInventory.CheckFreshness`. Pads inside a `Track.Crossings.GradeCrossingController` qualify: the controller reads its circuit sets and its `KeyValueObject`, not the pad marker, and the reference scan still refuses any direct holder other than the colocated `TrackRelativePosition` and pad builder.

Sources: `Track.TrackCurveMeshBuilder.GetCurves`, `BezierCurveMesh.CurveMeshBuilderBase.Generate`, `OnEnable`, `CullingSphereStateChanged` and `RequestUpdateCullingPosition`, `Helpers.TransformExtensions.DestroyAllChildren`, which destroys the old children at the end of the frame, and `Helpers.Culling.CullingManager.Update`.

## Implement the milepost capability

`MilepostScene` implements `IScene`, `IRelationshipScene`, `IVersionedScene`, `ITargetConfirmation`, `IPlacementPreflight` and `IFollowUpdateScene` over `IMilepostWorld`, which extends `ITrackMarkerWorld` with `Milepost`, the state an edit preserves (`MilepostState`: prefix, origin flag, mile value, displayed text, a model signature and the origin cache entry for the prefix). ## Implement the crossing-coverage capability

`CrossingCoverageScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingCoverageWorld`, which `CrossingCoverageWorld` implements with Unity. Coverage is the core `CrossingCoverage`: an ordered list of circuits keyed by the ID of the map's own island span, each a `CircuitCoverage` that is `Native` (span IDs), `Tracks` (three `SpanRange` values) or `Detached`. `ObjectState.Coverage` carries it; This mod's coverage lists only explicit circuits, observed coverage lists every circuit plus any `Residue`, owned spans left registered by an incomplete cleanup. `PatchEngine.Desired` overlays this mod's circuits on the underlying coverage per circuit, so omission keeps a circuit's effective coverage.

- The adapter keeps a baseline per controller: the circuit set objects, the detection spans the map assigns to them, and their keys at first observation, and every span it owns. `Read` classifies each baseline circuit as detached (not in the controller's list), native (its native references) or tracks (owned references, read back through `Range`), and throws for anything else.
- `CheckRelationships` refuses placement, activity and `trackMarker`, unknown circuits, `Native` entries, unresolved or zero-length ranges, and an effective coverage with every circuit detached. Because the engine passes it every mod value, these refusals happen before mutation. `TrackMarkerScene` refuses coverage, and a scene or adapter without relationships refuses coverage like any other relationship.
- `Write` converges from any state the adapter can leave: it reuses a registered owned span with the exact range, creates missing ones and checks that they registered and cover track before any circuit refers to them, sets each circuit's references, sets the controller's list to the non-detached circuits in native order and retires unused owned spans. A span that stays registered after `DestroySpan` stays owned, so `Verify` reports it and `Restore` returns false. `Preflight` ignores such residue; `Read` exposes it, so `PatchEditingSession.Recheck` sees a difference and applies the scene patch file, which retires it.
- `PatchEditingSession.Cover(target, circuit, coverage, inspected)` sets, replaces or detaches one circuit's entry in the keyed `circuits` object, and a null coverage clears it. The session removes `circuits` or `additions` with its last entry and `crossingCoverage` with both, never writes one of them empty, and removes a modification left without content. `PreviewCoverage` runs the same checks and returns one line per circuit from `CrossingCoverage.Describe` without mutating, recording history or changing the scene patch file. `Coverage(target)` reads the current coverage for the panel.
- `CrossingCoverageWorld` creates an owned span as the game's track span loader does: a disabled `GameObject` with `HideFlags.DontSave` under one root per map scene, then `TrackSpan.id`, `_lower` and `_upper`, `InvalidateCache`, and activation, whose `OnEnable` calls `Graph.AddSpan`. `DestroySpan` refuses to disable a span whose ID now belongs to another span, because `Graph.RemoveSpan` removes by ID. `SetCircuits` clears and refills the controller's own list, which its loop indexes on every pass.

### Detection additions

A detection addition is a `CircuitCoverage` of kind `Added` in the same `CrossingCoverage`, named by a `DetectionAddition.Key(owner, id)` instead of an island span ID. `PatchEngine.Parse(item, owner)` reads it from the keyed `additions` object of `crossingCoverage`, where its key is its ID, and gives it the owner, which is the scene patch file key of `PatchEngine.Apply`. `PatchEditingSession` takes the same key as `scenePatchFileKey` and passes it to `Parse` and `Desired`, so the session and the world-load application name an addition alike. `EntryPoint` applies each scene patch file under its mod identifier and `MapEditorAttachment` passes `ModScenePatchFiles.EditedModId()`.

- An observed coverage is complete: `Read` lists every native circuit and every added circuit the controller evaluates. `CrossingCoverageScene.Apply` converges on a complete coverage as it stands and lays any other coverage over the observed one. A modification therefore keeps the additions it does not list, which may belong to another modification or mod, while the session's `Desired`, a restoration and a `Recheck` remove every addition their complete coverage lacks. `Overlay` keeps the completeness of its base, so `Desired`, which starts from the underlying state, stays complete.
- `PatchEngine.SharedAdditionIds` finds the IDs that more than one modification of a scene patch file uses. `Execute` fails each of those modifications before its dependencies run, and `Desired` leaves them out, so the result does not depend on the order of the modifications. `PatchEditingSession.AddDetection` refuses an ID another modification already uses.
- `Write` gives each listed addition one `Circuit` in the baseline's `Added` list. It builds missing spans under `CrankyAnt.ScenePatcher.added.<owner>.<id>.<role>`, checks that they registered and cover track, and creates the circuit set through `ICrossingCoverageWorld.CreateCircuit` before it changes any existing reference. It then sets the spans, sets the controller's list to the native circuits that are not detached followed by the added circuits in ordinal key order, drops the circuits of deleted additions and retires unused spans. A failure after the new set exists leaves it in the baseline, so `Restore` writes the captured coverage and removes it with its spans.
- `BaselineOf` asks `ICrossingCoverageWorld.AdditionKey` for each circuit set it finds. `CrossingCoverageWorld` keeps the key of every set it created in a static `ConditionalWeakTable`, keyed by the set object. A set with a key enters the baseline as an added circuit with owned spans, so a new adapter over a retained world reuses it. A native circuit whose spans an earlier adapter replaced holds spans under the `CrankyAnt.ScenePatcher.` prefix; `BaselineOf` refuses such a circuit with "Reload before editing it" instead of recording the patched spans as native.
- `PatchEditingSession.AddDetection(target, id, tracks, inspected)` adds or replaces one addition, `DeleteDetection` removes its entry, and `PreviewAddition` describes either without mutating. Before a mutation and in every preview the session passes the complete desired coverage to `CheckRelationships`, which refuses a result without detection. Deleting the last detecting addition is thereby refused before anything changes.

Sources: `Track.Crossings.GradeCrossingController.LoopCoroutine` and `UpdateCircuit` re-read `circuitSets` and the three span references every pass and cache nothing from the spans; `Track.TrackSpan.OnEnable` and `OnDisable` register and remove by ID; `Game.MapEditor.MapEditor.Save` serializes graph nodes, segments, turntables and groups, and industry spans only from ops DTOs, so neither runtime spans nor controller references reach map data. `GradeCrossingController.CircuitSet` is a class with a parameterless constructor and the three span fields; the controller's other fields hold no state per circuit set. The inspected build is Railroader 0.6.2 build 26335745.

## Implement crossing equipment

Crossing equipment is a second relationship of `CrossingCoverageScene`, which takes an optional `ICrossingEquipmentWorld`; without one, `crossingEquipment` is refused. `CrossingEquipmentWorld` implements it with Unity. The core types are in `CrossingEquipment.cs`: an `EquipmentAddition` holds a persistent `Id`, a `Pattern`, an `EquipmentSource` (scene and path), a fixed `Placement` and its `Scope`, the supplying mod's identifier. `CrossingEquipment` is a set of additions keyed by scope and ID, either a mod's set (only explicit additions) or `Complete` (every addition the controller should own). `ObjectState.Equipment` carries it.

- Scope: equipment uses the same owner as detection additions. `PatchEngine.Parse(item, owner)` scopes a scene patch file's equipment with its `scenePatchFileKey`, the supplying mod's identifier, and `PatchEngine.Desired(modifications, target, owner)` starts from the equipment that stands now, less that owner's additions, so other mods' additions are kept, before overlaying the scene patch file, because a mod's additions exist only through its scene patch file. The native map editor passes the same key to `PatchEditingSession` from `ModScenePatchFiles.EditedModId()`. `Release` and `Dispose` retire the equipment of a crossing with its owned spans when a retained world drops the crossing or the state ends. `PatchEngine.AdditionIds` lists equipment IDs as `equipment <id>` beside detection addition IDs, so an equipment ID may appear in one modification of a scene patch file.
- `Apply` converges on a complete set exactly and overlays a mod's set on the observed additions, so runtime application never removes another mod's additions. `CrossingEquipmentPart.Write` keeps a matching addition and moves it, rebuilds one whose source or pattern changed, retires one absent from the set and constructs a missing one after rechecking its source. An addition that is `Present` but not `Built`, a wrapper whose copy or player is gone, counts as not built, like an addition that was never built: `Observed` leaves it out. `Write` retires such a wrapper only when the set clears it (`Clears`): the set names it, and `Write` then constructs it fresh, or the set is complete and its `Owner`, the mod that `CrossingEquipment.Without` scoped it to, is the wrapper's own mod and leaves it out. Another mod's set, a restoration's included, leaves the wrapper as it is. `Capture` returns coverage and the complete built equipment; `Restore` converges on both and reports false when an addition cannot be released or rebuilt. A failed attempt that rebuilt a lost copy therefore ends with that addition not built, which `Verify` accepts. `Verify` reports a stale wrapper that the set cleared and that still stands, so a destroy that does not take guards the crossing. Because `Read` does not show a stale wrapper, `PatchEditingSession.Recheck` also applies when `ICrossingEquipmentScene.EquipmentLeftover` says the desired state would remove one, and `Status` reads the built addition of an ID before a stale wrapper of the same ID. `Apply` and `Restore` skip the equipment part when its effective set equals the observed one, so an operation that leaves the additions alone never touches them.
- `CheckRelationships` resolves every source and checks its pattern before any mutation, so a missing, ambiguous, unavailable or nonconforming source refuses the whole modification. When a modification changes the effective equipment, `CheckRelationships` also refuses it while a built addition fails `Problem`. An addition that is not built is never judged by `Problem`, so another mod's lost copy refuses nothing. Each source refusal names the source by `EquipmentSource.StoredName`, as the addition's row does, says when the addition's copy is missing, and ends with what the modder can do, such as making the source available or removing the addition. These refusals, and the one for an addition without a fixed placement, are `InvalidPatchDefinitionException`s: a problem of the mod author's scene patch file, so the world load's warning names the mod author. Only a bell source refused because this game build cannot provide crossing bells (`EquipmentAddition.BellsUnavailable`) stays a patcher problem. `Preflight` does not check additions, so a faulty addition blocks only equipment operations and coverage operations of the same crossing stay independent. The adapter adopts `Owned` additions at its first observation of a controller.
- `PatchEditingSession.AddEquipment`, `RemoveEquipment`, `PreviewEquipment`, `Equipment`, `EquipmentEntries`, `EquipmentSources` and `EquipmentStatus` serve the panel; `EquipmentEntries` lists this mod's additions from the scene patch file, from every modification of the crossing and in the ordinal order of their IDs, with their built state or why they were not built, so a failed addition can be edited or removed. When several modifications of the scene patch file target an object, crossing or not, `SeveralModificationsBlock` returns the refusal that every edit of it gives. The panel reads it once per rebuild and adds it to `EditBlock`, so every edit control and Remove modification are inactive with it; Recheck, which does not meet that refusal, stays available. The panel names such an entry `<id>: <source>` (`InventoryPresentationState.UnbuiltEquipmentName`): the matching source candidate's label, or else `EquipmentSource.StoredName` of the recorded source, never the kind alone. Equipment placements compare with the native map editor's tolerance, and `PreservingJson.KeepStoredPrecision` keeps an entry's untouched axes; sources and status come through `ICrossingEquipmentScene`, which `SceneCapabilities` forwards to the resolving adapter.
- The eligibility rules are core: `LightGatePattern.Problem(DeviceFacts, keys)`. `CrossingEquipmentWorld.Facts` only reads the device into `DeviceFacts` and `LampFacts`/`GateFacts`, so the core tests exercise the production rules. The source must lie in the destination controller's scene, which keeps the shared model, material and clip assets loaded for the copy's lifetime.
- Each addition is one added object: `NativeInventory` observes the `OwnedEquipment` wrapper in the family `Added light or gate`, and the layout marks it `+` and `+ ADDED`. The wrapper stands at the addition's placement and the copy at its origin. `NativeInventory` implements `IOwnedObjectScene` for the copy's child objects below the wrapper: `SceneInventory` takes no observation of them from a refresh, a check, a stepped pass or `ReobserveRelated`, so applying a copy adds exactly its one entry and the expected count stays consistent. `NativeInventory` also passes `DiscoveryWalk.Steps` an `owned` predicate for those components and skips them in `ObserveRelated`, and the controller's observation counts their DontSave wrapper as runtime state. The patcher's own copies are therefore never observed or read as referrers, and their culling, initialization and history steps do not make the inventory stale.
- `CrossingEquipmentWorld` reads the published keys from the controller's `KeyLights` and `KeyGates` constants. `Construct` builds a disabled wrapper with an `OwnedEquipment` component, which stores the source with its name (`EquipmentSource.StoredName`: the device name, or a bell definition's name) and kind, so `DisplayName`, the stored source name followed by `(added: <Equipment ID>)`, does not depend on the copy object, instantiates the source beneath it, checks the copy, joins the controller's `GameObjectCuller.gameObjects` with the state in `_cullingState` and enables the wrapper last. `Destroy` leaves the culler first. `Status` reads the lamps' and gates' private `_observer` fields for the panel only. `Candidates` also lists each controller's generated bell player, which the pattern rejects with its reason, and gives each candidate its device name, its crossing and the crossing's placement. `SourceCandidate.Label` reads "Signal 1 at Allen", with the place from `CrossingEquipment.Place`: the part after "Grade Crossing - " of the crossing's name, or else its nearest enclosing place without a leading "Roads ", such as "Andrews" for a setup crossing; `CrossingEquipment.Describe` lists what changes before what is kept; `EquipmentPlacement.Propose` carries the device's placement relative to its crossing over to the inspected crossing, five metres aside; `PatchEditingSession.NewEquipmentId` adds a numeric suffix to an ID the scene patch file already uses.

Sources: `Track.KeyValueLampMaterialController.OnEnableWithProperties` and `RollingStock.Controls.KeyValueBoolAnimator.OnEnableWithProperties` take `GetComponentInParent<KeyValueObject>()`, read their key's Boolean value and observe it; the lamp's `DiscoverRenderers` matches renderers under `targetObjects` by shared material; `Game.GameBehaviour.OnEnable` defers that initialization through `Game.State.RestoreNotifier`; `Helpers.Culling.GameObjectCuller.CullingSphereStateChanged` calls `SetActive` on each listed object when `_cullingState` changes between `Visible` and `NotVisible`. The inspected build is Railroader 0.6.2 build 26335745.

### Bells

A bell is an equipment addition with the pattern `crossing-bell-v1` and a definition source: `EquipmentSource.ForDefinition(identifier)` holds the content-library identifier in `Definition` instead of `Scene` and `Path`. `EquipmentAddition.SourceKindProblem` ties each pattern to its source kind, and `PatchEngine.ParseEquipment` refuses a bell source other than `definition` alone, so a bell never resolves a scene. Everything else runs through `CrossingEquipmentPart` unchanged: the part rechecks the source, builds, moves, rebuilds and retires bells as it does copies, and `Problem` and `Status` come from the world.

- The eligibility rules are core: `BellPattern.Problem(BellFacts)` judges the definition's kind, its audio reference and whether it resolves, its volume and indexes, and the destination controller's key-value objects. `BellPattern.ClipProblem` judges the loaded clip against the indexes. `CrossingBells.Facts` only reads the definition into `BellFacts`; it resolves the audio with `IContentLibrary.TryResolveAssetReference`, which loads nothing.
- `CrossingEquipmentWorld` dispatches a definition source and the bell pattern to `CrossingBells`, which it constructs separately: a build without one of the bell prerequisites keeps lights and gates and refuses bells with `the crossing-bell capability is unavailable` and the reason. `ResolveSource` returns the bell definitions under the identifier from `IDefinitionProvider.AllDefinitionInfosOfType<BellDefinition>()`, or a definition of another kind from `TryGetDefinitionInfo<ObjectDefinition>` for the pattern to reject. `CrossingBells.Sources` holds the identifier the controller's `DefaultCrossingBellIdentifier` constant names; a build without that constant has no bell capability. `Facts` sets `BellFacts.CrossingBell` from it, so `BellPattern.Problem` refuses any other bell definition with `BellPattern.NotACrossingBell`, in the list and at application. `Candidates` lists through `BellPattern.Sources` only the definitions under those identifiers, and one rejected row with `BellPattern.CrossingBellMissing` for an identifier the content library lacks; `SourceCandidate.Pattern` tells the panel which pattern an addition from the source takes.
- `CrossingBells.Construct` adds a child named after the definition (its metadata name, or else the last part of its identifier) to the disabled wrapper with an `Audio.IntegerLoopingPlayer` (mixer group `LocomotiveBell`, priority `EquipmentAddition.BellPriority`, `AudioDistance.Distant`, as `GradeCrossingController.CreateBellPlayer` sets them; the priority is 9 since Railroader 0.6.3, 10 before) and an `OwnedBell`. `OwnedBell` subscribes to the controller's `KeyValueObject` with `Observe(KeyBell, callback, true)`, through a `BellRelay<Value>` delegate, and sets the player's `play` field from `Value.BoolValue`. It then calls `PrefabStoreExtensions.LoadAssetAsync<AudioClip>` with an `AssetLocator` for the definition's audio and its own `CancellationTokenSource`, and continues on the main thread's `TaskScheduler`: a completed load keeps the `LoadedAssetReference` in `OwnedBell.AudioReference` and calls `IntegerLoopingPlayer.Configure(clip, indexes, volume)`; a failed load, a cancelled load, an empty result or a failed clip check or configuration goes through `CrossingBells.Failed`, which sets `LoadProblem`, which `Problem` reports, and raises one warning per bell through `CrossingBells.Warn`. `EntryPoint` sets that to its `Report` route, so the warning reaches the game's log attributed to `<scope>:Data/scene-patches.json`, deduplicated per load attempt; without it the warning goes to `Debug.LogWarning`. `CrossingEquipmentPart.Refusal` tells a faulty bell, which can be removed or replaced, from another fault, which needs a reload. `CrossingEquipmentPart.Coherence` takes the desired set and skips additions the change removes or rebuilds, so `Coherence` blocks edits that keep a failed bell while its removal or replacement applies. `OwnedBell.OnEnable` calls `Configure` again when the bell is enabled after its first activation, because `IntegerLoopingPlayer.OnDisable` destroys the clips it split and `OnEnable` does not split them again. A bell is built only beneath an active controller, because Unity calls `OnDestroy`, which releases the audio on scene unload, only for objects that were active; `SourceProblem` refuses an inactive controller before any change and `ConstructBell` keeps the check as a guard. Without the bell prerequisites, `Candidates` lists one rejected entry with the reason.
- `OwnedBell.Release` stops the player, disposes the observer, cancels the load and disposes the audio reference; it runs from `CrossingEquipmentWorld.Destroy`, from a failed construction and from `OnDestroy` when Unity destroys the bell with its scene, and is safe to repeat. A load that completes after release disposes its reference in the continuation. The bell never touches the controller's own `_bellPlayer` or `_audioLoadReference`, which keep their lifetime; the asset store counts both references.
- The inventory lists a bell's wrapper in the family `Added bell` (`CommandBand.AddedBellFamily`); `CommandBand.IsAddedFamily` marks both added families `+` and `+ ADDED`, and `NativeInventory.CopyPart` keeps the player and its pooled audio sources out of the inventory. `CrossingBells.Status` reads the player's `play` field and its private `_sources`, and the controller's private `_bellPlayer`, for the panel only.

## Implement construction segments

The construction segments of a rail bridge construction are the relationship `constructionSegments`, in `ConstructionSegments.cs`. `ConstructionSegments` is a set of segment IDs or the explicit detach; `Same` compares sets, and `Overlay` lets a modification's set replace the one below. `ObjectState.Segments` carries it, and `ObjectState.WithSegments` copies a state with a setting, so `Overlay`, `Underlying`, `Evaluate`, `Desired` and `LeavingActivity` in `PatchEngine` keep it. `PatchEngine.ParseSegments` reads `{ "segments": [...] }` with at least one ID, each once, and reads `{ "detach": true }` so the capability refuses it with its reason.

Only a scene marked `IConstructionSegmentScene` accepts the relationship: `PatchEngine.CheckRelationships` and `SceneCapabilities.CheckRelationships` refuse it for every other capability with `ConstructionSegmentRule.NoRelationship`, so the existing relationship scenes need no change. `ConstructionSegmentRule` holds what both holders share:

- `Check` refuses, before mutation, an object without a controller, the detach (`NoDetach`), and a segment that `IConstructionSegmentWorld.SegmentMatches` finds zero times or more than once. A set equal to `NativeConstructionSegments`, the IDs the world first read in this load, is accepted as it stands: it is the object's state without the mod, which a removal applies back.
- `Apply` writes only a set that differs from the current one, so repeated application writes nothing; `Verify` compares the set after the write.

`SceneObjects` holds the relationship for a top scene object whose world implements `IConstructionSegmentWorld`: `Read` adds the segments, `Capture` keeps them beside the top scene object observation, `Apply` writes them before the complex's own checks take their layout, and `Restore` writes the captured set first. `GroupWorld` implements the world for a rail bridge root that carries its controller on the root. `ConstructionSceneryScene` (`bridge-construction-scenery-v1`, component `Game.Mow.TrackConstructionScenery`) holds it for a controller on an object of its own, `ConstructionSceneryWorld`; it refuses a `placement` or `active` that differs from the object's own. `ConstructionSegmentNative` reads and writes `segmentIds`, clears `_cachedSegments` and calls `UpdateVisibility` on an enabled controller only when every segment exists, because the decompiled `UpdateVisibility` dereferences each segment before it switches anything, so a missing segment would stop it there. Railroader logs that stop at world load as `Error during DidRestore of Bridge 1 (Game.Mow.TrackConstructionScenery)` when the saved controller names a removed segment; the deferred restore below holds the game's call back until the repair has applied. `PatchEditingSession.SetConstructionSegments` writes, replaces, clears or detaches the relationship; `Normalised` drops a set equal to the underlying one; `ScenePatchFile` writes `segments` in ordinal order; and `RemainingState` names the remaining segments after an unverified restoration. The core test is `ConstructionSegmentTests`.

### Deferred restore

The game runs a `Game.GameBehaviour`'s `OnEnableWithProperties` through `Game.State.RestoreNotifier`: `NotifyDidRestore` runs every registration while it is in progress, before the mods' `OnWorldLoad`, and `LateUpdate` runs later registrations once it is complete. A callback that reads data a scene patch file changes therefore reads the scene's data before the patcher applies. `DeferredRestores` in the mod defers such a call and never suppresses it:

- A Harmony prefix on each hooked `OnEnableWithProperties` skips the call only while the notifier is in progress and only when `DeferredRestoreRule` says to wait. Its inputs come from `RestoreTargets`, which reads the applicable scene patch files once per load attempt through `ModScenePatchFiles.Discover` and the engine's own `Parse`, and matches a modification to exactly the object by scene, path and a component the object carries.
- `HandBack` runs at the end of every `OnWorldLoad` exit path, on world unload and on mod unload. It registers each skipped call again with `RestoreNotifier.RegisterForRestore`, with the component as observer and its own `EnablePriority`, so the game is expected to run its own code one frame later: with the repaired data, or with the game's own error when the repair did not apply. This is read from the decompiled `RestoreNotifier` and not yet observed in Railroader. It hands nothing back while the notifier is in progress, and it drops a call whose component was destroyed or disabled since.
- A `DeferredRestoreRelay`, armed before the first skip, hands the calls back once in a later frame when the notifier is complete. A restore that no `OnWorldLoad` follows therefore does not hold a skipped call until unload.
- Any internal failure runs the original. A failed install leaves the game's order unchanged and is logged once at mod load, like the early marker warning hook.
- Each hooked type is one row of `DeferredRestores.Hooks`. The only row is `Game.Mow.TrackConstructionScenery`: `DeferredRestoreRule.DeferConstruction` waits when a saved segment ID is not on the track graph while every ID of the setting that stays applied is. That setting is the last one in load order that passes `ConstructionSegmentRule.Check`: not a detach, and every ID on the track or the saved set itself. The engine refuses a later detach or stale setting before mutation, so an earlier repair stays applied and the call still waits. Without such a setting, or with saved IDs that are all on the track, the game's call runs. `RestoreTargets` matches the component names a target of the object can use, not the components it carries, so a modification with the wrong component name also waits; the engine then refuses it and the game's error comes after the patcher's load.

A survey of the decompiled game found no other restore-time callback of a type a scene patch file targets that reads data the file changes before the apply. `Track.Crossings.GradeCrossingController` starts its circuit loop in `OnEnableWithProperties`, but `TrainController.GetCarsOnSpan` returns no car for an invalid span and the loop reads `circuitSets` again on each pass. `Track.TrackMarker` registers its named location in a plain `OnEnable`, which `NativeRepairHooks` handles. The crossing lamp, gate and bell components, the sign, water and animator parts, and the bulk industry storage read key values or storage IDs only. `Helpers.MilePost`, `Character.SpawnPoint` and `UI.Map.MapIcon` have no restore-time callback. The core test is `DeferredRestoreTests`.

## Implement existing crossing equipment

`ExistingEquipmentScene` places and enables or disables the light object of an existing crossing mast, with the gate on its child, and the bell a crossing controller creates. `Masts` and `Bells` give the two capabilities, for the structures `existing-crossing-mast-v1` and `existing-crossing-bell-v1`; both take an `IGroupWorld` and one shared `PartHolds`. The world treats the crossing controller's object as the top scene object and the equipment as its child objects, so the capability reuses the complex checks and own culling of child objects: `GroupChecks.Plan` computes the `CullingPlan` of the crossing from the held equipment whose placement differs from the scene's, `GroupChecks.Layout` verifies that nothing but the equipment changed, and `GroupChecks.Culling` verifies the spheres. A crossing's game-object culler lists the object above each mast. `CullingPlan.Compute` therefore gives a mast that left the culler's sphere a sphere of its own, hands the listed object above it, which has no presence of its own, to the mast's own sphere, so no sphere stays at the mast's old place, and sets the objects between by the activity rule; the culler keeps its radius. A bell stands below no culler and gets no sphere. Capture holds the observation with the fixed placement and the scene placement of the hold, and Restore puts back placement, activity, hold and culling plan and verifies them. Relationships of any kind are refused in `CheckRelationships`, so a modification leaves the logical binding alone, and so is a track-following placement (`NoFollowing`), before any mutation. `Read` returns the placement in the frame of the object above for equipment without a hold, so removing a modification recomputes the underlying placement from the scene, and returns no activity for equipment a game-object culler lists itself.

`ExistingEquipmentPattern.MastProblem` and `BellProblem` judge `MastFacts` and `ExistingBellFacts`, which the native world fills: the lamps on the light object and the gates at and below it with their keys, what else the hierarchy holds, whether the nearest key-value object above is a crossing controller's, whether a gate stands beside the light object below the object above it, and whether a track-relative component switches the object with a track group. Model, material and animation values do not matter.

`CrossingDeviceWorld` is the native world, one instance per kind over the scene's `GroupWorld`. It observes the controller through `GroupWorld.Observe(root, listingRoot, moves)`: the listing root makes a listed object that its culler hides read as on (`GroupWorld.Authored`), so a scene patch that applies while the crossing is culled still plans the mast's sphere, and `moves` marks the transforms at and below an `Animator`, such as a gate's arm, as animated, so a gate that moves between a capture and a restoration fails no layout check. `ActivityProblem` refuses Enabled for equipment that a game-object culler on an object above lists itself, and for a bell when the build cannot configure it again. `SetPartActive` goes through the group world, so a mast that own culling switches takes the value as its desired activity. For a bell that is off and is to be enabled it first calls `CrossingBells.ReconfigureNative` and only then switches the bell on, on every path that enables it: `OnEnable` starts the player's loop at once, and with the crossing ringing that loop would play a clip the player destroyed when it was disabled; `Configure` on the inactive player sets the new clips and starts no loop. `ReconfigureNative` configures the controller's player with the clip in the controller's `_audioLoadReference` and the indexes and volume of the definition `GradeCrossingController.DefaultCrossingBellIdentifier` names, as `LoadBellAudio` does: `Audio.IntegerLoopingPlayer.OnDisable` destroys the clips it split and `OnEnable` splits none for a player that was configured through `Configure`.

Sources: `Track.KeyValueLampMaterialController.OnEnableWithProperties` and `RollingStock.Controls.KeyValueBoolAnimator.OnEnableWithProperties` take `GetComponentInParent<KeyValueObject>()`, show the key's current value and observe it, so a moved or re-enabled mast keeps its controller; `GradeCrossingController.CreateBellPlayer` creates the `Crossing Bell` child in `OnEnableWithProperties` and `OnDisable` destroys it, so a controller that is switched off and on holds a new bell that no modification has reached until the next load attempt; `Helpers.Culling.GameObjectCuller.CullingSphereStateChanged` sets the activity of the objects in `gameObjects`. The core tests `ExistingEquipmentTests` cover the whole-file contract against the controlled group world; they miss the native lifecycle, rendering, audio and the controller's behaviour.

## Implement mod objects

A modification with a `source` makes a mod object (`ModObjects`, ADR 0008). `PatchEngine.Parse` reads the source like a target and checks the modification's own target against it: the same scene and component, the structure that `ModObjects.StructureOf` gives for the source's (a part's `child-object-v1` becomes `scene-object-v1`, any other stays), no key, and a path that `ModObjects.IsPath` accepts. A mod object without a placement is an invalid definition.

A scene that builds mod objects implements `IModObjectScene`. `Build(identity, source, placement)` makes the object from the resolved source, at the placement, and returns it; afterwards the identity must resolve to that object alone, through the capability of its family. `Remove` takes it away with everything below it. `SceneCapabilities` forwards both to the host's `ModObjectWorld` and releases the removed object from the capability that resolved it. In the game, `ModObjectWorld` instantiates the source below an inactive holder, names and places the copy, and moves it into the parent that its target path names, so its components start at the placement. That parent is the source's parent, or for a part's copy the parent of the part's group, an object above the source. Before that, `Prepare` undoes what the running game made of the source and the copy took over: it switches on the renderers and objects that a culler hid at the source, gives a night light its full intensity, removes a floating-origin registration of the copy's own, and removes the model that a prop instance loaded, which the copy's prop instance loads itself. `StandBuilt` then makes the copy stand built and active whatever the progression and construction state, and keeps every switch of the game away from it. Base-game progression switches a rail bridge through the construction controller (`Game.Mow.TrackConstructionScenery`), which reads the construction state of its track segments; map features enable those segments' track groups and construction milestones set their state. A map feature also sets its `gameObjectsEnableOnUnlock`, a progression controller (`Game.Progression.ProgressionEntityObjectController`) its two lists, and a `Game.MapObjectActivation` its own object. Each object of the copy that such a switch names gets the activity it has with all track complete (`ConstructionSegmentRule.ShownWhenComplete`), every feature unlocked and every progression enabled. The switches inside the copy, whose lists Unity pointed at the copy's own objects, are removed, and the switches elsewhere keep naming only the source. A failure of this step refuses the build. The scene asset and the source are never changed.

The engine builds a mod object in `Execute` when its target does not resolve yet. The source resolves through the same exact rule as a target, keys included. When no object matches the source and the modification's `source.build` is present, the engine asks a scene that implements `IModObjectSources` for `Identical(source, build)` and builds from the first instance; `PatcherLog.Warning` writes `ModObjects.FallbackWarning`. An ambiguous source has no fallback, and neither has a target or an equipment source (ADR 0008). In the game, `ModObjectWorld.BuildOf` hashes the components of the object and its parts in hierarchy order with their mesh and material asset names, without object names, and stops below a `Helpers.PropInstance`, whose identifier it takes instead. The signature starts with `v1:` and the number of objects read, so `Identical` walks the source's scene once, counts each subtree, and hashes only the subtrees of that size. It lists them by hierarchy path in ordinal order, then by sibling index, and leaves out mod objects. The engine gives `IModObjectScene.Build` the path beside the object it builds from: the parent that `ModObjects.StandsIn` gives, as many levels above that object as the written target's parent stands above the written source, and the name of the written target. A mod object built from an identical instance stands in the instance's parent, a part's copy beside the group of the part it is built from, and no parent is created. It records that root per mark (`ModObjects.MarkOf`) in `standingRoots`; `Matches` moves a written path in or below a mod object to the recorded root (`ModObjects.Moved`), so the written target and the edits of its parts keep resolving. `TargetIdentity.SameObject` and `Text` compare paths in a mod object by `ModObjects.Canonical`, the mark and the path after it, so a session finds the existing modification whether the window names the written path or the path where the object stands. `RemoveModObject` drops the recorded root. From then on the modification runs like any other: preflight, the state before the change, apply and verify. A failure after the build removes the object again, except an incomplete cleanup, which keeps it for Recheck. The engine records what it built per scene patch file key and modification ID. A complete application of a scene patch file removes the recorded mod objects that the file no longer holds; an early route removes none.

`ModObjects.Path` gives the target path that scene patch editing writes: the path that `ModObjects.Beside` gives, which is the source's path or for a part the path beside its group with the part's name, with a mark that holds the mod ID and the modification ID. `ScenePlaces.Of` and `ScenePlaces.SourcesOf` treat a path in a mod object as naming no place, and `SceneClassification` reads the kind from the path without the mark, so a mod object has its source's kind and the place where it stands.

In a session, `PlaceModObject(inspectedObject, placement, inspected, group)` is the placing click of Duplicate; `group` is the path of the inspected part's group, and the part's copy then stands beside that group as a top scene object of its own. It writes the modification under a new key with the prefix `mod-object-`, with the source's `build` from `IModObjectSources.BuildOf` when the scene knows it (a duplicated mod object passes on its own `source` as written), builds and places the object, and registers one history step. A mod object of the same scene patch file is duplicated from its own source, and an object below a mod object from the map's object that it was copied from, so no mod object depends on another. `Remove` of a mod object removes the object, its modification and the modifications whose target lies below its path, in one history step that Undo puts back. An edit of an object below a mod object gets the mod object's key in `dependsOn`. Every other edit of a mod object goes through `Change` as for an existing target; the edit keeps `source` and never drops the placement. `ModObjectsChanged` tells the host that the scene holds other objects than its inventory.

The window part is `DuplicateState`: the blank object window with its two steps, the reasons that keep Duplicate inactive (a starter placement marker, an inspection-only object and a family that a copy does not rebuild; scene objects, parts, station map icons, location signs and the Ela bridge are duplicated), and `Tick`, which gives a recorded or real left click on the world to the session. `IPlacingPointer` is the adapter for the click and the map point under it.

## Combine capabilities

`SceneCapabilities` implements `IScene` and `IInspectionScene` over a list of capability adapters. `Resolve` asks every adapter and remembers which adapter resolved each object; an object claimed by two adapters appears twice and fails as ambiguous. Every other call goes to the adapter that resolved the object. `AddUnavailable(structure, reason)` records a capability whose game functions are missing: a target naming that `structure` resolves to a placeholder whose preflight fails with "incompatible with this game build" and the reason, while unrelated modifications still apply. `InspectedTarget.Validate` checks for that placeholder first, so an edit of an object whose capability is unavailable is refused with the incompatibility and its reason instead of a changed inspected context; the inspected-context guard itself is unchanged. `Capability` is `Incompatible` only when no adapter is available. `EntryPoint` constructs each native adapter separately, so a failed bridge check leaves location sign placement available and the reverse. `SceneCapabilities` also implements `IDependentOutputScene` and `IVersionedScene`: `Output` and `RetryOutput` go to the adapter that resolved the object, and an adapter without dependent output reports none; `MinimumPatcherVersion` takes the highest value any adapter returns. The location sign inventory's problems come from the location sign adapter's `Refusal`, the same check its `Preflight` runs.

## Implement a bridge capability

`BridgeScene` is the core part of the bridge capability. It implements `IScene` over `IBridgeWorld`, which `BridgeWorld` implements with Unity:

- `IBridgeWorld.Resolve` matches the supported path, scene name and root culler. `BridgeWorld.SupportedPaths` holds the one retained bridge.
- `CheckPattern` refuses inactive parents, a disabled root culler, missing scripts, rigidbodies, track-owned components (`Track.*`, `AutoTrestle.*`, `Game.Mow.TrackConstructionScenery`) in the hierarchy, a hierarchy without colliders, and a construction-scenery entry that targets the root or one of its parents.
- `Observe` returns a `BridgeObservation`: the root state in map coordinates, one `ColliderState` per collider (identity, shape properties, enabled flag, activity below the root, placement relative to the root, and for box, sphere and capsule colliders whether the physics bounds are centered on the transformed shape after `Physics.SyncTransforms`), and a text description of the separate scenery. That description covers the loaded `AutoTrestle.AutoTrestle` components within 250 m of the bridge's first observed position (local transform, activity, control points, generated flag, beam-matrix digest) and the construction-scenery controllers that reference the bridge.
- `SetPlacement` converts map coordinates, sets the root placement, calls `RequestUpdateCullingPosition` on every active culler in the hierarchy and synchronises physics. `SetActive` switches the root only.

`BridgeScene` records the first observation of each bridge in the load as its reference. `Preflight` refuses a bridge whose collider layout differs from that reference. `Apply` enables before the placement change and disables after it, as the location sign does, then verifies root placement and activity, the collider layout against the reference, collider activity against the root, and separate scenery against the observation before the change. `Restore` reapplies the captured root state and returns true only when all of those match the capture. The adapter's capability minimum is `0.5.0` for a `bridge-colliders-v1` target, also when the bridge adapter is unavailable.

## Implement the station map icon capability

`StationMapIconScene` implements `IScene`, `IVersionedScene` and `IRelationshipScene` over `IMapIconWorld`, which `MapIconWorld` implements with Unity. Its target component is `UI.Map.MapIcon` and its structure `station-map-icon-v1` (`StationMapIconRules`). `Resolve` takes only a path directly in `World/Map Labels/Station Icons` (`StationMapIconRules.Listed`), the same objects that `SceneObjectRules.Classify` makes candidates there, so the map icons the game creates for cars and players never resolve.

- `MapIconWorld.Problem` refuses an unloaded scene, an object outside the Station Icons object, missing scripts, rigidbodies and any culler (`Helpers.Culling.*`, `Helpers.SimpleCuller`) in the icon's own hierarchy, because the capability moves no culling sphere; another icon stays editable. The inventory shows the same reason under Supported edits.

- `SetPlacement` converts map coordinates with the origin rule and synchronises physics for the icon's click collider. `SetActive` switches the object; `MapIcon.OnEnable` and `OnDisable` add it to the map builder and remove it.

`Apply` enables before the placement change and disables after it, then verifies placement, activity, the parent and, for an icon active with its parents, the map registration. `MapBuilder.OnEnable` also registers inactive icons, so a disabled icon's registration is not checked. `Restore` reapplies the captured placement and activity and returns true only when the same checks pass. `StationMapIconScene.Requires` gives the `0.5.0` minimum for a `station-map-icon-v1` target or a `UI.Map.MapIcon` target component, also when the capability is unavailable. A `ProgressionEntityObjectController` can switch an icon at load and on `IndustriesDidChange`; `MapIconWorld` reads and sets the activity of such an icon through `GameSwitchActivity`, so an explicit disable holds through the switch (see the construction controller notes above).

Sources: `UI.Map.MapIcon` (`[RequireComponent(typeof(Canvas))]`; `OnEnable` and `OnDisable` call `MapBuilder.Shared.Add` and `Remove`); `UI.Map.MapBuilder` (`_mapIcons` is a `HashSet<MapIcon>`; its `OnEnable` fills it with `FindObjectsByType<MapIcon>(FindObjectsInactive.Include)`; `Add` sets the icon's zoom); `Game.Progression.ProgressionEntityObjectController` (`UpdateObjectStates` calls `SetActive` on `activeOnProgressionEnabled` and `inactiveOnProgressionEnabled`, from `Awake` and on `IndustriesDidChange`). The native map editor's **Scene Patcher** window reads `NativeInventory` through `IInspectionScene`. ## Bind each peer to its local world

Every host and client loads the patcher DLL and applies scene patch files to its own scene. The native entry point holds one peer's state in a `LocalWorldBinding<PatcherBehaviour>`: the capability adapters, the `PatchEngine` with its captured underlying states and guards, and the `PatchRuntime` with the reported warnings of the current load attempt. It sends nothing to other peers and receives nothing from them.

The binding takes two keys. The world key is the map context: the active map definition and resolved map layer identifiers, and whether the map is open in the native map editor. The patcher state lives as long as this key stays the same, across world unloads. The attempt key combines the `Map.Runtime.MapManager` instance and the `Track.Graph.Shared` instance when that member exists. Neither key is a verified world identity: a replaced map manager or graph does not establish that the scene objects are new, and an equal key does not establish that they are retained. The reconciliation decides that per object.

`EntryPoint.OnWorldLoad` calls `Enter(world, attempt)` on every world-load callback. It returns a `WorldEntry`:

- `Started`: the peer had no state for this map context and created it. A different map context releases the previous state first.
- `Reentered`: a new load attempt over the state retained for the same map context, because the attempt key changed or `OnWorldUnload` ended the previous attempt.
- `Repeated`: another callback in the current load attempt. Successful modifications reconcile to their absolute map placement; failed modifications stay blocked and targets with unverified cleanup stay guarded.

A native marker check can run before the world-load callback. It calls `Prepare(world)`, which opens the load attempt for the current map context; the callback then joins that attempt instead of starting another. A marker check on another map context releases the retained state. When a key cannot be read, the patcher reports a native warning and applies nothing for that callback. If creating the state throws, `Error` is set and the next load attempt checks the prerequisites again.

Every new load attempt over retained state calls `PatchEngine.Reenter`, which returns a `ReentryResult`:

- An object that still resolves under the identity it was first resolved under is retained. Its underlying state, captured before its first mutation, stays, so a later removal returns it to its native state rather than to the patched one. Its unverified-cleanup guard carries over.
- An object that does not resolve but that its `IRetainedScene` reports as `Unsettled` is retained as well. It still exists, but cannot be checked yet: crossing coverage reports a controller whose scene is valid but not loaded, as during a native marker check inside a scene load. A destroyed controller, or one in a loaded scene that no longer stands under its identity, is not unsettled.
- Any other object is released. The engine forgets it, and an adapter that implements `IRetainedScene` removes what the patcher owns for it, never native state. Crossing coverage destroys the owned spans of a reconstructed crossing; the map's own detection spans and circuits for that crossing, and other crossings, stay as they are. A rebuilt crossing therefore gets one owned set under the original span IDs.
- Failures recorded in the previous attempt are cleared, so the new attempt retries them once.
- A release that leaves owned state behind, or a retained object that cannot be checked, is listed in `Failures`. The object stays recorded, so the next load attempt retries the release.

`PatcherBehaviour.BeginAttempt` then starts a fresh `PatchRuntime`, so diagnostics, overlap notices and the warning identity start over, and logs one line with the retained, released and failed counts. Each application at a world-load callback moves the location-sign terrain subscription to a replaced map manager through an `InstanceSubscription`, which moves its one handler to a new instance, adds nothing when it is bound again to the same instance and removes it when the state is released. Each cleanup failure becomes a local native warning. It reports no failure to another peer and triggers no rollback, disconnection or session-wide failure. A retained object whose check throws is kept with its state and listed in `Failures`; the next load attempt checks it again. If `Reenter` itself throws, the binding sets `ReentryError`, releases the state and starts a new one for the map context; the entry point reports it as a local native warning. `OnWorldUnload` ends the load attempt and the native map editor-bound parts, such as the panel and the scene patch editing session; the next load attempt reconciles the rest. Observers follow two lifetimes. The world state holds the terrain subscription and one owned-span root per scene; the process holds the Harmony hooks. Repeated callbacks, re-entry and unloads reuse them. Each load attempt holds the Scene Patcher window's handlers, the scene patch editing session's history-change handler and an active gizmo's drag and origin-move subscriptions; `EndAttempt` disposes them before the next attempt attaches new ones. A native marker check observes the message collector only for the duration of that check.

Each peer converts map coordinates through its own `Helpers.WorldTransformer`, so differing local origins on host and client yield the same map placement. Repeated application writes the placement again and refreshes its dependent state; it does not accumulate an offset.

The patcher writes no shared game property, so host authority checks have nothing to gate. It adds no synchronization, admission check, disconnection or session-wide rollback. Reconnect and re-entry go through Railroader's own admission and synchronization unchanged. Railroader's own checks of required mods and versions govern joining, and each installation needs the mods and its own DLL permission. Native version matching does not prove that peers hold identical scene patch files or applied them successfully.

When the binding releases the state, because the map context changed, `Reenter` threw or `OnModUnload` ran, `PatcherBehaviour.Release` disposes `SceneCapabilities`, which disposes every capability that implements `IDisposable`. `CrossingCoverageScene.Dispose` writes the native circuits and spans back to every crossing it holds a baseline for and that still conforms, and retires every owned span, also for a crossing that is gone. This protects the case where the patcher state ends while the scene stays loaded, such as a mod reload or unload that calls `OnWorldUnload` and `OnModUnload` without unloading the map scenes; the next state then records the true native coverage and applies each modification once. Railroader 0.6.2 offers no such route inside the native map editor, and the protection has not been tested in the game. Dispose throws nothing: a crossing it cannot restore keeps its patched circuits, and the next state refuses them as described under detection additions.

Retained-world limits: an object counts as retained when the capability that resolved it finds the same instance under its identity at the start of the load attempt, or, for crossing coverage, when the instance still exists in a scene that is not loaded yet. The reconciliation can run during a native marker check, before Unity marks a loading scene as loaded. Any other capability's object that cannot be resolved at that moment is released, which forgets its captured underlying state. In Railroader 0.6.2 every route into a new load attempt for the same entry point has already unloaded the map scenes, so this releases only objects that are gone. A replaced map context, including a replaced map manager with a changed map identifier, starts from new state; crossings return to their native coverage first, while other objects retained across that change start from their current, possibly patched state. Crossing coverage with its equipment, child objects and existing crossing equipment implement `IRetainedScene`. Location signs, the bridge, track markers and crossing pads hand their effects to the target or to native registrations that the native components hold, such as mask and heightmap modifiers in map-manager storage, culling spheres and graph locations; pads keep their generated geometry under the pad. For a reconstructed target in a retained map manager, the patcher releases nothing of those, and whether the native components remove their own registrations when they are destroyed has not been checked.

Native single-player observation, commit `e2f526d` on Railroader 0.6.2: reloading the same save in one process through the main menu, twice each with the CrossingReroute and FixedPlacementBaseline fixtures, logged "0 objects retained, 2 released, 0 cleanup failures" on every reload. The current build writes that line as a debug line, `Loading again in the same world: N objects retained, N released, N cleanup failures.`, while Debug logging is on. The game rebuilt every modded and added object, the patcher applied each modification once (one owned span set without duplicate IDs, the moved location sign moved once, the disabled location sign still inactive), and the crossing detected on the added tracks. Native map editor sessions load another map context first and always start new state. In Railroader 0.6.2 single player the path where the patcher state ends while the map stays loaded is not reachable natively: the map editor offers no mod reload, and the definition editor loads `rr/editor-default-map`, not the edited map, so the restoration on that path rests on the core tests. Retention of scene objects across a load attempt has therefore been exercised only by the core tests. Whether reconnect retains scene objects, the map manager or the graph has not been observed.

The core tests exercise peer independence, per-peer map and capability checks, repeated callbacks, re-entry after a reconstructed graph or an unload, early checks that open the load attempt and keep a crossing whose scene is not loaded, retained guards and underlying states, retried failures, released reconstructed targets, owned-span cleanup with preserved native state, native crossing coverage restored when the state is discarded while the scene stays, refusal of patched circuits as native, isolated cleanup and reconciliation failures, and single observers across load attempts, through `LocalWorldBinding` and complete scene patch files with controlled scenes. They do not exercise Railroader networking. Live host/client loading, later joining, reconnect, native synchronization and crossing-controller behavior with this build remain unverified.

### Crossing changes on a later join and a reconnect

A crossing's patcher state is the `Baseline` of `CrossingCoverageScene`: the native circuits, the owned spans, the added circuit sets and the equipment additions. Each peer holds its own, and a load attempt handles it by the rules above:

- A crossing the game rebuilt is released. `CrossingCoverageScene.Release` retires the owned spans and calls `CrossingEquipmentPart.ReleaseAll`, which destroys each addition that still stands and drops each one that is gone. `CrossingCoverageWorld.DestroySpan` and `CrossingEquipmentWorld.Destroy` return at once for an object Unity already destroyed, so a release after a map unload writes nothing. The rebuilt crossing then gets a new baseline and one set of spans, circuit sets and equipment under the IDs of the scene patch file.
- A crossing that still stands keeps its baseline. `Write` and `CrossingEquipmentPart.Write` reuse the owned spans, circuit sets and additions that match, so the application writes nothing.
- A release that leaves a span or an addition behind throws, `PatchEngine.Reenter` lists it in `Failures`, and the next load attempt retries it. The rebuilt crossing is applied in the meantime, so until that retry succeeds two sets can stand: the additions of the old crossing that could not be destroyed, and the new set of the rebuilt crossing. `CrossingJoinTests.AFailedCleanupIsReportedLocallyAndRetried` holds that state and its end.
- An added bell holds one observer of the controller's bell key and one loaded audio reference. `OwnedBell.Release` gives both up when the patcher destroys the bell and, through `OnDestroy`, when Unity destroys it with its scene. A bell is built only beneath an active controller, because Unity calls `OnDestroy` only for objects that were active.
- `ExistingEquipmentScene.Release` drops the hold of a mast or bell that is gone, and `PartCullingController.Unload` has already forgotten the spheres of the unloaded map.

What the code of Railroader 0.6.3 says about the routes, read from the decompiled game and not observed in a session:

- `Track.Crossings.GradeCrossingController.LoopCoroutine` runs while the controller is enabled, with no host, sandbox or multiplayer check. It reads `circuitSets` and the three spans of each set on every pass, asks `TrainController.Shared` for the cars on a span, writes the lights, gates and bell keys of its own `KeyValueObject` and sets `_bellPlayer.play`. Nothing reassigns `circuitSets`. The controller does not register its key-value object with `StateManager.RegisterPropertyObject`; `KeyValue.Runtime.KeyValueObject` is outside the decompiled sources, so whether it sends those keys to other peers was not read. Detection therefore runs per peer, from that peer's own cars, and each peer needs its own additions.
- `UI.Menu.GlobalGameManager._ReturnToMainMenu` is the one route out of a session: `Network.Multiplayer.OnClientDisconnect`, a failed snapshot, leaving, and `LeaveAndJoin` all call it. It publishes `MapWillUnloadEvent`, unloads the map scenes, disconnects, calls `UnloadMainScripts`, which reaches `IWorldLifecycle.OnWorldUnload`, and loads the main menu. `Game.MapLoader.OnDestroy` clears `Graph.Shared`. The world-unload callback thus runs after the map objects are destroyed.
- A join runs `_Launch`, `Multiplayer.ConnectClient` and `HandleClientDidReceiveSnapshot`, which loads the map, calls `PopulateFromRemoteSnapshot` and then `ExecuteMainScriptsOnWorldLoad`, before `SessionDidBecomeActive`. The host's own start takes the same route. `ModAssemblyManager.WorldLoad` guards the callback with a flag that `WorldUnload` resets, so it runs once per loaded map.
- `Network.Multiplayer.CloseServer` and `OpenServer` stop and start hosting without a map load or a world callback.

A later join and a reconnect are therefore expected to be a new world load over objects the game built anew: the load attempt releases every crossing of the earlier session without a write and applies each modification once. The single-player observation above, a reload of the same save in one process, takes that path for crossing coverage. It did not cover added equipment or existing masts and bells.

The core test `CrossingJoinTests` drives two peers through complete scene patch files that reroute a circuit, add detection, and add a light or gate and a bell: a later join that changes only the joining peer, repeated callbacks, a reconnect over rebuilt crossings, a new load attempt over kept crossings, two supplying mods with equal IDs, a prerequisite one peer lacks, a construction failure on one peer with its retry at the next join, a cleanup failure with its retry, an early check over a crossing whose scene is not loaded, and the end of the state while the scene stays. `ExistingEquipmentTests.RejoinAppliesOnceToTheRebuiltCrossing` covers moved and disabled masts and a moved bell. These tests model the unload as the destruction of every addition, with a bell's observer and audio. They do not exercise Unity, the game's networking, the controller's loop, rendering or audio.

## Apply a scene patch file

`ModScenePatchFiles.Discover` returns a `LoadedMod` for each loaded mod with `Data/scene-patches.json`, in the order of `AssetPackManager.OrderedPacks`. It decodes the scene patch file and `Info.json` as strict UTF-8; a mod entry that cannot be read becomes a `LoadedMod` with an `Error` and does not hide the mods after it. `LoadedMod.Read` takes the name, version, author, website and the identifiers under `dependencies.required` from `Info.json`. In the native map editor, discovery returns only the edited mod, marked `EditTarget`, so its scene patch file applies before Save has declared the dependency; the native map editor's Save writes the missing or insufficient dependency entry. `LoadedMod.Applicable` is true for a readable mod that is the edit target or declares `crankyant/scene-patcher`.

`PatchRuntime.ApplyLoaded` applies the applicable mods in the given order and returns a `LoadedScenePatchFile` per mod: the engine's `ScenePatchFileResult`, or `Skipped` for a mod that never reached the engine. The engine rejects a scene patch file whose scene target map is not in the map context, as an error reported in the native map editor, and sets `ScenePatchFileResult.NotApplicable` to the reason with the named map and the loaded maps. `ApplyLoaded` reports that reason for a mod that is not the native map editor's edit target as a `PatchFailure` with `FailureCause.NotApplicable`, once per supplying mod per loaded world; that cause has no `ReportTo`, and its message names the mod, identifier and version and then the reason, without the operation, object or report direction of a failure. `NotApplicable` stays null while the loaded map is `SceneTargetMapCheck.EditorDefaultMap` (`rr/editor-default-map`), which the game loads when Editor is clicked in the main menu, before a map is chosen (`MenuManager.EditorGameSetup`); New Game never offers that map. The early routes `BeforeNativeCheck` and `BeforeNewGameStart` report no such warning, so a load gives one. A failure report or overlap notice that cannot be delivered is recorded in `PresentationError` and does not stop the next mod. `ApplyLoaded` passes an `OverlapNotice` to `IOverlapNotices` when a second or further supplying mod has an outcome whose `ResolvedTarget` is the same object, compared by reference. Only an outcome that resolved its target uniquely carries that object. The notice's `Key` stays the same for the object, so the native adapter replaces the row with `MessageLog.Info` when another mod joins; the same set of mods gives one notice per loaded world. `Dependencies` describes the declared dependencies among the named mods. Overlap does not change application or failure handling. The `PatchEngine.Apply` overload with `scenePatchFileKey` distinguishes modification identities across scene patch files during one load. Keep the key stable for each supplying mod scene patch file in that load.

The returned `ScenePatchFileResult.Error` reports refusal of the whole scene patch file, including invalid format, a `modifications` value that is not an object keyed by modification ID, a repeated property name at any depth, scene target map mismatch and incompatible capability. Modifications that `dependsOn` does not order are processed in the ordinal order of their keys (`PatchEngine.Entries`). Per-modification failures appear in `Outcomes`. The engine records failures and does not retry the same scene patch file modification during the load attempt; `Reenter` clears them for the next attempt. If a mutation fails, it asks the adapter to restore the captured snapshot. If restoration cannot be confirmed, the engine rejects later operations on that resolved target for the load.

### Classify failures

`Outcome.Failure` is a `FailureKind` that says what a failure did to the scene:

| Kind | Meaning |
| --- | --- |
| `Refused` | Stopped before any mutation: an invalid value, a missing or ambiguous target, a failed preflight, relationship check or mutation guard, or a changed inspected observation. |
| `DependencyFailed` | Not attempted because a modification in its `dependsOn` closure failed. |
| `Restored` | The mutation failed and `Restore` verified the captured state. |
| `AwaitingOutput` | Restored, but the restored dependent output has not completed, or refused because that output of an earlier restoration is still outstanding (`PatchEngine.Guarded`). The target waits until the output completes; this is no incomplete cleanup and needs no `Recheck`. |
| `IncompleteCleanup` | The mutation failed and the restoration did not verify. `Outcome.Remaining` names what remains. |
| `Blocked` | Refused because an earlier `IncompleteCleanup` guards the target. `Remaining` repeats that state. |
| `AlreadyFailed` | A world-load modification that already failed in this load attempt; it is not retried before `Reenter`. |

A file-level refusal sets `ScenePatchFileResult.Error` and leaves `Outcomes` empty. Before capture the engine reads the target's state once more, and after an unverified restoration it reads it again. `RemainingState.Describe` compares the two readings and returns one line per differing setting (position, rotation, activity, track binding, crossing coverage) and one line for owned spans still registered (`CrossingCoverage.Residue`). A read that throws makes every setting uncertain. When every setting agrees, the adapter's own verification, such as a registration or generated output, failed, and the line says that this state is uncertain. The engine keeps those lines with the guard, and `Reenter` drops them with a released target.

Adapters throw from `Apply` and return false from `Restore` as before; the engine and the session decide the kind. An adapter needs no change to take part.

A native journey can produce each failure kind on demand with the test-only fault build; see [inject a failure into a native journey](fault-injection.md).

The core engine accepts JSON text. Runtime application does not rewrite the source scene patch file. `ScenePatchFile.Write` returns the original text for an unedited supported v1 scene patch file. After an edit it returns the canonical text, which follows the canonical order of the [format reference](../../guides/scene-patches/scene-patch-file-v1.md#canonical-order) and in which every number that was not replaced keeps its source literal. `PreservingJson.WriteCanonical` orders the text as it writes; the tokens stay in their source order, so reading never reorders a scene patch file. `PreservingJson.KeepLiterals` gives a number that an edit leaves at its value the literal of the number it replaces. There is no format-conversion API in this slice. Unsupported or malformed scene patch files are protected against writes.

## Edit through a session

`PatchEditingSession` owns one scene patch editing session for the edited mod. It takes the `PatchEngine` that applied the scene patch file at world load, an `INativeHistory` and an `IStorage`.

- The engine and the session decide whether a scene patch file's scene target map lets it apply through `SceneTargetMapCheck.Problem`: the map must be in `IScene.MapIds`, and it must not be one of the map patches a scene that implements `IMapPatchContext` lists. Railroader 0.6.3 puts the edited map patch, and the map patches it builds on, in the native map editor's map context, while in a save a map patch is never in the map context, so a scene patch file that names a map patch would be accepted in the editor and skipped in play. The refusal says so and names the bottom map layer, and the session's diagnosis at `sourceMap.mapId` expects that layer. `SceneCapabilities.MapPatches` supplies the list; the game side reads `ModScenePatchFiles.MapPatchIds`, the map definitions in the map context whose `MapDefinition.Role` is `Patch`.
- Without a scene patch file in storage, the session creates one whose scene target map is `PatchEditingSession.SceneTargetMapFor(scene.MapIds)`: the last entry of the loaded map context. `IScene.MapIds` must therefore list the edited map definition first and then all its resolved map layers topmost first, as Railroader's `ActiveMapDefinition.MapLayerIdentifiers` does, so the last entry is the bottom map layer, or the map definition itself without layers. An existing scene patch file keeps its scene target map. `SceneTargetMap` returns the scene patch file's scene target map, which for a new scene patch file is the one it was created with, and `CopyId(entry)` builds the Copy ID JSON with it. While the session cannot read the scene patch file, `SceneTargetMap` is null and `CopyIdRefusal` holds the session's refusal, which `CopyId(entry)` throws. The static `CopyId(mapIds, entry)` serves Copy ID outside scene patch editing.
- Before the equal-content check, `PreservingJson.KeepStoredPrecision` gives every axis of `placement.position` and `placement.rotation` that equals the existing value at single precision the existing value, so `KeepLiterals` keeps its source literal and an edit of one axis leaves the others' text alone.
- `Edit`, `Remove` and `Recheck` accept the `InspectedTarget` of the inspected observation; the Scene Patcher window always passes `inventory.Pin(selected)`, so a stale inventory or changed observation refuses the edit. Immediately before the scene mutation, with or without a token, the session runs the engine's guard: preflight again, the same unique object, the same map context, and the token when given. A refusal there restores the scene patch file and requests no scene restoration, because no mutation started. History replay passes no token, since Undo and Redo return to states the user did not inspect, and still runs the guard.
- `Edit` and `Remove` resolve and preflight the target, change the scene patch file, and reconcile the object: the engine's underlying state for that object, captured before its first mutation, overlaid with every effective modification that resolves to it. Removal therefore recomputes the state instead of restoring a snapshot. A failure restores scene patch file and object; an unverified restoration blocks the object until `Recheck` verifies it. Every session outcome carries a `FailureKind` as in the engine: a refusal before `scene.Apply` is `Refused`, a verified restoration `Restored` or `AwaitingOutput`, an unverified one `IncompleteCleanup` with `Remaining` measured against the state read before the edit, and an edit of a guarded object `Blocked`. Track-following reconciliation reports `Restored`, `IncompleteCleanup` and `Blocked` the same way.
- `Recheck` resolves, validates the inspected token and preflights afresh, computes the desired state from the scene patch file and applies it only when the object differs. The scene patch file's persistent identities, its modification keys and addition IDs, decide the result: crossing coverage reuses owned spans for an addition the scene patch file names and retires owned spans an interrupted attempt left for any other, before anything new is built. When the state then verifies, the guard ends. When the apply throws or does not verify, the object stays or becomes guarded as `IncompleteCleanup`, with `Remaining` measured against the scene patch file's desired state. `CleanupUnverified(target)` and `RemainingState(target)` read the guard by identity from the engine's record, without searching the scene, so the panel can ask on every rebuild. `GuardOutcome(target)` returns the refusal an edit of a guarded object gets, as `Blocked` or `AwaitingOutput`, in the same way. The panel's `EditFeedback.Run` checks it before the pin compares the scene, because an incomplete cleanup leaves the object changed and the comparison would otherwise call the inspection stale. The panel's Recheck runs the panel's own Refresh first and then pins the fresh entry of the same object, so it needs no separate Refresh after a failed attempt. `SceneInventory.Refresh` reads only; it neither mutates nor ends a guard.
- `RecoveryGuidance.For(outcome, place, action, structure)` turns a failed outcome into a `Recovery`: a heading that tells `refused`, `failed and was undone`, `failed; cleanup incomplete` and `blocked by an incomplete cleanup` apart, the problem, a correction in scene patch editing terms, the remaining state and the guide of the operation. `Guide(place, action, structure)` picks the guide from the action first, so a `Detection addition` in the `Crossing coverage` group opens the detection guide, then from the panel's action group, such as `Placement` or `Track binding`, and otherwise from the target's capability. The panel's `EditFeedback.Run` reports `Recovery.Line(action)` and keeps the `Recovery` with its message. The footer's **Guide** opens that guide, and the footer's state line shows the remaining state of an inspected object whose cleanup is unverified. Runtime player warnings (`PatchFailure`) do not use this guidance: they name the mod and the operation and ask for a report, never a repair of the distributed document.
- Each completed change registers one inverse with the native history. The inverse sets the modification under its key to an absolute earlier state and registers its own inverse, so Undo and Redo are repeatable. It never throws: an exception inside `Core.UndoManager.Undo` leaves the native grouping open. A failed replay keeps the scene patch file, sets `IncompleteOperation` and keeps the session dirty until a complete Save. When native Undo or Redo itself throws, the native manager keeps its partial group open and later edits reach neither its stack nor its change count; the session then keeps native map data outstanding and `IncompleteOperation` set through every Save until the native map editor is reloaded.
- `Outstanding` names the participants that still need a write: native map data, scene patch file and dependency metadata. The scene patch file is Saved exactly when its current content and the text last read or written have equal content (`PreservingJson.SameContent`): object members match without regard to their order, the `dependsOn` of a modification that is an array of strings matches as a list sorted in ordinal order with duplicates counted, every other array matches in order, strings, booleans and null match exactly, and numbers compare by the value they denote as a double. When no scene patch file existed at load, the scene patch file is Saved while it has no modification. Otherwise the scene patch file is outstanding. The checked native history exposes each group's actions. A separate history identity excludes groups containing only this session's patcher callbacks; mixed groups retain their native identity. Native data is outstanding when that identity differs from the last complete Save, a native upgrade is unsaved, or history recovery is incomplete. A history without action inspection retains the conservative native-count and full-history comparison.
- The history identity gives every undo group a token. Undo and Redo carry the token to the group the native manager creates, a new edit gets a new token, and when the manager prunes its oldest group at 50 levels the state below the stack takes the pruned group's token. Two histories with the same native change count therefore differ, and a pruned or cleared history is never mistaken for the saved state.
- `BeginSave` writes the dependency metadata and then the scene patch file, each only when needed, and throws on the first failure. `CompleteNativeSave` records the saved identity. `FailSave` reports completed and outstanding writes. The scene patch file write first compares the file with the text last read or written under the Saved equality and refuses to overwrite an external change. A reorder or other spacing is not an external change; a changed value, a file that cannot be parsed, a deleted file and a file created after a load that found none are.
- `CheckFileVersion` compares disk content on focus, Refresh and Save. A readable outside change waits for `UseFileVersion` or `KeepEditorVersion`; an unreadable change retains diagnostics and waits for a byte-verified backup before the editor version may overwrite it. The reviewed backup path is reserved before the write. Fingerprints bracket reads and verify that the choice and backup refer to the reviewed bytes.
- `UseFileVersion` restores removed edits through guarded mutation, then applies the incoming scene patch file without a native history step. Earlier patcher callbacks retain their names and register inverse no-ops, so Undo and Redo remain available without rewriting the chosen file version. Explicit application can retry that scene patch file's failed IDs only when their previous cleanup is verified; ordinary runtime application still blocks retries in the same load attempt.
- `ModStorage` is the storage of the edited mod; `ModScenePatchFiles.ActiveStorage` creates it for the native map editor. Each write puts the complete new content in a file beside the target, named after it with `.saving` appended, and replaces the target with it (`File.Replace`), or moves it into place when the target does not exist yet. A failure at any step removes the `.saving` file and leaves the target as it was, so the retry's comparison meets the text it last read or wrote. A leftover `.saving` file from an interrupted Save is deleted before the next write. Windows refuses the replacement while another process, such as a virus scanner, a sync client or the patcher's own periodic read of the scene patch file, holds the target open for a moment; an `IOException` from the replacement is therefore tried again, up to `ModStorage.ReplaceAttempts` times with pauses of 50 to 200 ms, while any other failure, such as a read-only target, fails at once. The file operations go through `IModFiles`, which the core tests replace to stop a write midway.

`SnapController` prepares one physical edit from an inspected object and a confirmed graph candidate. `ISnapScene` supplies copied map-coordinate node positions or cubic segment control points with the candidate's native handle and evidence. Preparation verifies the confirmed candidate and retains its geometry. Application rechecks map context, unique identity, handle and geometry both before scene patch editing and through the five-argument `PatchEditingSession.Edit` pre-mutation validator, after scene patch file and object-state callbacks. A pre-mutation refusal restores the scene patch file without calling scene mutation or registering history. The original four-argument edit remains available. Undo, Redo and runtime replay use only the resulting fixed placement, so they need no retained graph token. The validator runs synchronously and must only inspect its prerequisite, without mutating the scene.

Segment snapping evaluates the squared distance to a cubic curve at both ends and all stationary candidates in the unit parameter interval. The distance derivative is a polynomial of degree at most five. Recursive derivative-root isolation divides the interval into monotonic ranges for bisection. This uses the curve controls rather than the world ribbon's display samples. Node snapping uses its copied position directly. Both preserve the inspected rotation and pass the result through the existing fixed-placement adapter and restoration boundary. The controlled snap tests cover these scene patch editing and complete scene patch file outcomes; they do not establish native geometry or presentation behavior.

`NativeDirtyTracker` compares the native change count with changes in undo-stack depth, accounting for pruned groups, to retain unexplained native work until Save. Native work already dirty at attachment clears when the count returns to the native clean count; an unexplained count change still stays outstanding until Save. The session separately tracks grouped native history, and the tracker includes the native map editor's upgraded-on-load flag. The native `DidChange` handler catches tracking failures and records a fault so the native undo group can finish.

`Hooks` connects the session to the native map editor with Harmony patches, installed once per process and checked as one capability: a prefix, postfix and finalizer on `Game.MapEditor.MapEditor.Save`, a postfix on its `IsDirty` getter, a prefix and finalizer on `Core.UndoManager.Undo` and `Redo`, and a prefix on `MapEditorWindow.ConfirmExitEditor`. The Save prefix runs after the native map editor wrote edited terrain tiles and before the native map write. After Undo and Redo the finalizer settles the history identity and calls `MapEditorWindow.RefreshChrome`, because the native handler rebuilds the title and Save button before that point. Every other history change reaches the attachment's `UndoManager.DidChange` handler after the native controller's own `RefreshChrome`; `PatchEditingSession.HistoryChanged` accounts it and raises `OutstandingMayHaveChanged`, on which the attachment calls `RefreshChrome` again, so a scene patch-only edit also turns the title star and the Save button's unsaved tint on. When a required member is missing, scene patch editing is disabled with a message and runtime application continues. These hooks were exercised in recorded isolated journeys on Railroader 0.6.2 build 26335745: native scene patch editing journeys A and B on commit `caa9d3e`, and UI replay C on commit `9fb3ce4`. Those journeys establish only the cases they measured on that build and fixture; they do not establish other builds, object families, history pruning, an exception inside native history execution or multiplayer.

Since Railroader 0.6.3 the Save button is always enabled and is tinted orange with an Unsaved Changes tooltip while `IsDirty` is true; the patcher does not change the button. Its click callback in `MapEditorWindow.BuildDocumentRow` saves edited terrain tiles, calls `MapEditor.Save` and presents a Save Failed alert on any exception. `NativeSaveClick` adds a prefix to that callback. It finds the callback as the only method among the nested types of `MapEditorWindow` that is an instance method, takes no parameters, has a method body and calls `MapEditor.Save`, and it reads the Map Editor from the one instance field of that type. The prefix calls `PatchEditingSession.SaveRefusalBeforeWrite`, which checks the scene patch file again and returns the reason for every refusal of the Save route: a pending version choice, a file that needs repair, an original or backup that changed after a fresh start or after a version backup, and an `Info.json` that the dependency check cannot raise. That last check is a dry run of `DependencyMetadata.Raise` on a fresh read of `Info.json` while the scene patch file has modifications; it refuses an unreadable or inexact file, the patcher listed more than once, dependencies that are not an object and a constraint that excludes the required minimum, and `BeginSave` reads and raises the file again when it writes. With a reason the prefix skips the callback, so neither terrain nor map data is written and no Save Failed alert appears. It reports `Save refused.` with that reason in the editing feedback under the general place Save and, while the Scene Patcher window is closed, in a native alert titled Save refused (`CommandBand.SaveRefusalAlert`), so the enabled button never seems to ignore the click. When the callback cannot be identified, the mod log says so and the Save prefix still refuses before the map write; the edited terrain tiles are then already written, and the refusal reaches the native Save Failed alert. `BeginSave` writes the scene patch file only when its content differs from the text last read or written, and the dependency metadata only when its minimum must rise, so a Save with nothing outstanding writes no patcher file. The click hook, the refresh after a scene patch-only edit and the world-click gates in `InspectionInputBlocker` are new for Railroader 0.6.3. The 0.6.3 smoke run on commit `237c386` exercised the click hook with a pending version choice, with the Scene Patcher window open and closed, and the popup-blocker gate with the native context menu (rows S4 and S6 of its report). ## Enable protected scene patch file recovery

`ScenePatchFile.Load` reads the top-level `formatVersion` first, with a reader that skips everything else and makes none of the full read's checks. It compares the source literal, because the reader also accepts and normalises forms such as `01` and `0x1`; only a JSON integer literal is a version number. `ScenePatchFile.FormatProblem` returns the same answer, so `LoadedScenePatchFile` logs a scene patch file of another format version as not applied whatever map it names. A missing, unrecognized or newer version protects the scene patch file before the rest of the text is read, so a newer scene patch file is reported as newer even when its content would not read as format version 1. A version declared before the text stops being readable still counts. Text that is no JSON object, or no JSON, falls through to the full read and is reported as such.

`ScenePatchFile.Diagnostics` and `PatchEditingSession.ScenePatchFileDiagnostics` describe the last read: why the scene patch file is protected, and each modification the engine would not execute. Each `ScenePatchFileDiagnostic` has `Path`, `StartLine`, `EndLine`, `Fragment`, `Message`, `Expected`, `Reference` (the format reference) and `Corrections` (the recovery guide). A zero `StartLine` means the text has no line for the problem, such as a missing field. `Fragment` is at most `ScenePatchFileDiagnostic.FragmentLines` lines and `FragmentCharacters` characters; a cut fragment ends by saying so and sets `Truncated`. The diagnostic of numbers that cannot be kept exactly points at the first such number.

A protected session offers two routes. Both refuse unless the caller passes `confirmed`, and both refuse while the native map editor has unsaved work, the history identity moved since the session started, or native history is unrecovered. Neither clears history or changes the scene.

- `Reread(confirmed, nativeDirty)` reads the scene patch file and mod metadata again and, when the text reads as a scene patch file of this session, makes it the session's scene patch file with that text as its Saved state. It writes nothing. It then applies the adopted scene patch file through `PatchEngine.Apply` under the session's scene patch file key, as a world load does, and keeps the result in `LastReread`; every object then shows the scene patch file's state, so an edit that starts from the object changes only the field it edits.
- `FreshStart(confirmed, nativeDirty)` is available only while the scene patch file itself blocks the session (`CanStartFresh`); unreadable mod metadata blocks the session without offering it. It needs a storage that also implements `IRecoveryStorage`. `BackupScenePatchFile` copies the scene patch file's bytes, also bytes that are not UTF-8, to a new file and verifies the copy; `MatchesPatchBackup` confirms that the backup and the scene patch file both still hold those bytes. The session then holds an empty current-format scene patch file naming `SceneTargetMapFor(scene.MapIds)`, exposes `LastBackup` and keeps the scene patch file outstanding (`FreshStartPending`) until Save. `BeginSave` replaces the original only while `MatchesPatchBackup` holds; otherwise it refuses and keeps both files. `ModStorage` implements `IRecoveryStorage` beside the scene patch file as `scene-patches.json.backup-<id>` through `IModFiles`, removes a backup it could not verify, and never deletes a verified backup.

## Guard dependencies during editing

Every edit goes through one change route in `PatchEditingSession`. Before it touches the scene patch file or the scene, that route refuses two cases.

- An edit that would take a modification out of the scene patch file, such as Remove, Clear activity of a modification that sets nothing else, clearing the last crossing-coverage entry or an edit back to the underlying value, while another modification of the scene patch file names its key in `dependsOn`. The refusal names those modifications.
- An edit that keeps a modification in the scene patch file while `PatchEngine.IneffectiveReason` reports it does not take effect: a dependency is missing from the scene patch file, fails itself (its own content, a shared addition ID or a target that does not resolve uniquely), or the dependencies form a cycle. These are the rules `Desired` uses to choose which modifications to overlay. Removing such a modification stays possible unless the first rule refuses it; every member of a cycle of two or more is named by another member, so a cycle is broken only in the file, which the session reads when the native map editor opens again.

Undo and Redo of earlier edits are not refused: they return to states the scene patch file already had.

`ReloadReturn` keeps the same-map working-location handoff separate from the mod's lifetime. It stores only a serialized string in the current `AppDomain`, with a request identity, origin controller identity, map, ground point in map coordinates and a five-minute expiry. Mod teardown removes hooks and local state while leaving that bounded handoff for the replacement instance. The native loader invokes `OnModUnload` and replaces entry points in the same process and domain; the handoff does not support process restarts. A different map, expiry, failure or checked completion removes it. No Unity object, callback or product-defined object remains in the runtime store.

`MapEditorReload` waits for a different controller, session readiness and completion of native camera initialization and pending jumps. It requests a strategy-camera jump, then on a later poll measures `CurrentCameraGroundPosition` converted with `WorldToGame`. `ReloadReturn.Complete` accepts arrival only after a matching request and within 0.5 map units horizontally. This internal check identifies the working area, not camera orientation or exact terrain height. An old request cannot complete a newer one. Controlled tests load separate collectible copies of the core assembly to exercise the scalar handoff, map isolation and requested-versus-measured arrival. They do not establish native lifecycle callbacks or visible arrival.

## Build and run the core test

Build the mod project against the local Railroader managed assemblies:

```powershell
dotnet build Src/RailroaderScenePatcher -p:GameManaged="C:/path/to/Railroader/Railroader_Data/Managed"
```

Build and run the core test project with the installed .NET SDK:

```powershell
dotnet run --project Tests/RailroaderScenePatcher.Core.Tests --configuration Release
```

The core test uses an in-memory adapter, a model of the native undo manager's grouping, pruning and change count, and storage with a failure switch per write. It also runs `ModStorage` on a temporary mod folder with file operations that stop a write midway or fail the replacement, for each written file and for the first Save without a scene patch file. It does not load Railroader, exercise a native scene object, or prove native history, title or Save button behavior.

Build outputs and intermediate files go to `RailroaderScenePatcherBuild` under the operating system's temporary directory. Override `BuildArtifactsRoot` with an absolute path when separate builds need independent output directories. The core tests restore Newtonsoft.Json 13.0.2 and need no game assemblies. The native project needs the local game DLLs through `GameManaged`; it does not distribute those files. It restores Lib.Harmony 2.4.2 and copies `0Harmony.dll` to its output.

For an isolated load test, copy only `RailroaderScenePatcher.dll`, `RailroaderScenePatcher.Core.dll`, `0Harmony.dll` and `Info.json` from the native build output into the selected test mod. The game already supplies Newtonsoft.Json. Replacing loaded DLLs requires a process restart. This is local test preparation, not a release package.
