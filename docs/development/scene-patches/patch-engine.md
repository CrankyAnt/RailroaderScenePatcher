# Apply fixed placement through the core engine

The core library exposes `RailroaderScenePatcher.Core.PatchEngine` over an `IScene` adapter. The engine owns scene patch file parsing, map-context matching, dependency ordering, target uniqueness checks, preflight, snapshot, mutation, and failure handling. `SceneCapabilities` assembles the scene of a load from independent capability adapters: `IndependentBoards` for independent boards, over the native `BoardScene` port, `BridgeScene` for the Ela bridge, `TrackMarkerScene` for Generic track markers, `CrossingPadScene` for crossing pads and `StarterPlacementScene` for starter placement markers. It reports the active map definition identifier and its resolved map layers. An isolated native test on Railroader 0.6.2 build 26335745 verified fixed placement, origin conversion, culler and mask updates, settled terrain work and declarative restoration. The core tests use controlled scenes for failure injection; native mutation-failure rollback and live multiplayer behavior remain unproven.

## Implement the scene adapter

`IndependentBoards` in the core library implements `IScene` for the independent-board pattern. It holds the capability's rules and talks to the game only through `IBoardWorld`, which the native `BoardScene` implements with reflection on the game's members. The core tests drive `IndependentBoards` through a controlled `IBoardWorld` that models the culler, mask and terrain lifecycle.

- `MapIds` returns the selected map definition identifier and identifiers for its resolved map layers.
- `Capability` remains `Unchecked`. `BoardScene` checks the required native types, methods, fields and events when it is constructed; missing prerequisites prevent initialization.
- `Resolve` matches the scene name, full hierarchy path and culler component, and accepts no other `structure` than `independent-board-v1`. `Refusal` names why an object does not match the pattern: a missing or disabled culler, other than exactly one enabled circle mask, an inactive parent, a height-flattening mask, or another dependency in the hierarchy (`Track.*`, another culler, mask component or culling handler, a missing script). `Preflight` throws with that reason. The board itself may be inactive through an explicit disable. The inventory uses the same `Refusal` for its problems.
- `Read` returns the complete current state: position in map coordinates, rotation, and activity. `Apply` takes an `ObjectState`; a null placement or activity leaves that part untouched. `BoardScene` converts map coordinates with `Helpers.WorldTransformer` and checks the round trip. For an active board `Apply` requests `RequestUpdateCullingPosition` and calls the circle map mask's `Rebuild` method. Enabling and disabling rely on the `OnEnable` and `OnDisable` of the culler and mask; an inactive board gets no culling or mask call.
- After every application `Apply` verifies the placement, the activity and the registrations: `BoardScene.Registration` reads the culler's culling-sphere centre and the board's mask keys in the terrain system's modifier storage. An active board must have its sphere and every mask descriptor at its position, with no key missing from storage; a disabled board must hold neither. A mismatch throws, so the engine or session restores the captured state.
- `Capture` and `Restore` handle position, rotation, parent, and active state. `Restore` reapplies the snapshot with the same verification.

### Dependent output

`IDependentOutputScene` describes native writes that follow a mutation asynchronously. `Output(target)` returns a `DependentOutput` with the completed and outstanding writes and an error when they stopped; `RetryOutput(target)` requests the outstanding writes again. `IndependentBoards` implements it for generated terrain output:

- Each mask change records the board's old and new positions. A position whose tile `IBoardWorld.TileLoaded` reports unbuilt is complete at once, because the game builds that tile later from the current masks.
- `Poll`, called every frame by the entry point, completes a position after an `OnTileBuilt` notification covering it, once terrain work is idle with no pending invalidations. A position whose tile unloads completes for the same reason. A position still outstanding 30 seconds after the last mask change sets the error. `Failures` lists the boards whose output stopped.
- `RetryOutput` invalidates the tiles of the outstanding positions through the game's public `MapManager.Invalidate(Vector2Int)` and restarts the timer.

The engine uses the output to guard retries. After a mutation fails and `Restore` verifies, the target stays guarded while its restored output is outstanding, and the guard lifts once that output completes. Output that stops turns the guard into unverified cleanup. `PatchEditingSession` exposes `Output` and `RetryOutput` for the Scene patches window, applies the same guard to a failed edit, and `Recheck` requests stopped output again. Generated terrain output is not a Save participant: Save does not write the output generated from board masks, and the game regenerates it from the saved placement on load. Native edited terrain tiles are a separate native Save concern; the board capability does not change them.

### Patcher version per target

`IVersionedScene.MinimumPatcherVersion(target)` returns the patcher version required by a target, or null. `PatchEditingSession.MinimumPatcherVersion` takes the highest of the scene patch file's format requirements and these values. Fixed placement requires `0.1.0`, and generic `active` requires `0.2.0`; target-specific capabilities can raise that base minimum. `IndependentBoards` returns `0.5.0` for pattern boards other than the legacy Sylva location sign. The Sylva target still uses the pattern checks, but does not raise the pattern-based board dependency minimum. Bridge, track-marker relationship and target/group activity, crossing coverage and track-following capability gates remain `0.5.0`. Runtime reporting adds no scene patch file, schema or capability requirement.

## Implement a relationship capability

`ObjectState.Marker` carries the track-marker relationship: `MarkerBinding.At(TrackLocation)` sets or replaces it, `MarkerBinding.Detached` clears it, and null leaves it untouched. `PatchEngine.Parse` reads it from `relationships.trackMarker`. `Desired` overlays it like placement and activity, so removal recomputes the underlying relationship plus the remaining contributions, and `PatchEditingSession` verifies it with the placement after every change, restoration and `Recheck`.

An adapter that supports relationships implements `IRelationshipScene.CheckRelationships(target, state)`. The engine and `SceneCapabilities` call it for every state of an implementing adapter, not only for states with a relationship, so an adapter can also refuse a setting its relationships make unsupported. The engine calls it after `Preflight` and before capture; `PatchEditingSession` calls it for the modification before its mutation guard, so the underlying relationship may be the broken one being repaired. A scene without `IRelationshipScene` refuses any relationship, and `SceneCapabilities` refuses a relationship on an object whose adapter lacks it.

`TrackMarkerScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ITrackMarkerWorld`, which `TrackMarkerWorld` implements with reflection on `Track.TrackMarker` and `Track.Graph`:

- `PatternProblem` refuses everything except one Generic marker without milepost, crossing pad, crossing parent, location-change listener, `TrackRelativePosition` with group-driven activity that targets another object or whose `_setTargetActive` another component replaced, new-game car placement (`SetupDescriptor.placements[].marker`) or direct reference from any loaded component other than the colocated `TrackRelativePosition._marker`. `TrackMarkerWorld.Problem` is the same check for the inventory, which passes the reference scan and the setup index of its discovery; the adapter scans at most once per frame and builds a setup index per check. `NativeInventory.Discover` walks the fields once, one owner at a time through `ReferenceScan.Begin` so that the stepped discovery can pause between owners: the walk, like `ReferenceScan.Of` with an observer, reads every field of every owner once and hands each value or failure to the dependency strings, while the marker scan applies its own relevance and errors to the same reads. The setup index is a core `HolderIndex`: it walks the setup placements in their original order once, at the first marker that reaches the setup check, holds every marker found before the walk's first read failure and passes that failure to any other marker. Field descriptors and their relevance are cached per type; values are read afresh in every scan, and no scan result, value or error outlives its discovery. The scan is a core `ReferenceScan` over `ReferenceField` values: `ReferenceScan.CanHold` counts a field whose declared type can hold a component, directly or as the element of a non-generic `IList`, an array or a generic `IList<T>`, and the scan enumerates values of those list kinds. A relevant field that cannot be read, a list that cannot be enumerated or an owner whose fields cannot be listed makes the scan incomplete. `Refusal` then refuses every marker, because an unread field may hold any of them.
- `RefreshDependents` and `DependentProblem` hold the consumer state that caches the location. `MapBuilder.Add(MapLabel)` caches the track group from `TrackGroupIdFor(label)`, so the adapter removes and adds every registered label in the hierarchy and compares `_mapLabels` with `TrackGroupIdFor` afterwards. The group subscription has its own members, below.
- `Location` reads the serialized `_location`; `SetLocation` uses the native `Location` setter, which clears the cached pose and does not change the registration.
- `Registrations` reads every entry under the marker ID from `Graph._namedLocationsBySegmentId`; `Unregister` and `Register` call `RemoveNamedLocation` and `AddNamedLocation` as the marker's `OnDisable` and `OnEnable` do.
- `Resolve` starts from the loaded marker components and builds the hierarchy path only for their objects; an object with several markers counts once, so a missing, ambiguous or duplicate identity resolves as before.
- `SegmentLengths` resolves a segment through `Graph.GetSegment`. The graph keys segments by ID, so the native world returns zero or one length.

Sources for the consumers: `Game.Scripting.Modules.Railroader.NativeTrack.GetMarkerLocation` (graph lookup, then the stored location), `UI.Map.MapBuilder.Add` and `TrackGroupIdFor`, `Game.State.CompanyModeSetup.Setup` reading `SetupDescriptor.CarPlacement.marker`, `Game.FlareManager.NearbyFlares` and `Model.AI.AutoEngineerPlanner`, which filter registrations by their own marker types through `Track.NamedLocationExtensions` and `TrackMarkerType`, and `TrackRelativePosition.ConfigureAndApply`, called only from `MapObjectSpawner`, `ObjectsEditor` and `TrackAnchorReposer` for map objects.

- `GroupActivity` reads a `TrackRelativePosition` with group-driven activity: whether the hold is installed, `_observing`, `_observedGroupId`, its `OnGraphGroupEnabledDidChange` handlers on `Graph.GroupEnabledDidChange`, whether the marker location resolves, the segment's `groupId` and whether `Graph.enabledGroupIds` contains it. It returns null for any other object. `ObserveGroup` calls the relative position's private `UnsubscribeFromGroupEvents` and `ObserveTrackGroup`, which subscribe once for the current location's group and set the object's activity from the group. `HoldDisabled` installs or removes the explicit-disable hold: a delegate in `_setTargetActive`, which the native `SetTargetActive` calls instead of `SetActive`, and which keeps the object inactive. `TrackMarkerWorld` keeps the delegate per relative position so it can recognise and release its own hold; the pattern refuses a callback it did not install.

`Preflight` requires the registration rule: one owned registration at the stored location for an enabled, active marker with a resolvable location, none otherwise. `Apply` rewrites the registration and refreshes the dependents when the relationship changes or either disagrees, then applies activity and placement, and verifies location, placement, activity, the registration rule and `DependentProblem`. `Restore` writes the captured location, placement and activity the same way and returns true only when they verify. For a group follower, `Read` reports activity as null (group-driven) unless the hold is installed, so `Desired` keeps group-driven activity when no mod sets `active`, and removal returns to it. A null `Active` therefore has two meanings for a follower, and `ObjectState.LeavesActivity` tells them apart. A complete desired state, as `Desired`, `Restore` and the scene patch editing session's commit, clearing and removal pass it, has the flag unset, and a null `Active` releases the hold. One modification's own state has the flag set through `LeavingActivity()`, and a null `Active` keeps an installed hold; the runtime's `Execute` and `PlacementGesture.Preview` apply such a state. `CheckRelationships` refuses `active: true` on a follower; the engine and `SceneCapabilities` call it for every state of an adapter that implements `IRelationshipScene`, not only for states with a relationship. `Apply` installs the hold and deactivates the object before the relationship step when `active` is false, runs `ObserveGroup` after a rebinding, a release of the hold or a subscription that disagrees with the location, and verifies the subscription and activity with `GroupProblem` beside the registration rule. `Capture` records whether the hold was installed; `Restore` reinstalls or releases it with the captured location. The adapter's capability minimum is `0.5.0` for `track-marker-v1`. `PatchEditingSession.Bind(target, binding, inspected)` sets, replaces or detaches this mod's relationship; a null binding clears it and removes a modification left without content.

## Implement the starter placement capability

`ObjectState.Starter` carries a starter placement: a `StarterSetting` with the `Setup` whose new-game car placement reads the marker and the `Track` location as a `MarkerBinding`, where null leaves the location untouched. `PatchEngine.Parse` reads it from the `starterPlacement` member and reads a `{ "detach": true }` track as `MarkerBinding.Detached`, so the capability refuses it with its reason. `PatchEngine.Overlay` lays it over the underlying state like the other members, so removal recomputes the underlying location plus the remaining contributions. `StarterSetting.Same` compares the track location only; the setup identifies the car placement. Every other capability, and a scene without relationships, refuses a starter placement with `StarterPlacements.NotAStarter`.

`StarterPlacementScene` implements `IScene`, `IRelationshipScene`, `IVersionedScene` and `ITargetConfirmation` over `IStarterPlacementWorld`, which extends `ITrackMarkerWorld` and `IStarterTrack`. It reuses `MarkerRelationship` for the location, the registration rule, capture and restoration, and resolves only identities whose `structure` is `starter-placement-v1`. `Read` returns the object's placement and activity, which it never writes, and a `StarterSetting` with the reader's setup and the current location. `Apply` writes only the location. `CheckRelationships` refuses placement, activity, `trackMarker` and coverage, then asks `StarterSetups.Reader` for the one car placement of an active setup that reads the marker and refuses none, several, unreadable setups and another `setup`. For a track location it refuses a detach, a missing or ambiguous segment and a distance outside the segment, then runs the whole-cut check. The capability minimum is `0.5.0`.

`StarterCutRule` is the game's placement rule from `TrainController.CanPlaceAt` over `IStarterTrack`: `Checked` gives the front, a location every 1.5 m back while the walked distance stays below the cut's length, and the back end, as the game walks them; `Move` throws `StarterTrackException` with the game's reason at the end of the track or a switch lined against the movement, and `Unplaceable` gives the reason for a location that is not on available track. `Body` gives the positions of a placed cut every half metre. `Problem` checks the setup's cuts in placement order, each against the bodies of the cuts before it that passed, with the game's check radius of 0.75 m beside a body half a car wide; it returns the failure of the marker's own cut, or of a later cut that runs into it, and ignores a failure that this cut does not cause. `StarterPlacementScene` implements `IPlannedStateScene`: before a scene patch file's modifications are checked, `PatchEngine.Plan` resolves every modification with `starterPlacement` and passes the desired states, and the whole-cut check judges those markers' cuts at their desired locations instead of their current ones; `ApplyScenePatchFile` and the session's `Commit` call it and clear it again afterwards, and `SceneCapabilities` hands each adapter the states of the objects it resolved. A cut that the rule passed but whose body cannot be followed fails with that reason, and `StarterPlacementWorld` turns every native failure of the walk into a `StarterTrackException` with the reason. `StarterPlacementScene.CutPath` returns the body of the marker's cut at a location, which `PatchEditingSession.StarterCut` exposes for the world marking.

`StarterPlacementWorld` implements `IStarterPlacementWorld` by deriving from `TrackMarkerWorld`. `Belongs` claims a marker that `StarterSetups.Use` reports as used, which `TrackMarkerWorld.Consumers` refuses for the Generic-marker capability; `PatternProblem` checks the marker shape, its ID, location listeners, group-driven activity and direct holders other than the colocated `TrackRelativePosition`. `Setups` reads `TrackMarkerWorld.StarterSetups` once per frame and turns a read failure into `StarterSetups.Unreadable`. `CutLength` invokes `StateManager.DescriptorsForIdentifiers`, which adds each steam locomotive's tender, and `ConsistLength.OfDescriptors`, which adds the drawbar gaps. `Move` invokes `Graph.LocationByMoving` with the switch check and maps `EndOfTrack` and `SwitchAgainstMovement` to the game's reasons. `Unplaceable` reads `TrackSegment.Available` without the sandbox exception, because a new company game is no sandbox. `Position` reads `Graph.GetPosition`.

`PatchEditingSession.PlaceStarter(target, location, inspected)` writes `starterPlacement` with the reader's setup and the location, keeping other members of an existing modification; a new modification's key starts with `starter-`. `ClearStarterTrack` removes the track and the member with it when only `setup` remains. `Normalised` removes a track equal to the underlying one, so placing the marker back on the map's location reverts the setting. `HasStarterTrack` reads the scene patch file alone. `MinimumPatcherVersion` returns at least `0.5.0` for a modification with `starterPlacement` or a `starter-placement-v1` target.

Timing: `GlobalGameManager` calls `ExecuteMainScriptsOnWorldLoad`, which invokes every mod's `OnWorldLoad` and so the patcher's application, before `StateManager.SessionDidBecomeActive`, which runs `CompanyModeSetup.Setup` for a pending new company game. `CompanyModeSetup.Setup` reads `placement.marker.Location.Value` for each placement in order and calls `TrainController.PlaceTrain`; `HandlePlaceTrain` throws when `CanPlaceAt` fails, and the setup's catch around all placements stops the remaining placements, the initial track conditions and the initial industry storage. The source is Railroader 0.6.2 build 26335745; whether a patched location reaches a new company game is a Railroader journey's evidence, not this reading's.

## Evaluate track-following placement

`Placement.Following` holds a `TrackFollowing`: a `TrackAnchor` (a `TrackLocation` on a segment, or an endpoint node ID), an offset in the track's frame and a rotation applied after the track's rotation. `PatchEngine.Parse` reads it from `placement.mode = "trackFollowing"` with a null position and rotation. `PatchEngine.Evaluate` asks the scene, which must implement `ITrackPoseScene`, for the anchor's current `TrackPose` in map coordinates and replaces the placement with its absolute evaluation, keeping `Following` set. `Execute` evaluates after `Preflight` and before the relationship check and capture, so an anchor that does not resolve fails the modification without mutation; `Desired` evaluates the effective state. Adapters receive an ordinary absolute placement and need no change. `TrackFollowing.Relative` computes the offset and rotation that keep a given absolute placement at the anchor's current pose.

`SceneCapabilities.Tracks` supplies the poses for every capability; `EntryPoint` sets it to `NativeTrackPoses`, which reads `Graph.GetPositionRotation` for a segment location (forward axis away from the measured end) and `TrackNode.Position` and `Rotation` for an endpoint, and refuses a missing segment or node and a distance beyond the segment's length.

`PatchEditingSession.Follow(target, anchor, inspected)` stores the current placement relative to the anchor, `StopFollowing` stores the current placement as fixed placement, and `Edit` with a placement keeps a following object's anchor and stores the new relative values. `ReconcileTrackFollowing` re-evaluates every following modification of the active scene patch file and applies the ones whose object differs from its evaluation, without changing the scene patch file or the history. It reports each moved or failed object by modification ID, restores the prior state on failure, and marks the object unsafe when that restoration does not verify; an unsafe object is skipped until `Recheck`. `EntryPoint` calls it four times a second while the native map editor is attached, no gizmo is active and `HasTrackFollowing` is true. Each pass first tries a check that does no scene-wide work: it holds the target each following modification last resolved to while that modification object stays in the scene patch file, and skips the modification when `ITargetConfirmation.StillIdentifies` confirms the held object, no other modification names the same target, and the object's state and `IDerivedStateScene.DerivedProblem` already agree with the modification evaluated from `PatchEngine.Underlying` at the anchor's current pose. That check mutates nothing, so it needs no preflight. When the check finds a difference in placement or derived state only, a held update follows: the scene confirms the held object, `IPlacementPreflight.PreflightPlacement` checks the object's own pattern and registration through `IPlacementPattern.PlacementProblem`, without the setup-placement index and the direct-reference scan, and the relationship, activity and coverage must already agree. It applies through `IFollowUpdateScene.ApplyFollowUpdate`, which skips `ITrackMarkerDiagnostics.AfterVerifiedState` and its search of every marker unless the binding or activity changed; explicit edits, history steps and removal always reconcile the warning. Any other difference, a missing confirmation or an exception takes the full path, which resolves, preflights, applies and verifies as before. `TrackMarkerWorld.StillIdentifies` reads the held object only: it is loaded in the identity's scene, at its path, with its marker and capability; uniqueness is checked again by the next resolution. `PatchEditingSession.MinimumPatcherVersion` returns `0.5.0` for a `trackFollowing` placement and for an `active` value on a `track-marker-v1` target, from the scene patch file alone. `ClearActivity` removes the mod value of `active`.

Both marker capabilities share the internal `MarkerRelationship`, which holds the location, registration, placement, activity and group-activity rules above. The crossing-pad capability refuses pads with group-driven activity in `PadProblem`, so its objects never take the group-activity path. `CrossingPadWorld` inherits `TrackMarkerWorld.AfterVerifiedState`, so a verified pad state reconciles the native not-on-the-track warning of its marker like a Generic marker, and `EntryPoint.ReconcileMarkerWarning` retracts an exactly attributed warning after a verified pad repair. The early repair before `TrackMarker.OnEnable` resolves only `track-marker-v1` targets, so pads are repaired when their scene patch files apply. A capability whose objects derive state from the marker location passes an `IMarkerConsumer`: `Capture` with the snapshot, `Refresh` after every write, `Problem` in the verification after `Apply` and `Restore`, and `Restored` to compare the restored state with the captured one.

## Implement the crossing-pad capability

`CrossingPadScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingPadWorld`, which extends `ITrackMarkerWorld` with `Geometry` and `Generate`. `CrossingPadWorld` implements it by deriving from `TrackMarkerWorld`:

- `Resolve` returns only marker objects with a `Track.TrackCurveMeshBuilder`; `TrackMarkerWorld.Resolve` returns only those without one, so the two capabilities never claim the same object. `PadProblem` is the pattern check shared with the inventory; it uses `TrackMarkerWorld.Consumers` for the ID, listener, group-driven activity, setup-placement and reference rules, and also allows the builder's `_marker` reference.
- `Generate` calls `CurveMeshBuilderBase.Generate()`, which reads the marker's graph curves, replaces the mesh container's children, offsets the mesh by the pad's map position and moves the culling token to the new bounds. The new renderer starts enabled, so the adapter adds the token to `CullingManager._needsUpdate`; the manager's next `Update` calls `CullingSphereStateChanged`, which sets the renderer visibility. The adapter records the location, map position and signature it generated from in a weak table.
- `Geometry` returns the signature of the current `_renderers` (vertex count, FNV-1a hash of the local vertex positions, local bounds and mesh map position), the recorded source while the signature still matches, and whether the culling sphere equals the pad position plus `_boundsCenterLocal` with `_boundsRadius`. A pad without a live token, such as a disabled pad, has nothing to align.

For a track-following pad, `MarkerRelationship.Apply` passes `following` to the consumer, which also regenerates when `PadGeometry.Curves`, the `ICrossingPadWorld.SourceCurves` fingerprint recorded at generation, is unknown or differs from the current one. `CrossingPadWorld.SourceCurves` invokes `TrackCurveMeshBuilder.GetCurves()` for a resolvable location and joins every curve's `P0` to `P3`, `_up0` and `_up3`, rounded to millimetres. `MarkerRelationship.Apply` also passes `explicitApply`, so an applied edit, history step or removal regenerates any pad whose recorded `Curves` differ from the current ones; reconciliation (`DerivedProblem`) and `Restore` do not. An unknown token, on either side, never confirms the recorded curves. `Track.TrackSegment` and `Track.TrackNode` are plain graph objects, not Unity objects, so the token checks them against null. The consumer builds those curves only when `ICrossingPadWorld.CurveToken` differs from the token recorded with them. `CrossingPadWorld.CurveToken` reads the cached `TrackSegment.Curve` of every segment within half the pad width plus one metre of the marker location and the segment IDs `Graph.SegmentsConnectedTo` returns at each node it reaches, which decide the builder's next segment; it builds no curve. When built curves match the recorded ones under a changed token, the adapter records the new token. `Geometry` reuses the signature of a builder's renderer array until generation assigns a new array. `CrossingPadScene.DerivedProblem` reports a curve-only change once the changed curves have held still between two reconciliation checks, so a native drag regenerates the pad once, on its final curve; an applied edit regenerates at once. `CrossingPadScene` and `SceneCapabilities` implement `IDerivedStateScene.DerivedProblem`, and `PatchEditingSession.ReconcileTrackFollowing` applies the desired state when the placement differs or `DerivedProblem` reports a difference. The core consumer regenerates when the pad holds no geometry for a resolvable location, geometry for an unresolvable one, geometry of unknown or other source, geometry generated at another position, or a misaligned culling sphere. A restoration requires the regenerated signature to equal the captured one when the pad held geometry at capture. `CheckRelationships` refuses a detach: with no marker location, `TrackCurveMeshBuilder.GetCurves` logs "Track marker is not set or invalid" and returns no curves, so `Generate` leaves no renderer and `CullingSphereStateChanged` calls `Generate` again, with the same error, whenever the sphere becomes visible or near. `MinimumPatcherVersion` returns `0.5.0` for `crossing-pad-v1`, and `PatchEditingSession.MinimumPatcherVersion` returns at least `0.5.0` for a modification naming that structure. The inventory describes a pad's generated `DontSave` mesh objects with one dependency line instead of per component, because culling toggles their renderers and generation replaces them; otherwise an inspected pad would become stale with every camera move. `HierarchyDependencies.Describe` holds that rule without Unity, and the core tests run it through `SceneInventory.CheckFreshness`. Pads inside a `Track.Crossings.GradeCrossingController` qualify: the controller reads its circuit sets and its `KeyValueObject`, not the pad marker, and the reference scan still refuses any direct holder other than the colocated `TrackRelativePosition` and pad builder.

Sources: `Track.TrackCurveMeshBuilder.GetCurves`, `BezierCurveMesh.CurveMeshBuilderBase.Generate`, `OnEnable`, `CullingSphereStateChanged` and `RequestUpdateCullingPosition`, `Helpers.TransformExtensions.DestroyAllChildren`, which destroys the old children at the end of the frame, and `Helpers.Culling.CullingManager.Update`.

## Implement the crossing-coverage capability

`CrossingCoverageScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingCoverageWorld`, which `CrossingCoverageWorld` implements with Unity. Coverage is the core `CrossingCoverage`: an ordered list of circuits keyed by native island span ID, each a `CircuitCoverage` that is `Native` (span IDs), `Tracks` (three `SpanRange` values) or `Detached`. `ObjectState.Coverage` carries it; This mod's coverage lists only explicit circuits, observed coverage lists every circuit plus any `Residue`, owned spans left registered by an incomplete cleanup. `PatchEngine.Desired` overlays this mod's circuits on the underlying coverage per circuit, so omission keeps a circuit's effective coverage.

- The adapter keeps a baseline per controller: the circuit set objects, their native spans and keys at first observation, and every span it owns. `Read` classifies each baseline circuit as detached (not in the controller's list), native (its native references) or tracks (owned references, read back through `Range`), and throws for anything else.
- `CheckRelationships` refuses placement, activity and `trackMarker`, unknown circuits, `Native` entries, unresolved or zero-length ranges, and an effective coverage with every circuit detached. Because the engine passes it every mod value, these refusals happen before mutation. `TrackMarkerScene` refuses coverage, and a scene or adapter without relationships refuses coverage like any other relationship.
- `Write` converges from any state the adapter can leave: it reuses a registered owned span with the exact range, creates missing ones and checks that they registered and cover track before any circuit refers to them, sets each circuit's references, sets the controller's list to the non-detached circuits in native order and retires unused owned spans. A span that stays registered after `DestroySpan` stays owned, so `Verify` reports it and `Restore` returns false. `Preflight` ignores such residue; `Read` exposes it, so `PatchEditingSession.Recheck` sees a difference and applies the scene patch file, which retires it.
- `PatchEditingSession.Cover(target, circuit, coverage, inspected)` sets, replaces or detaches one circuit's entry in the keyed `circuits` object, and a null coverage clears it. The session removes `circuits` or `additions` with its last entry and `crossingCoverage` with both, never writes one of them empty, and removes a modification left without content. `PreviewCoverage` runs the same checks and returns one line per circuit from `CrossingCoverage.Describe` without mutating, recording history or changing the scene patch file. `Coverage(target)` reads the current coverage for the panel.
- `CrossingCoverageWorld` creates an owned span as the native span loader does: a disabled `GameObject` with `HideFlags.DontSave` under one root per map scene, then `TrackSpan.id`, `_lower` and `_upper`, `InvalidateCache`, and activation, whose `OnEnable` calls `Graph.AddSpan`. `DestroySpan` refuses to disable a span whose ID now belongs to another span, because `Graph.RemoveSpan` removes by ID. `SetCircuits` clears and refills the controller's own list, which its loop indexes on every pass.

### Detection additions

A detection addition is a `CircuitCoverage` of kind `Added` in the same `CrossingCoverage`, named by a `DetectionAddition.Key(owner, id)` instead of an island span ID. `PatchEngine.Parse(item, owner)` reads it from the keyed `additions` object of `crossingCoverage`, where its key is its ID, and gives it the owner, which is the scene patch file key of `PatchEngine.Apply`. `PatchEditingSession` takes the same key as `scenePatchFileKey` and passes it to `Parse` and `Desired`, so the session and the world-load application name an addition alike. `EntryPoint` applies each scene patch file under its mod identifier and `MapEditorAttachment` passes `ModScenePatchFiles.EditedModId()`.

- An observed coverage is complete: `Read` lists every native circuit and every added circuit the controller evaluates. `CrossingCoverageScene.Apply` converges on a complete coverage as it stands and lays any other coverage over the observed one. A modification therefore keeps the additions it does not list, which may belong to another modification or mod, while the session's `Desired`, a restoration and a `Recheck` remove every addition their complete coverage lacks. `Overlay` keeps the completeness of its base, so `Desired`, which starts from the underlying state, stays complete.
- `PatchEngine.SharedAdditionIds` finds the IDs that more than one modification of a scene patch file uses. `Execute` fails each of those modifications before its dependencies run, and `Desired` leaves them out, so the result does not depend on the order of the modifications. `PatchEditingSession.AddDetection` refuses an ID another modification already uses.
- `Write` gives each listed addition one `Circuit` in the baseline's `Added` list. It builds missing spans under `CrankyAnt.ScenePatcher.added.<owner>.<id>.<role>`, checks that they registered and cover track, and creates the circuit set through `ICrossingCoverageWorld.CreateCircuit` before it changes any existing reference. It then sets the spans, sets the controller's list to the native circuits that are not detached followed by the added circuits in ordinal key order, drops the circuits of deleted additions and retires unused spans. A failure after the new set exists leaves it in the baseline, so `Restore` writes the captured coverage and removes it with its spans.
- `BaselineOf` asks `ICrossingCoverageWorld.AdditionKey` for each circuit set it finds. `CrossingCoverageWorld` keeps the key of every set it created in a static `ConditionalWeakTable`, keyed by the set object. A set with a key enters the baseline as an added circuit with owned spans, so a new adapter over a retained world reuses it. A native circuit whose spans an earlier adapter replaced holds spans under the `CrankyAnt.ScenePatcher.` prefix; `BaselineOf` refuses such a circuit with "Reload before editing it" instead of recording the patched spans as native.
- `PatchEditingSession.AddDetection(target, id, tracks, inspected)` adds or replaces one addition, `DeleteDetection` removes its entry, and `PreviewAddition` describes either without mutating. Before a mutation and in every preview the session passes the complete desired coverage to `CheckRelationships`, which refuses a result without detection. Deleting the last detecting addition is thereby refused before anything changes.

Sources: `Track.Crossings.GradeCrossingController.LoopCoroutine` and `UpdateCircuit` re-read `circuitSets` and the three span references every pass and cache nothing from the spans; `Track.TrackSpan.OnEnable` and `OnDisable` register and remove by ID; `Game.MapEditor.MapEditor.Save` serializes graph nodes, segments, turntables and groups, and industry spans only from ops DTOs, so neither runtime spans nor controller references reach map data. `GradeCrossingController.CircuitSet` is a class with a parameterless constructor and the three span fields; the controller's other fields hold no state per circuit set. The inspected build is Railroader 0.6.2 build 26335745.

## Implement crossing equipment

Crossing equipment is a second relationship of `CrossingCoverageScene`, which takes an optional `ICrossingEquipmentWorld`; without one, `crossingEquipment` is refused. `CrossingEquipmentWorld` implements it with Unity. The core types are in `CrossingEquipment.cs`: an `EquipmentAddition` holds a persistent `Id`, a `Pattern`, an `EquipmentSource` (scene and path), a fixed `Placement` and its `Scope`, the supplying mod's identifier. `CrossingEquipment` is a set of additions keyed by scope and ID, either a mod's set (only explicit additions) or `Complete` (every addition the controller should own). `ObjectState.Equipment` carries it.

- Scope: equipment uses the same owner as detection additions. `PatchEngine.Parse(item, owner)` scopes a scene patch file's equipment with its `scenePatchFileKey`, the supplying mod's identifier, and `PatchEngine.Desired(modifications, target, owner)` starts from the equipment that stands now, less that owner's additions, so other mods' additions are kept, before overlaying the scene patch file, because a mod's additions exist only through its scene patch file. The native map editor passes the same key to `PatchEditingSession` from `ModScenePatchFiles.EditedModId()`. `Release` and `Dispose` retire the equipment of a crossing with its owned spans when a retained world drops the crossing or the state ends. `PatchEngine.AdditionIds` lists equipment IDs as `equipment <id>` beside detection addition IDs, so an equipment ID may appear in one modification of a scene patch file.
- `Apply` converges on a complete set exactly and overlays a mod's set on the observed additions, so runtime application never removes another mod's additions. `CrossingEquipmentPart.Write` keeps a matching addition and moves it, rebuilds one whose source or pattern changed, retires one absent from the set and constructs a missing one after rechecking its source. `Capture` returns coverage and complete equipment; `Restore` converges on both and reports false when an addition cannot be released or rebuilt. `Apply` and `Restore` skip the equipment part when its effective set equals the observed one, so an operation that leaves the additions alone never touches them.
- `CheckRelationships` resolves every source and checks its pattern before any mutation, so a missing, ambiguous, unavailable or nonconforming source refuses the whole modification. When a modification changes the effective equipment, `CheckRelationships` also refuses it while a present addition fails `Problem`; `Preflight` does not check additions, so a faulty addition blocks only equipment operations and coverage operations of the same crossing stay independent. The adapter adopts `Owned` additions at its first observation of a controller.
- `PatchEditingSession.AddEquipment`, `RemoveEquipment`, `PreviewEquipment`, `Equipment`, `EquipmentEntries`, `EquipmentSources` and `EquipmentStatus` serve the panel; `EquipmentEntries` lists this mod's additions from the scene patch file with their built state or why they were not built, so a failed addition can be edited or removed. Equipment placements compare with the native map editor's tolerance, and `PreservingJson.KeepStoredPrecision` keeps an entry's untouched axes; sources and status come through `ICrossingEquipmentScene`, which `SceneCapabilities` forwards to the resolving adapter.
- The eligibility rules are core: `LightGatePattern.Problem(DeviceFacts, keys)`. `CrossingEquipmentWorld.Facts` only reads the device into `DeviceFacts` and `LampFacts`/`GateFacts`, so the core tests exercise the production rules. The source must lie in the destination controller's scene, which keeps the shared model, material and clip assets loaded for the copy's lifetime.
- Each addition is one added object: `NativeInventory` observes the `OwnedEquipment` wrapper in the family `Added light or gate`, and the layout marks it `+` and `+ ADDED`. The wrapper stands at the addition's placement and the copy at its origin. `NativeInventory` implements `IOwnedObjectScene` for the copy's parts below the wrapper: `SceneInventory` takes no observation of them from a refresh, a check, a stepped pass or `ReobserveRelated`, so applying a copy adds exactly its one entry and the expected count stays consistent. `NativeInventory` also passes `DiscoveryWalk.Steps` an `owned` predicate for those components and skips them in `ObserveRelated`, and the controller's observation counts their DontSave wrapper as runtime state. The patcher's own copies are therefore never observed or read as referrers, and their culling, initialization and history steps do not make the inventory stale.
- `CrossingEquipmentWorld` reads the published keys from the controller's `KeyLights` and `KeyGates` constants. `Construct` builds a disabled wrapper with an `OwnedEquipment` component, instantiates the source beneath it, checks the copy, joins the controller's `GameObjectCuller.gameObjects` with the state in `_cullingState` and enables the wrapper last. `Destroy` leaves the culler first. `Status` reads the lamps' and gates' private `_observer` fields for the panel only. `Candidates` also lists each controller's generated bell player, which the pattern rejects with its reason, and gives each candidate its device name, its crossing and the crossing's placement. `SourceCandidate.Label` reads "Signal 1 at Allen", with the place from `CrossingEquipment.Place`: the part after "Grade Crossing - " of the crossing's name, or else its nearest enclosing place without a leading "Roads ", such as "Andrews" for a setup crossing; `CrossingEquipment.Describe` lists what changes before what is kept; `EquipmentPlacement.Propose` carries the device's placement relative to its crossing over to the inspected crossing, five metres aside; `PatchEditingSession.NewEquipmentId` adds a numeric suffix to an ID the scene patch file already uses.

Sources: `Track.KeyValueLampMaterialController.OnEnableWithProperties` and `RollingStock.Controls.KeyValueBoolAnimator.OnEnableWithProperties` take `GetComponentInParent<KeyValueObject>()`, read their key's Boolean value and observe it; the lamp's `DiscoverRenderers` matches renderers under `targetObjects` by shared material; `Game.GameBehaviour.OnEnable` defers that initialization through `Game.State.RestoreNotifier`; `Helpers.Culling.GameObjectCuller.CullingSphereStateChanged` calls `SetActive` on each listed object when `_cullingState` changes between `Visible` and `NotVisible`. ## Combine capabilities

`SceneCapabilities` implements `IScene` and `IInspectionScene` over a list of capability adapters. `Resolve` asks every adapter and remembers which adapter resolved each object; an object claimed by two adapters appears twice and fails as ambiguous. Every other call goes to the adapter that resolved the object. `AddUnavailable(structure, reason)` records a capability whose game functions are missing: a target naming that `structure` resolves to a placeholder whose preflight fails with "incompatible with this game build" and the reason, while unrelated modifications still apply. `InspectedTarget.Validate` checks for that placeholder first, so an edit of an object whose capability is unavailable is refused with the incompatibility and its reason instead of a changed inspected context; the inspected-context guard itself is unchanged. `Capability` is `Incompatible` only when no adapter is available. `EntryPoint` constructs each native adapter separately, so a failed bridge check leaves board placement available and the reverse. `SceneCapabilities` also implements `IDependentOutputScene` and `IVersionedScene`: `Output` and `RetryOutput` go to the adapter that resolved the object, and an adapter without dependent output reports none; `MinimumPatcherVersion` takes the highest value any adapter returns. The board inventory's problems come from the board adapter's `Refusal`, the same check its `Preflight` runs.

## Implement a bridge capability

`BridgeScene` is the core part of the bridge capability. It implements `IScene` over `IBridgeWorld`, which `BridgeWorld` implements with Unity:

- `IBridgeWorld.Resolve` matches the supported path, scene name and root culler. `BridgeWorld.SupportedPaths` holds the one retained bridge.
- `CheckPattern` refuses inactive parents, a disabled root culler, missing scripts, rigidbodies, track-owned components (`Track.*`, `AutoTrestle.*`, `Game.Mow.TrackConstructionScenery`) in the hierarchy, a hierarchy without colliders, and a construction-scenery entry that targets the root or one of its parents.
- `Observe` returns a `BridgeObservation`: the root state in map coordinates, one `ColliderState` per collider (identity, shape properties, enabled flag, activity below the root, placement relative to the root, and for box, sphere and capsule colliders whether the physics bounds are centred on the transformed shape after `Physics.SyncTransforms`), and a text description of the separate scenery. That description covers the loaded `AutoTrestle.AutoTrestle` components within 250 m of the bridge's first observed position (local transform, activity, control points, generated flag, beam-matrix digest) and the construction-scenery controllers that reference the bridge.
- `SetPlacement` converts map coordinates, sets the root placement, calls `RequestUpdateCullingPosition` on every active culler in the hierarchy and synchronises physics. `SetActive` switches the root only.

`BridgeScene` records the first observation of each bridge in the load as its reference. `Preflight` refuses a bridge whose collider layout differs from that reference. `Apply` enables before the placement change and disables after it, as the board does, then verifies root placement and activity, the collider layout against the reference, collider activity against the root, and separate scenery against the observation before the change. `Restore` reapplies the captured root state and returns true only when all of those match the capture. The adapter's capability minimum is `0.5.0` for a `bridge-colliders-v1` target, also when the bridge adapter is unavailable.

The native map editor's **Scene patches** window reads `NativeInventory` through `IInspectionScene`. It exposes searchable observations, dependencies and detected problems for typed markers, spans, mileposts, crossings and independent boards, plus the known Ela bridge roots, which carry the `bridge-colliders-v1` structure and any `CheckPattern` problem. `IndependentBoards` implements `IInspectionScene` by delegating to the native inventory. Refresh does not apply patches. Scene patch editing inspects only the edited mod's scene patch file. These additional inspection patterns do not enable mutations. See [inventory integration](scene-inventory.md) for the observation and revalidation interfaces. The same window edits the placement and activity of an inspected object that has a mutation adapter, as described under Edit through a session.

Do not infer in-game rendering or culling correctness from the adapter's prerequisite checks or core tests. The isolated native fixture test described above supplies separate empirical evidence for the tested board and build. The runtime still logs that production integration is unchecked and reports `Capability.Unchecked`; prerequisite availability and fixture observations do not establish support for other builds or the complete culling range.

## Bind each peer to its local world

Every host and client loads the patcher DLL and applies scene patch files to its own scene. The native entry point holds one peer's state in a `LocalWorldBinding<PatcherBehaviour>`: the capability adapters, the `PatchEngine` with its captured underlying states and guards, and the `PatchRuntime` with the reported warnings of the current load attempt. It sends nothing to other peers and receives nothing from them.

The binding takes two keys. The world key is the map context: the active map definition and resolved map layer identifiers, and whether the map is open in the native map editor. The patcher state lives as long as this key stays the same, across world unloads. The attempt key combines the `Map.Runtime.MapManager` instance and the `Track.Graph.Shared` instance when that member exists. Neither key is a verified world identity: a replaced map manager or graph does not establish that the scene objects are new, and an equal key does not establish that they are retained. The reconciliation decides that per object.

`EntryPoint.OnWorldLoad` calls `Enter(world, attempt)` on every world-load callback. It returns a `WorldEntry`:

- `Started`: the peer had no state for this map context and created it. A different map context releases the previous state first.
- `Reentered`: a new load attempt over the state retained for the same map context, because the attempt key changed or `OnWorldUnload` ended the previous attempt.
- `Repeated`: another callback in the current load attempt. Successful modifications reconcile to their absolute map placement; failed modifications stay blocked and targets with unverified cleanup stay guarded.

A native marker check can run before the world-load callback. It calls `Prepare(world)`, which opens the load attempt for the current map context; the callback then joins that attempt instead of starting another. A marker check on another map context releases the retained state. When a key cannot be read, the patcher reports a native warning and applies nothing for that callback. If creating the state throws, `Error` is set and the next load attempt checks the prerequisites again.

Every new load attempt over retained state calls `PatchEngine.Reenter`, which returns a `ReentryResult`:

- An object that still resolves under the identity it was first resolved under is retained. Its underlying state, captured before its first mutation, stays, so a later removal returns it to its native state rather than to the patched one. Its unverified-cleanup guard carries over.
- An object that does not resolve but that its `IRetainedScene` reports as `Unsettled` is retained as well. It still exists, but cannot be checked yet: crossing coverage reports a controller whose scene is valid but not loaded, as during a native marker check inside a scene load. A destroyed controller, or one in a loaded scene that no longer stands under its identity, is not unsettled.
- Any other object is released. The engine forgets it, and an adapter that implements `IRetainedScene` removes what the patcher owns for it, never native state. Crossing coverage destroys the owned spans of a reconstructed crossing; its native spans and circuits, and other crossings, stay as they are. A rebuilt crossing therefore gets one owned set under the original span IDs.
- Failures recorded in the previous attempt are cleared, so the new attempt retries them once.
- A release that leaves owned state behind, or a retained object that cannot be checked, is listed in `Failures`. The object stays recorded, so the next load attempt retries the release.

`PatcherBehaviour.BeginAttempt` then starts a fresh `PatchRuntime`, so diagnostics, overlap notices and the warning identity start over, and logs one line with the retained, released and failed counts. Each application at a world-load callback moves the independent-board terrain subscription to a replaced map manager through an `InstanceSubscription`, which moves its one handler to a new instance, adds nothing when it is bound again to the same instance and removes it when the state is released. Each cleanup failure becomes a local native warning. It reports no failure to another peer and triggers no rollback, disconnection or session-wide failure. A retained object whose check throws is kept with its state and listed in `Failures`; the next load attempt checks it again. If `Reenter` itself throws, the binding sets `ReentryError`, releases the state and starts a new one for the map context; the entry point reports it as a local native warning. `OnWorldUnload` ends the load attempt and the native map editor-bound parts, such as the panel and the scene patch editing session; the next load attempt reconciles the rest. Observers follow two lifetimes. The world state holds the terrain subscription and one owned-span root per scene; the process holds the Harmony hooks. Repeated callbacks, re-entry and unloads reuse them. Each load attempt holds the Scene patches window's handlers, the scene patch editing session's history-change handler and an active gizmo's drag and origin-move subscriptions; `EndAttempt` disposes them before the next attempt attaches new ones. A native marker check observes the message collector only for the duration of that check.

Each peer converts map coordinates through its own `Helpers.WorldTransformer`, so differing local origins on host and client yield the same map placement. Repeated application writes the placement again and refreshes its dependent state; it does not accumulate an offset.

The patcher writes no shared game property, so host authority checks have nothing to gate. It adds no synchronization, admission check, disconnection or session-wide rollback. Reconnect and re-entry go through Railroader's own admission and synchronization unchanged. Railroader's own checks of required mods and versions govern joining, and each installation needs the mods and its own DLL permission. Native version matching does not prove that peers hold identical scene patch files or applied them successfully.

When the binding releases the state, because the map context changed, `Reenter` threw or `OnModUnload` ran, `PatcherBehaviour.Release` disposes `SceneCapabilities`, which disposes every capability that implements `IDisposable`. `CrossingCoverageScene.Dispose` writes the native circuits and spans back to every crossing it holds a baseline for and that still conforms, and retires every owned span, also for a crossing that is gone. This protects the case where the patcher state ends while the scene stays loaded, such as a mod reload or unload that calls `OnWorldUnload` and `OnModUnload` without unloading the map scenes; the next state then records the true native coverage and applies each modification once. Railroader 0.6.2 offers no such route inside the native map editor, and the protection has not been tested in the game. Dispose throws nothing: a crossing it cannot restore keeps its patched circuits, and the next state refuses them as described under detection additions.

Retained-world limits: an object counts as retained when the capability that resolved it finds the same instance under its identity at the start of the load attempt, or, for crossing coverage, when the instance still exists in a scene that is not loaded yet. The reconciliation can run during a native marker check, before Unity marks a loading scene as loaded. Any other capability's object that cannot be resolved at that moment is released, which forgets its captured underlying state. In Railroader 0.6.2 every route into a new load attempt for the same entry point has already unloaded the map scenes, so this releases only objects that are gone. A replaced map context, including a replaced map manager with a changed map identifier, starts from new state; crossings return to their native coverage first, while other objects retained across that change start from their current, possibly patched state. Only crossing coverage implements `IRetainedScene`. Boards, the bridge, track markers and crossing pads hand their effects to the target or to native registrations that the native components hold, such as mask and heightmap modifiers in map-manager storage, culling spheres and graph locations; pads keep their generated geometry under the pad. For a reconstructed target in a retained map manager, the patcher releases nothing of those, and whether the native components remove their own registrations when they are destroyed has not been checked.

Native single-player observation, commit `e2f526d` on Railroader 0.6.2: reloading the same save in one process through the main menu, twice each with the CrossingReroute and FixedPlacementBaseline fixtures, logged "0 objects retained, 2 released, 0 cleanup failures" on every reload. The game rebuilt every modded and added object, the patcher applied each modification once (one owned span set without duplicate IDs, the moved board moved once, the disabled board still inactive), and the crossing detected on the added tracks. Native map editor sessions load another map context first and always start new state. In Railroader 0.6.2 single player the path where the patcher state ends while the map stays loaded is not reachable natively: the map editor offers no mod reload, and the definition editor loads `rr/editor-default-map`, not the edited map, so the restoration on that path rests on the core tests. Retention of scene objects across a load attempt has therefore been exercised only by the core tests. Whether reconnect retains scene objects, the map manager or the graph has not been observed.

The core tests exercise peer independence, per-peer map and capability checks, repeated callbacks, re-entry after a reconstructed graph or an unload, early checks that open the load attempt and keep a crossing whose scene is not loaded, retained guards and underlying states, retried failures, released reconstructed targets, owned-span cleanup with preserved native state, native crossing coverage restored when the state is discarded while the scene stays, refusal of patched circuits as native, isolated cleanup and reconciliation failures, and single observers across load attempts, through `LocalWorldBinding` and complete scene patch files with controlled scenes. They do not exercise Railroader networking. Live host/client loading, later joining, reconnect, native synchronization and crossing-controller behavior with this build remain unverified.

## Apply a scene patch file

`ModScenePatchFiles.Discover` returns a `LoadedMod` for each loaded mod with `Data/scene-patches.json`, in the order of `AssetPackManager.OrderedPacks`. It decodes the scene patch file and `Info.json` as strict UTF-8; a mod entry that cannot be read becomes a `LoadedMod` with an `Error` and does not hide the mods after it. `LoadedMod.Read` takes the name, version, author, website and the identifiers under `dependencies.required` from `Info.json`. In the native map editor, discovery returns only the edited mod, marked `EditTarget`, so its scene patch file applies before Save has declared the dependency; the native map editor's Save writes the missing or insufficient dependency entry. `LoadedMod.Applicable` is true for a readable mod that is the edit target or declares `crankyant/scene-patcher`.

`PatchRuntime.ApplyLoaded` applies the applicable mods in the given order and returns a `LoadedScenePatchFile` per mod: the engine's `ScenePatchFileResult`, or `Skipped` for a mod that never reached the engine. The engine rejects a scene patch file whose target map is not in the map context, as an error reported only in the native map editor. A failure report or overlap notice that cannot be delivered is recorded in `PresentationError` and does not stop the next mod. `ApplyLoaded` passes an `OverlapNotice` to `IOverlapNotices` when a second or further supplying mod has an outcome whose `ResolvedTarget` is the same object, compared by reference. Only an outcome that resolved its target uniquely carries that object. The notice's `Key` stays the same for the object, so the native adapter replaces the row with `MessageLog.Info` when another mod joins; the same set of mods gives one notice per loaded world. `Dependencies` describes the declared dependencies among the named mods. Overlap does not change application or failure handling. The `PatchEngine.Apply` overload with `scenePatchFileKey` distinguishes modification identities across scene patch files during one load. Keep the key stable for each supplying mod scene patch file in that load.

The returned `ScenePatchFileResult.Error` reports rejection of the whole scene patch file, including invalid format, a `modifications` value that is not an object keyed by modification ID, a repeated property name at any depth, target map mismatch and incompatible capability. Modifications that `dependsOn` does not order are processed in the ordinal order of their keys (`PatchEngine.Entries`). Per-modification failures appear in `Outcomes`. The engine records failures and does not retry the same scene patch file modification during the load attempt; `Reenter` clears them for the next attempt. If a mutation fails, it asks the adapter to restore the captured snapshot. If restoration cannot be confirmed, the engine rejects later operations on that resolved target for the load.

### Classify failures

`Outcome.Failure` is a `FailureKind` that says what a failure did to the scene:

| Kind | Meaning |
| --- | --- |
| `Refused` | Stopped before any mutation: an invalid value, a missing or ambiguous target, a failed preflight, relationship check or mutation guard, or a changed inspected observation. |
| `DependencyFailed` | Not attempted because a modification in its `dependsOn` closure failed. |
| `Restored` | The mutation failed and `Restore` verified the captured state. |
| `AwaitingOutput` | Restored, but the restored dependent output has not completed, or refused because that output of an earlier restoration is still outstanding (`PatchEngine.Guarded`). The target waits until the output completes; this is no incomplete cleanup and needs no `Recheck`. |
| `IncompleteCleanup` | The mutation failed and the restoration did not verify. `Outcome.Remaining` names what remains. |
| `Blocked` | Refused because an earlier `IncompleteCleanup` guards the target. `Remaining` repeats that state. |
| `AlreadyFailed` | A world-load modification that already failed in this load attempt; it is not retried before `Reenter`. |

A file-level rejection sets `ScenePatchFileResult.Error` and leaves `Outcomes` empty. Before capture the engine reads the target's state once more, and after an unverified restoration it reads it again. `RemainingState.Describe` compares the two readings and returns one line per differing setting (position, rotation, activity, track binding, crossing coverage) and one line for owned spans still registered (`CrossingCoverage.Residue`). A read that throws makes every setting uncertain. When every setting agrees, the adapter's own verification, such as a registration or generated output, failed, and the line says that this state is uncertain. The engine keeps those lines with the guard, and `Reenter` drops them with a released target.

Adapters throw from `Apply` and return false from `Restore` as before; the engine and the session decide the kind. An adapter needs no change to take part.

A native journey can produce each failure kind on demand with the test-only fault build; see [inject a failure into a native journey](fault-injection.md).

The core engine accepts JSON text. Runtime application does not rewrite the source scene patch file. `ScenePatchFile.Write` returns the original text for an unedited supported v1 scene patch file. After an edit it returns the canonical text, which follows the canonical order of the [format reference](../../guides/scene-patches/scene-patch-file-v1.md#canonical-order) and in which every number that was not replaced keeps its source literal. `PreservingJson.WriteCanonical` orders the text as it writes; the tokens stay in their source order, so reading never reorders a scene patch file. `PreservingJson.KeepLiterals` gives a number that an edit leaves at its value the literal of the number it replaces. There is no format-conversion API in this slice. Unsupported or malformed scene patch files are protected against writes.

## Connect runtime diagnostics

For native marker restoration, `NativeMarkerLocation` can write the captured serialized segment/end/distance when the original segment is missing, then invalidate the native cache and notify location listeners. Supplied references still pass `CheckRelationships` before mutation. `ITrackMarkerDiagnostics.AfterVerifiedState` runs only after binding, registration and dependent-state verification. The native implementation invokes the original marker check for an active restored broken reference while preventing early repair of that same marker from reapplying the unsaved disk scene patch file. `NativeMarkerWarnings` retains only the row emitted by that invocation and reconciles its exact unchanged identity after a later verified repair, including Undo. It preserves unrelated and changed rows and never closes a shared warning window.

Keep one `PatchEngine` for a retained world and one `PatchRuntime` over it for each load attempt, including early marker checks and later world-load callbacks. Pass the supplying mod's metadata in `PatchSource` and send failures through `IPatchDiagnostics`. Use `Outcome.Cause` and `MapEditorOnly` to distinguish checked invalid definitions, unknown application failures and scene patch editing recovery. An adapter should throw `InvalidPatchDefinitionException` only for a demonstrably invalid supplied value or reference; unexpected native exceptions retain an unknown cause.

Call `BeforeNativeCheck` from a prefix that leaves the original native method enabled. It validates the complete scene patch file before selecting matching dependency-free relationship-only repairs. Check native readiness before entering this boundary. The native hook requires a valid target scene, populated graph and unique marker ID. Unity can invoke this check before marking the scene loaded. `TrackMarkerWorld.DuringEnable` admits that current target and scans holders in valid scenes for the duration of the check, then restores normal loaded-scene checks. The later runtime application reuses the engine's captured underlying state. Do not use a separate early engine that loses that baseline.

If early preflight cannot establish the target or replacement, retain `ScenePatchFileResult.EarlyRouteUnavailable` and defer to world-load application without consuming its guarded runtime attempt. A reference that remains invalid at world load fails normally. For fallback, capture the structured row emitted during the original native check, its object identity and the concrete reason an early route was unavailable. Pass that `WarningAttribution` to `Reconcile` only after applying the supplying scene patch file, with a separate check of the actual binding, registration and dependent state. The runtime refuses missing, changed or ambiguous rows, unsuccessful operations and an available early route. Implement `ICurrentWarnings.Remove` as exact current-collector removal, without historical-log or shared-window changes.

The native adapter calls the four-argument `MessageLog.Warning(originator, description, source, deduplicationKey)`. The game's Log window heads a row with the originator followed by the source, and native rows name the thing as originator, such as a mod's file or a definition, and their subsystem as source. The patcher passes `Railroader Scene Patcher` as source and, as originator, `<mod identifier>:Data/scene-patches.json` for a scene patch file or modification failure, the target object for an overlap notice and `crankyant/scene-patcher` for a state of the patcher itself. Queue delivery until `MessageCollector.Shared` exists, because the earlier fallback collector writes only to the ordinary logger. Keep stable diagnostic keys distinct for scene patch file and modification failures. `DiagnosticTests` exercises these scene patch file and diagnostic boundaries without native lifecycle or window ownership; the production native journey remains a separate check.

## Edit through a session

`PatchEditingSession` owns one scene patch editing session for the edited mod. It takes the `PatchEngine` that applied the scene patch file at world load, an `INativeHistory` and an `IStorage`.

- Without a scene patch file in storage, the session creates one whose target map is `PatchEditingSession.TargetMapFor(scene.MapIds)`: the last entry of the loaded map context. `IScene.MapIds` must therefore list the edited map definition first and then all its resolved map layers topmost first, as Railroader's `ActiveMapDefinition.MapLayerIdentifiers` does, so the last entry is the bottom map layer, or the map definition itself without layers. An existing scene patch file keeps its target map. `TargetMap` returns the scene patch file's target map, which for a new scene patch file is the one it was created with, and `CopyId(entry)` builds the Copy ID JSON with it. While the session cannot read the scene patch file, `TargetMap` is null and `CopyIdRefusal` holds the session's refusal, which `CopyId(entry)` throws. The static `CopyId(mapIds, entry)` serves Copy ID outside scene patch editing.
- Before the equal-content check, `PreservingJson.KeepStoredPrecision` gives every axis of `placement.position` and `placement.rotation` that equals the existing value at single precision the existing value, so `KeepLiterals` keeps its source literal and an edit of one axis leaves the others' text alone.
- `Edit`, `Remove` and `Recheck` accept the `InspectedTarget` of the inspected observation; the Scene patches window always passes `inventory.Pin(selected)`, so a stale inventory or changed observation refuses the edit. Immediately before the scene mutation, with or without a token, the session runs the engine's guard: preflight again, the same unique object, the same map context, and the token when given. A rejection there restores the scene patch file and requests no scene restoration, because no mutation started. History replay passes no token, since Undo and Redo return to states the user did not inspect, and still runs the guard.
- `Edit` and `Remove` resolve and preflight the target, change the scene patch file, and reconcile the object: the engine's underlying state for that object, captured before its first mutation, overlaid with every effective modification that resolves to it. Removal therefore recomputes the state instead of restoring a snapshot. A failure restores scene patch file and object; an unverified restoration blocks the object until `Recheck` verifies it. Every session outcome carries a `FailureKind` as in the engine: a rejection before `scene.Apply` is `Refused`, a verified restoration `Restored` or `AwaitingOutput`, an unverified one `IncompleteCleanup` with `Remaining` measured against the state read before the edit, and an edit of a guarded object `Blocked`. Track-following reconciliation reports `Restored`, `IncompleteCleanup` and `Blocked` the same way.
- `Recheck` resolves, validates the inspected token and preflights afresh, computes the desired state from the scene patch file and applies it only when the object differs. The scene patch file's persistent identities, its modification keys and addition IDs, decide the result: crossing coverage reuses owned spans for an addition the scene patch file names and retires owned spans an interrupted attempt left for any other, before anything new is built. When the state then verifies, the guard ends. When the apply throws or does not verify, the object stays or becomes guarded as `IncompleteCleanup`, with `Remaining` measured against the scene patch file's desired state. `CleanupUnverified(target)` and `RemainingState(target)` read the guard by identity from the engine's record, without searching the scene, so the panel can ask on every rebuild. `GuardOutcome(target)` returns the refusal an edit of a guarded object gets, as `Blocked` or `AwaitingOutput`, in the same way. The panel's `EditFeedback.Run` checks it before the pin compares the scene, because an incomplete cleanup leaves the object changed and the comparison would otherwise call the inspection stale. The panel's Recheck runs the panel's own Refresh first and then pins the fresh entry of the same object, so it needs no separate Refresh after a failed attempt. `SceneInventory.Refresh` reads only; it neither mutates nor ends a guard.
- `RecoveryGuidance.For(outcome, place, action, structure)` turns a failed outcome into a `Recovery`: a heading that tells `refused`, `failed and was undone`, `failed; cleanup incomplete` and `blocked by an incomplete cleanup` apart, the problem, a correction in scene patch editing terms, the remaining state and the guide of the operation. `Guide(place, action, structure)` picks the guide from the action first, so a `Detection addition` in the `Crossing coverage` group opens the detection guide, then from the panel's action group, such as `Placement` or `Track binding`, and otherwise from the target's capability. The panel's `EditFeedback.Run` reports `Recovery.Line(action)` and keeps the `Recovery` with its message. The footer's **Guide** opens that guide, and the footer's state line shows the remaining state of an inspected object whose cleanup is unverified. Runtime player warnings (`PatchFailure`) do not use this guidance: they name the mod and the operation and ask for a report, never a repair of the distributed document.
- Each completed change registers one inverse with the native history. The inverse sets the modification under its key to an absolute earlier state and registers its own inverse, so Undo and Redo are repeatable. It never throws: an exception inside `Core.UndoManager.Undo` leaves the native grouping open. A failed replay keeps the scene patch file, sets `IncompleteOperation` and keeps the session dirty until a complete Save. When native Undo or Redo itself throws, the native manager keeps its partial group open and later edits reach neither its stack nor its change count; the session then keeps native map data outstanding and `IncompleteOperation` set through every Save until the native map editor is reloaded.
- `Outstanding` names the participants that still need a write: native map data, scene patch file and dependency metadata. The scene patch file is Saved exactly when its current content and the text last read or written have equal content (`PreservingJson.SameContent`): object members match without regard to their order, the `dependsOn` of a modification that is an array of strings matches as a list sorted in ordinal order with duplicates counted, every other array matches in order, strings, booleans and null match exactly, and numbers compare by the value they denote as a double. When no scene patch file existed at load, the patch is Saved while it has no modification. Otherwise the scene patch file is outstanding. Native data is outstanding when the native map editor's own count says so, or when the history identity differs from the identity recorded at the last complete Save.
- The history identity gives every undo group a token. Undo and Redo carry the token to the group the native manager creates, a new edit gets a new token, and when the manager prunes its oldest group at 50 levels the state below the stack takes the pruned group's token. Two histories with the same native change count therefore differ, and a pruned or cleared history is never mistaken for the saved state.
- `BeginSave` writes the dependency metadata and then the scene patch file, each only when needed, and throws on the first failure. `CompleteNativeSave` records the saved identity. `FailSave` reports completed and outstanding writes. The patch write first compares the file with the text last read or written under the Saved equality and refuses to overwrite an external change. A reorder or other spacing is not an external change; a changed value, a file that cannot be parsed, a deleted file and a file created after a load that found none are.
- `ModStorage` is the storage of the edited mod; `ModScenePatchFiles.ActiveStorage` creates it for the native map editor. Each write puts the complete new content in a file beside the target, named after it with `.saving` appended, and replaces the target with it (`File.Replace`), or moves it into place when the target does not exist yet. A failure at any step removes the `.saving` file and leaves the target as it was, so the retry's comparison meets the text it last read or wrote. A leftover `.saving` file from an interrupted Save is deleted before the next write. Windows refuses the replacement while another process, such as a virus scanner, a sync client or the patcher's own periodic read of the scene patch file, holds the target open for a moment; an `IOException` from the replacement is therefore tried again, up to `ModStorage.ReplaceAttempts` times with pauses of 50 to 200 ms, while any other failure, such as a read-only target, fails at once. The file operations go through `IModFiles`, which the core tests replace to stop a write midway.

`SnapController` prepares one physical edit from an inspected object and a confirmed graph candidate. `ISnapScene` supplies copied map-coordinate node positions or cubic segment control points with the candidate's native handle and evidence. Preparation verifies the confirmed candidate and retains its geometry. Application rechecks map context, unique identity, handle and geometry both before scene patch editing and through the five-argument `PatchEditingSession.Edit` pre-mutation validator, after scene patch file and object-state callbacks. A pre-mutation refusal restores the scene patch file without calling scene mutation or registering history. The original four-argument edit remains available. Undo, Redo and runtime replay use only the resulting fixed placement, so they need no retained graph token. The validator runs synchronously and must only inspect its prerequisite, without mutating the scene.

Segment snapping evaluates the squared distance to a cubic curve at both ends and all stationary candidates in the unit parameter interval. The distance derivative is a polynomial of degree at most five. Recursive derivative-root isolation divides the interval into monotonic ranges for bisection. This uses the curve controls rather than the world ribbon's display samples. Node snapping uses its copied position directly. Both preserve the inspected rotation and pass the result through the existing fixed-placement adapter and restoration boundary. The controlled snap tests cover these scene patch editing and complete scene patch file outcomes; they do not establish native geometry or presentation behavior.

`Hooks` connects the session to the native map editor with Harmony patches, installed once per process and checked as one capability: a prefix, postfix and finalizer on `Game.MapEditor.MapEditor.Save`, a postfix on its `IsDirty` getter, a prefix and finalizer on `Core.UndoManager.Undo` and `Redo`, and a prefix on `MapEditorWindow.ConfirmExitEditor`. The Save prefix runs after the native map editor wrote edited terrain tiles and before the native map write. After Undo and Redo the finalizer settles the history identity and calls `MapEditorWindow.RefreshChrome`, because the native handler rebuilds the title and Save button before that point. When a required member is missing, scene patch editing is disabled with a message and runtime application continues. These hooks were exercised in recorded isolated journeys on Railroader 0.6.2 build 26335745: native scene patch editing journeys A and B on commit `caa9d3e`, and UI replay C on commit `9fb3ce4`. Those journeys establish only the cases they measured on that build and fixture; they do not establish other builds, object families, history pruning, an exception inside native history execution or multiplayer.

## Enable protected scene patch file recovery

`ScenePatchFile.Load` reads the top-level `formatVersion` first, with a reader that skips everything else and makes none of the full read's checks. It compares the source literal, because the reader also accepts and normalises forms such as `01` and `0x1`; only a JSON integer literal is a version number. `ScenePatchFile.FormatProblem` returns the same answer, so `LoadedScenePatchFile` logs a scene patch file of another format version as not applied whatever map it names. A missing, unrecognized or newer version protects the scene patch file before the rest of the text is read, so a newer scene patch file is reported as newer even when its content would not read as format version 1. A version declared before the text stops being readable still counts. Text that is no JSON object, or no JSON, falls through to the full read and is reported as such.

`ScenePatchFile.Diagnostics` and `PatchEditingSession.ScenePatchFileDiagnostics` describe the last read: why the scene patch file is protected, and each modification the engine would not execute. Each `ScenePatchFileDiagnostic` has `Path`, `StartLine`, `EndLine`, `Fragment`, `Message`, `Expected`, `Reference` (the format reference) and `Corrections` (the recovery guide). A zero `StartLine` means the text has no line for the problem, such as a missing field. `Fragment` is at most `ScenePatchFileDiagnostic.FragmentLines` lines and `FragmentCharacters` characters; a cut fragment ends by saying so and sets `Truncated`. The diagnostic of numbers that cannot be kept exactly points at the first such number.

A protected session offers two routes. Both refuse unless the caller passes `confirmed`, and both refuse while the native map editor has unsaved work, the history identity moved since the session started, or native history is unrecovered. Neither clears history or changes the scene.

- `Reread(confirmed, nativeDirty)` reads the scene patch file and mod metadata again and, when the text reads as a scene patch file of this session, makes it the session's scene patch file with that text as its Saved state. It writes nothing. It then applies the adopted scene patch file through `PatchEngine.Apply` under the session's scene patch file key, as a world load does, and keeps the result in `LastReread`; every object then shows the scene patch file's state, so an edit that starts from the object changes only the field it edits.
- `FreshStart(confirmed, nativeDirty)` is available only while the scene patch file itself blocks the session (`CanStartFresh`); unreadable mod metadata blocks the session without offering it. It needs a storage that also implements `IRecoveryStorage`. `BackupScenePatchFile` copies the scene patch file's bytes, also bytes that are not UTF-8, to a new file and verifies the copy; `MatchesPatchBackup` confirms that the backup and the scene patch file both still hold those bytes. The session then holds an empty current-format scene patch file naming `TargetMapFor(scene.MapIds)`, exposes `LastBackup` and keeps the scene patch file outstanding (`FreshStartPending`) until Save. `BeginSave` replaces the original only while `MatchesPatchBackup` holds; otherwise it refuses and keeps both files. `ModStorage` implements `IRecoveryStorage` beside the scene patch file as `scene-patches.json.backup-<id>` through `IModFiles`, removes a backup it could not verify, and never deletes a verified backup.

## Guard dependencies during editing

Every edit goes through one change route in `PatchEditingSession`. Before it touches the scene patch file or the scene, that route refuses two cases.

- An edit that would take a modification out of the scene patch file, such as Remove, Clear activity of a modification that sets nothing else, clearing the last crossing-coverage entry or an edit back to the underlying value, while another modification of the scene patch file names its key in `dependsOn`. The refusal names those modifications.
- An edit that keeps a modification in the scene patch file while `PatchEngine.IneffectiveReason` reports it does not take effect: a dependency is missing from the scene patch file, fails itself (its own content, a shared addition ID or a target that does not resolve uniquely), or the dependencies form a cycle. These are the rules `Desired` uses to choose which modifications to overlay. Removing such a modification stays possible unless the first rule refuses it; every member of a cycle of two or more is named by another member, so a cycle is broken only in the file, which the session reads when the native map editor opens again.

Undo and Redo of earlier edits are not refused: they return to states the scene patch file already had.

## Build and run the core test

Build the mod project against the local Railroader managed assemblies:

```powershell
dotnet build Src/RailroaderScenePatcher -p:GameManaged="C:/path/to/Railroader/Railroader_Data/Managed"
```

Build and run the core test project with the installed .NET SDK:

```powershell
dotnet run --project Tests/RailroaderScenePatcher.Core.Tests --configuration Release
```

The core test uses an in-memory adapter, a model of the native undo manager's grouping, pruning and change count, and storage with a failure switch per write. It also runs `ModStorage` on a temporary mod folder with file operations that stop a write midway or fail the replacement, for each written file and for the first Save without a scene patch file. It does not load Railroader, exercise a native scene object, or prove native history, title or Save button behavior.

Build outputs and intermediate files go to `RailroaderScenePatcherBuild` under the operating system's temporary directory. Override `BuildArtifactsRoot` with an absolute path when separate builds need independent output directories. The core tests restore Newtonsoft.Json 13.0.2 and need no game assemblies. The native project needs the local game DLLs through `GameManaged`; it does not distribute those files. It restores Lib.Harmony 2.4.2 and copies `0Harmony.dll` to its output.

For an isolated load test, copy only `RailroaderScenePatcher.dll`, `RailroaderScenePatcher.Core.dll`, `0Harmony.dll` and `Info.json` from the native build output into the selected test mod. The game already supplies Newtonsoft.Json. Replacing loaded DLLs requires a process restart. This is local test preparation, not a release package.
