# Apply fixed placement through the core engine

The core library exposes `RailroaderScenePatcher.Core.PatchEngine` over an `IScene` adapter. The engine owns document parsing, map-context matching, dependency ordering, target uniqueness checks, preflight, snapshot, mutation, and failure handling. `SceneCapabilities` assembles the scene of a load from independent capability adapters: `IndependentBoards` for independent boards, over the native `BoardScene` port, `BridgeScene` for the Ela bridge, `TrackMarkerScene` for Generic track markers and `CrossingPadScene` for crossing pads. It reports the active Map definition identifier and its resolved map layers. An isolated native test on Railroader 0.6.2 build 26335745 verified fixed placement, origin conversion, culler and mask updates, settled terrain work and declarative restoration. The core tests use controlled scenes for failure injection; native mutation-failure rollback and retained-world multiplayer re-entry remain unproven.

## Implement the scene adapter

`IndependentBoards` in the core library implements `IScene` for the independent-board pattern. It holds the capability's rules and talks to the game only through `IBoardWorld`, which the native `BoardScene` implements with reflection on the game's members. The core tests drive `IndependentBoards` through a controlled `IBoardWorld` that models the culler, mask and terrain lifecycle.

- `MapIds` returns the selected Map definition identifier and identifiers for its resolved map layers.
- `Capability` remains `Unchecked`. `BoardScene` checks the required native types, methods, fields and events when it is constructed; missing prerequisites prevent initialization.
- `Resolve` matches the scene name, full hierarchy path and culler component, and accepts no other `structure` than `independent-board-v1`. `Refusal` names why an object does not match the pattern: a missing or disabled culler, other than exactly one enabled circle mask, an inactive parent, a height-flattening mask, or another dependency in the hierarchy (`Track.*`, another culler, mask component or culling handler, a missing script). `Preflight` throws with that reason. The board itself may be inactive through an explicit disable. The inventory uses the same `Refusal` for its problems.
- `Read` returns the complete current state: position in map coordinates, rotation, and activity. `Apply` takes an `ObjectState`; a null placement or activity leaves that part untouched. `BoardScene` converts map coordinates with `Helpers.WorldTransformer` and checks the round trip. For an active board `Apply` requests `RequestUpdateCullingPosition` and calls the circle map mask's `Rebuild` method. Enabling and disabling rely on the `OnEnable` and `OnDisable` of the culler and mask; an inactive board gets no culling or mask call.
- After every application `Apply` verifies the pose, the activity and the registrations: `BoardScene.Registration` reads the culler's culling-sphere centre and the board's mask keys in the terrain system's modifier storage. An active board must have its sphere and every mask descriptor at its position, with no key missing from storage; a disabled board must hold neither. A mismatch throws, so the engine or session restores the captured state.
- `Capture` and `Restore` handle position, rotation, parent, and active state. `Restore` reapplies the snapshot with the same verification.

### Dependent output

`IDependentOutputScene` describes native writes that follow a mutation asynchronously. `Output(target)` returns a `DependentOutput` with the completed and outstanding writes and an error when they stopped; `RetryOutput(target)` requests the outstanding writes again. `IndependentBoards` implements it for generated terrain output:

- Each mask change records the board's old and new positions. A position whose tile `IBoardWorld.TileLoaded` reports unbuilt is complete at once, because the game builds that tile later from the current masks.
- `Poll`, called every frame by the entry point, completes a position after an `OnTileBuilt` notification covering it, once terrain work is idle with no pending invalidations. A position whose tile unloads completes for the same reason. A position still outstanding 30 seconds after the last mask change sets the error. `Failures` lists the boards whose output stopped.
- `RetryOutput` invalidates the tiles of the outstanding positions through the game's public `MapManager.Invalidate(Vector2Int)` and restarts the timer.

The engine uses the output to guard retries. After a mutation fails and `Restore` verifies, the target stays guarded while its restored output is outstanding, and the guard lifts once that output completes. Output that stops turns the guard into unverified cleanup. `AuthoringSession` exposes `Output` and `RetryOutput` for the editor panel, applies the same guard to a failed edit, and `Recheck` requests stopped output again. Generated terrain output is not a Save participant: Save does not write the output generated from board masks, and the game regenerates it from the saved placement on load. Native edited terrain tiles are a separate native Save concern; the board capability does not change them.

### Patcher version per target

`IVersionedScene.MinimumPatcherVersion(target)` returns the patcher version required by a target, or null. `AuthoringSession.MinimumPatcherVersion` takes the highest of the document's format requirements and these values. Fixed placement requires `0.1.0`, and generic `active` requires `0.2.0`; target-specific capabilities can raise that base minimum. `IndependentBoards` returns `0.5.0` for pattern boards other than the legacy Sylva location sign. The Sylva target still uses the pattern checks, but does not raise the pattern-based board dependency minimum. Bridge, track-marker relationship and target/group activity, crossing coverage and track-following capability gates remain `0.5.0`. Runtime reporting adds no document, schema or capability requirement.

## Implement a relationship capability

`ObjectState.Marker` carries the track-marker relationship: `MarkerBinding.At(TrackLocation)` sets or replaces it, `MarkerBinding.Detached` clears it, and null leaves it untouched. `PatchEngine.Parse` reads it from `relationships.trackMarker`. `Desired` overlays it like placement and activity, so removal recomputes the underlying relationship plus the remaining contributions, and `AuthoringSession` verifies it with the pose after every change, restoration and `Recheck`.

An adapter that supports relationships implements `IRelationshipScene.CheckRelationships(target, state)`. The engine and `SceneCapabilities` call it for every state of an implementing adapter, not only for states with a relationship, so an adapter can also refuse a setting its relationships make unsupported. The engine calls it after `Preflight` and before capture; `AuthoringSession` calls it for the authored modification before its mutation guard, so the underlying relationship may be the broken one being repaired. A scene without `IRelationshipScene` refuses any relationship, and `SceneCapabilities` refuses a relationship on an object whose adapter lacks it.

`TrackMarkerScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ITrackMarkerWorld`, which `TrackMarkerWorld` implements with reflection on `Track.TrackMarker` and `Track.Graph`:

- `PatternProblem` refuses everything except one Generic marker without milepost, crossing pad, crossing parent, location-change listener, group-following relative position that targets another object or whose `_setTargetActive` another component replaced, new-game car placement (`SetupDescriptor.placements[].marker`) or direct reference from any loaded component other than the colocated `TrackRelativePosition._marker`. `TrackMarkerWorld.Problem` is the same check for the inventory, which passes the reference scan and the setup index of its discovery; the adapter scans at most once per frame and builds a setup index per check. `NativeInventory.Discover` walks the fields once, one owner at a time through `ReferenceScan.Begin` so that the stepped discovery can pause between owners: the walk, like `ReferenceScan.Of` with an observer, reads every field of every owner once and hands each value or failure to the dependency strings, while the marker scan applies its own relevance and errors to the same reads. The setup index is a core `HolderIndex`: it walks the setup placements in their original order once, at the first marker that reaches the setup check, holds every marker found before the walk's first read failure and passes that failure to any other marker. Field descriptors and their relevance are cached per type; values are read afresh in every scan, and no scan result, value or error outlives its discovery. The scan is a core `ReferenceScan` over `ReferenceField` values: `ReferenceScan.CanHold` counts a field whose declared type can hold a component, directly or as the element of a non-generic `IList`, an array or a generic `IList<T>`, and the scan enumerates values of those list kinds. A relevant field that cannot be read, a list that cannot be enumerated or an owner whose fields cannot be listed makes the scan incomplete. `Refusal` then refuses every marker, because an unread field may hold any of them.
- `RefreshDependents` and `DependentProblem` hold the consumer state that caches the location. `MapBuilder.Add(MapLabel)` caches the track group from `TrackGroupIdFor(label)`, so the adapter removes and adds every registered label in the hierarchy and compares `_mapLabels` with `TrackGroupIdFor` afterwards. The group subscription has its own members, below.
- `Location` reads the serialized `_location`; `SetLocation` uses the native `Location` setter, which clears the cached pose and does not change the registration.
- `Registrations` reads every entry under the marker ID from `Graph._namedLocationsBySegmentId`; `Unregister` and `Register` call `RemoveNamedLocation` and `AddNamedLocation` as the marker's `OnDisable` and `OnEnable` do.
- `Resolve` starts from the loaded marker components and builds the hierarchy path only for their objects; an object with several markers counts once, so a missing, ambiguous or duplicate identity resolves as before.
- `SegmentLengths` resolves a segment through `Graph.GetSegment`. The graph keys segments by ID, so the native world returns zero or one length.

Sources for the consumers: `Game.Scripting.Modules.Railroader.NativeTrack.GetMarkerLocation` (graph lookup, then the stored location), `UI.Map.MapBuilder.Add` and `TrackGroupIdFor`, `Game.State.CompanyModeSetup.Setup` reading `SetupDescriptor.CarPlacement.marker`, `Game.FlareManager.NearbyFlares` and `Model.AI.AutoEngineerPlanner`, which filter registrations by their own marker types through `Track.NamedLocationExtensions` and `TrackMarkerType`, and `TrackRelativePosition.ConfigureAndApply`, called only from `MapObjectSpawner`, `ObjectsEditor` and `TrackAnchorReposer` for map objects.

- `GroupActivity` reads a group-following `TrackRelativePosition`: whether the hold is installed, `_observing`, `_observedGroupId`, its `OnGraphGroupEnabledDidChange` handlers on `Graph.GroupEnabledDidChange`, whether the marker location resolves, the segment's `groupId` and whether `Graph.enabledGroupIds` contains it. It returns null for any other object. `ObserveGroup` calls the relative position's private `UnsubscribeFromGroupEvents` and `ObserveTrackGroup`, which subscribe once for the current location's group and set the object's activity from the group. `HoldDisabled` installs or removes the explicit-disable hold: a delegate in `_setTargetActive`, which the native `SetTargetActive` calls instead of `SetActive`, and which keeps the object inactive. `TrackMarkerWorld` keeps the delegate per relative position so it can recognise and release its own hold; the pattern refuses a callback it did not install.

`Preflight` requires the registration rule: one owned registration at the stored location for an enabled, active marker with a resolvable location, none otherwise. `Apply` rewrites the registration and refreshes the dependents when the relationship changes or either disagrees, then applies activity and pose, and verifies location, pose, activity, the registration rule and `DependentProblem`. `Restore` writes the captured location, pose and activity the same way and returns true only when they verify. For a group follower, `Read` reports activity as null (group-driven) unless the hold is installed, so `Desired` keeps group-driven activity when no MapMod authors `active`, and removal returns to it. `CheckRelationships` refuses `active: true` on a follower; the engine and `SceneCapabilities` call it for every state of an adapter that implements `IRelationshipScene`, not only for states with a relationship. `Apply` installs the hold and deactivates the object before the relationship step when `active` is false, runs `ObserveGroup` after a rebinding, a release of the hold or a subscription that disagrees with the location, and verifies the subscription and activity with `GroupProblem` beside the registration rule. `Capture` records whether the hold was installed; `Restore` reinstalls or releases it with the captured location. The adapter's capability minimum is `0.5.0` for `track-marker-v1`. `AuthoringSession.Bind(target, binding, inspected)` sets, replaces or detaches the authored relationship; a null binding clears it and removes a modification left without content.

## Evaluate track-following placement

`Placement.Following` holds a `TrackFollowing`: a `TrackAnchor` (a `TrackLocation` on a segment, or an endpoint node ID), an offset in the track's frame and a rotation applied after the track's rotation. `PatchEngine.Parse` reads it from `placement.mode = "trackFollowing"` with a null position and rotation. `PatchEngine.Evaluate` asks the scene, which must implement `ITrackPoseScene`, for the anchor's current `TrackPose` in map coordinates and replaces the placement with its absolute evaluation, keeping `Following` set. `Execute` evaluates after `Preflight` and before the relationship check and capture, so an anchor that does not resolve fails the modification without mutation; `Desired` evaluates the effective state. Adapters receive an ordinary absolute pose and need no change. `TrackFollowing.Relative` computes the offset and rotation that keep a given absolute pose at the anchor's current pose.

`SceneCapabilities.Tracks` supplies the poses for every capability; `EntryPoint` sets it to `NativeTrackPoses`, which reads `Graph.GetPositionRotation` for a segment location (forward axis away from the measured end) and `TrackNode.Position` and `Rotation` for an endpoint, and refuses a missing segment or node and a distance beyond the segment's length.

`AuthoringSession.Follow(target, anchor, inspected)` stores the current pose relative to the anchor, `StopFollowing` stores the current pose as fixed placement, and `Edit` with a placement keeps a following object's anchor and stores the new relative values. `ReconcileTrackFollowing` re-evaluates every following modification of the active document and applies the ones whose object differs from its evaluation, without changing the document or the history. It reports each moved or failed object by modification ID, restores the prior state on failure, and marks the object unsafe when that restoration does not verify; an unsafe object is skipped until `Recheck`. `EntryPoint` calls it four times a second while the editor is attached, no gizmo is active and `HasTrackFollowing` is true. Each pass first tries a check that does no scene-wide work: it holds the target each following modification last resolved to while that modification object stays in the document, and skips the modification when `ITargetConfirmation.StillIdentifies` confirms the held object, no other modification names the same target, and the object's state and `IDerivedStateScene.DerivedProblem` already agree with the modification evaluated from `PatchEngine.Underlying` at the anchor's current pose. That check mutates nothing, so it needs no preflight. When the check finds a difference in pose or derived state only, a held update follows: the scene confirms the held object, `IPlacementPreflight.PreflightPlacement` checks the object's own pattern and registration through `IPlacementPattern.PlacementProblem`, without the setup-placement index and the direct-reference scan, and the relationship, activity and coverage must already agree. It applies through `IFollowUpdateScene.ApplyFollowUpdate`, which skips `ITrackMarkerDiagnostics.AfterVerifiedState` and its search of every marker unless the binding or activity changed; explicit edits, history steps and removal always reconcile the warning. Any other difference, a missing confirmation or an exception takes the full path, which resolves, preflights, applies and verifies as before. `TrackMarkerWorld.StillIdentifies` reads the held object only: it is loaded in the identity's scene, at its path, with its marker and capability; uniqueness is checked again by the next resolution. `AuthoringSession.MinimumPatcherVersion` returns `0.5.0` for a `trackFollowing` placement and for an `active` value on a `track-marker-v1` target, from the document alone. `ClearActivity` removes the authored `active` value.

Both marker capabilities share the internal `MarkerRelationship`, which holds the location, registration, pose, activity and group-activity rules above. The crossing-pad capability refuses group-following pads in `PadProblem`, so its objects never take the group-activity path. `CrossingPadWorld` inherits `TrackMarkerWorld.AfterVerifiedState`, so a verified pad state reconciles the native not-on-the-track warning of its marker like a Generic marker, and `EntryPoint.ReconcileMarkerWarning` retracts an exactly attributed warning after a verified pad repair. The early repair before `TrackMarker.OnEnable` resolves only `track-marker-v1` targets, so pads are repaired when their documents apply. A capability whose objects derive state from the marker location passes an `IMarkerConsumer`: `Capture` with the snapshot, `Refresh` after every write, `Problem` in the verification after `Apply` and `Restore`, and `Restored` to compare the restored state with the captured one.

## Implement the crossing-pad capability

`CrossingPadScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingPadWorld`, which extends `ITrackMarkerWorld` with `Geometry` and `Generate`. `CrossingPadWorld` implements it by deriving from `TrackMarkerWorld`:

- `Resolve` returns only marker objects with a `Track.TrackCurveMeshBuilder`; `TrackMarkerWorld.Resolve` returns only those without one, so the two capabilities never claim the same object. `PadProblem` is the pattern check shared with the inventory; it uses `TrackMarkerWorld.Consumers` for the ID, listener, group-following, setup-placement and reference rules, and also allows the builder's `_marker` reference.
- `Generate` calls `CurveMeshBuilderBase.Generate()`, which reads the marker's graph curves, replaces the mesh container's children, offsets the mesh by the pad's map position and moves the culling token to the new bounds. The new renderer starts enabled, so the adapter adds the token to `CullingManager._needsUpdate`; the manager's next `Update` calls `CullingSphereStateChanged`, which sets the renderer visibility. The adapter records the location, map position and signature it generated from in a weak table.
- `Geometry` returns the signature of the current `_renderers` (vertex count, FNV-1a hash of the local vertex positions, local bounds and mesh map position), the recorded source while the signature still matches, and whether the culling sphere equals the pad position plus `_boundsCenterLocal` with `_boundsRadius`. A pad without a live token, such as a disabled pad, has nothing to align.

For a track-following pad, `MarkerRelationship.Apply` passes `following` to the consumer, which also regenerates when `PadGeometry.Curves`, the `ICrossingPadWorld.SourceCurves` fingerprint recorded at generation, is unknown or differs from the current one. `CrossingPadWorld.SourceCurves` invokes `TrackCurveMeshBuilder.GetCurves()` for a resolvable location and joins every curve's `P0` to `P3`, `_up0` and `_up3`, rounded to millimetres. `MarkerRelationship.Apply` also passes `explicitApply`, so an applied edit, history step or removal regenerates any pad whose recorded `Curves` differ from the current ones; reconciliation (`DerivedProblem`) and `Restore` do not. An unknown token, on either side, never confirms the recorded curves. `Track.TrackSegment` and `Track.TrackNode` are plain graph objects, not Unity objects, so the token checks them against null. The consumer builds those curves only when `ICrossingPadWorld.CurveToken` differs from the token recorded with them. `CrossingPadWorld.CurveToken` reads the cached `TrackSegment.Curve` of every segment within half the pad width plus one metre of the marker location and the segment IDs `Graph.SegmentsConnectedTo` returns at each node it reaches, which decide the builder's next segment; it builds no curve. When built curves match the recorded ones under a changed token, the adapter records the new token. `Geometry` reuses the signature of a builder's renderer array until generation assigns a new array. `CrossingPadScene.DerivedProblem` reports a curve-only change once the changed curves have held still between two reconciliation checks, so a native drag regenerates the pad once, on its final curve; an applied edit regenerates at once. `CrossingPadScene` and `SceneCapabilities` implement `IDerivedStateScene.DerivedProblem`, and `AuthoringSession.ReconcileTrackFollowing` applies the desired state when the pose differs or `DerivedProblem` reports a difference. The core consumer regenerates when the pad holds no geometry for a resolvable location, geometry for an unresolvable one, geometry of unknown or other source, geometry generated at another position, or a misaligned culling sphere. A restoration requires the regenerated signature to equal the captured one when the pad held geometry at capture. `CheckRelationships` refuses a detach: with no marker location, `TrackCurveMeshBuilder.GetCurves` logs "Track marker is not set or invalid" and returns no curves, so `Generate` leaves no renderer and `CullingSphereStateChanged` calls `Generate` again, with the same error, whenever the sphere becomes visible or near. `MinimumPatcherVersion` returns `0.5.0` for `crossing-pad-v1`, and `AuthoringSession.MinimumPatcherVersion` returns at least `0.5.0` for a modification naming that structure. The inventory describes a pad's generated `DontSave` mesh objects with one dependency line instead of per component, because culling toggles their renderers and generation replaces them; otherwise an inspected pad would become stale with every camera move. `HierarchyDependencies.Describe` holds that rule without Unity, and the core tests run it through `SceneInventory.CheckFreshness`. Pads inside a `Track.Crossings.GradeCrossingController` qualify: the controller reads its circuit sets and its `KeyValueObject`, not the pad marker, and the reference scan still refuses any direct holder other than the colocated `TrackRelativePosition` and pad builder.

Sources: `Track.TrackCurveMeshBuilder.GetCurves`, `BezierCurveMesh.CurveMeshBuilderBase.Generate`, `OnEnable`, `CullingSphereStateChanged` and `RequestUpdateCullingPosition`, `Helpers.TransformExtensions.DestroyAllChildren`, which destroys the old children at the end of the frame, and `Helpers.Culling.CullingManager.Update`.

## Implement the crossing-coverage capability

`CrossingCoverageScene` implements `IScene`, `IRelationshipScene` and `IVersionedScene` over `ICrossingCoverageWorld`, which `CrossingCoverageWorld` implements with Unity. Coverage is the core `CrossingCoverage`: an ordered list of circuits keyed by native island span ID, each a `CircuitCoverage` that is `Native` (span IDs), `Tracks` (three `SpanRange` values) or `Detached`. `ObjectState.Coverage` carries it; authored coverage lists only explicit circuits, observed coverage lists every circuit plus any `Residue`, owned spans left registered by an incomplete cleanup. `PatchEngine.Desired` overlays authored circuits on the underlying coverage per circuit, so omission keeps a circuit's effective coverage.

- The adapter keeps a baseline per controller: the circuit set objects, their native spans and keys at first observation, and every span it owns. `Read` classifies each baseline circuit as detached (not in the controller's list), native (its native references) or tracks (owned references, read back through `Range`), and throws for anything else.
- `CheckRelationships` refuses placement, activity and `trackMarker`, unknown circuits, `Native` entries, unresolved or zero-length ranges, and an effective coverage with every circuit detached. Because the engine passes it every authored state, these refusals happen before mutation. `TrackMarkerScene` refuses coverage, and a scene or adapter without relationships refuses coverage like any other relationship.
- `Write` converges from any state the adapter can leave: it reuses a registered owned span with the exact range, creates missing ones and checks that they registered and cover track before any circuit refers to them, sets each circuit's references, sets the controller's list to the non-detached circuits in native order and retires unused owned spans. A span that stays registered after `DestroySpan` stays owned, so `Verify` reports it and `Restore` returns false. `Preflight` ignores such residue; `Read` exposes it, so `AuthoringSession.Recheck` sees a difference and applies the document, which retires it.
- `AuthoringSession.Cover(target, circuit, coverage, inspected)` sets, replaces or detaches one circuit's entry, and a null coverage clears it, removing a modification left without content. `PreviewCoverage` runs the same checks and returns one line per circuit from `CrossingCoverage.Describe` without mutating, recording history or changing the document. `Coverage(target)` reads the current coverage for the panel.
- `CrossingCoverageWorld` creates an owned span as the native span loader does: a disabled `GameObject` with `HideFlags.DontSave` under one root per map scene, then `TrackSpan.id`, `_lower` and `_upper`, `InvalidateCache`, and activation, whose `OnEnable` calls `Graph.AddSpan`. `DestroySpan` refuses to disable a span whose ID now belongs to another span, because `Graph.RemoveSpan` removes by ID. `SetCircuits` clears and refills the controller's own list, which its loop indexes on every pass.

### Detection additions

A detection addition is a `CircuitCoverage` of kind `Added` in the same `CrossingCoverage`, named by a `DetectionAddition.Key(owner, id)` instead of an island span ID. `PatchEngine.Parse(item, owner)` reads it from a `crossingCoverage` entry with `addition` and gives it the owner, which is the document key of `PatchEngine.Apply`. `AuthoringSession` takes the same key as `documentKey` and passes it to `Parse` and `Desired`, so the session and the world-load application name an addition alike. `EntryPoint` applies each document under its pack identifier and `Authoring` passes `PackDocuments.ActivePackId()`.

- An observed coverage is complete: `Read` lists every native circuit and every added circuit the controller evaluates. `CrossingCoverageScene.Apply` converges on a complete coverage as it stands and lays any other coverage over the observed one. An authored modification therefore keeps the additions it does not list, which may belong to another modification or MapMod, while the session's `Desired`, a restoration and a `Recheck` remove every addition their complete coverage lacks. `Overlay` keeps the completeness of its base, so `Desired`, which starts from the underlying state, stays complete.
- `PatchEngine.SharedAdditionIds` finds the IDs that more than one modification of a document uses. `Execute` fails each of those modifications before its dependencies run, and `Desired` leaves them out, so the result does not depend on the order of the modifications. `AuthoringSession.AddDetection` refuses an ID another modification already uses.
- `Write` gives each listed addition one `Circuit` in the baseline's `Added` list. It builds missing spans under `CrankyAnt.ScenePatcher.added.<owner>.<id>.<role>`, checks that they registered and cover track, and creates the circuit set through `ICrossingCoverageWorld.CreateCircuit` before it changes any existing reference. It then sets the spans, sets the controller's list to the native circuits that are not detached followed by the added circuits in ordinal key order, drops the circuits of deleted additions and retires unused spans. A failure after the new set exists leaves it in the baseline, so `Restore` writes the captured coverage and removes it with its spans.
- `BaselineOf` asks `ICrossingCoverageWorld.AdditionKey` for each circuit set it finds. `CrossingCoverageWorld` keeps the key of every set it created in a static `ConditionalWeakTable`, keyed by the set object. A set with a key enters the baseline as an added circuit with owned spans, so a new adapter over a retained world reuses it. This covers additions only: a native circuit whose spans an earlier adapter replaced is still read as native by a new adapter.
- `AuthoringSession.AddDetection(target, id, tracks, inspected)` adds or replaces one addition, `DeleteDetection` removes its entry, and `PreviewAddition` describes either without mutating. Before a mutation and in every preview the session passes the complete desired coverage to `CheckRelationships`, which refuses a result without detection. Deleting the last detecting addition is thereby refused before anything changes.

Sources: `Track.Crossings.GradeCrossingController.LoopCoroutine` and `UpdateCircuit` re-read `circuitSets` and the three span references every pass and cache nothing from the spans; `Track.TrackSpan.OnEnable` and `OnDisable` register and remove by ID; `Game.MapEditor.MapEditor.Save` serializes graph nodes, segments, turntables and groups, and industry spans only from ops DTOs, so neither runtime spans nor controller references reach map data. `GradeCrossingController.CircuitSet` is a class with a parameterless constructor and the three span fields; the controller's other fields hold no state per circuit set. The inspected build is Railroader 0.6.2 build 26335745.

## Combine capabilities

`SceneCapabilities` implements `IScene` and `IInspectionScene` over a list of capability adapters. `Resolve` asks every adapter and remembers which adapter resolved each object; an object claimed by two adapters appears twice and fails as ambiguous. Every other call goes to the adapter that resolved the object. `AddUnavailable(structure, reason)` records a capability whose game functions are missing: a target naming that `structure` resolves to a placeholder whose preflight fails with "incompatible with this game build" and the reason, while unrelated modifications still apply. `InspectedTarget.Validate` checks for that placeholder first, so an editor edit of an object whose capability is unavailable is refused with the incompatibility and its reason instead of a changed inspected context; the inspected-context guard itself is unchanged. `Capability` is `Incompatible` only when no adapter is available. `EntryPoint` constructs each native adapter separately, so a failed bridge check leaves board placement available and the reverse. `SceneCapabilities` also implements `IDependentOutputScene` and `IVersionedScene`: `Output` and `RetryOutput` go to the adapter that resolved the object, and an adapter without dependent output reports none; `MinimumPatcherVersion` takes the highest value any adapter returns. The board inventory's problems come from the board adapter's `Refusal`, the same check its `Preflight` runs.

## Implement a bridge capability

`BridgeScene` is the core part of the bridge capability. It implements `IScene` over `IBridgeWorld`, which `BridgeWorld` implements with Unity:

- `IBridgeWorld.Resolve` matches the supported path, scene name and root culler. `BridgeWorld.SupportedPaths` holds the one retained bridge.
- `CheckPattern` refuses inactive parents, a disabled root culler, missing scripts, rigidbodies, track-owned components (`Track.*`, `AutoTrestle.*`, `Game.Mow.TrackConstructionScenery`) in the hierarchy, a hierarchy without colliders, and a construction-scenery entry that targets the root or one of its parents.
- `Observe` returns a `BridgeObservation`: the root state in map coordinates, one `ColliderState` per collider (identity, shape properties, enabled flag, activity below the root, pose relative to the root, and for box, sphere and capsule colliders whether the physics bounds are centred on the transformed shape after `Physics.SyncTransforms`), and a text description of the separate scenery. That description covers the loaded `AutoTrestle.AutoTrestle` components within 250 m of the bridge's first observed position (local transform, activity, control points, generated flag, beam-matrix digest) and the construction-scenery controllers that reference the bridge.
- `SetPose` converts map coordinates, sets the root pose, calls `RequestUpdateCullingPosition` on every active culler in the hierarchy and synchronises physics. `SetActive` switches the root only.

`BridgeScene` records the first observation of each bridge in the load as its reference. `Preflight` refuses a bridge whose collider layout differs from that reference. `Apply` enables before the pose change and disables after it, as the board does, then verifies root pose and activity, the collider layout against the reference, collider activity against the root, and separate scenery against the observation before the change. `Restore` reapplies the captured root state and returns true only when all of those match the capture. The adapter's capability minimum is `0.5.0` for a `bridge-colliders-v1` target, also when the bridge adapter is unavailable.

The editor's **Scene patches** window reads `NativeInventory` through `IInspectionScene`. It exposes searchable observations, dependencies and detected problems for typed markers, spans, mileposts, crossings and independent boards, plus the known Ela bridge roots, which carry the `bridge-colliders-v1` structure and any `CheckPattern` problem. `IndependentBoards` implements `IInspectionScene` by delegating to the native inventory. Refresh does not apply patches. The editor inspects only the active edited MapMod's document. These additional inspection patterns do not enable mutations. See [inventory integration](scene-inventory.md) for the observation and revalidation interfaces. The same window edits the placement and activity of an inspected object that has a mutation adapter, as described under Author through a session.

Do not infer in-game rendering or culling correctness from the adapter's prerequisite checks or core tests. The isolated native fixture test described above supplies separate empirical evidence for the tested board and build. The runtime still logs that production integration is unchecked and reports `Capability.Unchecked`; prerequisite availability and fixture observations do not establish support for other builds or the complete culling range.

## Apply a document

`PackDocuments` reads documents from loaded packs in pack order. In ordinary play, discovery skips a pack that does not declare a dependency on `crankyant/scene-patcher`. In the editor, discovery filters to the active edited MapMod and reads its document whether or not the pack declares that dependency yet; the editor's Save writes the missing or insufficient dependency entry. It decodes `Data/scene-patches.json` and `Info.json` as strict UTF-8. The `PatchEngine.Apply` overload with `documentKey` distinguishes modification identities across documents during one load. Keep the key stable for each supplying MapMod document in that load.

The returned `DocumentResult.Error` reports document-level rejection, including invalid format, source-map mismatch, incompatible capability, and duplicate modification identities. Per-modification failures appear in `Outcomes`. The engine records failures and does not retry the same document modification during the load. If a mutation fails, it asks the adapter to restore the captured snapshot. If restoration cannot be confirmed, the engine rejects later operations on that resolved target for the load.

The core engine accepts JSON text. Runtime application does not rewrite the source document. `PatchDocument.Write` returns the original text for an unedited supported v1 document. After an edit it returns the canonical text, in which every number that was not replaced keeps its source literal. There is no format-conversion API in this slice. Unsupported or malformed documents are protected against writes.

## Connect runtime diagnostics

For native marker restoration, `NativeMarkerLocation` can write the captured serialized segment/end/distance when the original segment is missing, then invalidate the native cache and notify location listeners. Supplied references still pass `CheckRelationships` before mutation. `ITrackMarkerDiagnostics.AfterVerifiedState` runs only after binding, registration and dependent-state verification. The native implementation invokes the original marker check for an active restored broken reference while preventing early repair of that same marker from reapplying the unsaved disk document. `NativeMarkerWarnings` retains only the row emitted by that invocation and reconciles its exact unchanged identity after a later verified repair, including Undo. It preserves unrelated and changed rows and never closes a shared warning window.

Keep one `PatchRuntime` and its `PatchEngine` for a loaded world, including early marker checks and later world-load callbacks. Pass the supplying pack's metadata in `PatchSource` and send failures through `IPatchDiagnostics`. Use `Outcome.Cause` and `EditorOnly` to distinguish checked invalid definitions, unknown application failures and editor recovery. An adapter should throw `InvalidPatchDefinitionException` only for a demonstrably invalid supplied value or reference; unexpected native exceptions retain an unknown cause.

Call `BeforeNativeCheck` from a prefix that leaves the original native method enabled. It validates the complete document before selecting matching dependency-free relationship-only repairs. Check native readiness before entering this boundary. The native hook requires a valid target scene, populated graph and unique marker ID. Unity can invoke this check before marking the scene loaded. `TrackMarkerWorld.DuringEnable` admits that current target and scans holders in valid scenes for the duration of the check, then restores normal loaded-scene checks. The later runtime application reuses the engine's captured underlying state. Do not use a separate early engine that loses that baseline.

If early preflight cannot establish the target or replacement, retain `DocumentResult.EarlyRouteUnavailable` and defer to world-load application without consuming its guarded runtime attempt. A reference that remains invalid at world load fails normally. For fallback, capture the structured row emitted during the original native check, its object identity and the concrete reason an early route was unavailable. Pass that `WarningAttribution` to `Reconcile` only after applying the supplying document, with a separate check of the actual binding, registration and dependent state. The runtime refuses missing, changed or ambiguous rows, unsuccessful operations and an available early route. Implement `ICurrentWarnings.Remove` as exact current-collector removal, without historical-log or shared-window changes.

The native adapter calls the four-argument `MessageLog.Warning(originator, description, source, deduplicationKey)`. Queue delivery until `MessageCollector.Shared` exists, because the earlier fallback collector writes only to the ordinary logger. Keep stable diagnostic keys distinct for document and modification failures. `DiagnosticTests` exercises these document and diagnostic boundaries without native lifecycle or window ownership; the production native journey remains a separate check.

## Author through a session

`AuthoringSession` owns one editor session for the active edited MapMod. It takes the `PatchEngine` that applied the document at world load, an `INativeHistory` and an `IStorage`.

- `Edit`, `Remove` and `Recheck` accept the `InspectedTarget` of the inspected observation; the editor panel always passes `inventory.Pin(selected)`, so a stale inventory or changed observation refuses the edit. Immediately before the scene mutation, with or without a token, the session runs the engine's guard: preflight again, the same unique object, the same map context, and the token when given. A rejection there restores the document and requests no scene restoration, because no mutation started. History replay passes no token, since Undo and Redo return to states the user did not inspect, and still runs the guard.
- `Edit` and `Remove` resolve and preflight the target, change the document, and reconcile the object: the engine's underlying state for that object, captured before its first mutation, overlaid with every effective modification that resolves to it. Removal therefore recomputes the state instead of restoring a snapshot. A failure restores document and object; an unverified restoration blocks the object until `Recheck` verifies it.
- Each completed change registers one inverse with the native history. The inverse sets the modification to an absolute earlier state and registers its own inverse, so Undo and Redo are repeatable. It never throws: an exception inside `Core.UndoManager.Undo` leaves the native grouping open. A failed replay keeps the document, sets `IncompleteOperation` and keeps the session dirty until a complete Save. When native Undo or Redo itself throws, the native manager keeps its partial group open and later edits reach neither its stack nor its change count; the session then keeps native map data outstanding and `IncompleteOperation` set through every Save until the editor is reloaded.
- `Outstanding` names the participants that still need a write: native map data, patch document and dependency metadata. The patch document is outstanding when its canonical text differs from the last text read or written. Native data is outstanding when the editor's own count says so, or when the history identity differs from the identity recorded at the last complete Save.
- The history identity gives every undo group a token. Undo and Redo carry the token to the group the native manager creates, a new edit gets a new token, and when the manager prunes its oldest group at 50 levels the state below the stack takes the pruned group's token. Two histories with the same native change count therefore differ, and a pruned or cleared history is never mistaken for the saved state.
- `BeginSave` writes the dependency metadata and then the patch document, each only when needed, and throws on the first failure. `CompleteNativeSave` records the saved identity. `FailSave` reports completed and outstanding writes. The patch write first compares the file with the text last read or written and refuses to overwrite an external change.

`SnapController` prepares one physical edit from an inspected object and a confirmed graph candidate. `ISnapScene` supplies copied map-coordinate node positions or cubic segment control points with the candidate's native handle and evidence. Preparation verifies the confirmed candidate and retains its geometry. Application rechecks map context, unique identity, handle and geometry both before authoring and through the five-argument `AuthoringSession.Edit` pre-mutation validator, after document and object-state callbacks. A pre-mutation refusal restores the document without calling scene mutation or registering history. The original four-argument edit remains available. Undo, Redo and runtime replay use only the resulting fixed pose, so they need no retained graph token. The validator runs synchronously and must only inspect its prerequisite, without mutating the scene.

Segment snapping evaluates the squared distance to a cubic curve at both ends and all stationary candidates in the unit parameter interval. The distance derivative is a polynomial of degree at most five. Recursive derivative-root isolation divides the interval into monotonic ranges for bisection. This uses the curve controls rather than the world ribbon's display samples. Node snapping uses its copied position directly. Both preserve the inspected rotation and pass the result through the existing fixed-placement adapter and restoration boundary. The controlled snap tests cover these authoring and complete-document outcomes; they do not establish native geometry or presentation behavior.

`Hooks` connects the session to the editor with Harmony patches, installed once per process and checked as one capability: a prefix, postfix and finalizer on `Game.MapEditor.MapEditor.Save`, a postfix on its `IsDirty` getter, a prefix and finalizer on `Core.UndoManager.Undo` and `Redo`, and a prefix on `MapEditorWindow.ConfirmExitEditor`. The Save prefix runs after the editor wrote edited terrain tiles and before the native map write. After Undo and Redo the finalizer settles the history identity and calls `MapEditorWindow.RefreshChrome`, because the native handler rebuilds the title and Save button before that point. When a required member is missing, authoring is disabled with a message and runtime application continues. These hooks were exercised in recorded isolated journeys on Railroader 0.6.2 build 26335745: native authoring journeys A and B on commit `caa9d3e`, and UI replay C on commit `9fb3ce4`. Those journeys establish only the cases they measured on that build and fixture; they do not establish other builds, object families, history pruning, an exception inside native history execution or multiplayer.

## Build and run the core test

Build the mod project against the local Railroader managed assemblies:

```powershell
dotnet build Src/RailroaderScenePatcher -p:GameManaged="C:/path/to/Railroader/Railroader_Data/Managed"
```

Build and run the core test project with the installed .NET SDK:

```powershell
dotnet run --project Tests/RailroaderScenePatcher.Core.Tests --configuration Release
```

The core test uses an in-memory adapter, a model of the native undo manager's grouping, pruning and change count, and storage with a failure switch per write. It does not load Railroader, exercise a native scene object, or prove native history, title or Save button behavior.

Build outputs and intermediate files go to `RailroaderScenePatcherBuild` under the operating system's temporary directory. Override `BuildArtifactsRoot` with an absolute path when separate builds need independent output directories. The core tests restore Newtonsoft.Json 13.0.2 and need no game assemblies. The native project needs the local game DLLs through `GameManaged`; it does not distribute those files. It restores Lib.Harmony 2.4.2 and copies `0Harmony.dll` to its output.

For an isolated load test, copy only `RailroaderScenePatcher.dll`, `RailroaderScenePatcher.Core.dll`, `0Harmony.dll` and `Info.json` from the native build output into the selected test pack. The game already supplies Newtonsoft.Json. Replacing loaded DLLs requires a process restart. This is local test preparation, not a release package.
