# Scene inventory interfaces

`IInspectionScene.Discover` returns copied `SceneObservation` values for loaded objects, independently of scene patch files and warnings. Each observation contains an opaque object handle, target identity, family, activity, map-coordinate placement, serialized bindings, dependencies, detected problems and the available operation boundary. A provider must include inactive objects and perform no mutation, registration, cache rebuild or binding repair while observing.

`SceneInventory.Refresh` replaces its snapshot. `Search` matches names, paths, component and family names, activity, bindings, dependencies and problems. `CheckFreshness` compares handles, observation values and map context against a new scan. Any difference or failed scan marks the snapshot stale until explicit refresh. `InspectScenePatchFile` reports scene patch file errors, scene target map mismatch, target matches and missing modification dependencies without applying or rewriting a scene patch file. It is an inspection result, not operation preflight.

`StaleReason` holds why the snapshot is stale: the first difference a check found, or its failure. `Pin` puts it in its refusal. `EditFeedback`, a UI-independent part of the panel, runs each edit through `Pin` and leaves the result, with the reason of every refusal and of every edit that did not run, for the panel section of the control and for the log.

`DiscoveryWalk.Steps` holds the order and the pause points of a discovery over components: search, loaded check per component, field reads per owner, classification per component, one observation per candidate. `NativeInventory` supplies the native operations. A paused walk meets components that were destroyed since its search, such as the widgets of a rebuilt panel. The walk checks each component again before it reads, classifies or observes it and skips one that left, as a discovery starting at that moment would not find it. An observation that depended on the component then differs and marks the snapshot stale; a component no observation depends on changes nothing.

`AdvanceFreshnessCheck(more)` makes the same comparison in steps, for a caller that cannot afford one whole scan in a frame. Each call performs at least one unit of the scan and continues while `more()` holds; `CheckInProgress` tells whether a pass is unfinished. A provider that implements `ISteppedInspectionScene` supplies `DiscoverInSteps`: the walk of `Discover`, yielding null wherever it can pause and each observation as it is produced. Any other provider is stepped per observation. A paused pass reads the scene at different times. It therefore only marks the snapshot stale, on a difference, a changed map context or a failure. It replaces no observation, and a pass that finds no difference concludes nothing. `Pin` and `CheckFreshness` still scan the whole scene in one call, so an unfinished pass authorizes no edit. `Refresh` and `CancelFreshnessCheck` end an unfinished pass without a conclusion. The panel advances a pass for three milliseconds per frame while it is open, starts the next pass two seconds after one ends and cancels the pass when it closes. One unit can take longer than that budget: the search for loaded components, one component's fields, one observation with its hierarchy, and the first marker's walk over setup placements are not divided.

Whether a marker's binding is a problem follows what the game needs from its kind (`BindingRules` in the core). The game does not tell an empty binding from one that names a missing segment, and it warns only for an enabled marker, about a missing effect. `BindingRules.Need` gives the kind: Required for a crossing pad and a Crossing-type marker, ReadAnyway for a starter marker that an active setup descriptor references (`StarterSetups.Reading`; the game takes an active descriptor at a new game and reads the marker whatever its own activity), Never for a flare marker, Optional for every other marker, mileposts included. `BindingRules.Problem` lists an empty or missing-segment binding for Required while the object's own active flag is on and for ReadAnyway always, and a missing segment alone for Optional while enabled. `BindingRules.Problems` then decides what an object is listed with: an object whose own active flag is off triggers no problem of any kind, binding or other, a span's included, and stays reachable through the Disabled filter; only what the game reads whatever the activity, a ReadAnyway binding, stays listed. `BindingRules.Note` adds a `Marker binding note` line to the bindings where the state is no problem but worth knowing. A span's two locations keep their own check while the span is enabled. A problem is a defect the modder can repair with the patcher. Three things are therefore no problems. The reason a capability refuses an object of a supported family is the text after "Not editable: " under Supported edits (`CommandBand.Refusal`); the object stays in its family. An object of a kind no supported family covers, which the native map editor does not edit either, is inspection only: `SceneObservation.InspectionOnly` holds the reason, the outliner lists it in the Inspection only group, and the observation moves what would be its problems into its notes. `NativeInventory.Observe` sets that state for every family without an edit (a Track span the patcher added that no crossing controller holds, Track-relative scene object; an inspection-only object with a category, through `OfFamily`, stays in the Baked scenery group family under that category), for a marker of another type than Generic, and for a group root or crossbuck that the baked scenery rule leaves out of the Baked scenery group family, with the reason of `BakedSceneryRules`. A marker that an active setup's car placement holds is a starter placement marker, a supported kind with its own workflow: `TrackMarkerWorld.StarterSetups` reads every loaded `Game.Progression.SetupDescriptor` with its identifier, activity and car placements (cars, marker, wreck setting) once per discovery, and `StarterSetups` in the core decides the family, Starter placement for a used marker, and, through `StarterSetups.Reading`, what the game needs from each marker's binding and the reader lines (`StarterPlacements.Reader`) that the Object tab lists under Read by. The family is decided after the rules that keep a marker out of the inventory or in a Milepost row, so one object never gives two rows. When the setups cannot be read (`StarterSetups.Unreadable`), no marker counts as a starter placement marker: every marker keeps its own family and carries the inspection note `StarterPlacements.Unreadable`, and Refresh reports the same text under Diagnostics in the session details. Its Supported edits text is `StarterPlacements.Operations`, so every placement, activity and binding control stays disabled with that reason; the Generic marker capability refuses the marker with `StarterPlacements.MarkerCapabilityRefusal`. Focus and the world marking go to its track point, the map position of its serialized track location on the loaded graph (`NativeTrackPoses.MarkerPoint`), which is not its object position; `FocusTarget.Point` refuses one without a track point with `StarterPlacements.NoTrackPoint`, and the command band disables Focus with that reason beforehand, or with the reason that the track graph is unavailable or the object no longer exists. A track location whose distance lies beyond its segment's length has no track point either; it disables Focus without a problem, because the binding check only asks whether the segment exists. What the inspection could not read or check (`BindingRules.IsNote`: an incomplete reference scan, an unreadable value, a segment that could not be checked, a missing script) goes to `SceneObservation.Notes`, whatever the object's activity. A crossing mast is one entry in the Crossing mast family, the light object that carries `Track.KeyValueLampMaterialController` below a crossing controller; a gate (`RollingStock.Controls.KeyValueBoolAnimator`) at or below a light object is a part of that entry and gets no row (`NativeInventory.Family`, `CrossingDeviceWorld.OnLightObject`), and a gate on no light object stays listed in the family with its reason. The bell player a controller creates is one entry in the Crossing bell family. `CrossingDeviceWorld.MastProblem` and `BellProblem` give the pattern's refusal, which stands under Supported edits; a conforming entry carries `existing-crossing-mast-v1` or `existing-crossing-bell-v1`, and its name carries its crossing (`CrossingEquipment.Place`). A detection span, a track span that a crossing controller holds in a circuit (`CrossingDeviceWorld.HolderOf`, read from every loaded controller's `circuitSets` once per frame and again at every discovery and every re-observation after an edit, `InvalidateHolders`), is no inspection-only object (`CommandBand.SpanInspectionOnly`): `SceneObservation.HolderPath` names its controller, `InventoryPresentationState.Groups` puts it in the Crossing controller family, `Held` nests it under its controller, taking a controller the search left out from the whole inventory, and `HolderOf` finds the controller's entry for the Object tab's **Select controller** button. Its Supported edits text is `CommandBand.DetectionSpanOperations`, so every placement mode but Numeric is disabled with the reason that a span's position is its track locations. A patch names its target by scene, path and component. Where more than one loaded object holds those, `NativeInventory.Observe` gives the object no structure and the reason "Not editable: N objects share this hierarchy path and component ..." (`CommandBand.SharedPath`); the engine's refusal of a target that does not resolve uniquely stays as it is. One object with two components of one type gives two observations with the same handle and identity; both rows stay inspectable, and `InventoryPresentationState.CurrentSelection` finds the inspected one again by what it reads. A component the game adds to an authored object while it runs, such as the playable-graph adapter an animator of crossing equipment gets when it first animates, is runtime state and no dependency (`HierarchyDependencies.IsRuntimeComponent`): its arrival marks nothing stale. The kinds that stay out of the inventory are named in the coverage statement below. `SceneObservation.Enabled` is the object's own active flag, which the Disabled filter lists (`AuthoredActivity.Enabled`). A culler switches the objects on its list off while the camera is far away: an object that is off while its culler shows its objects (`_cullingState` is Visible) was switched off by the scene or by a patch and counts as disabled; off while its culler hides them, it counts as enabled, because the culler alone may have switched it. That reading follows the camera for a disabled object on a culler's list, so `Enabled` is no part of what an inspection pins or of the stale comparison. Add a new kind to `BindingRules.Need` with the game code that reads its binding.
A holder of a duplicate marker ID has a detected problem only when it is active and can receive a replacement ID. `MarkerIdHolders.Problem(self, repairable)` returns the problem `Duplicate marker ID <id> is shared with <N> other scene markers. Give one of them a replacement ID to repair it.` only for an active holder with `repairable` true; `NativeInventory` passes `repairable` as the structure equals `TrackMarkerScene.Structure` (`track-marker-v1`). Crossing pads, mileposts, starter placement markers and unsupported generic markers pass false and show no problem. `MarkerIdHolders.Dependencies(self, offer)` gives the explanation for every holder, active or inactive, and `NativeInventory` adds it to the dependencies; `offer` appends the repair sentence to the first line for a repairable holder, which the Object tab then pairs with the **Repair duplicate ID** button and the **Or give the replacement ID to** rows.

`NativeInventory` reads serialized marker and span endpoints and the graph's complete segment lookup, including group-disabled segments. It avoids resolving location/cache getters. Controller circuit roles remain explicit. A direct-reference scan reads loaded component fields and direct list entries; its result does not cover every indirect consumer. Per-object missing fields become visible problems. It uses exact type names and the established bridge roots. New inspection adapters must supply the same observation contract and preserve these limits. See [the coverage reference](../../guides/scene-patches/inspect-scene-objects.md).

The retained bridge construction controller's full type is `Game.Mow.TrackConstructionScenery`. Its `segmentIds` identify graph segments. Each serialized `entries` item supplies `trackConstructionState`, `condition` and `targets`. Reading those nested target arrays is necessary because the controller root can have no children while controlling the bridge's steel and abutments. Inspection reads the fields without invoking construction-state changes or moving the targets.

## Families and their inspection routes

Each family or case below has its inspection or ownership route. A named case is an example, not proof of every possible custom hierarchy.

| Family or case | Inspection or ownership route |
| --- | --- |
| Retained whistle/speed/yard-limit/station signs | Typed `TrackMarker` and `TrackRelativePosition`. This covers M5pp, Mm8w, Mwp1, Mkwd and Mi4f; labels do not determine marker enums. |
| Crossing pads | Typed markers with `TrackCurveMeshBuilder`, including Mg74, M5ib and Muef. Generated geometry is a dependency, not an inferred binding. Pads that match `CrossingPadWorld.PadProblem` carry `crossing-pad-v1`; their mesh objects are described by one dependency line through `HierarchyDependencies.Describe`, so culling and regeneration do not change the observation fingerprint. Output is every object the game created while running and everything below the builder's mesh container (`HierarchyDependencies.IsOutput`): the builder destroys every child of that container when it generates, so a mesh object that was saved with the scene there is replaced the first time the pad comes into view. |
| Independent boards | The Sylva culler and mask hierarchy has no invented track binding. Placement, activity and logical references are separate. Every culler object with a circle mask and no track marker is classified as an independent board; the board capability's `Refusal` supplies its problems. |
| Scene spawn points | Every `Character.SpawnPoint` below a listed scene root is one entry of the Spawn point family (`SpawnPoints.FamilyOf`), with `spawn-point-v1` while `SpawnPointWorld.Problem` finds no reason against an edit. Its bindings name the object name that teleport offers, its priority and each loaded `Game.Progression.SetupDescriptor` active in the hierarchy that names it, by identifier or object name (`SpawnPointWorld.Bindings`; the game finds setups with `FindObjectsByType`). When the setup type or its `spawnPoint` or `identifier` field is missing, one `Start setups unread=` binding says so instead, and the capability is unavailable. `SpawnPoints.Uses` turns the bindings into the Object tab's expected uses, with the spawn point's activity, the number of other active spawn points with the same priority from the object list, and the native spawn count from `Game.MapSpawns.Shared` (null, and so unknown, until the map loads). | Mileposts and visuals with group-driven activity | `Helpers.MilePost` and serialized `TrackRelativePosition` observations cover mileposts and their target and group relationships. | Existing crossing detection and equipment | Typed spans, explicit controller circuit roles and controller-bound lamp, gate and bell components cover existing crossings without assigning relationships by proximity. |

| CTC, signals and interlocking | Outside the operation boundary and kept out of the inventory, as the coverage statement says. |

## Coverage statement

### Baked scenery groups

`BakedSceneryRules.Classify` decides, from the hierarchy below each loaded `World` root, which objects are group roots. A candidate without a renderer, collider, light, storage pile or log pond at or below it is not listed, whatever components it holds; that check comes before the exclusions below. `GroupWorld.Verdicts` keeps the verdicts until a whole discovery calls `GroupWorld.Invalidate`, or until the loaded scenes, their World roots or the objects down to the group roots change; a stepped pass reuses them. A category folder that holds a generator of runtime objects (`Track.TrackObjectManager`, `Game.MapLoader`, `TelegraphPoles.TelegraphPoleManager`) gives no group roots. A candidate that the scene does not serialize, that carries `Game.MapObjectActivation`, or that an existing family lists is no group. A group root that holds one of the kinds below at any depth is left out of the family and listed in the Inspection only group with the reason; the table below says where each kind is edited, if anywhere. The native inventory observes a group root through its `UnityEngine.Transform`, with the structure `baked-scenery-group-v1` when `GroupWorld.Problem` finds no refusal; `BakedSceneryGroups` in the core applies placement and activity through `GroupWorld`.

`BakedSceneryCategories` holds the categories of the family in the outliner's order (`All`), the subgroups of Bridge (`Subcategories`) and the category table of the Railroader 0.6.3 Large Scenery catalogue (`Table`, `Find`): for each scene object in a group-root position its hierarchy path and its category, or no category for a folder. `Classify` gives every listed or inspection-only verdict the table's category and subgroup (`GroupRootVerdict.Category`, `Subcategory`). A bridge the table does not name takes Bridge with its subgroup from the bridge rule (`RoadBridge` for a road bridge, `RailBridge` for a rail bridge construction outside Ela), as the road bridges below the World/Roads folders do. A folder one level below World/Large Scenery that the table names as a group, not as a folder, is itself the group root: the Almond Bridge folder carries the construction controller and the simple culler of its bridge, so its abutments and steel are its parts. An object that another family lists takes a category by its family (`BakedSceneryCategories.OfFamily`): the Bridge and Bridge construction scenery families stand under Bridge / Rail bridges, and `InventoryPresentationState.Groups` puts every row with a category in the Baked scenery group family. A group row that holds matching parts and matches a search only through a dependency line that names an object below it is shown as context (`SceneObservation.MatchesItself`). A listed group the table does not name stands under Other; an inspection-only group the table does not name has no category and stays in the Inspection only group. The native inventory passes both to `SceneObservation.Category` and `Subcategory`, an inspection-only group stands in the Baked scenery group family (`GroupWorld.FamilyOf`), and `GroupWorld.Report` ends each verdict line with the category in brackets. `InventoryPresentationState.Groups` keeps an inspection-only row with a category in its family, and `Categories` nests the family's rows: category, subgroup, group, part. A part whose group the search or filter left out is shown under that group, taken from the whole inventory and marked `Context`. `GroupOf` finds the entry of a part's group for the Object tab's **Select group** button, and `PartOf` gives the line that names the group. A modification that names a folder as a group, or a group root as a part, resolves so that it fails before mutation with its own reason, and the file's other modifications still apply (`BakedSceneryRules.FolderRefusal`, `GroupRefusal`, `ResolvesGroup`; `GroupRootRefusal`, `PartRefusal` and `Resolves` with the group verdict; `GroupWorld.Find`, `Problem`, `FindParts`, `PartProblem`). `BakedSceneryParts.Resolve` leaves a group root out for an identity without a structure, so that identity resolves to the group alone. A group row names where it stands (`InventoryPresentationState.GroupWhere`), which tells groups of one name apart. Add a group to the table with its category when a game version adds one; the core test `BakedCategoryTests` compares the rule with the expected category table.

`BakedSceneryRules.Parts` decides, below each listed group root, which objects are parts. It walks every depth. An object the scene does not serialize, a level of a LOD group, an object an existing family lists and an object without a renderer, collider, light, storage pile or log pond at or below it are no parts, and nothing below them is either, except an object that holds a scene ground mask (`BakedSceneryRules.HoldsGroundMask`): it is a part, the exception to the presence rule of the coverage statement. A transform the game animates while it runs, such as a clock hand or a stall's doors, is no part, and nothing below it is either; an object with a component of `BakedSceneryRules.Animators` (a `KeyValueBoolAnimator`) counts as animated in the part rule itself (`BakedSceneryRules.Animates`), and `GroupWorld.Verdicts` collects these transforms once per pass from every such component and every field of `BakedSceneryRules.DrivenFields` (the needle of a `GaugeNeedle`, the filament renderer of a `LanternController`) below a loaded World root, wherever the component stands relative to the transform, and both the part rule and `GroupWorld.Observe` use that one set; `GroupWorld.Observe` marks the transform and everything below it `Animated`, and `GroupChecks.Layout` checks only the identity and activity of such a part, so the hand neither makes the inventory stale nor fails a group's verification or restore. Siblings that share a name are no parts, and neither is anything below them. A culling container is no part, but the objects in it are, at any depth. `GroupWorld.Verdicts` reads the part verdicts together with the group verdicts, one group at a time: a group whose parts cannot be read keeps its root entry without parts, and one developer diagnostic line `Group skipped: <group root>: <reason>` goes to the Player log. The native inventory observes a part through its `UnityEngine.Transform` in the Baked scenery group family, with the structure `baked-scenery-part-v1` when `GroupWorld.PartProblem` finds no refusal, and `SceneObservation.GroupPath` names its group root, so the outliner names the part with its group (`BakedSceneryRules.PartName`). `BakedSceneryParts` in the core applies placement and activity through `GroupWorld`. An edit of a group root or a part moves or switches every part below it, so `NativeInventory.ObserveRelated` returns those parts with the edited object and `SceneInventory.ReobserveRelated` takes their new observations: the edit's own consequence does not mark the inventory stale. A search matches a part by the name its row shows, with its group (`SceneObservation.SearchText`).

## Bind an edit to its inspection

Call `inventory.Pin(entry)` on the inspected entry. This checks freshness and returns an `InspectedTarget`. An edit that runs in the same call uses `PinForEdit`: the pin has just compared the whole scene, so the edit's first validation reuses that comparison, and the guard immediately before the mutation reads the scene again. An edit therefore scans the scene twice, not three times. The panel goes one step further so that an edit does not block: it runs the whole-scene comparison as a stepped pass over frames and then calls `PinAfterPass`, which requires a pass that completed without a difference since the edit was requested. A stepped pass can refuse and cannot vouch for the target at this moment, so the guard still reads the target immediately before the mutation. A scene that implements `ITargetedInspectionScene` lets the guard observe that one object: the object itself is read in the mutation frame, and what other objects say about it, such as the references they hold, comes from the last discovery, which for a panel edit is the pass that ended in the same frame. The engine's guard checks beside it that the identity still resolves to this one object. A scene without that interface is discovered in full. After the edit, `ReobserveRelated` takes the new observations of the edited object and of what belongs with it; every other entry stays as it was compared. A scene that implements `IRelatedInspectionScene` says what belongs with an object: the native inventory returns the observed components of the object's hierarchy, which holds a crossing's lights, gates and bells, and for a crossing the spans the patcher owns in its scene. Those entries are replaced, observations the change created are added, and entries whose object no longer exists are dropped, so a coverage edit that adds or removes owned spans leaves the inventory in agreement with the scene. A scene without that interface re-observes the object alone (`Reobserve`). The same happens after Undo or Redo of the patcher's own steps (`PatchEditingSession.Replayed`) and after a follow update moved an object with its track, so they do not read as foreign changes. A follow outcome carries the object it moved and no identity, so the panel re-observes every entry of that object and reads the inspected one's placement into its fields again. When the snapshot was compared with the whole scene since the native map editor's history last changed by another hand, by a refresh or a completed pass, the panel skips the pass and calls `PinCompared`: it compares nothing, requires a snapshot that is not stale, and its token observes the target at every validation. `PinAfterPass(entry, passes, validateEvery: true)` gives the same token after a pass; a preview, which validates once, needs it to observe the target at all. The Scene patches window passes that token to `PatchEditingSession.Edit`, `Remove` and `Recheck`, which validate it at resolution and again in the guard immediately before the mutation. A completed edit changes the observed values, so the panel refreshes the inventory after it, two frames later so that the result shows first. Pass a dictionary from modification IDs to those tokens to `PatchEngine.Apply(json, scenePatchFileKey, inspectedTargets)`. Every modification in such a call needs its own token, including prerequisites. The `IScene` adapter must also implement `IInspectionScene` so token validation can compare live observations. `IndependentBoards` implements both interfaces.

Token validation checks the loaded map context, object handle, target identity, placement, bindings, dependencies and problems. A position counts as the same within 2 centimetres on every axis: the game keeps positions relative to a moving origin in single precision, so the same map position reads a few millimetres differently after the origin moved. The game shifts only the transforms registered as origin targets, with everything below them. A holder of data outside them, such as `Setups/Starter Equipment Setup` with its track markers, stays where it is in the scene, so the game's map conversion would move its position by whole tiles at every origin move. `MapOrigin.Position` gives the position that stays the same while the origin moves: the scene position less the offset for an object that moves with the origin, and the scene position itself for one that does not. The native inventory observes the latter in scene coordinates and says so in the runtime state; a move of either kind of object still differs. `NativeInventory.MapPosition` and `NativeInventory.ScenePosition` apply this rule and its inverse, `MapOrigin.ScenePosition`, to live positions. Focus jumps to the map position. The generic marker capability reads and writes fixed placement through them, so the placement of a marker outside the origin targets is its scene position at every origin. The transform gizmo stands at its object's marking, the map position at the current origin (`MapOrigin.MarkPosition`), where the world marking and Focus place the object, and shifts with every origin change. For an object outside the origin targets that is not its own scene position; its writes still keep its own rule through the marker capability. The serialized transforms of the starter markers match the track positions of the map's graph directly, so this scene position is the map position. The stale reason names what differs: activity, position, rotation, or the first binding, dependency or problem line that only one side has. A token refusal names the same difference (`SceneObservation.Difference`), as in `Inspected target changed (position); refresh and inspect again`, or says that the target is missing, held by several objects or another object. Rotation stays an exact comparison. A completed gizmo gesture restores its captured placement before it commits the final one, and a native transform can read that placement back one unit in the last place off. `PlacementGesture.Complete` therefore checks the target against what its previews made of it, restores and verifies the placement within the read-back tolerance, and then binds the edit to a token recorded from the target as restored, not to the inspection from before the gesture. An observation also carries runtime state: the enabled flag of each child behaviour, which the game switches while it runs, for example a crossing bell's audio player by distance. A reference to the object from a field Unity does not serialize is runtime state as well: a culling or audio manager's working list starts and stops holding an object when the camera moves or the object is inspected, while a reference in a serialized field is authored scene state and stays a dependency (`ReferenceScan.IsSerialized`). Whether crossing equipment is active in the game is runtime state too: its lights, gates and bells sit under objects that a `GameObjectCuller` switches off when the camera is far away, so a camera jump changes it. The inventory reads every culler's list in its walk over the fields and observes such equipment as active when every object from it upward that no culler switches is switched on (`AuthoredActivity.Of`); switching off the equipment itself, or an object above the culled one, still differs. Runtime state is shown and is no part of the fingerprint, so a change of it alone neither marks the snapshot stale nor refuses an edit. Which components exist remains a dependency, except on a child object the game created while running (`HideFlags.DontSave`), such as the pooled audio sources that the game parents under a crossing bell while it is audible: such a child is runtime state too. It rejects changed, missing or ambiguous observations. Runtime application can use the existing overload without tokens. Every path repeats preflight and unique target resolution after capture and before `IScene.Apply`, and rejects changed map context. A pre-mutation rejection does not request restoration because no mutation has started. Mutation failures retain the existing restoration and guarded-retry rules.

The native Focus action jumps to the map position of the inspected handle as it is now, through the existing game camera-jump route. `FocusTarget.Point` decides that point: a track span's transform means nothing, so Focus lands midway between the map positions of the span's lower and upper track locations that resolve (`NativeTrackPoses.SpanPositions`), and refuses with its reason when neither does. It needs no fresh inventory and scans nothing; it refuses in the message area when the handle no longer exists. It does not change inspected selection or call the application engine. Camera jumps can cause native origin changes; they do not make placement changes.

## Native pointer input

Native pointer input has two separate gates. `UI.GameInput.IsMouseOverUI` checks EventSystem raycasts on `Helpers.Layers.UI` and guards scene patch editing selection and the start of Strategy pan/rotation. Strategy wheel input instead uses `IsMouseOverGameWindow`, then reads raw scroll delta even when `IsMouseOverUI` was true. Product Focus explicitly selects Strategy. Registering only a uGUI raycast region therefore leaves that post-Focus wheel path unguarded.

The `GameInput.ZoomDelta` property checks both gates, but Strategy's input method bypasses that property. `IsMouseOverGameWindow` compares `WindowManager.HitTest` with its optional Window argument; the default query treats a null hit as game input. A native Window hit is therefore distinct from an EventSystem UI hit.

`InspectionInputBlocker` owns a screen-space Canvas and GraphicRaycaster with regions matching the product button and panel. The panel code reports the bounds it drew in each IMGUI event, so the regions follow the button and the panel as they open, close or move; the blocker holds no position of its own. Mod-owned windows stack on the right side of the viewport. The button takes the first slot from the top of the right edge that native chrome does not occupy. A slot is occupied when it overlaps the native Map Editor window, read from its `RectTransform`, or when an EventSystem raycast at sample points in the slot hits a native UI graphic that takes pointer input, such as the upper-right status and icon strip. World raycasts, the patcher's own regions and graphics covering half the screen or more do not count. The search repeats twice a second. Native graphics that take no pointer input are not detected. The toggle and panel colours are readability values, not native styling. The panel first opens right-aligned below the button, at most 700 by 620 pixels and 40 percent of the viewport width with a 360-pixel floor, clamped to the actual viewport; it stays draggable and is not repositioned afterwards. Button and panel are drawn with an opaque backing; the blocker's own regions stay invisible. Fully transparent graphics keep raycasting enabled and transparent-mesh culling disabled. A pointer press inside either region captures the drag through the release frame, including movement outside the panel. The capture region updates before normal input consumers. When idle, only the button and open panel intercept pointer input. Keyboard movement is not globally disabled. A world click for a pending world choice follows the native object picker's gates as well. A press over a popup blocker, such as the one behind an open context menu, is no world click: the blocker checks `GameInput.IsScreenPointOverUI` with popup blockers included while its own shield is hidden. Nor is a press that the native map editor claims through `GameInput.ClaimPrimaryPress`, as `MapEditorController` does for a tool that owns the pointer and `ObjectPicker` does while a transform gizmo is in use. The claim is made after the blocker's `Update`, so the blocker keeps the press as a candidate, reads the claim of the primary press state in `LateUpdate` and publishes an unclaimed press as `WorldClick` in the next frame. A claim counts only when that state started a press this frame: its claim flag is reset only when a press starts, so while a text field has focus and the game's actions are off, the flag still holds the previous press's claim. A problem reading the claim stays in `WorldInputProblem` until the claim reads again. These gates exist since Railroader 0.6.3. World unload or component disable removes the regions from raycasting; the panel draws only while its blocker and the native EventSystem are available.

The blocker also owns one hidden instance of the native manager's `windowPrefab`, parented directly under `WindowManager`. A bare Window component is invalid because its Awake/Start methods require serialized content, drag and resizer references. The prefab's graphics and interaction are disabled. Its native shown state and bounds participate in `WindowManager.HitTest`, which makes the default `IsMouseOverGameWindow` query false. This window boundary is shown only while the pointer is over the product button/panel or captured by a drag. The screen rectangle uses the same bottom-left screen space as native HitTest and accounts for parent canvas scale. Native show/close methods manage visibility. Cleanup closes the active boundary, detaches it from hit-test enumeration, and deactivates it before deferred destruction. No camera controller, movement map or global keyboard flag is disabled.

The isolated native regression must replay panel wheel scrolling after product Focus has selected Strategy, with a stable no-input camera control first. It must also retain the earlier scrollbar/title/outside-release and ordinary outside-navigation checks. Compare native selection and camera state. A core inventory test cannot establish this result.

## World selection

World picking uses the inventory's scene-object positions and the loaded graph's native segment and node IDs. The patcher projects scene and node markings and samples segment curves in the current camera. It uses the current floating origin when projecting. A click offers every matching marking or segment path at the pointer. Distinct overlapping candidates require a separate choice. Confirmation checks map context, source, unique candidate identity, native handle, and observed graph geometry. The in-memory handoff records the confirmed source and target identities and map context. An operation using it still performs its own preflight. The scene objects offered for a choice are the entries of the inventory snapshot, so starting a choice and clicking in the world discover nothing; a snapshot that was never read falls back to a discovery. Confirmation reads the present: a scene that implements `ITargetedSelectionScene` returns every current candidate of one identity (`Find`), which the native scene answers for a scene object by resolving its path and observing each object there, so an object that is gone, changed or ambiguous is refused as a discovery would refuse it, and the refusal names which of those it was. An identity that several objects share is refused with the identity and without a request to inspect or pick the same object again: a patch names its target by that identity and cannot tell the objects apart. A stepped pass replaces what single-object observation uses only when its own walk over the fields completed; a pass whose reference scan was left incomplete by components that came and went would otherwise classify every marker as unsupported for an observation made meanwhile. References held by the patcher's own components are no part of an observation. Confirming a scene object inspects its snapshot entry as it is and reads the inventory again only when the snapshot does not hold the object. The track-marker capability checks a marker against every direct reference in the scene, which is most of a discovery; while a queued panel request runs, or while the snapshot still counts as compared, it uses the reference scan of the last discovery (`TrackMarkerWorld.KnownReferrers`, `NativeInventory.LastReferrers`). Runtime application and the check while a marker is enabled always scan themselves.

The overlay shares projected shapes between drawing and hit testing. Scene objects use their renderer bounds and a 24-pixel square marker. Track ribbons use the native track picker's two-metre radius and a minimum ten-pixel half-width. Curve subdivision targets a one-pixel screen error with a maximum depth of ten. The identity label owns its painted hit rectangle. Markings are clipped to screen regions outside the patcher panel, shown native windows and visible screen-space native controls. Labels use their own opaque backing and the measured 16-pixel native compact text size, with their text colour independent of the marking colour.

A renderer contributes to its object's frame whether or not the game's distance culling shows it now; a renderer or object that the scene or a modder switched off does not (`ObjectMarkingGeometry.Outlines`). Inactive inventory objects retain their explicit marker and label. A combined source label preserves its existing Choice or Candidate role, including when another overlapping object is chosen.

While a choice is pending, the pointer blocker arms a UI raycast region over the world before the primary press. The native UI gate checks cached pointer hover before raycasting again. The blocker checks native UI beneath its own region and removes the region during right or middle button navigation. The existing native Window shield still applies to the product panel and its drags. Markers, object frames and labels use IMGUI. Track ribbons and centerlines use a private alpha-blended triangle material; they do not change scene colliders or scene materials. The selection owner destroys that material when released. The compact entry uses its actual visible graphics for paint and input exclusion; its wider layout slot is used only for placement.

`WorldRibbonGeometry.ProjectCurve` constructs the track corridor with the native world radius and square end geometry, clips it against the camera frustum before perspective division, and retains the minimum ten-pixel footprint around the visible centerline. Picking uses the same projected ribbon triangles. `WorldStrokeGeometry.ClipTriangles` then clips complete triangles against the final UI-excluded screen rectangles. `ScreenRect.FromEdges` keeps the UI producer's exact edges. The renderer draws these vertices in top-left screen coordinates without rotating `GUI.matrix`. Controlled tests use the actual offered/chosen camera and curve captures, off-track world witnesses, projected width and end caps, near/far/edge and degenerate cases, and final UI zones. These tests establish geometry and shared picking, not shader availability, rendered pixels or native input behavior.

## Validation limits

The core executable covers inactive and independent observations, binding/problem search, dependency reporting, stale snapshots and complete scene patch file revalidation. Its Refresh assertions verify replacement with the changed active value, cleared stale state and unchanged source activity, placement and marker binding. Controlled fixtures replace targets during capture and change placement after inspection. A stepped fixture covers changes ahead of and behind an unfinished pass, added, removed and replaced objects, map changes, scan failures, cancellation, refresh during a pass and pinning during a pass. A component fixture that fails when used after it left the scene covers components leaving during a pass, with and without a dependent observation, and the stale reasons. Edit feedback is covered for a stale inventory, a pending interaction, a missing inspection, a failing edit, a refused outcome, unreadable input and completion. The panel's inventory notice is covered for an unscanned, current, stale and missing inventory and for changed definitions alone, where it announces no refusal because `Pin` makes none. The serialized-field rule, a runtime reference that appears after inspecting, the two scans of an edit pinned for immediate use and the guard's refusal of a change after that pin are covered. A runtime toggle is covered to leave the snapshot fresh and pinnable, in the one-call and the stepped check, while a changed component and a changed activity still mark it stale. The outliner rows are covered for the Problems filter alone, cleared, and combined with search, with the count line and the rebuild that a filter change requests. These tests miss the duration of native scan units, native field extraction, rendering, camera movement, input and game lifecycle. A native build checks assembly references only. Live discovery, refresh and focus require separate retained observations; the family routes above and the fixed-placement journey do not establish those runtime results.
