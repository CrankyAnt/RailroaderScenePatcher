# Scene inventory interfaces

`IInspectionScene.Discover` returns copied `SceneObservation` values for loaded objects, independently of patch documents and warnings. Each observation contains an opaque object handle, target identity, family, activity, map-coordinate pose, serialized bindings, dependencies, detected problems and the available operation boundary. A provider must include inactive objects and perform no mutation, registration, cache rebuild or binding repair while observing.

`SceneInventory.Refresh` replaces its snapshot. `Search` matches names, paths, component and family names, activity, bindings, dependencies and problems. `CheckFreshness` compares handles, observation values and map context against a new scan. Any difference or failed scan marks the snapshot stale until explicit refresh. `InspectDocument` reports document errors, source-map mismatch, target matches and missing modification dependencies without applying or rewriting a document. It is an inspection result, not operation preflight.

`StaleReason` holds why the snapshot is stale: the first difference a check found, or its failure. `Pin` puts it in its refusal. `EditFeedback`, a UI-independent part of the panel, runs each edit through `Pin` and leaves the result, with the reason of every refusal and of every edit that did not run, for the panel section of the control and for the log.

`DiscoveryWalk.Steps` holds the order and the pause points of a discovery over components: search, loaded check per component, field reads per owner, classification per component, one observation per candidate. `NativeInventory` supplies the native operations. A paused walk meets components that were destroyed since its search, such as the widgets of a rebuilt panel. The walk checks each component again before it reads, classifies or observes it and skips one that left, as a discovery starting at that moment would not find it. An observation that depended on the component then differs and marks the snapshot stale; a component no observation depends on changes nothing.

`AdvanceFreshnessCheck(more)` makes the same comparison in steps, for a caller that cannot afford one whole scan in a frame. Each call performs at least one unit of the scan and continues while `more()` holds; `CheckInProgress` tells whether a pass is unfinished. A provider that implements `ISteppedInspectionScene` supplies `DiscoverInSteps`: the walk of `Discover`, yielding null wherever it can pause and each observation as it is produced. Any other provider is stepped per observation. A paused pass reads the scene at different times. It therefore only marks the snapshot stale, on a difference, a changed map context or a failure. It replaces no observation, and a pass that finds no difference concludes nothing. `Pin` and `CheckFreshness` still scan the whole scene in one call, so an unfinished pass authorizes no edit. `Refresh` and `CancelFreshnessCheck` end an unfinished pass without a conclusion. The panel advances a pass for three milliseconds per frame while it is open, starts the next pass two seconds after one ends and cancels the pass when it closes. One unit can take longer than that budget: the search for loaded components, one component's fields, one observation with its hierarchy, and the first marker's walk over setup placements are not divided.

`NativeInventory` reads serialized marker and span endpoints and the graph's complete segment lookup, including group-disabled segments. It avoids resolving location/cache getters. Controller circuit roles remain explicit. A direct-reference scan reads loaded component fields and direct list entries; its result does not cover every indirect consumer. Per-object missing fields become visible problems. It uses exact type names and the established bridge roots. New inspection adapters must supply the same observation contract and preserve these limits. See [the coverage reference](../../guides/scene-patches/inspect-scene-objects.md).

The retained bridge construction controller's full type is `Game.Mow.TrackConstructionScenery`. Its `segmentIds` identify graph segments. Each serialized `entries` item supplies `trackConstructionState`, `condition` and `targets`. Reading those nested target arrays is necessary because the controller root can have no children while controlling the bridge's steel and abutments. The [frozen bridge helper](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/5e99c72dee551762316c0b8cf5aafec5bf40b748/Research/SceneOperationBatch/Geometry/BridgeSceneryState.cs#L132-L194) records these members. Inspection reads the fields without invoking construction-state changes or moving the targets.

## Original inventory accounting

The [original scope inventory](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/ScopeInventory.md#L7-L15) and [candidate-family list](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/CandidateFamilies.md#L5-L20) define the source set. The following routes account for that set without treating a source sample as proof of every possible custom hierarchy.

| Source family or case | Inspection or ownership disposition |
| --- | --- |
| Retained whistle/speed/yard-limit/station signs | Typed `TrackMarker` and `TrackRelativePosition`. This covers M5pp, Mm8w, Mwp1 and the Mkwd/Mi4f identities recovered by #20; labels do not determine marker enums. |
| Crossing pads | Typed markers with `TrackCurveMeshBuilder`, including Mg74 and the original M5ib/Muef cases. Generated geometry is a dependency, not an inferred binding. Pads that match `CrossingPadWorld.PadProblem` carry `crossing-pad-v1`; their mesh objects are described by one dependency line through `HierarchyDependencies.Describe`, so culling and regeneration do not change the observation fingerprint. | Independent boards | The identified Sylva culler/mask hierarchy has no invented track binding. #16 separates pose, activity and logical references. Every culler object with a circle mask and no track marker is classified as an independent board; the board capability's `Refusal` supplies its problems. |

## Bind an editor edit to its inspection

Call `inventory.Pin(entry)` on the inspected entry. This checks freshness and returns an `InspectedTarget`. An edit that runs in the same call uses `PinForEdit`: the pin has just compared the whole scene, so the edit's first validation reuses that comparison, and the guard immediately before the mutation reads the scene again. An edit therefore scans the scene twice, not three times. The panel goes one step further so that an edit does not block: it runs the whole-scene comparison as a stepped pass over frames and then calls `PinAfterPass`, which requires a pass that completed without a difference since the edit was requested. A stepped pass can refuse and cannot vouch for the target at this moment, so the guard still reads the target immediately before the mutation. A scene that implements `ITargetedInspectionScene` lets the guard observe that one object: the object itself is read in the mutation frame, and what other objects say about it, such as the references they hold, comes from the last discovery, which for a panel edit is the pass that ended in the same frame. The engine's guard checks beside it that the identity still resolves to this one object. A scene without that interface is discovered in full, as before. After the edit, `ReobserveRelated` takes the new observations of the edited object and of what belongs with it; every other entry stays as it was compared. A scene that implements `IRelatedInspectionScene` says what belongs with an object: the native inventory returns the observed components of the object's hierarchy, which holds a crossing's lights, gates and bells, and for a crossing the spans the patcher owns in its scene. Those entries are replaced, observations the change created are added, and entries whose object no longer exists are dropped, so a coverage edit that adds or removes owned spans leaves the inventory in agreement with the scene. A scene without that interface re-observes the object alone (`Reobserve`). The same happens after Undo or Redo of the patcher's own steps (`AuthoringSession.Replayed`) and after a follow update moved an object with its track, so they do not read as foreign changes. A follow outcome carries the object it moved and no identity, so the panel re-observes every entry of that object and reads the inspected one's pose into its fields again. When the snapshot was compared with the whole scene since the editor's history last changed by another hand, by a refresh or a completed pass, the panel skips the pass and calls `PinCompared`: it compares nothing, requires a snapshot that is not stale, and its token observes the target at every validation. `PinAfterPass(entry, passes, validateEvery: true)` gives the same token after a pass; a preview, which validates once, needs it to observe the target at all. The editor panel passes that token to `AuthoringSession.Edit`, `Remove` and `Recheck`, which validate it at resolution and again in the guard immediately before the mutation. A completed edit changes the observed values, so the panel refreshes the inventory after it, two frames later so that the result shows first. Pass a dictionary from modification IDs to those tokens to `PatchEngine.Apply(json, documentKey, inspectedTargets)`. Every modification in such a call needs its own token, including prerequisites. The `IScene` adapter must also implement `IInspectionScene` so token validation can compare live observations. `IndependentBoards` implements both interfaces.

Token validation checks the loaded map context, object handle, target identity, pose, bindings, dependencies and problems. A position counts as the same within 2 centimetres on every axis: the game keeps positions relative to a moving origin in single precision, so the same map position reads a few millimetres differently after the origin moved. The game shifts only the transforms registered as origin targets, with everything below them. A holder of data outside them, such as `Setups/Starter Equipment Setup` with its track markers, stays where it is in the scene, so the game's map conversion would move its position by whole tiles at every origin move. `MapOrigin.Position` gives the position that stays the same while the origin moves: the scene position less the offset for an object that moves with the origin, and the scene position itself for one that does not. The native inventory observes the latter in scene coordinates and says so in the runtime state; a move of either kind of object still differs. The stale reason names what differs: activity, position, rotation, or the first binding, dependency or problem line that only one side has. An observation also carries runtime state: the enabled flag of each child behaviour, which the game switches while it runs, for example a crossing bell's audio player by distance. A reference to the object from a field Unity does not serialize is runtime state as well: a culling or audio manager's working list starts and stops holding an object when the camera moves or the object is inspected, while a reference in a serialized field is authored scene state and stays a dependency (`ReferenceScan.IsSerialized`). Whether crossing equipment is active in the game is runtime state too: its lights, gates and bells sit under objects that a `GameObjectCuller` switches off when the camera is far away, so a camera jump changes it. The inventory reads every culler's list in its walk over the fields and observes such equipment as active when every object from it upward that no culler switches is switched on (`AuthoredActivity.Of`); switching off the equipment itself, or an object above the culled one, still differs. Runtime state is shown and is no part of the fingerprint, so a change of it alone neither marks the snapshot stale nor refuses an edit. Which components exist remains a dependency, except on a child object the game created while running (`HideFlags.DontSave`), such as the pooled audio sources that the game parents under a crossing bell while it is audible: such a child is runtime state too. It rejects changed, missing or ambiguous observations. Runtime application can use the existing overload without tokens. Every path repeats preflight and unique target resolution after capture and before `IScene.Apply`, and rejects changed map context. A pre-mutation rejection does not request restoration because no mutation has started. Mutation failures retain the existing restoration and guarded-retry rules.

The native Focus action jumps to where the inspected handle is now, through the existing game camera-jump route. It needs no fresh inventory and scans nothing; it refuses in the message area when the handle no longer exists. It does not change inspected selection or call the application engine. Camera jumps can cause native origin changes; they do not author placement changes.

## Native pointer input

Native pointer input has two separate gates. `UI.GameInput.IsMouseOverUI` checks EventSystem raycasts on `Helpers.Layers.UI` and guards editor selection and the start of Strategy pan/rotation. Strategy wheel input instead uses `IsMouseOverGameWindow`, then reads raw scroll delta even when `IsMouseOverUI` was true. Product Focus explicitly selects Strategy. Registering only a uGUI raycast region therefore leaves that post-Focus wheel path unguarded.

The `GameInput.ZoomDelta` property checks both gates, but Strategy's input method bypasses that property. `IsMouseOverGameWindow` compares `WindowManager.HitTest` with its optional Window argument; the default query treats a null hit as game input. A native Window hit is therefore distinct from an EventSystem UI hit.

`InspectionInputBlocker` owns a screen-space Canvas and GraphicRaycaster with regions matching the product button and panel. The panel code reports the bounds it drew in each IMGUI event, so the regions follow the button and the panel as they open, close or move; the blocker holds no position of its own. Mod-owned windows stack on the right side of the viewport. The button takes the first slot from the top of the right edge that native chrome does not occupy. A slot is occupied when it overlaps the native Map Editor window, read from its `RectTransform`, or when an EventSystem raycast at sample points in the slot hits a native UI graphic that takes pointer input, such as the upper-right status and icon strip. World raycasts, the patcher's own regions and graphics covering half the screen or more do not count. The search repeats twice a second. Native graphics that take no pointer input are not detected. The toggle and panel colours are provisional readability values, not native styling; see the native UI convention findings when they are recorded. The panel first opens right-aligned below the button, at most 700 by 620 pixels and 40 percent of the viewport width with a 360-pixel floor, clamped to the actual viewport; it stays draggable and is not repositioned afterwards. Button and panel are drawn with an opaque backing; the blocker's own regions stay invisible. Fully transparent graphics keep raycasting enabled and transparent-mesh culling disabled. A pointer press inside either region captures the drag through the release frame, including movement outside the panel. The capture region updates before normal input consumers. When idle, only the button and open panel intercept pointer input. Keyboard movement is not globally disabled. World unload or component disable removes the regions from raycasting; the panel draws only while its blocker and the native EventSystem are available.

The blocker also owns one hidden instance of the native manager's `windowPrefab`, parented directly under `WindowManager`. A bare Window component is invalid because its Awake/Start methods require serialized content, drag and resizer references. The prefab's graphics and interaction are disabled. Its native shown state and bounds participate in `WindowManager.HitTest`, which makes the default `IsMouseOverGameWindow` query false. This window boundary is shown only while the pointer is over the product button/panel or captured by a drag. The screen rectangle uses the same bottom-left screen space as native HitTest and accounts for parent canvas scale. Native show/close methods manage visibility. Cleanup closes the active boundary, detaches it from hit-test enumeration, and deactivates it before deferred destruction. No camera controller, movement map or global keyboard flag is disabled.

The isolated native regression must replay panel wheel scrolling after product Focus has selected Strategy, with a stable no-input camera control first. It must also retain the earlier scrollbar/title/outside-release and ordinary outside-navigation checks. Compare native selection and camera state. A core inventory test cannot establish this result.

## World selection

World picking uses the inventory's scene-object positions and the loaded graph's native segment and node IDs. The editor projects scene and node markings and samples segment curves in the current camera. It uses the current floating origin when projecting. A click offers every matching marking or segment path at the pointer. Distinct overlapping candidates require a separate choice. Confirmation checks map context, source, unique candidate identity, native handle, and observed graph geometry. The in-memory handoff records the confirmed source and target identities and map context. An operation using it still performs its own preflight. The scene objects offered for a choice are the entries of the inventory snapshot, so starting a choice and clicking in the world discover nothing; a snapshot that was never read falls back to a discovery. Confirmation reads the present: a scene that implements `ITargetedSelectionScene` returns every current candidate of one identity (`Find`), which the native scene answers for a scene object by resolving its path and observing each object there, so an object that is gone, changed or ambiguous is refused as a discovery would refuse it, and the refusal names which of those it was. An identity that several objects share is refused with the identity and without a request to inspect or pick the same object again: a patch names its target by that identity and cannot tell the objects apart. A stepped pass replaces what single-object observation uses only when its own walk over the fields completed; a pass whose reference scan was left incomplete by components that came and went would otherwise classify every marker as unsupported for an observation made meanwhile. References held by the patcher's own components are no part of an observation. Confirming a scene object inspects its snapshot entry as it is and reads the inventory again only when the snapshot does not hold the object. The track-marker capability checks a marker against every direct reference in the scene, which is most of a discovery; while a queued panel request runs, or while the snapshot still counts as compared, it uses the reference scan of the last discovery (`TrackMarkerWorld.KnownReferrers`, `NativeInventory.LastReferrers`). Runtime application and the check while a marker is enabled always scan themselves.

The overlay shares projected shapes between drawing and hit testing. Scene objects use their renderer bounds and a 24-pixel square marker. Track ribbons use the native track picker's two-metre radius and a minimum ten-pixel half-width. Curve subdivision targets a one-pixel screen error with a maximum depth of ten. The identity label owns its painted hit rectangle. Markings are clipped to screen regions outside the patcher panel, shown native windows and visible screen-space native controls. Labels use their own opaque backing and the measured 16-pixel native compact text size, with their text colour independent of the marking colour.

Only enabled renderers whose objects are active in the hierarchy contribute expanded object rectangles. Inactive inventory objects retain their explicit marker and label. A combined source label preserves its existing Choice or Candidate role, including when another overlapping object is chosen.

While a choice is pending, the pointer blocker arms a UI raycast region over the world before the primary press. The native UI gate checks cached pointer hover before raycasting again. The blocker checks native UI beneath its own region and removes the region during right or middle button navigation. The existing native Window shield still applies to the product panel and its drags. Markers, object frames and labels use IMGUI. Track ribbons and centerlines use a private alpha-blended triangle material; they do not change scene colliders or scene materials. The selection owner destroys that material when released. The compact entry uses its actual visible graphics for paint and input exclusion; its wider layout slot is used only for placement.

`WorldRibbonGeometry.ProjectCurve` constructs the track corridor with the native world radius and square end geometry, clips it against the camera frustum before perspective division, and retains the minimum ten-pixel footprint around the visible centerline. Picking uses the same projected ribbon triangles. `WorldStrokeGeometry.ClipTriangles` then clips complete triangles against the final UI-excluded screen rectangles. `ScreenRect.FromEdges` keeps the UI producer's exact edges. The renderer draws these vertices in top-left screen coordinates without rotating `GUI.matrix`. Controlled tests use the actual offered/chosen camera and curve captures, off-track world witnesses, projected width and end caps, near/far/edge and degenerate cases, and final UI zones. These tests establish geometry and shared picking, not shader availability, rendered pixels or native input behavior.

## Validation limits

The core executable covers inactive and independent observations, binding/problem search, dependency reporting, stale snapshots and complete-document revalidation. Its Refresh assertions verify replacement with the changed active value, cleared stale state and unchanged source activity, placement and marker binding. Controlled fixtures replace targets during capture and change pose after inspection. A stepped fixture covers changes ahead of and behind an unfinished pass, added, removed and replaced objects, map changes, scan failures, cancellation, refresh during a pass and pinning during a pass. A component fixture that fails when used after it left the scene covers components leaving during a pass, with and without a dependent observation, and the stale reasons. Edit feedback is covered for a stale inventory, a pending interaction, a missing inspection, a failing edit, a refused outcome, unreadable input and completion. The panel's inventory notice is covered for an unscanned, current, stale and missing inventory and for changed definitions alone, where it announces no refusal because `Pin` makes none. The serialized-field rule, a runtime reference that appears after inspecting, the two scans of an edit pinned for immediate use and the guard's refusal of a change after that pin are covered. A runtime toggle is covered to leave the snapshot fresh and pinnable, in the one-call and the stepped check, while a changed component and a changed activity still mark it stale. The outliner rows are covered for the Problems filter alone, cleared, and combined with search, with the count line and the rebuild that a filter change requests. These tests miss the duration of native scan units, native field extraction, rendering, camera movement, input and game lifecycle. A native build checks assembly references only. Live discovery, refresh and focus require separate retained observations; source-based family accounting and the prior fixed-placement journey do not establish those runtime results.
