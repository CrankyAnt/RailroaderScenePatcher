# Record the native fixed-placement journey

The patcher applies its scene patch files in its own world-load callback, which the game calls before the observer's, because the observer depends on the patcher. The traces captured since the last world unload therefore belong to the load that follows: the observer's world-load callback gives them that load's `sourceLoadId` and `sourceLifecycle: active-world`, marks them `assignedAtWorldLoad: true`, and they emit as `attempt-trace` once the observer is ready. `TraceLoad` in `Observation.cs` makes that assignment and picks the event; it uses no Unity type, so a recorded `observations.jsonl` can be replayed through the built assembly outside the game. A world unload drops the traces still buffered. A buffered trace whose load ID is not the current one, as after a second world load without an unload, emits as `unassigned-attempt-trace` and stays out of active-world counts. A deliberate replay after observer readiness measures same-engine retries.

This test-only mod records observations for the fixed-placement fixture. It does not install itself or start the game. Build it against the installed game assemblies, placing all build outputs outside the repository:

```powershell
dotnet build Tests/NativeObservation/NativeObservation.csproj -p:GameManaged='<Railroader_Data/Managed>' -p:BaseIntermediateOutputPath=C:/TMP/Issue39ObservationBuild/obj/ -p:OutputPath=C:/TMP/Issue39ObservationBuild/bin/
```

A later authorized test must install `NativeObservation.dll` and `Info.json` in `C:/TMP/RailroaderMapResearch/RuntimeHome/Mods/Issue39Observation`. The observer checks the sole `-homedir` argument and its mod directory before recording or exposing controls. It writes `Evidence/<loadId>/observations.jsonl` under that mod directory on any map in the isolated home, with the `world-ready` event and the attempt traces. Each row's `mapId` names the loaded map; `world-ready` also records `fixtureMap` and the patcher's `engineRuntimeId`, which `Tests/FixedPlacementJourney/Summarize-Attempts.ps1` takes as its `-EngineRuntimeId`. Snapshots, tile events, focus, replay and the trace-stage snapshots need active map `crankyant/fixed-placement-fixture-map`; on another map they record nothing, and a click on their buttons records an error. The observer creates a fresh load ID for each world load. Preserve the complete evidence directory with the corresponding build and fixture provenance.

Use the explicit baseline, after and restoration snapshot buttons at the intended phases. A successful snapshot contains one unique Sylva location sign in BushnellWhittier-MapManager, origin conversion, the T-47 marker and graph registrations, culler token and sphere, mask modifier descriptors and targets, and terrain pending/idle state. A `snapshot-error` means that phase is incomplete. `OnTileBuilt` events contain native map-coordinate bounds. JSONL rows carry schema and evidence kind, event sequence, load ID, frame, UTC, process ID, and SHA-256 hashes of the loaded Railroader, observer and patcher assemblies. Startup attempt traces can precede observer readiness; buffered rows retain their original `sourceFrame`, while their sequence identifies when they were written. Trace capture requires the patcher's debug option to be on. The patcher writes each `Attempt trace:` line as a debug line only while that option is on, and the observer reads those lines from the game's log. `Tests/FixedPlacementJourney/TestHome.ps1` installs `Tests/FixedPlacementJourney/DebugSettings.json` as `Mods/Issue39ScenePatcher/settings.json` in the test home, which starts the option on. The journey uses the normal patcher build, not a separate instrumented one. The observer does not patch native methods.

The replay button explicitly calls the current patcher application callback once and records whether the engine reference stayed the same. It is a diagnostic action, not a native world reload. The observer also takes snapshots on the mutation, applied, restore-request and restore-result trace stages while it is ready. Buffered startup traces cannot recover an earlier snapshot. Capture the baseline in an unmodified fixture session with the patcher engine loaded before generating the test scene patch file. The generator produces `Baseline.json`; copy it to the observer mod through the test-home preparation command. Its shape is `{ "schemaVersion": 1, "snapshot": <selected baseline JSON object> }`. On later loads the observer validates its identity and uses its location sign's map position for both tree sample regions. It records the original process, load, graph, scene and location sign identities in `referenceSource`. An invalid file is reported in `referenceError` and `measurementErrors`; its presence disables baseline recapture. Snapshot methods do not set object placements, activity, hierarchy, graph registrations, masks or terrain. The explicit replay control can change targets through production application. Focus board and Focus T-47 move the native strategy camera and can trigger floating-origin movement. Snapshot labels are operator claims, not proof that application or restoration occurred. Compare state and trace events and inspect errors before drawing a conclusion. The probe was used in an isolated Railroader 0.6.2 build 26335745 journey. Snapshot labels alone remain insufficient evidence; compare the recorded placements, registrations and terrain state. Generated-tree samples count and hash native array entries within 20 m of the baseline position and baseline plus 5 m, and record the native handoff and loaded array relationships. They also record interpolated map height at each sample point. They do not inspect the complete heightmap or rendered pixels.

## Culling readout

The **Culling readout** window works on any map in the isolated home. It checks the sole `-homedir` argument and the observer's mod directory, not the fixture map. Enter the path of a top scene object, such as `World/Large Scenery/Whittier/Whittier Saw Mill`, and a label for the phase, then click **Culling readout**. Each click appends one row to `Evidence/culling/readout.jsonl` under the mod directory.

The **Collider readout** button in the same window uses the path and pad marker ID already entered. It appends one row per `Collider` below the target to `Evidence/culling/colliders.jsonl` under the mod directory, including disabled colliders, or one `no-colliders` row when there are none. Each row carries the `event`, `index`, object `path`, component `type`, `enabled`, `isTrigger`, `activeSelf`, `activeInHierarchy`, the attached `rigidbody` (path, instance ID, `isKinematic`, or null), and world `bounds` as `center` and `size`, with the readout's `sequence`, `label` and `padMarkerId`. The window shows the readout number and the collider count.

A row holds the camera's map position and its distance to the complex. For each simple, renderer and game-object culler in the complex it holds the radius the scene gives it, the center and radius of the sphere it holds, and its visibility or culling state. For a simple culler it also names the handler on its culling group. For each own sphere of a moved child object it holds the ID, the child object, the center in map coordinates, the radius, whether it waits for a game culler, whether it shows the child object, and the enabled state of the child object's renderers. `gameObjectCullers` lists every game-object culler of the loaded scenes with the path of each object in its `gameObjects` list, and `handedOver` lists the objects the patcher took out of such a list for a moved child object. The `activity` list gives `activeSelf`, `activeInHierarchy` and the patcher's desired value for the top scene object and every object below it, up to 600 objects. An object between the top scene object and a moved child object with its own sphere also lists the components directly on it.

## Crossing span readout

The **Crossing span readout** button in the same window reads the detection spans of a grade-crossing controller. Enter the path of the controller or of a complex that holds exactly one, such as `World/Large Scenery/Bryson/Grade Crossing - Bryson Everett`, and a label, then click the button. Each click appends one row per circuit role (`approachA`, `island`, `approachB`) to `Evidence/crossing/spans.jsonl` under the mod directory, and the window shows the number of spans and circuits.

A row holds the controller path, the circuit index, the role, and for the span its `id`, path and the game's `IsValid`. For each end, `lower` and `upper`, it holds the stored segment ID, end and distance, the segment's length (`TrackSegment.GetLength`), whether the end is valid, the end's position, and the clamped distance and position. Each position is given as `mapPosition` and as `scenePosition`. A position the game cannot compute is recorded as `positionError` or `clampedPositionError`.

The readout never calls `TrackSpan.Length`, because that getter builds the span's cached route when the cache is empty. Instead it records two routes:

- `cachedRoute`: the route the running game uses, read from the span's cache fields as they are. `present: false` means the cache is empty, and the game builds it at its next read. Otherwise the row holds the cached length, which is the value `Length` returns, its point count, and its segments with their current lengths. After a native Move Node this route can be stale until a span end is set or the world loads again.
- `currentRoute`: the route the game would build now. The readout makes the same call as the span, `RouteSearchPoints.FindPoints` from the clamped ends with a 10 m step, into lists of its own, and sums the distances between the points as the span does. It holds that length, the point count, `noRoute` and the segments with their lengths. When the search fails, the game logs `<span name>: Search failed`, as it does for the span itself.

`unchanged` is true when the span's stored ends and its cached route (points, segments and length) are the same after the readout as before it. Reading a segment's length can build that segment's curve cache. That cache holds no span state, and the game rebuilds it the same way on its next read. The readout writes nothing to the span, the controller or the graph.
