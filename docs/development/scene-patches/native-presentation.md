# Present scene patch editing feature content

`PatcherBehaviour.DrawWindow` in `ScenePatcherLayout.cs` builds Inspector mode: the outliner column beside the inspector column with a draggable divider between them. The command band is split at that divider: each column starts with its own band (`DrawLeftBand`, `DrawRightBand`), so each band is as wide as its column wherever the divider stands. `NativePresentation` owns the entry icon, the visible window, its placement, refresh scheduling and disposal. The patcher's state for a world outlives a world unload; the window does not. `PatcherBehaviour.EndAttempt` disposes the presentation with its entry icon and title-bar help button and ends the requests that waited on the scene, and `Attach` builds a new presentation when the next native map editor appears. `BeginAttempt` starts the panel's own state over for the new load attempt: the inventory, what was read and compared, the messages and any open form. Keep the feature's operation and error handling in its existing owner.

Every region has a fixed height or scrolls inside its own rectangle, so showing or hiding text or feedback moves no other control. The footer reserves 104 canvas units for messages in Inspector and Guided, and 64 in Version choice, Repair and Import. The viewport keeps that height when the messages change, including when it is empty. With automatic viewport expansion disabled, explicit stretch anchors give that viewport its available width, excluding the scrollbar. The native vertical layout then gives each message its wrapped text height. At the minimum window height of 470 canvas units, the recorded native layout uses about 249 units for the frame, headers, spacing, action rows and resize grip clearance. The 104-unit message viewport leaves about 117 units for the tab viewport, above its 100-unit minimum. Keep these rectangles when adding content.

- Give a row a fixed height (`Height`) and a one-line text an ellipsis (`Line`), with the complete text in its tooltip.
- Never show or hide a control on a state change. Keep it in place and disable it with the reason in its tooltip.
- Put text of varying length inside a tab body, the session details or a help view, which scroll.

Add feature content to the place its meaning names:

- What the object is, its enabled state and what was detected about it: `DrawObject`.
- A way to put the object somewhere: a mode of `DrawPlacement`, with its fields in the body.
- A binding or another relationship of the object, such as Track binding or a crossing operation: a section of `DrawConnections`.
- What the edited mod changes on the object and what that change still awaits: `DrawChanges`.
- A command for the inspected object or the world: `DrawRightBand`, which holds Select in world, Focus, Clear and Copy ID. Clear ends the inspection through `ClearInspection` and is disabled only when nothing is inspected and no world choice is pending (`CommandBand.Clear`). A window command, Session details or Reset layout, is an icon in the title bar. A status of the session: a lamp in `DrawLeftBand`, beside Refresh. The first lamp reads Stale when the inventory snapshot no longer matches the scene or when the supplied definitions changed, each through something the panel did not do itself. `SuppliedDefinitions` holds the scene patch files the last refresh read and compares the scene patch files on disk with them every two seconds: a scene patch file edited, added or removed outside scene patch editing marks them stale until Refresh. The patcher's own Save does not: `ModStorage.WriteScenePatchFile` reports the text it wrote once that text has replaced the file (`ModScenePatchFiles.Written`), and that text becomes what later comparisons expect. State that belongs to the session and not to one object goes into `DrawSession`, which the Session details icon in the title bar opens.

The decisions of the band that need no game live in `CommandBand.cs`, which the core tests compile: a status lamp's word, colour and reserved word, whether the lamp words fit the left band, why a command is disabled, the markers of an outliner row and the state-line badges. A tooltip of a control that cannot be used is only its short reason as a sentence, without a prefix (`CommandBand.Tooltip`): the description of what the control does applies only while it can be used, and the tooltip's title names the control; `CommandBand.Sentence` gives that reason, like the editing message (`CommandBand.EditReason`) and a binding that cannot be set, as one plain sentence without its own label such as `Not editable:` or `Track binding unavailable:`. The outliner lists its rows in one tree, by category or by place, in the alphabetical order of their names and then their paths (`OutlineTree`, `OutlineTree.NaturalComparer`). A row gets its full name. A row of added equipment is fitted to the width its cell has: only when the full name doesn't fit is the source name shortened before `(added: <Equipment ID>)`, which stays readable (`InventoryPresentationState.FittedRow`, `OutlineNameFit`). The cell is fitted again when the list reuses it or the divider changes its width. A lamp is a round image and a word without a frame, both in the lamp's colour; it has no button component, and its tooltip gives the reason. The word's rectangle has a fixed width that holds the lamp's longer word (`CommandBand.InventoryWord`, `CommandBand.SaveWord`), so the other word takes its place without moving anything. The band's widths are constants in `CommandBand`, and whether the words fit is decided from them before the band is built (`CommandBand.WordsFit`): a text measured while the band was being built, before its first layout, gave widths under which the words never showed. Refresh and both lamps with their words need 251 units, the three items and the row's three spacings, and the outliner is never narrower than 296; each lamp also keeps its own width, so a row short of room cannot pull it towards Refresh. When a band cannot hold them, each lamp keeps its dot. The tooltip sits on the dot and on the word themselves, is titled with the state word and starts its text with it (`CommandBand.LampTooltip`). The game shows the tooltip of the first object under the pointer that is on the UI layer (`GameInput.IsMouseOverUI`): an object the mod creates itself, as the dot is, must be on that layer, because a stack the builder makes is on the default layer and an object that takes its parent's layer is skipped. A disabled command stays in place with its reason: Select in world only while a world choice is pending, Focus and Copy ID only when nothing is inspected. The object's name takes its whole row and is shortened when the row is too narrow. The tooltip holds the full path for other objects and the full display name for added equipment. The Inspector and Guided segmented control occupies the right end of the row, and the name gives way to it when shown. The name has a LayoutElement with zero minimum and preferred width, flexible width 1 and layout priority 2, so its text cannot push the switch.

An outliner row carries `!`, `*` or `×`, and `+` before its name (`CommandBand.RowMarkers`); `×` (U+00D7, `#FF8080`) replaces `*` while this mod's modification of the object is not applied (`CommandBand.ShownFailure` and `PatchEditingSession.NotApplied`), and an `x` is the documented fallback if a game font lacks the glyph: the native outline appends ` *` and ` +`, and the panel puts them first so that a name that is cut off keeps them. The state line shows the native map editor's badges `* CHANGED` and `+ ADDED`, or the panel's own `× REFUSED` and `× NOT APPLIED` in `#FF8080` instead of `* CHANGED`, bold, in capitals, at 90 percent of the line's size (`CommandBand.Badge`). The badges and the problem count lead the line, before the family, **Inactive** and **Inspection only** (`CommandBand.StateParts`): the line ends in an ellipsis beside the Inspector and Guided switch, so a narrow line cuts the family's end, never a badge. `*` never means unsaved, and the window's title carries no `*`: unsaved work shows only in the Saved or Unsaved lamp. `IsAdded` identifies the Added light or gate and Added bell families.

A control sits where its scope is. The actions of a tab stand in a pinned row at the bottom of its tab body (`Tab`, `TabActs`), below the scrolling part and inside the tab, just above the footer's divider; the row has a fixed height and exists on every tab, so the scrolling part has the same rectangle whatever the tab shows. The footer is the same on every tab: the message area, then one row with the actions on the inspected object that belong to no tab, Remove modification and Recheck (`FooterActs`). Enable or Disable and Clear activity stay together on the Object tab, and Retry for terrain output on Changes. Both rows are drawn by `ActionRow`. The footer's row is the window's last row and stands at its lower edge, on the native padding below the last row. Its buttons start at the left, so the native resize grip in the lower right corner covers only the row's empty end. The message area is 124 units high in the inspector and 84 beside the file panel (`InspectorMessageHeight`, `FilePanelMessageHeight`). A native compact button sizes itself to its text through its content size fitter, and every button of the panel keeps that size: its label and 6 units of padding on each side. Only a button whose label changes in place, such as Disable and Enable, gets the width of its widest label (`FitButton`), so the change moves no control. The rule and its call sites are under Shared rules below. Keep the description of a control at the bottom edge to one line: the native tooltip opens below the pointer. A disabled control keeps that description and adds its reason on a line that starts with "Unavailable:" (`CommandBand.Tooltip`), in the band and in the footer. An action slot is a label, a tooltip, the reason the action cannot run now, or null, the action, and optionally a longer tooltip title and the other label the button changes to. Name a control that takes something back by what it takes back: Clear activity, Clear binding, Clear circuit, Discard for a prepared snap, Remove modification. No tab holds a bare Clear. A slot does not carry the name of its mode: the Follow mode starts following with Start. The Gizmo mode has a Move and Rotate switch in the tab body, Move first (`gizmoTool`), disabled with its reason while a world choice is pending, and no action: the gizmo stands on the object while the mode is open (`ArmGizmo`), and choosing the other tool changes it at once (`GizmoController.SetMode`). A pending world choice takes the footer's row over with Confirm, Cancel, Focus and Details; a gizmo takes it only during a drag, with Cancel. A gizmo that merely stands leaves the row as it is. While a choice is pending, every control of the tab is disabled with that reason (`ChoiceBlock`); the fields stay as they are. The fourth slot of a pending choice is Details. It shows only the clicked candidate's identity and details, in the message area below the candidate line (`candidateDetails`), and is disabled until something was clicked (`CommandBand.CandidateDetailsReason`). It never opens the session details: two controls do not show the same thing, and the tab body is for tabs. The session details open from their title-bar icon alone, in a native builder window of their own (`SessionDetailsWindow`, `NativePresentation.ToggleDetails`), which the game saves under its own key, which opens beside the panel the first time and which closes with the panel. They hold only session state the panel shows nowhere else (`DrawSession`): the candidates of a world choice, the inventory status, the edited mod's scene patch file with a failed Save or incomplete operation, the supplied definitions and diagnostics. The messages and the reasons of the lamps are not repeated there. Their World choice section (`DrawChoice`) lists the other candidates, with Choose buttons labelled by `CommandBand.ChoiceLabel`, which leads with the name that tells a candidate from the others. For added equipment, shortening the name keeps `(added: <Equipment ID>)` at the end. Starting a choice changes no view. The supported-edits text of an object of a supported family that cannot be edited lists each edit it holds back under "Unavailable:", with its reason (`SupportedEdits.Lines`, `CommandBand.NotEditable`). That wording keeps clear of "Inspection only", which names the state of an object whose kind has no edit yet; such an object carries its reason in `SceneObservation.InspectionOnly` (`CommandBand.NotYetSupported`). A group left out under a settled rule, such as one that holds track markers, has no edit coming: its reason reads "Not editable as a group:" instead (`CommandBand.GroupInspectionOnly`). The world marks the track the inspected object follows in green, as a confirmed relation, also during a pending choice: `MarkFollowed` reads the followed element from the scene patch file when the inspection or the native map editor's history changes, and `SpatialSelection.Followed` rebuilds its marking from the graph element a few times a second, after one lookup by ID. The footer reserves the height of the message area above the action slots. It is a native scroll view of that height: its entries stack from the top without gaps, each as high as its wrapped text (`MessageSlot`), the viewport cuts off what does not fit, and the rest is reached by scrolling. Do not replace it by a stack of fixed height: a layout group that has less room than its entries need squeezes them below their text, and the text of one entry is drawn over the next. The first line says what the window waits for or why the open tab cannot edit, when there is such a state: a pending world choice with its candidate, the gizmo hint, a prepared snap, a confirmed identity, or `EditBlock`. The confirmed identity shows until an edit uses it: Start following, Set binding, a snap's Apply and a coverage Apply pass `consumes` to `Edit`, and a completed one clears the confirmation (`SpatialSelection.Consume`). Below it come `EditFeedback.Messages`: the action result and, above it, the latest follow-up. A new result replaces earlier results. A Gizmo result keeps the previous Copy ID result below it. A result has the scope of its place. The result of a tab's own action goes when the view it was reported in changes (`EditFeedback.View`, keyed by tab and placement mode). The result of a general place (`EditFeedback.GeneralPlaces`: the footer's Modification, Copy ID and Fit) stays through that change. Every result goes when another object is inspected and when the native map editor's history moves by a native edit, Undo or Redo (`EditFeedback.HistoryMoved`): "Enable completed" is not true after Undo. A refusal reported after the inspection was cleared is kept until an object is inspected again (`Message.Kept`). Give a new place its scope when you add it. Results do not repeat where Undo, Redo and Save are; the first anchor of the outliner says that once. An action that only opens a form, such as Add detection, reports that, for the same reason, and the row is withdrawn when the form closes (`OpenedForm`, `EditFeedback.Withdraw`). A completed preview is a result as well, so it leads an earlier preview refusal. The text stops 4 units short of the area's right edge: the native scroll view lets its viewport run 3 units under its scroll bar. A follow-up is a consequence that arrives by itself after a result, such as terrain output after an activity edit; report it with `Follow`, which replaces the follow-up before it and never a result, and report the result of an action the user selected with `Report`. Every line starts with its source in bold, one space before its text. The text names no label of its own after that source, in the footer or the log line: a result that begins with its source drops it (`CommandBand.WithoutSource`), and an unchanged result is a plain sentence (`CommandBand.EditResult`). A result's source is the place it was reported to, so name a place as the modder knows the action group: Placement, Enabled, Track binding. A tab switch changes `inspectorTab`, which is part of the content snapshot, so the footer follows the tab. An object without an editable binding names its own detected reason on the binding's slots and fields (`BindingUnavailable`), before the general reason it cannot be edited. The outliner width is stored in the game's preferences under the window's key, beside the bounds the native window saves there; nothing is written through Unity's `PlayerPrefs`, which is the registry key the user's normal play shares. After a world choice is cancelled nothing counts as confirmed (`SpatialSelection.Confirmed`). The Connections tab serves three structures with the same fields and slots where they apply: the track binding of a generic track marker, the binding of a crossing pad, whose section is titled Crossing pad binding and whose Detach slot is disabled with its reason, and the coverage of a crossing.

Each region has help in the `Help` table: an introduction, short terms and guide links. Each `?` sits in the region it explains, names its scope in its tooltip and keeps its glyph while help is open (`HelpButton`). A `?` opens its region's help in the help window (`HelpWindow`, `NativePresentation.ToggleHelp`): one native builder window, separate from the panel and movable, which shows the region of the `?` that was selected last (`HelpRegion`). It replaces nothing in the panel, so the outliner's anchors and the tab's content stay in view. After its content is laid out, two frames later, `SizeHelp` makes it as high as that content, within the screen's height less a margin, and places it beside the panel, never over it (`PanelPlacement.HelpPlace`, `Beside`): right of the panel where the screen has room, else left of it, its top a margin below the screen's top. Every help opens with the same width and at the same place, whichever `?` opens it; only its height follows its content. It never covers the native Map Editor window's title bar (`MapEditorTitleBar`, the chrome's `Title Bar`): a help whose place would cover it starts below it, and its content takes the height left there and scrolls (`PanelPlacement.Beside` with a title bar). A UI scale change sizes and places an open help again. Every mod scroll view gets the game's wheel step, 20 units per notch on Windows (`CommandBand.WheelStep`), also when the game's `ScrollRectSettingsApplicator`, which sets it only in its `Start`, does not run for it. Where the wheel's event does not reach the view, as in the outliner's help at UI scale 1.25, `WheelFallback` takes the step itself: after every Update, when the pointer's topmost object belongs to the view, the wheel turned and the view did not move that frame, it moves the content within its measured height (`CommandBand.WheelOffset`). The first time it does so for a view, it writes one debug line naming the object under the pointer and the handler the event went to. Its content is 610 wide, which makes the window 634 with its frame (`PanelPlacement.HelpSize`, `HelpWidth`). Content that doesn't fit the screen takes the screen's height, and its scroll view shows the rest from the top. It closes with the `?` of its region, with its own close button, with the panel, and, for the help of a tab, when another tab opens (`CommandBand.ClosesHelp`, `CloseHelp`). A closed native window stays in the UI tree, so the help window is removed on the tick after it closed (`RemoveClosedHelp`) and made again when a `?` asks for it. The title bar holds, left of the close button and from right to left, the window's `?`, the Reset layout icon and the Session details icon (`AddTitleHelp`, `TitleIcon`): native compact buttons without their face (`BareTitleButton`) in the close button's parent, placed from the close button's rectangle, each a bare glyph in the close glyph's colour and named in its tooltip. The game's assets were searched by name for sprites to use: of the icon sprites only `GearIcon` and `LocateIcon` exist, none for a reset or for details, so `ResetGlyph` draws a round arrow and `DetailsGlyph` a page. The page is brighter while the session details are open. The whole-window help starts with the Scene Patcher help heading. When the title bar cannot take the `?`, `TitleHelpProblem` says why and the right band holds a `?` after Copy ID; when it cannot take an icon (`TitleReset`, `TitleDetails`), `TitleIconProblem` says why, the Player log names it with Debug logging on, and the window's help holds a button for it. The first row of a tab body also holds the tab's description. After the native tab strip is built, each tab title gets 8 units of padding and an ellipsis for a strip that is too narrow; the four titles are never renamed. A help term is a field caption above its explanation, and a section heading in a tab is bold body text under a rule (`Section`): the native section header has the small capitals of a field caption, and two of them in a row read as an empty section. Add a term when a feature needs explaining, in the tone of a native tooltip, and put a standing explanation in the panel only where an action needs it.

Status colors are the native map editor's: `#FF8080` for a problem or failure, `#E8A33D` for changed, stale or blocked, `#7FB86B` for completed or confirmed, and `#4DCCFF` for a proposed target. Use `Tint` with the constants `Red`, `Amber`, `Green` and `Blue`. World markings use the same meanings through `WorldSelectionOverlay`: gold frames the inspected object, one frame per object; blue marks the chosen candidate; green a confirmed relation; the inspected object has no world label, so its detected problems show in the panel; other choices are neutral. Amber never appears in the world. `ObjectMarkingGeometry.Frame` in the core decides an object's frame, which drawing and picking share, for the gold frame and for candidates alike. The overlay passes every renderer that outlines its object (`ObjectMarkingGeometry.Outlines`): one that shows, and one that the game's distance culling hides now. That is a renderer that a `Helpers.Culling.RendererCuller` or the builder of a curve mesh, such as a crossing pad, holds and has switched off, or a renderer below an object that own culling, a simple culler on it or a game-object culler that lists it switched off, whether that game-object culler stands on the object, on an object above it, such as a crossing root, or in its complex (`GroupWorld.OffThroughCuller`, `CullingActivity.OffThroughCuller`, `MarkingLink`). A frame and its marker therefore do not change with camera distance or culling. A renderer or object that the scene or a modder switched off does not count. The overlay passes the renderer's world-aligned box and, for a mesh renderer, the corners of the box that follows its mesh's points (`RendererBoxes`: a `BoxAlongBuilder` over the mesh vertices in the mesh's own space, kept per mesh with its point count and bounds, so a rebuilt mesh is read again unless it keeps both), so a mesh built along a curve in axes of its own, such as a crossing pad, is framed along its track; where the points cannot be read, the corners of its oriented mesh box (`MeshFilter.sharedMesh.bounds`). A static-batched renderer whose combined mesh can be read is framed by the box that follows its own submeshes' points, placed where its world box stands and kept in its object's own space. The point list of each combined mesh is read once for all its parts and kept up to two million points. Points are read within the overlay's share of each frame: in parts of 4096, and the bulk read of a mesh's point list only as the first read of a frame, so the first view of an area builds up over some frames. Where the game build does not expose a part's place in its static batch (the engine's internal `Renderer.subMeshStartIndex` and `staticBatchRootTransform`), static-batched parts keep their world boxes and, with Debug logging on, the Player log says so once with the reason; a combined mesh that cannot be read is said once too. With Debug logging on, the frame check is written once per object and again only when the one box its frame outlines changes (`LogOnChange`, keyed by `LogOnChange.ObjectKey`: the object's path, label and instance ID, because the pads of crossings can share a path and a label), with the camera line before the first block written from a camera position. A child object the game moves while running, such as a clock hand, is left out of that comparison, and an object the game moves as a whole gets no frame check. The block names each renderer's own box (`Own box: fitted to its mesh points`, `fitted to its part of the static batch`, `mesh bounds`, or a world box with the reason) and the object's yaw and the yaw of the frame's box (`ObjectMarkingFrame.Box`); a hidden renderer reports no world box, so the box around its oriented box stands in. A static batch combines its meshes, so neither the renderer's local bounds nor `MeshFilter.sharedMesh.bounds` are its own there, and a static-batched renderer has its world-aligned box only while it shows. The overlay keeps that box from when the renderer last showed, in its object's own space (`WorldSelectionOverlay.keptBoxes`), and a hidden static-batched renderer outlines with it, carried to the world with its object's current placement, so it follows a patcher move (`ObjectMarkingGeometry.RendererBox`). A hidden renderer with neither a mesh box nor a kept box, a static-batched one that the overlay has not measured while it showed since the world loaded, adds nothing. `ObjectMarkingGeometry.KindOf` leaves out effects (particles, visual-effect graphs such as water spray, lines, trails, billboards and the `VLB.BeamGeometry*` geometry of a volumetric light), shadows-only renderers and renderers of a lower level of detail; the overlay reads each renderer's kind once. The core starts from the box at the object's position, in world coordinates, leaves out boxes more than four times its size and 10 metres larger, and joins boxes within a quarter of its size, at least a metre, of the growing piece. Only then does it project each box, clipping each face at the six planes of the view volume, so a box that crosses the near plane or a view edge still outlines a near object, and a box outside the view adds nothing; only the overlap with the oriented box counts. An object far to the side with little depth would otherwise project its corners over more than the whole view. The frame is the convex outline of the included boxes on screen (`ObjectMarkingFrame.Outline`). The core uses the oriented corners when available and the world-aligned corners otherwise. It clips each box face to the view and adds the margin around the projected points. A rectangle around a box that stands at an angle to the view is larger than the box at its corners, which made frames overlap; the outline is not. It stays convex, one closed line per object, so a point is tested against it with one pass over its edges, and drawing (`OutlineStroke`) and picking (`Contains`) share it. `Frame` is the rectangle around the outline. The marker stands on `ObjectMarkingFrame.Marker`, the center of the one box the outline is drawn from: a point of the object, so the marker stays on it as the camera zooms and turns, where the center of the rectangle on screen would wander. The marker stands on that point whenever it is in front of the camera, also outside the rectangle or the view, as for a frame larger than the view; only a point behind the camera falls back to the rectangle's center (`ObjectMarkingGeometry.MarkerScreen`). Falling back whenever the point left the rectangle made the marker of Ela Signs, whose box is larger than the view, follow the center of the visible part of the frame as the camera zoomed. Beyond the frame distance the marker stands on the center of the box uncut by the ground, so no ground is read for an object that shows only its marker. The inspected object is projected without a frame distance, so its frame and marker stay at any camera distance and while culling hides it. A crossing pad lies on its track: the ballast and the road it crosses are no ground it stands in, so it is framed whole. The frame is the object's outline projected onto the screen: tight, in straight lines, turning with the object, because it follows the oriented boxes. A single box encloses the cut boxes of an object or complex. Each box is cut where it meets the terrain or ballast, so the frame shows only what stands above the surface. That surface is `ObjectMarkingGeometry.Surface`: the terrain, or the ballast of track that lies at most `BallastDepth`, 1 metre, above that terrain. Track that is carried higher over the terrain, as on a bridge deck, is no surface an object stands in, so a bridge is cut only where it meets the terrain at its ends. The overlay reads the heights with one ray from above against the game's Terrain and Track layers, the track collider standing for the ballast, once per half metre of the world (`WorldSelectionOverlay.GroundAt`), and reads them again after an origin move, a move of the native map editor's history, a completed terrain output and a track that moved (`ClearSurface`). A build without one of the layers is cut at the terrain alone, or not at all, and, with Debug logging on, says so once in the Player log. A box is divided along each of its own axes, read from its corners, into pieces of `GroundPiece`, 10 metres over the ground, and into at most `GroundPieces`, 5; along an axis longer than 50 metres the five pieces are a fifth of that axis each. Each piece is cut at the surface under its center, so a long platform on a slope is cut along the slope. Burial is decided for the object: an object whose boxes all lie under the surface found from above, as in a tunnel or under an overhang, is framed whole, because that surface is not the ground it stands in; otherwise every box or piece that lies wholly under the surface is buried and adds nothing. A piece that lies inside the view is projected by its corners above the surface and the points where its edges cross it; only a piece that crosses a plane of the view volume has its faces clipped there. The frame distance is 500 metres: beyond it an object shows only its square marker. A static-batched renderer supplies only a world-aligned box. For a building that stands at an angle, that box and its frame are wider than the building. The game data allows no tighter one. Close up the frame always shows, also when it fills the view. Beyond `ObjectMarkingGeometry.FrameDistance`, measured from the camera to the bounds of the framed piece, the object shows only its colored marker and label. Its value is 500 metres: measured in the game in 50 metre steps from 100 to 600 metres, every frame still surrounded only its own object at 550 metres with the pointer over each, less one step; the 600 metre step was not checked by hover. It equals `MapEditorGizmoRenderer.MaxGizmoDistance`, 500 metres by default, up to which the native map editor draws and picks its own object markers; it draws segments up to 1.25 times that.

The outliner (`DrawOutliner`) holds a top row with the native filter field, its `?` and the Fit button beside the divider, then the All, Changed, Disabled and Problems segments, All first and the rest by name. A native segment is as wide as its word plus 12 units of padding and the segments have no spacing, so the four need 292.4 units (`CommandBand.FilterSegments`: All, Changed and Problems measured in the game, Disabled from the glyph advances fitted to 168 measured labels); the column's default and least width of 296 (`CommandBand.OutlinerWidth`) holds them. A new or renamed filter changes that sum: recompute it and the widths that follow from it, a count line, the `AddOutlineView` rows of the tree, and three anchors. An object that no supported family covers stands under its category, marked inspection only: it has no problem marker and no edit, and the Object tab starts with its reason. The Object tab lists `SceneObservation.Notes` under Inspection notes, in plain text without the problem marker. Its Track group line names Disable and Clear activity only for an object that offers them (`CommandBand.TrackGroup`). A row's markers stand directly before its name and take room only on a row that has them, so the column's width goes to the names and the end of a long name can be cut off without losing a marker. A folder row starts with its count, followed directly by the folder's name. An inactive object's name is italic and its row adds the word inactive; an object marked inspection only adds the words inspection only to its row, dimmed. `InventoryPresentationState.Rows` and `FitWidth` decide which entries show and how wide the column becomes, and `OutlinerGrouping.Build` decides how they group; `PatchEditingSession.IsChanged` reads the scene patch file alone, so it can be asked for every row.

Use `PatcherBehaviour.Button` for a compact action that requests a content refresh after its callback. Use `Heading` for a heading in the native H3 style. The inspector reserves 24 units for its object name and the line below it. The full object path appears in the name tooltip. The Inspector and Guided switch sits to the right of the badges and the family. A line with an ellipsis draws nothing when its rectangle is lower than its text line by any fraction, so do not give such a line a height below what the text needs. `PatcherBehaviour.Edit` queues the edit through `Queue`, which also serves every other request that needs an inspection token: the guided Target pin, the Review comparison, guided Apply, the crossing coverage preview, preparing a snap after its target is confirmed, and starting the gizmo. Otherwise the first message slot shows the action group with "Working..." while a stepped pass compares the whole scene, 8 milliseconds a frame. The waiting request lives in `RequestQueue`, which the core tests compile. It belongs to the open panel and its native map editor: closing the panel, leaving the native map editor (`Detach`), clearing the inspection (`RequestQueue.Release`, which drops the object's results first so the refusal stays) and ending the load attempt cancel it with a refusal that names the reason, so it never runs later and no pass steps for it while the window is closed. No pass steps while a gizmo is active either: the placement of its target is the patcher's own preview, and its target is observed again when the gizmo ends, by a release or a cancellation. ## Compact window

The title-bar icon `AddCompactIcon` switches the window between the full window and the compact window. `NativePresentationCompact.cs` owns the mode: entering compact mode stores the full window's rectangle in canvas units and its saved-bounds record (`FullWindowRecord`), lowers the resize grip's minimum to the rail's content (`CompactMinimumSize`), and places the rail at the right screen edge, bottom-aligned. While compact, `RestoreFullRecord` writes the full window's record back every tick, so the native persistence never saves compact bounds. Leaving compact mode restores the full rectangle at the current UI scale, at least the window's minimum of 704 by 470 and inside the screen (`CompactRail.RestoredFull`), restores the grip's minimum, and drops the places of the help and the session details on every exit (`ResetSecondaryWindows`). Close, Reset layout, a file lock and disposal leave compact mode first. The compact icon and Reset layout move the window only once the mouse button is up and one more tick has passed (`AfterRelease`): a button acts on the release, which the native map editor reads too, and a window that moved away in that frame left the pointer over the world, where the editor took the release as a click and selected an object. The help and the session details move beside the window after the same wait. The mode and the rail's dragged rectangle live in memory for the session only.

`PatcherBehaviour.DrawCompact` in `ScenePatcherCompactRail.cs` builds the rail from the full window's own parts: `DrawLeftBand` at the rail's width, `DrawRightBand`, `ObjectHeading`, `StateLineRow`, `DrawMessages` at 112 units, `ActionRow` and `DrawOutlinerRows`. `CompactCurrentView` maps the open tab or guided task to the rail's title, context section and actions. The actions come from the full window's own sources: `TabActs` for the Object, Placement and Changes tabs, `TrackLocationActs` for Set and Picked or Cancel on the Connections tab, `ReplacementActs` and `CoverageRoleAct` for the world choices, `RecheckAct` and `GuideAct` for Recheck and Guide, `GuidedWorldActsInPlace` in a guided task, and `FooterActs` during a world choice or gizmo drag. A new action belongs in one of these sources, not in the rail.

`CompactRail` holds the rail's decisions that need no game, which the core tests cover: the rail's sizes, with the default and least content heights derived from its rows, the default place, the full window's restored rectangle, a dragged rail's place after a UI scale change (`Rescaled`), the outliner's rows for the rail's height (`OutlinerRowsFor`), the whole-row viewport (`WholeRows`) and scroll offset (`SnappedOffset`), the room that keeps a short context at three lines (`ContextPadding`), and the one-line track location text. The outliner takes a fixed height of whole rows, six at the default height and one more for each row's height the user adds by resizing (`FollowOutlinerRows`); the message area takes the height the other rows leave free, so a short context gives its room to the messages, and no outliner row is cut off by the window's edge. `TrimOutlinerToWholeRows` keeps the native outline view's viewport at whole rows and snaps its scroll offset. `RailPlacement` looks at the rail's bounds every tick and keeps a drag or resize by the user, so a rail the user dragged keeps its place, also through a UI scale change; a rail at its default place goes to the new scale's default place.

Each mode or outliner switch writes one debug line, `Compact window: mode=…; outliner=…; rect=(x, y, w x h) px; scale=…; tab=…; inspected=…; pending world choice=…`, with a `reason=` for a switch that the user did not click.

The rail draws the outliner's rows with the full window's `DrawOutlinerRows`, so it shows the same tree, by category or by place as chosen in the full window, and its rows' tooltips wait as the full window's do (`OutlineTooltipDelay`). The rail sets the object count line itself: the rows' section words the count through the caller's markup, so the rail can show a filtered count in amber.

## Guided tasks

`GuidedTaskState` holds the pinned target and draft values for the active task. Back from Review returns to Values and keeps the draft; Back from Values returns to Target and clears the pin and draft. Cancel ends the task and clears its target and draft. Complete records the result and moves to Applied after success. While Values or Review is active, Clear and clicking the pinned object's row cancel a pending world choice and clear its prepared snap, keeping the target and draft. Escape cancels pending interactions without ending the inspection or the guided task. Without a pending choice, Clear and a click on the pinned row are refused with the feedback used when selecting another object. Return to Inspector cancels the guided task explicitly.

`DrawGuided` reuses the native field, section, segment, scroll and action-row builders. Its Target, Values, Review and Apply step titles are inert native Toggle components, which retain the native selected and unselected appearance. The footer row uses `GuidedActs` while Guided mode is active and no world choice is pending. Guided mode retains the previous inspector tab and restores it when leaving Guided mode, including cancellation and Back to inspector. Apply and returning to Target leave Guided mode open. Feedback uses one view key per guided step. Entering Values, Review or Target clears results from the preceding step. Entering Applied preserves the new Apply result; restoring the inspector tab also preserves it, while a later ordinary tab change clears a tab-local result as before. Explicit Refresh clears earlier messages without releasing the inspected object or changing the feedback context. Queued Review and Apply requests show no recovery text; their refusal callbacks set it. `EnteredEditValues` parses placement and track-location fields for both modes. Its FillTrackLocation helper fills segment, end and distance together after validation. The shared confirmed-click path supplies the inspector fields and the guided Picked action with that complete track location. Guided Apply uses `Edit` with the same action text and world-choice consumption flag as Inspector; its completion callback updates the task state after the shared feedback and refresh path.
