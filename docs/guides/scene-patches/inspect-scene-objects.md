# Inspect scene objects

Open **Scene patches** from the **Scene Patcher** icon in the top-right icon strip of the map editor. The icon appears only in the map editor. If the strip cannot take it, a floating **Scene Patcher** button replaces it, and the reason appears under **Diagnostics** in the session details. The window opens flush with the left screen edge, directly below the native Map Editor window. It is 690 units wide by default, or as wide as the Map Editor window when that is wider, and it extends down to the bottom of the screen. Where fewer than 600 units of height remain there, as on a 1080-high screen, it opens at the top right of the screen instead, below the button strip and the status readout, with the same width. Drag its title to move it, and use its close control or the entry to close it. Closing cancels a pending world choice. After that it stays where you put it, at the size you gave it, like a native window: a native window or menu that opens over it does not move or resize it. Only a screen or UI-scale change that leaves it partly off screen places it again. **Reset layout**, in the window help (the **?** in the window's title bar, beside the close control), puts it back at that default place and restores the outliner width. Its minimum size is 660 by 410 units, which keeps the outliner, the command band and a tab body in view. A panel that was open when you left the editor opens again when you enter it. Select **Refresh** in the command band. Refresh reads the loaded scene and the active edited MapMod's supplied definitions and verifies stored target identities. It does not apply patches, save files, change object activity, repair bindings or regenerate dependent output. Objects need no patch or warning to appear.

The command band across the top is split at the divider between the two columns. Above the outliner it holds **Refresh** and two status lamps: a dot with the word **Current** or **Stale**, and a dot with **Saved** or **Unsaved**. A lamp is green when all is well and amber otherwise; it is information, not a button, and its tooltip gives the reason. Above the inspector the band holds **Select in world**, **Focus** and **Copy ID**, and at its right end **Details**, which opens the session details. A command that cannot run now stays in place, greyed out: **Select in world** while a world choice is pending, **Focus** and **Copy ID** while nothing is inspected. The **?** for help on the whole window sits in the window's title bar, beside the close control. Below the band, the outliner on the left holds a search field with a **?** for outliner help, the **All**, **Problems** (objects with a detected problem) and **Changed** (objects the active MapMod changes) filters, a count line in the form `N of M objects`, and the object rows. **Fit**, at the right end of the outliner's top row beside the divider, sizes the outliner to most of the names, and the divider between the outliner and the inspector can be dragged. When the column would need more than 40 percent of the window, **Fit** stops there and a message with the source **Fit** says how wide the names are. Three notes at the bottom of the outliner state when Save writes, when to refresh after native edits, and that a reload clears the Undo history. The inspector on the right shows the object's name, a state line (family, **Inactive**, `* CHANGED` and the problem count), and four tabs: **Object**, **Placement**, **Connections** and **Changes**. Each tab body starts with a one-line description of the tab and a **?** at the right end of that row, which opens the tab's help. The footer under the tabs has three message slots above four action slots. The first message slot says what the window is waiting for, such as a world choice, a gizmo or a snap, or why the open tab cannot edit the object now. The next two show the two newest results or refusals, newest first, each with the action group it came from as its bold source. The four action slots hold the actions of the open tab. Each tab body scrolls on its own; the window itself does not.

Use [world selection](select-world-targets.md) to find an object by its marking or check a replacement candidate against the track and scene.

## Find and inspect an object

Search by name, full hierarchy path, family, binding identifier, dependency or detected problem. The inventory includes active and inactive loaded objects. Rows sit under a folder for their family, which stays collapsed until you search or filter; the folder of a newly inspected object opens once. Select the object's row in the outliner. Markers stand before its name: a red `!` marks a detected problem, an amber `*` an object this MapMod changes, and a green `+` an object it adds. The native Map Editor puts `*` and `+` after a name; here they come first, so that a long name that is cut off keeps them. The state line under the object's name shows the same as the badges `* CHANGED` and `+ ADDED`. Neither marker means unsaved work: only the **Unsaved** lamp does. An inactive object's name is italic and followed by `inactive`. The row's tooltip gives the name, path, family and problems. The **Object** tab shows the identity (scene, component, structure and path), whether the object is **Enabled**, its supported edits, its detected problems and its dependencies. The **Placement** tab shows the position in map coordinates and the rotation in degrees, as the six fields of its **Numeric** mode. The **Connections** tab shows the track binding and the observed bindings. **Copy ID** in the command band copies JSON values from that observation; the footer's message slots and the log then name the object whose identity was copied. A copied identity does not establish support for editing the object.

An independent object has no invented track binding. A missing or empty segment reference appears as a problem. A reference to an existing segment can still name the wrong track. The patcher cannot decide whether a valid binding or physical placement matches the map author's intention. Compare the displayed identifiers and placement with the world.

Supplied definitions remain visible under **Supplied definitions** in the session details when their target is missing or ambiguous, their modification dependency is missing, or their document cannot be read. Such a target cannot be selected. The referring definition identifies the problem. Inspection does not rewrite an unreadable or newer-format document.

## Focus and refresh

Select **Focus** in the command band to jump the camera to where the inspected object is now. Focus keeps the inspected selection, works while the inventory is stale and does not author a scene edit. If the object no longer exists, the message area reports the refusal under **Focus**. Native camera jumps may shift the floating origin or load terrain. Map coordinates remain the placement reference.

Mouse actions inside the product button or panel belong to that UI. Scrolling an observation should not also zoom the world, and dragging the scrollbar or title should not select objects behind the panel. A drag that begins inside remains captured until release. Outside the panel, normal world navigation remains available.

When the inventory is unscanned or changed, the first status lamp turns amber and reads **Stale** in place of **Current**. The lamp also reads **Stale** when the MapMod's patch document was changed outside the editor while the editor runs; saving from the editor does not make it stale. Its tooltip and the session details name the reason: the first observation that changed or disappeared, a changed number of observations, a changed map context, or a check that failed. The log receives the same reason. Stale means that the observations differ from the scene or that the check could not complete; using the panel does not make the inventory stale by itself. While the inventory is stale, rows can still be inspected and **Focus** works; only edits are refused. Runtime references, which are held in fields the game does not serialize, such as culling or audio lists, and enabled flags that the game switches while it runs, such as a crossing bell's audio player, appear under **Runtime state** on the **Object** tab and do not make the inventory stale. While the panel is open it compares the scene with the snapshot in the background, a small part in each frame, and starts again two seconds after a comparison ends. A scene change therefore appears as stale after a delay that grows with the number of loaded objects. Supplied-document changes are checked every two seconds. These checks do not replace the displayed snapshot. An edit does not rely on the background comparison: at the moment of the edit the patcher compares the whole scene again and refuses when anything differs. Refresh explicitly replaces the observations and retains the inspected object when its handle and component still exist. Refresh after native edits, Undo/Redo, activity changes or document changes. Supplied document observations update only on explicit refresh.

Focus uses the inspected object itself, not a fresh inventory, so it never jumps to another object that has the same path. Before a complete-document placement, the engine repeats unique resolution and preflight immediately before mutation and checks that the map context has not changed. Editor integrations can additionally pass an inspected-target token to reject changes in observed placement, bindings or dependencies. Refresh cannot substitute another object with the same path for a completed edit.

## Coverage and dependencies

| Family or ownership path | Inventory coverage and editing route |
| --- | --- |
| Track markers, including yard-limit and station signs | Typed markers and serialized track-relative placement. The object's label does not establish its marker type. Generic markers that match the supported pattern carry the structure `track-marker-v1` and accept binding edits, as described in [repair, replace or detach a track-marker binding](repairing-track-bindings.md); the others show the reason in their problems. |
| Mileposts | Marker binding, prefix, origin, mileage and component dependencies. Inspection leaves models and mileage unchanged. |
| Track-group-linked visuals | Serialized `TrackRelativePosition` targets, offsets, terrain snapping and group-following settings. Construction-controlled targets retain their separate segment and target relationships. |
| Crossing pads | Markers with the curve-mesh component, including their generated-geometry dependency. Pads that match the supported pattern carry the structure `crossing-pad-v1` and accept binding edits that regenerate the pad, as described in [rebind a crossing pad and regenerate its geometry](rebinding-crossing-pads.md). |
| Crossing detection | Loaded spans and controller circuit roles. A missing endpoint segment differs from a valid but unintended track. Crossing controllers that match the supported pattern carry the structure `crossing-coverage-v1` and accept coverage edits, as described in [correct the detection coverage of an existing crossing](correcting-crossing-coverage.md); spans the patcher owns appear under `CrankyAnt Scene Patcher crossing coverage`. |
| Existing crossing equipment | Controller-bound lamp-material, gate-animation and bell-player components under loaded crossing controllers. Component presence does not prove functional detection, light output or audible playback. |
| Independent boards | Loaded objects with a renderer culler and a circle map mask and no track marker. Those that match the board pattern accept fixed placement and activity, as described in [move a board with its terrain effects](moving-boards.md); the others show the reason in their problems. |
| Retained bridges and construction scenery | The original inventory's identified Ela bridge culler and separate `Game.Mow.TrackConstructionScenery` controller. The controller exposes its segment IDs, construction conditions and referenced targets, including the bridge's steel and abutments. Moving the controller does not imply moving its targets. |
| Generated track trestles | The two `AutoTrestle` controls identified near Ela belong to generated track-segment hierarchies. They remain native track geometry, separately owned from the retained bridge. |
| Industry/passenger spans and map-object anchors | OpsDTO spans and MapObjectSpawner anchors use native map/operations data. This covers the original P7ec/Pfaj, Wilmot and Sox anchor cases. The current Ela passenger span is native operations data; the historical FUSE warning concerns the previous game line. |
| Player-created signs | Use the native sign editor. Its ownership and persistence do not establish an inherited scene-sign editing route. |
| Missing object configurations or industry definitions | The original Sylva diesel-stand and Bryson textile cases concern native configuration/definition data, with no identified scene-object repair. |
| Signals, CTC and interlocking | Their relationships appeared in the historical inventory but the first-version operation boundary excludes their edits. A span's presence in the inventory does not enable these operations. |

Discovery reads loaded objects, including inactive ones. It does not load otherwise absent scenes. Dependencies include child components, serialized marker/span/controller relationships and direct references from loaded scene component fields and lists. Identifier-based or indirect consumers can remain unknown. An unavailable field or graph reports an inspection limit rather than proving a binding valid. Names and proximity never create a functional relationship.

All newly inventoried patterns are inspection-only unless an operation adapter explicitly supports them. The table accounts for the applicable families and ownership cases in the original inventory. It does not promise discovery of arbitrary custom scene hierarchies, require a separate bridge model whitelist, or establish native rendering or gameplay behavior. An unidentified timber object in an earlier bridge image remains unattributed; the two sampled native trestles do not identify that object.

The [candidate ownership findings](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/20#issuecomment-6717432391) distinguish retained signs from native passenger and anchor data. The [operation investigation](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/18#issuecomment-6725711245) records dependency observations and their limits. These research results do not establish production inspection behavior.

The original [candidate families](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/CandidateFamilies.md) and [ownership audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/f8b3a72f00dc6556e5d37894605b0312658ad598/Research/NativeCapabilityAudit.md) identify the retained bridge family and its native-data distinctions. The later [bridge trial](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/5e99c72dee551762316c0b8cf5aafec5bf40b748/Research/SceneOperationBatch/Evidence/Boot02/Bridge/Report.md) identifies the construction controller's steel and abutment references. The [trestle observations](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/5e99c72dee551762316c0b8cf5aafec5bf40b748/Research/SceneOperationBatch/Evidence/Boot03/Bridge/Report.md) distinguish the sampled track-owned controls from the retained root and the unattributed timber image.
