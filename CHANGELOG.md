# Changelog

Notable changes to this project are recorded here, newest first.

## 0.5.0

- A failed edit in scene patch editing now reports what happened: `refused` when nothing changed, `failed and was undone` when the object was restored, or `failed; cleanup is incomplete` with the position, activity, binding, coverage or leftover spans that could not be confirmed. Each message gives a correction, and the new **Guide** button in the footer opens the guide for the failed operation. While cleanup is incomplete, the footer shows what remains and further edits to that object report `is blocked by incomplete cleanup`. **Recheck** compares the object with the scene patch file, removes leftovers from the failed attempt and keeps what the file names. Once they agree, the object accepts edits again. Runtime failure reports also name the state left by an incomplete cleanup.
- Move, rotate, disable and restore individual parts of baked scenery groups, such as a sawmill jetty or station lamp, in the native map editor and through `scene-patches.json` (`baked-scenery-part-v1`, target component `UnityEngine.Transform`). Each listed group's parts appear in the **Baked scenery group** family, named with their group, for example `Whittier Saw Mill / Jetty`. The group and its other parts stay as they are. A part with a fixed placement keeps it when its group moves later, including during a gizmo drag. **Remove modification** returns the part to its place relative to the group or the part above it. While a part keeps a fixed placement, the culling spheres above it grow to enclose it. Siblings with the same name and LOD group levels are not listed as parts. Scene patch files with a part target require patcher 0.5.0.
- Move, rotate, disable and restore whole baked scenery groups, such as platforms, lamps, signs and small buildings that the native map editor does not edit, in the native map editor and through `scene-patches.json` (`baked-scenery-group-v1`, target component `UnityEngine.Transform`). The new **Baked scenery group** family lists one entry per group root below `World`. Everything below the root moves with it, culling and colliders follow, and the activity of the parts stays as it was; these groups are decorative. Groups that hold game logic or terrain shaping, road bridges, rail bridge constructions outside Ela and the crossbucks of unprotected crossings are listed as inspection only with the reason. Track spans the game builds from operations data and everything below the CTC roots are no longer listed. Scene patch files with a baked scenery group target require patcher 0.5.0.
- Beyond 125 m from the camera, a grade-crossing setup has one square marker for the whole setup. Within 500 m, it also has one object frame around its visible objects. Click the marker to open a list of the setup's objects beside the pointer, then choose an object and select **Confirm** to inspect it. The list excludes detection spans, which the controller manages; they remain in the outliner as inspection only rows. At 125 m or less, each object appears separately. Whistle signs appear separately at every distance.
- A crossing controller reports a problem if one of its circuit spans refers to a track segment that no longer exists. The message identifies the circuit and span. To repair it, open the controller's **Connections** tab and select tracks for the circuit or detach it.
- An object frame is one box. An object of several parts is framed by one box around all its parts, turned with the object, instead of the combined outline of its parts; the frame of a grade-crossing setup is one box around all its objects, turned with the crossing. On sloping ground the bottom of the box lies at the lowest ground under the object, so the frame stays one box instead of following the slope.
- The patcher reads a scene patch file's `formatVersion` before anything else. A scene patch file whose version is missing, not the number `1` or newer applies none of its modifications, also when the rest would read as format version 1; the other mods' scene patch files still apply, and scene patch editing protects the scene patch file from overwrite.
- When the edited mod's scene patch file is protected, the session details show each problem with its JSON path, lines, the text there and the expected value, with links to the format reference and the recovery guide. **Read again** adopts a scene patch file you corrected outside the native map editor and applies its modifications at once, without writing the file. **Start fresh** copies the original byte for byte to a verified `scene-patches.json.backup-<id>` and lets Save replace the original with an empty scene patch file. Both are reviewed and confirmed first.
- The game's Log window heads a scene patch row with the supplying mod's `Data/scene-patches.json` followed by `Railroader Scene Patcher`, instead of repeating the patcher's name. A failure of a modification whose dependency is missing names the dependency and the object.
- Scene patch editing refuses to remove a modification, also through **Clear activity** or by clearing its last crossing-coverage entry, while another modification names it in `dependsOn`, and names those modifications. An edit of a modification that does not take effect because a dependency is missing, fails or forms a cycle is refused with that reason instead of being reported as applied.
- A track marker or crossing pad that holds a duplicate marker id, such as `Mg6m` and `Mkft` in the base-game map, starts its dependencies with that marker id, followed by every holder with its activity and the registration it has under the marker id. The game removes a registration by marker id from every holder, so an activity, binding or track-following edit of a holder is refused before it changes anything, with a message that names the duplicate marker id and every holder instead of a registration error and advice to reload. At load, a modification that would make such a change fails with the same explanation, and the scene patch file's other modifications still apply. Fixed placement of a holder stays editable.
- A refusal in the message area reads as the action group followed by plain sentences, such as **Activity** with `Enable refused. The inspection was cleared before the request ran.`, without a second label before the reason.
- Starter placement markers, the markers whose track location a new-game setup reads to place its starting cars, have their own **Starter placement** family in scene patch editing. It lists each marker that an active setup uses, once, with every setup and car placement that reads it, the cars of each cut and its wreck setting. A listed marker shows a problem for an empty binding or a missing segment whether it is enabled or not, because the game reads it either way. The world marks the inspected marker's track point in gold, and Focus goes to that point instead of the marker's object position. A marker that only inactive setups use is no longer listed. Editing the wreck setting is not available yet.
- Place a starter placement marker on the track, so a new company game on your map starts with its cars where you intend. On the **Connections** tab, click the track and confirm it to fill the track location, then select **Set**. The world shows the track point as the front of the car cut and the track the cut stands on from there. Before anything changes, the patcher checks the whole cut, with the cuts of the setup's other placements, by the game's own placement rule, and refuses a missing or ambiguous segment, a distance outside the segment, a detach, and a marker that no car placement or several read, each with the reason. Native Undo and Redo, **Clear location**, **Remove modification** and failure restoration return the marker's earlier track location. `Data/scene-patches.json` stores it as `starterPlacement` with the setup and the track location, and Save raises the dependency to patcher 0.5.0.
- The outliner lists the objects of each family in the order of their names. The tooltip of a control that cannot be used gives its reason after **Unavailable:** as one plain sentence, without a second label such as `Not editable:`.
- A scene patch file that scene patch editing creates names the bottom map layer of the edited map definition as its target map, or the map definition itself when it has no map layers. A scene patch file from a map layered on `rr/bushnell-whittier` therefore applies on a save of the base-game map, where the mod's map-changing script brings its native changes, as well as on the mod's own map. **Copy ID** names the same target map. An existing scene patch file keeps the target map it names, also through Save; set `sourceMap.mapId` by hand to apply a scene patch file only on your own map. While the edited mod's scene patch file cannot be read, **Copy ID** is unavailable and its tooltip gives the reason.
- An edit in scene patch editing that writes a position or rotation keeps the text of every axis whose value equals the scene patch file's value at the precision the game stores, so changing one axis no longer rewrites the others as longer numbers read back from the game.
- `modifications` in `scene-patches.json` is an object keyed by modification ID, and a modification has no `id` member. `relationships.crossingCoverage` is an object that holds `circuits`, keyed by the ID of each circuit's native island span, and `additions`, keyed by addition ID. The order of keys and members has no meaning: the patcher applies modifications that `dependsOn` does not order in the ordinal order of their keys. A scene patch file whose `modifications` is an array is rejected and protected from overwrite; rewrite it by hand in the keyed shape. A modification that still carries an `id` member fails with a message that names its key, and the other modifications still apply.
- A Save writes the scene patch file in one canonical order and keeps the literal of every number it does not replace. The scene patch file counts as saved when its content equals the file's content, whatever the order of members, the spacing or the way a number is written, so reordering or reformatting the file by hand is not an unsaved or outside change and does not turn the Stale lamp on. A Save without a patch change leaves the file's bytes as they are.

- A Save that fails while writing `Data/scene-patches.json` or `Info.json` leaves the previous file intact, so your edits stay in memory and Save can be retried. Each file is written completely beside the original first, as a `.saving` file, and only then replaces it.

- When a player's game loads the same map again, for example on reconnect or same-map re-entry, the patcher checks each modded object and added object instead of relying on an applied flag. Applied modifications are not duplicated, an object the game keeps keeps its state, a rebuilt object gets its modification as new, and only the patcher's own leftovers for the old object, such as detection-addition spans, are removed. A cleanup failure is reported on that player's game only and retried at the next load. In single-player, loading the same save again rebuilds the modded objects and added objects, and each modification is applied once. Live reconnect has not been tested yet.
- When the patcher's state ends while the map stays loaded, for example when mods are reloaded or unloaded without unloading the map, the patcher first returns patched grade crossings to their native detection and removes its spans, so a new patcher state applies each crossing-coverage modification once instead of refusing it. A crossing that the patcher could not return to native detection is refused for editing until the map reloads. This has not been tested in the game yet.

- In multiplayer, the host and every client apply the scene patches from their own installed mods to their own scene when their world loads, and each checks the map, target and capability locally. A failure on one player's game is reported there only. The patcher adds no synchronization or admission check; Railroader's own checks of required mods and versions still decide who can join. Live host and client sessions with this release have not been tested yet.

- Apply the scene patches of several loaded mods in Railroader's load order. A mod applies only when it declares the patcher dependency and its target map matches the loaded map or one of its layers. When mods change the same existing target, an informational game message names the object and the mods; it reports a possible incompatibility, chooses no winner and does not stop application. A failure in one mod's scene patch file leaves the other mods' work in place.

- Remove a marker repair even when its original track is missing. Restore the captured native reference and warning; Undo and Redo recover the repaired and broken states without changing unrelated warning rows.

- Make an object follow an explicitly selected track segment location or endpoint, in the native map editor and through `placement.mode = "trackFollowing"` in `scene-patches.json`. The object keeps its position and orientation relative to that track; it moves with the track in the native map editor and is placed from the track's current pose on every load. In the native map editor the object also follows a track that turns by less than half a degree. Scene patch files with a track-following placement require patcher 0.5.0.
- Generic track markers whose activity follows a track group can be edited. Rebinding moves the group subscription with the marker. An explicit disable holds the object inactive when the group is enabled later; without it the group keeps switching the object. Clearing the mod's activity value or removing the modification returns the object to its group. A modification that omits `active`, in the same scene patch file or in a later mod, and a gizmo preview leave an explicit disable in place. Scene patch files with an `active` value on a track-marker object require patcher 0.5.0.
- Generic track markers inside a grade-crossing setup, such as whistle signs, can be edited like other Generic markers: binding, placement, track following and activity. The crossing pad and the crossing's own markers keep their own operations.
- A gizmo rotation of less than half a degree is kept. It completed without a modification or a history operation before.
- Runtime failures produce structured game warnings with the supplying mod, operation, target when resolved, error, and patcher and game versions. For eligible dependency-free relationship-only marker repairs, the patcher tries repair before the game's native marker check. If that route is unavailable, it removes only the exact current warning row after a successful operation and separate verification of the binding and dependent state. Reporting adds no scene patch file, schema or capability requirement.

- Remove the duplicated source prefix from runtime diagnostic text. The originating source remains available as the native warning originator.

- Add detection for explicitly selected extra tracks at an existing grade crossing, in the native map editor and through the `additions` object of `relationships.crossingCoverage`. An addition has an ID that is unique in its mod's scene patch file and is its key in `additions`, and the tracks and area of its three spans. The patcher builds one circuit with its own spans for it on every load, reuses it on a repeated load and removes it when the entry is deleted. Native circuits keep their coverage.
- Correct the detection coverage of existing grade crossings, in the native map editor and through `relationships.crossingCoverage` in `scene-patches.json` (`crossing-coverage-v1`). Each circuit, named by its native island span, keeps its coverage when omitted, covers explicitly selected tracks, or is detached. Native spans stay registered and unchanged, so a still-valid old route stops triggering the crossing; other circuits keep working. Scene patch editing previews the effect on every circuit before applying. Scene patch files with crossing coverage or a crossing-coverage target require patcher 0.5.0.
- Set or replace the track location of crossing pads in the native map editor and through `relationships.trackMarker` in `scene-patches.json` (`crossing-pad-v1`). The pad's graph registration follows the binding, and the game's pad generation rebuilds the pad geometry and culling at the new location; Undo, Redo, removal and failed edits generate the pad again from the restored location. Pads cannot be detached; disable them to hide them. Scene patch files with a crossing-pad modification require patcher 0.5.0.
- The Scene patches window opens from an icon in the top-right button strip, below the Map Editor window. An outliner with search, All, Problems and Changed filters, family folders and a resizable column sits beside an inspector with the Object, Placement, Connections and Changes tabs and a fixed footer for actions and results. Each region has context help behind a `?`.
- Add lights and gates to existing grade crossings, in the native map editor and through `relationships.crossingEquipment` in `scene-patches.json`, an object keyed by equipment ID. The patcher copies a device already loaded in the crossing's scene when its lamps and gates work through the crossing controller's lights and gates keys (`crossing-light-gate-v1`), whatever its model; scene patch editing lists rejected devices with their reason. The controller drives the copy, which joins the crossing's culling. Each addition has a persistent ID scoped to its mod; repeated loads and Undo/Redo keep one copy per ID. Scene patch files with crossing equipment require patcher 0.5.0.
- Add bells to existing grade crossings in the native map editor or through `relationships.crossingEquipment` in `scene-patches.json`, using `crossing-bell-v1`. Each bell has its own player beneath the crossing controller and rings when the controller rings its own bell. It can use any sound from a bell definition in the content library. The editor lists every bell definition and explains why any definition is refused. Each bell loads and keeps its own audio, then releases it on removal. If the audio fails to load, the bell stays silent and produces one warning that identifies it. Bells have persistent IDs scoped to their supplying mod. Repeated loads and Undo/Redo keep one player per ID. Scene patch files with crossing bells require patcher 0.5.0.

## 0.4.0

- Set, replace or detach the track location of Generic track markers, such as yard-limit and station signs, in the native map editor and through `relationships.trackMarker` in `scene-patches.json` (`track-marker-v1`). The marker's track-graph registration follows the binding; the object does not move. Placement and activity of a marker object are separate settings. Mileposts, crossing pads, crossings and markers whose activity follows a track group are inspection only. Scene patch files with a relationship or a track-marker target require patcher 0.4.0.

## 0.3.0

- Move, rotate, disable and restore the Ela bridge with its colliders and culling, in the native map editor and through `scene-patches.json` (`bridge-colliders-v1`). Separate track-owned trestles and construction scenery stay unchanged. Scene patch files with a bridge modification require patcher 0.3.0.
- Move, rotate, disable and restore independent boards with their culling and terrain mask, in the native map editor and through `scene-patches.json` (`independent-board-v1`). Scene patch editing tracks the terrain output the game regenerates, reports writes that do not complete and can request them again. Scene patch files that move a board other than the Sylva location sign require patcher 0.3.0.
- A capability that is incompatible with the running game build fails only the modifications that name its structure.
