# Early scene repair and player diagnostics

Research for [issue 30](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/30), serving [issue 10](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/10). This partial investigation includes an observe-only trial and two fixture-specific repairs on ordinary existing-save loads. It does not establish a general early repair or player-visible delivery guarantee. The isolated test home was used; no game installation or personal profile was changed.

## Sources and scope

On 2026-11-09, read-only inspection used the installed Railroader 0.6.2 build 26335745, `Railroader.dll` SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`, with ilspycmd 10.1.1. Official [DLL mod documentation](https://docs.railroadergame.com/modding/dll-mods/) and [Info.json reference](https://docs.railroadergame.com/modding/info-json/) were retrieved on 2026-11-09 and are not pinned to this binary.

The [earlier lifecycle inspection](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/3e5970722bb278cbbaee003300ada6ce916df702/Research/ApplicableLifecycleStatic.md), [continuation report](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/3e5970722bb278cbbaee003300ada6ce916df702/Research/ApplicableOperationsContinuation.md), and [marker experiment](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/ApplicableSceneOperations.md#broken-marker-preflight) provide earlier static and bounded runtime evidence. ## Early candidate and limits

`Track.TrackMarker.OnEnable` resolves its `Location` against `Graph.Shared`. If the result is valid, it calls `Graph.AddNamedLocation`; otherwise it emits the native structured warning. The `Location` setter changes serialized location, invalidates cached pose and invokes `OnLocationChanged`. Thus an interception immediately before this method is a concrete candidate for changing the target location while preserving the native check and its registration. Two fixture-specific trials below demonstrate this candidate on fresh-process loads of one existing save. It must call the original method in every case, including refusal and failure. Other affected consumers, initialization and group subscriptions need separate verification.

The earlier trace observed `MapWillLoad` without a graph or target and observed the warning before `MapDidLoad` and `OnWorldLoad`. Those callbacks do not exclude a narrower interception. Early installation of a hook does not establish that the graph, destination segment, marker identity, applicable patch and supplying-pack ownership are ready at interception. The bounded trial below establishes availability for its one fixture, not a general installation or lifecycle guarantee. `ModAssemblyManager.InstantiateAndLoad` calls `OnModLoad` and retains successfully initialized entry points; `WorldLoad` subsequently calls `OnWorldLoad`. This method-level order alone does not prove `OnModLoad` precedes the relevant marker activation on every launch or reload. The installed managed directory did not contain a Harmony-named assembly in this inspection. The separate Harmony observer has been exercised in the bounded trial below.

The trial used an independently authored, build-identified probe installed before an ordinary-save launch. At a prefix on the marker's `OnEnable`, the probe recorded invocation order, target identity, graph and destination-segment presence, and fixture-pack presence, then let the native method execute. The trial compared registration with the native warning and later callback. The observe-only run preceded the guarded rebind. Editor entry remains separate. The accompanying observe-only Harmony probe supplies one bounded measurement; it does not establish general game compatibility. It does not load actual patch data or prove ownership.

## Observe-only ordinary-world trial

The owning session installed the independently reviewed observer in the isolated test home. The old disposable save was not loaded because it required a retired probe. Instead the operator created a new ordinary sandbox with the broken-marker fixture. The observer recorded `OnModLoad`, successful Harmony patch installation, then paired prefix and postfix observations on M5pp in `crankyant/broken-marker-test-map`. Both observations recorded one fixture-pack match, a graph, the named replacement segment, no resolved original location and the original Shuo segment. The native game log recorded the M5pp warning; the operator saw the native Log window open automatically with that one warning. The observer later recorded `OnWorldLoad`. The original observer log SHA-256 was `89E0F97397833B7F2CDCAE22458E160C05A31EE864F7DA7028AD6A58DD54BBEF`. Full logs are not published.

This demonstrates the prefix ran before the native method on one new ordinary-world load, and that graph, replacement segment and fixture-pack metadata were present there. It does not prove destination location validity, patch-data discovery, patch ownership, safe mutation, native registration after repair, existing-save or editor behavior, or general player-visible delivery. The observer made no repair or collector change.

Both rows were visible; the header count did not reliably describe them. A further fresh-process load of the same disposable save used the same guarded repair with the research control explicitly skipped. It again recorded one matching replacement registration. The operator saw no Log window immediately after load or at a second observation about 53 seconds after `OnWorldLoad`, without closing it. The selected game log contained no warnings or errors at the later observation. Its visibility is one late-message observation outside a demonstrated cooldown test. No existing warning was removed. Neither trial proves all consumers or callbacks recovered, patch ownership, real patch discovery, editor loading, multiple markers, version compatibility, general player notification or race-safe automatic-window reconciliation. A setter exception can leave partial state; the probe is not a production rollback mechanism. The game was exited without a manual save; automatic saves were possible and disposable.

## Shared warning paths across the supported inventory

`TrackMarker` derives directly from `MonoBehaviour`; its `OnEnable` is private and nonvirtual. A recursive metadata scan of the installed `Railroader.dll`, including nested types, found no direct subclass. Its warning and registration branch does not select by marker enum. Therefore an actual `TrackMarker` instance that reaches this method uses the same native location check, warning construction and registration path as M5pp. The earlier [instance inventory](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/ApplicableSceneOperations.md) identifies TrackMarker on whistle Mm8w, speed Mwp1 and crossing pad Mg74. The later [ownership capture](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/f8b3a72f00dc6556e5d37894605b0312658ad598/Research/CandidateOwnership.md) identifies yard-limit Mkwd and station sign Mi4f as Generic markers. `Helpers.MilePost` requires a colocated `TrackMarker` and obtains it in `Awake`; its own `OnEnable` subscribes to that marker's location-change event. These facts support reuse of the M5pp native warning/check semantics for those identified marker-backed cases without demanding a separate warning trial for every object. The prefix is a candidate for this common method when the actual target, active map, graph, resolvable replacement, patch data and supplying owner are available and unique. The trial establishes those particular fixture prerequisites, not universal timing or ownership discovery. Different placement, cache, group, culling and geometry consumers have their own operation-specific evidence; a common warning method does not prove their state has been repaired.

The retained independent board and bridge are separate non-marker pose/activity examples in the [capability audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/8d3bfc0005d15e8b0404fc584479bd60f385c4fd/Research/NativeCapabilityAudit.md). Do not assign them a marker warning without an actual marker component. Crossing-circuit `TrackSpan` components have a distinct path. Their `OnEnable` adds the span to the graph; `UpdateCachedPointsIfNeeded`, reached by consumers such as `GetPoints`, `GetSegments` and `Contains`, resolves endpoints and computes the route. Its missing/invalid endpoint warning and no-route error use ordinary `Log.Warning` and `Log.Error`, not the structured `MessageLog` route. The `lower` and `upper` setters invalidate the cache. A correction applied before the first relevant cache computation can therefore be checked by the native code with the corrected endpoints, conditional on the span, graph, replacement locations and patch being available. This is a static candidate, not a demonstrated ordering guarantee. The established crossing circuit and consumer work owns actual endpoint, occupancy and restoration behavior; this separate plain-logger path is not evidence of a stale native player Log row.

`TrackRelativePosition.Awake` obtains its marker and, when group following is configured, calls `ObserveTrackGroup`. That method writes an ordinary logger warning for a missing marker location or segment. The marker prefix does not establish that this earlier callback already saw the repair. This is a separate ordering condition for file-log accuracy, not proof of an additional structured player warning. The supported inventory does not require a blanket absence of all game diagnostics. The scoped assembly scan found the marker structured-warning method and `MapDataLoader.Load` among warning/error callers in track, marker, crossing, milepost, bridge, mask and culler named types. `MapDataLoader` forwards graph-deserialization warnings for segments whose endpoint nodes are absent; the map-JSON path is distinct from an applied scene-object repair. This named-type scan is not an exhaustive audit of all game diagnostics.

## Current diagnostics and window

The earlier ordinary-save and editor experiments repaired one broken marker, checked object-matching registration, removed one exact current warning and preserved a separate control. The [frozen probe](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/BrokenMarkerProbeNext/Frozen9E1/BrokenMarkerWarningProbe.cs.txt) required one candidate and matched severity, source, key, originator and description before removing the same message object. It does not establish a general matching rule, safety for ambiguous or colliding IDs, or erasure of historical logs. Removal is conditional on independently verified underlying repair, a unique attributable live message, the active native collector and an unchanged message object. Otherwise leave the message intact.

`MessageCollector.Collect` deduplicates on source and nonempty key, updates existing entries, and issues an update event. `RemoveMessage` marks and removes the selected object and issues a removal event. `MessageLogWindow.HandleMessageRemoved` only schedules a list refresh; it neither clears `_autoShowPending` nor closes the window. Its `Update` opens the hidden window for a pending automatic show without rechecking remaining warning severity. `ShowIfNeeded` separately opens for any retained Warning or Error. These observations establish why an empty automatic window can remain or open after removal; they do not establish a safe native API to cancel or close it. A bounded reconciliation would need to distinguish automatic pending/open state from a player-opened window and preserve any other Warning or Error. No such distinction or race-safe implementation has been demonstrated.

## Actual failures and metadata

`StateManager.Awake` initializes the structured collector. Before initialization `MessageCollector.Active` can fall back to `SerilogCollector`, which logs without retaining a UI entry. `MessageLog.Warning` and `Error` use the active collector. `StateManager.OnPropertiesDidRestore` asks an existing log window to show if it contains a Warning or Error. A newly added warning may schedule display on the next window update when hidden and outside its five-second cooldown. An updated deduplicated entry does not schedule automatic display, and a new entry during cooldown is not queued by that handler. Therefore an ordinary file or mod log is not proof of player notification, and unique per-attempt keys alone do not guarantee visible delivery. A single late simulated warning was visible in Mutate03. Startup, cooldown, repeated attempts and actual patch-failure delivery remain untested. Editor presentation is a separate question.

The [Info.json reference](https://docs.railroadergame.com/modding/info-json/) documents required identifier and name, optional author and one optional HTTP or HTTPS website URL. It does not establish a support destination, multiple links or clickable log text. `AssetPackManager.PackEntry.Info` is an internal metadata candidate; the [ownership report](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/bc4d7bff4ddea226d08147f123fa0b95beabf2ef/Research/MapModPatchLoading.md) does not prove ownership of a particular patch. Attribute invalid supplied data only when ownership is established. Internal patcher faults and unknown causes require a patcher-maintainer route; do not assign unknown causes to a supplying pack.

## Pending evidence

The common `TrackMarker.OnEnable` check supports the identified marker-backed inventory as described above. The actual patch-discovery, attribution and readiness path still needs to supply its prerequisites at that method. If a selected supported repair reaches a different check after emission, exact reconciliation and preservation of a manually opened window remain unestablished. Actual patch-failure delivery, cooldown and repeated attempts remain distinct from the one visible simulated warning. Editor presentation remains separate. These limits do not require another empirical warning trial solely because an object name or marker enum differs. This report does not authorize a production interception, global suppression, window manipulation or release claim.
