# Scene mutation and lifecycle boundaries

Research for [Identify safe scene mutation and lifecycle boundaries](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/5) and [Define the first usable Railroader Scene Patcher](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/3). Evidence is read-only inspection of the installed Railroader 0.6.2 `Railroader.dll` with Mono.Cecil and the prior [position control](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/PositionControl.md), [candidate families](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/CandidateFamilies.md), and [isolated whistle result](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/Tests/07-Inventory/IsolatedWhistleResult.md). Assembly method names below refer to that build, SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. Static paths do not establish a supported API, call ordering in every loader, or successful runtime relocation. No runtime test or file mutation of game, mod or save was performed for this report.

The [official map guide](https://docs.railroadergame.com/modding/map-modding/) describes original scene objects including signs, mileposts and bridges as outside certain editor capabilities. Unity documents [OnEnable](https://docs.unity3d.com/ScriptReference/MonoBehaviour.OnEnable.html), [OnDisable](https://docs.unity3d.com/ScriptReference/MonoBehaviour.OnDisable.html), and [GameObject.SetActive](https://docs.unity3d.com/ScriptReference/GameObject.SetActive.html); these host conventions do not establish Railroader-specific readiness or ownership. Unity API links are general references, not evidence of the game's exact Unity version.

## Code-supported boundaries

* `Track.TrackMarker.id` is the graph registration key, not proof that an ID or scene path remains stable or unique across builds, mod combinations or reloads. `OnEnable` resolves `Location`, checks validity and calls `Graph.AddNamedLocation(id, location, type, this)` or emits a warning. `OnDisable` calls `RemoveNamedLocation(id)` if a graph exists. `Graph.AddNamedLocation` indexes by segment ID then marker ID; `RemoveNamedLocation` removes that ID from every segment bucket. A duplicate ID therefore matters, including to cleanup. Neither hierarchy name nor a scene serialization number is a validated durable cross-version identifier. Resolve with expected type, hierarchy and component checks, require exactly one match, and record build and original state; treat this as a proposed guard, not an existing host contract.
* `TrackMarker.set_Location` serializes the location, invalidates its cached pose and invokes `OnLocationChanged`. It neither calls graph add/remove nor writes a transform. Rebinding an already enabled marker requires explicit graph lifecycle handling; adding the new index without removing the old one can leave stale entries. Whether toggling a component or other sequencing is safe with every dependent component is untested. Do not call lifecycle methods manually as a substitute for a verified host sequence.
* `Track.TrackRelativePosition.Awake` finds the colocated marker. `TryApply` obtains its `PositionRotation` and, when a target exists, calls `MoveTransform`. The latter converts game coordinates using `Helpers.WorldTransformer.GameToWorld`, rotates the offset, optionally raycasts to terrain, and writes the target's world position and rotation. A failed terrain raycast returns false before writing the pose. `Apply` discards the result; `ConfigureAndApply` returns it and records `LastRuntimeApplySucceeded`. A location setter is not an explicit placement application. Inspect the actual target and its hierarchy before moving a root or child, and check resulting physical and logical state separately.
* If `targetActiveFollowsTrackGroup` is set, `Awake` observes the marker segment's group. `TryApply` unsubscribes and observes again while playing, even when placement fails. `SetTargetActive` invokes a supplied callback or calls `SetActive` on the target GameObject. `OnDestroy` unsubscribes; no `OnDisable` cleanup was found in this type. Rebinding, hiding a child and disabling a root can therefore have different effects. The target may be reactivated by group events. A scene instance and behavior after rebind still need verification.
* `Helpers.MilePost.Awake` obtains its colocated marker; `OnEnable` subscribes to location changes and `OnDisable` unsubscribes. Its event handler calls `UpdateMileage`, whose inspected 0.6.2 body is empty. `get_Origin` caches an origin by prefix and `FindOriginMilePost` searches for an origin with that prefix. These facts do not demonstrate automatic mileage recalculation, cache invalidation, or effects on other posts after an origin moves or is disabled.
* The prior scene inspection identifies `World/Signs/Loc: Sylva Int` as a standalone board with `RendererCuller`, `CircleMapMask` and `TextSynchronizer` on its root, and sign/text children. No marker or track-relative positioning was found in that hierarchy. Its scene hierarchy and component composition are identifying evidence for that inspected build, not a permanent public identifier. Moving its visual root does not establish any operational interchange change. Floating-origin conversion, culler bounds and mask updates need observation after movement. See [position control](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/PositionControl.md).

## Operation and lifecycle matrix

All relocation and disable outcomes below are runtime-untested for this investigation. Each row requires identity and component validation before an operation. First load means a fresh scene and graph; editor reload and live reapplication are separate cases, not assumed to recreate the same state.

| Representative and operation | First load | Editor reload | Live reapplication |
| --- | --- | --- | --- |
| Whistle or crossing marker, repair logical location | The code registers on `OnEnable` when location resolves. A correction before registration avoids retaining an old registration, but the patch hook and ordering need proof. Verify the named location and warning outcome. | Establish whether the scene object and graph are recreated or retained and whether the original or patched location is present. Resolve again; do not reuse an old object reference. | Inspect old index and dependent subscriptions. Remove old registration before adding the new one through a verified lifecycle, then verify exactly one new registration and none on the old segment. Setter alone is insufficient. |
| Marker visual, move or hide | Locate `targetTransform`; apply placement explicitly after a valid graph exists. Record offset, angle, terrain setting and success, then compare target pose and marker position. Hiding a renderer does not unregister the marker. | Test whether the target, pose and group observation were rebuilt or retained. Check for duplicate application and compare local and world poses. | Test reapply and group toggles; verify that a changed group has replaced the old subscription and that group callbacks cannot undo an intended active state. Preserve unrelated children and component state. |
| Milepost, move, rebind or disable | Record marker, prefix, origin flag, mileage and text. Registration and physical placement remain separate. The empty `UpdateMileage` body does not prove any automatic text change. | Check origin cache and displayed text after reload as separate observations. | Test both an origin and another post sharing its prefix. Check text, origin resolution, subscriptions and graph entry before and after disable/re-enable. Do not infer a repaired mileage chain. |
| Sylva independent board, move or disable | No logical marker to rebind. Check root versus child ownership and convert the destination to the correct coordinate space. Observe sign, text, culler and circle mask. | Resolve the board again and record whether original or changed pose and active state recur. | Apply twice and compare pose, active state, culling and mask. Check after a floating-origin shift; a renderer-only hide is not equivalent to root disable. |
| Retained bridge, move or disable | The guide establishes an editor limitation, not a specific bridge hierarchy or safe transform. Identify a concrete scene instance, its renderer, colliders and any controlling components first. | Re-identify the same bridge and compare root, child and collision state. | Compare repeated application and enable/disable with visual alignment, collider placement and adjacent track. No successful bridge relocation or collision safety is established. |

## Focused experiments and output

Run later in an isolated disposable map and save, with independently enabled cases and a separate probe. Keep original packs and normal saves untouched. Record game build, map identity, unique object match count, hierarchy and components, old and new segment/end/distance, group IDs, active flags, local/world/game poses, graph registrations, logs and repeated observations. Do not use a collision observation as proof of general safety.

1. **Marker lifecycle.** On a known whistle marker, replace its referenced segment and compare changing `Location` before registration, changing it after registration, and a verified disable/change/re-enable sequence. Query old and new segment registrations, warnings and train behavior. Expected output is a timestamped state table, including duplicate-ID and failure cases, not an assumed success. Reapply twice and perform a separate editor reload to discover object and graph identity changes.
2. **Physical placement and group ownership.** For an identified marker with `TrackRelativePosition`, move to a distant valid segment with a nonzero offset and angle; repeat with terrain snap where the raycast can fail. Record return/status, target and parent poses and child active flags. If a real group-following instance is found, change groups and toggle old and new groups independently. Output before/after poses and active states for first load, editor reload and two live applications.
3. **Milepost origin.** Identify an origin and at least one same-prefix post. Rebind and separately disable the origin; record each post's mileage, text and resolved origin before and after re-enable, editor reload and repeated live apply. Output an object-by-object comparison and cache observations. This tests the unknown behavior; it does not presume the empty handler recalculates anything.
4. **Board and bridge.** Identify the Sylva board and one concrete retained bridge. Independently move and disable each, capture hierarchy, renderers, colliders, culler and mask state, and compare before and after a verified floating-origin shift, editor reload and repeated live application. Output poses and screenshots plus mask and collision observations. Investigate unexpected behavior without treating one example as a generic contract.

Protected grade-crossing circuits remain a candidate only. `Track.Crossings.GradeCrossingController.CircuitSet` references approach and island spans, and `UpdateCircuit` uses occupancy and arrival estimates. First identify a scene-owned instance; a later isolated test must separately record endpoint resolution, train approaches in both directions, occupancy, gates, lights and bell. A marker repair alone does not establish circuit safety. Signals and CTC are excluded from this investigation.
