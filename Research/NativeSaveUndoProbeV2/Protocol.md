# Native Save and Undo probe v2 protocol

This follow-up probe is an experimental candidate for issue #34. The first probe and its results remain unchanged. The v2 runtime behavior has not yet been tested.

The mod installs its Harmony hooks once in `OnModLoad` and reports the number of owned `MapEditor.Save` prefixes at each world load. A count other than one is a failed prerequisite. The temporary objects have distinct baseline positions. Each assignment and history-token transfer logs the actual `localPosition` read from each object, as well as the tracked values. Capture baseline, apply, Undo and Redo, and compare every coordinate.

The native Undo manager remains responsible for history and executes each inverse. The candidate dirty guard augments `MapEditor.IsDirty`: it compares the last successful Save's native undo-group identity sequence and custom values with the current sequence and values. Undo and Redo create new native group objects; prefix/postfix hooks transfer a lightweight identity token from the consumed group to the resulting inverse group. This is metadata on the native history, not an alternative action stack. Save records the checkpoint only after `MapEditor.Save` returns successfully. The existing prefix writes the custom test file first and can throw a controlled `IOException`. The test must verify the displayed editor state and button, not only the probe's direct property read.

Test one ordinary save, then Undo and Redo back to that checkpoint. Verify the actual object positions, history names, dirty indication and Save enablement at each point. Create and save a native folder, undo it, and apply a different custom edit. Verify that the live count equals the saved count while the augmented dirty indication remains true and Save stays enabled. Save and verify that the custom file and native map match the current state. Test custom-write failure and native-map-lock failure with dirty state, existing error reporting and successful retries. A snapshot must include the actual transforms and both history names. Use only the disposable map.

The token scheme compares the retained native undo stack, not a complete document snapshot. History pruning, external mutations that bypass native history, other mods patching these methods, exceptions inside undo actions, event ordering and editor re-entry need separate assessment before production use. Conservative false-dirty results are possible. In particular, native change notifications may run before the postfix transfers a token; the trial must check the visible toolbar as well as the getter after Undo and Redo. Failure to meet any prerequisite is an observation, not permission to replace the native history manager.
