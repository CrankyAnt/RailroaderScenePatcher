# Construction of an additional crossing circuit

This static investigation supports [issue 21](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/21). It addresses adding detection on another track to an existing protected crossing. It does not establish that the construction works in a running game, survives a reload, or provides safe warning timing. No game was launched or mutated for this investigation.

## Sources and scope

The primary source is the installed `Railroader_Data/Managed/Railroader.dll`, SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. Method and field names below locate the inspected metadata and method bodies in that assembly. Findings are limited to this build. An independently authored metadata reader was built and used to inspect the assembly. The earlier [crossing operation report](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/ApplicableSceneOperations.md) supplies a previously observed existing crossing and circuit control. It does not demonstrate construction of a new circuit.

## Candidate construction

One concrete trial arrangement is a new `Track.Crossings.GradeCrossingController.CircuitSet` with three separate `Track.TrackSpan` components, assigned to `approachA`, `island`, and `approachB`. Append the set to the existing controller's `circuitSets` collection. `GradeCrossingController.UpdateCircuit` reads the island through `TrainController.AnyCarsOnSpan` and checks each approach through `CheckAndEstimateETA`. This supports testing the arrangement, but does not prove that three new spans are the minimum for every topology, or that an appended set operates correctly at runtime. The previously studied controller had two sets and six distinct spans; that observation is not a requirement for other crossings. Sources: `GradeCrossingController.UpdateCircuit` and `CircuitSet` metadata in the installed assembly; the prior operation report.

A guarded experiment needs the exact existing controller and graph, a physically established crossing of the additional track, and explicit segment IDs, ends and distances for each span endpoint. It also needs a populated graph and proof that the track is clear before changing membership or cleanup. A resolved endpoint alone does not prove connectivity or useful coverage. Capture original set order, references, endpoint values and graph registrations before any change. Select IDs unused in the graph and distinct from each other. Ensure the controller and graph remain the same throughout the operation. Sources: `Track.SerializableLocation`, `Track.TrackSpan.get_lower`, `get_upper`, `get_IsValid`, `UpdateCachedPointsIfNeeded`, `Track.Graph.SpanForId`, and `GradeCrossingController.UpdateCircuit`.

A candidate sequence for a disposable test is:

1. Create an inactive parent and three inactive `TrackSpan` objects. Assign each unique ID and its two serialized locations before activation. Assign the endpoints before asking for cached coverage. If endpoints are changed after a cache was populated, use the `lower` and `upper` setters or explicitly invalidate the cache; directly writing `_lower` or `_upper` does not invoke their invalidation. `SerializableLocation` carries `segmentId`, `distance`, and `end`.
2. Resolve both endpoints against the current graph. Check `IsValid`, then calculate `GetPoints`, `GetSegments`, and `Length`. Inspect the actual covered track, including connectedness and intended island and approach boundaries. Nonempty coverage and positive length are useful preconditions, not proof of correct warning behavior. `UpdateCachedPointsIfNeeded` calls `Graph.FindPoints` with clamped locations and retains the resulting cache until invalidated.
3. Check physical clearance independently. Activate the objects while the graph is available. `TrackSpan.OnEnable` calls `Graph.AddSpan` only when the graph exists and the ID is nonempty. Verify `Graph.SpanForId` returns the exact new object for every ID. An object enabled before the graph exists is not registered by that `OnEnable` call; do not assume a later registration without separate evidence.
4. Construct the set, populate all three references, and append it to the existing collection only after successful registration. Verify original set order and object identities and the new membership. Observe both original and added routes in a controlled runtime test before drawing a functional conclusion.

Sources: `Track.TrackSpan` endpoint setters, `InvalidateCache`, `GetPoints`, `GetSegments`, `UpdateCachedPointsIfNeeded`, `OnEnable`; `Track.Graph.AddSpan`, `SpanForId`; and `GradeCrossingController.UpdateCircuit` in the installed assembly. Unity component activation and exact initialization order for this arrangement remain to be tested in the game.

## Removal and failure handling

First confirm physical clearance and that the controller, graph, original membership and registrations still match the captured baseline. Remove only the exact added set from the controller. Before disabling any created span, verify each registered ID still resolves to that exact span. Disable the created objects, verify their registrations are absent, destroy the created parent, and compare all original references, endpoints and registrations with the baseline. Refuse destructive cleanup if ownership or baseline checks fail; discard the disposable session without saving and investigate. The static inspection does not establish that these checks cover all dependent state.

`Graph.AddSpan` uses `TryAdd`, while `Graph.RemoveSpan` removes by ID without testing object identity. A duplicate ID can therefore leave an existing registration in place when adding fails, and later disabling the duplicate can remove the existing object's registration. Recheck ownership immediately before deactivation, including partial initialization and error paths. Do not disable a potentially conflicting span merely to roll back. Sources: `Track.Graph.AddSpan`, `RemoveSpan`, `SpanForId`; `Track.TrackSpan.OnEnable` and `OnDisable`.

## Runtime evidence

A guarded runtime trial needs to show that the new set initializes after the world is ready, detects an actual train on the added route, preserves original detection, controls the intended crossing, and can be removed cleanly. Separate observations cover approach and island behavior, physical warnings, timing, cleanup, and reproduction after a fresh world load. The [completed feasibility report](AdditionalCrossingDetection.md) records those bounded trials and their limits. These results come from runtime observations, rather than metadata, endpoint resolution, or nonempty cached coverage alone.
