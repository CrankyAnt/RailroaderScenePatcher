# Warning timing for marker repair

Working note for issue 18. Static inspection used Mono.Cecil 6.0.4's bundled assembly against installed `Railroader_Data/Managed/Railroader.dll`, SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. These implementation details are version-specific and do not establish a supported mod API.

## Native warning and removal

`Track.TrackMarker.OnEnable` gets `Location` and checks its nullable value and `IsValid`. On failure it calls `Game.Diagnostics.MessageLog.Warning` with the Unity object name as `originator`, a formatted description identifying the marker ID, segment ID and distance, source `System`, and the marker ID as `deduplicationKey`. It then returns. On success it calls `Graph.AddNamedLocation`. The returned diagnostic object from the warning call is discarded. `set_Location` does not register a marker; see [SceneLifecycle.md at 0f8d3fb](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/0f8d3fb69cc362c5a56a22910bdb5a93aa75acc3/Research/SceneLifecycle.md).

`MessageLog.Warning` calls `IMessageCollector.LogMessage`. `MessageCollector.LogMessage` calls `Collect` and logs through Serilog. The public `Game.Diagnostics.MessageCollector.Active` returns `IMessageCollector`; `Messages` is `IReadOnlyList<DiagnosticMessage>`, and `RemoveMessage(DiagnosticMessage)` accepts a specific object. `DiagnosticMessage` exposes `Severity`, `Source`, `DeduplicationKey`, `Originator`, `Description` and `IsRemoved`. The actual `MessageCollector.RemoveMessage` marks and removes the supplied object and raises `OnMessageRemoved`. `UI.Diagnostics.MessageLogWindow.OnEnable` subscribes to that event; its handler schedules a refresh. This is a concrete candidate for clearing one resolved in-game diagnostic, subject to runtime verification. It does not erase the already written Serilog text.

`Active` falls back to `SerilogCollector.Instance` when no shared `MessageCollector` exists. That fallback's `RemoveMessage` is empty. Verify the actual collector and final UI, rather than assuming a call succeeded. `Collect` can update an existing message when deduplication applies. The ID alone is therefore insufficient to prove ownership. After proving the marker and graph repair, require one unambiguous current warning matching severity, source, key, originator, and the expected marker-specific description. Preserve all other diagnostics; leave ambiguity untouched and report it.

## Timing evidence and limits

`Game.Scripting.Modding.Managed.ModAssemblyManager.WorldLoad` invokes `IWorldLifecycle.OnWorldLoad` once for loaded entries implementing the interface. `AssetPackManager.ExecuteMainScriptsOnWorldLoad` calls `WorldLoad`. The complete scene activation and graph initialization order and any supported earlier hook remain unverified. Static code alone does not prove callback timing.

The assignment reports two disposable fresh-process runs where the probe repaired M5pp on the first `Update` after `OnWorldLoad` and verified matching graph registration. Their saved logs each retain the native missing Shuo warning: `C:/TMP/RailroaderMapResearch/Issue18BrokenHome/Player-BrokenArmed01.log:156` and `Player-BrokenArmed02.log:156`. Those lines were checked directly. The continued presence of a historical file log and the current in-game diagnostic are separate observations.

The minimum next test is a fresh disposable process that records the matched diagnostic and an unrelated warning, verifies M5pp and graph repair, removes only the exact matched diagnostic through the actual collector, and checks the current message list and visible message window after refresh. Verify the unrelated warning remains, and record that the historical file log remains. Also test an ambiguous or absent match without removing anything. An earlier callback remains a separate question: observe marker availability, graph and destination readiness, and warning emission at candidate supported callbacks before claiming prevention is possible.

## Earlier lifecycle investigation

Additional static inspection included nested compiler-generated async methods. `UI.Menu.GlobalGameManager._Launch` publishes `Game.Events.MapWillLoadEvent` before it calls `Multiplayer.ConnectClient`. The event and `EventBus.Subscribe` methods are public in this build. This is an earlier notification, not evidence that the target scene object or destination graph exists there, or that a given mod has already subscribed. `ModAssemblyManager.InstantiateAndLoad` invokes `IModEntryPoint.OnModLoad` as packs load, but mod-selection and reconciliation paths can affect when that happens.

`GlobalGameManager.HandleClientDidReceiveSnapshot` distinguishes editor pack mode from save mod reconciliation. When its map-load condition holds, it awaits `LoadMap`, then populates state from the snapshot and calls `IMainScriptLifecycle.ExecuteMainScriptsOnWorldLoad`. `AssetPackManager.ExecuteMainScriptsOnWorldLoad` calls `ModAssemblyManager.WorldLoad`, which invokes the loaded entries' `IWorldLifecycle.OnWorldLoad`. `LoadMap` awaits the selected scene loads through `LoadSceneAsyncAsync`; the latter uses `SceneDescriptor.LoadAsync` and Unity's scene manager. `Game.MapLoader.Awake` and `OnEnable` contain calls to `LoadMapData`, which creates the graph and assigns `Graph.Shared` on its applicable path. These are code paths and conditional ordering, not a proof of all callback ordering or availability. Unity owns scene activation and `TrackMarker.OnEnable`; the static inspection alone does not place that callback against every other object's callbacks. In particular, it does not establish an editable target with a ready destination graph between scene creation and the marker's first `OnEnable`.

The earliest named public notification located was `MapWillLoadEvent`; it is too early to establish that it can perform the requested object mutation. `OnModLoad` is another public entry point but the observed source does not establish a suitable scene and graph at that moment. `OnWorldLoad` is later in the snapshot path. Neither editor fixture nor ordinary save has a demonstrated supported callback that can both access the target and destination graph and repair the marker before its warning. This is an evidence limit, not a claim that no such hook exists. A direct comparison would require instrumentation of mod load, map-will-load, graph readiness, scene-object availability and warning emission for each load mode; the exact ordering must be observed separately for both.
