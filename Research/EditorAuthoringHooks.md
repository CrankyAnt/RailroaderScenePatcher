# Editor authoring hooks

Research for [Identify editor extension points for scene-object authoring](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/4), 2026-11-07. This is a static inspection, not a running extension or an interactive editor test. The installed experimental build was identified by the previous [0.6.2 inventory](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/FinalObservations.md). The inspected `Railroader_Data/Managed/Railroader.dll` SHA-256 is `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. Method references below identify observations from that binary, read with Mono.Cecil. They are internal implementation details, not a stable API. Online documentation was retrieved on 2026-11-07 and may change independently of the installed build.

## Finding

The documented extension mechanisms do not establish a map-editor inspector or selection extension point. A DLL can use the documented loading and lifecycle contract and inspect internal editor state, but every editor-specific connection below requires an unsupported, version-sensitive integration and remains runtime-untested. A separate diagnostic view backed by a scene inventory and graph comparison is a concrete investigation route; whether it can be opened and updated during an editor session must be tested. No inspected hook establishes a general scene-object editor or safe automatic repair.

## Documented extension patterns

The [Relay UI reference](https://docs.railroadergame.com/modding/relay-api/railroader/ui/) documents `ui.extend` for named car inspector points, plus custom windows and commands. Its listed company window point is reserved and not invoked. Unknown extension-point names return null. It lists no map editor point. This is evidence about the published list, not proof no private hook exists. The [Main.rl reference](https://docs.railroadergame.com/modding/main-rl/) describes script lifecycle; it does not establish editor-session availability of a particular window.

The [DLL contract](https://docs.railroadergame.com/modding/dll-mods/) documents `IModEntryPoint` and optional `IWorldLifecycle`; DLL loading is experimental and off by default. The contract provides lifecycle and context, not editor selection or inspector registration. Access to game and Unity assemblies is explicitly unsupported and can change. Entry points must clean up event subscriptions and objects; assembly static state survives re-enabling. Whether world lifecycle fires at the useful point in this editor is an empirical question.

The [map guide](https://docs.railroadergame.com/modding/map-modding/) documents editable track, operations and map objects and undo across native tools. It excludes signs, mileposts, map icons, signals and some scene scenery. The editor loads map data without `modifyMap` patches; save writes the mod map data, while exit discards unsaved editor changes. Layering on the base map is not officially supported. This prevents treating a runtime Data.rl patch as an editor preview.

## Inspected internal paths

All rows are **internal code inspected; runtime untested**. Public accessibility in an assembly is not a support promise.

| Capability | Evidence in the identified assembly | Limit |
| --- | --- | --- |
| Locate editor and observe selection | `Game.MapEditor.MapEditorController.OnEnable` checks host and loaded map, sets `Shared`, constructs `MapEditor`, subscribes to `MapEditorSelection.SelectionChanged`, and creates `MapEditorWindow`. `MapEditor.Selection` exposes selected items, typed enumerations, and `SelectionChanged`. | Availability and timing relative to mod callbacks are untested. Subscribe and unsubscribe with the actual editor lifetime. A selection event does not discover unselectable scene objects. |
| Selection and focus | `MapEditorSelection.Select`, `SetItems`, `SelectionCenter`, and `TryGetItemPosition` handle native selectable kinds. Position cases include graph nodes, segments, turntables, map-object DTOs, spawns, areas and industries. `MapEditorController.FocusSelection` passes the selection center to `CameraSelector.JumpToPoint`. | No inspected selectable case establishes arbitrary Unity scene-object selection. A separate camera jump to an inventory object's position is plausible but untested and requires correct coordinate conversion. It does not confer native inspector selection. |
| Outline and inspector | `MapEditorOutline.Build` takes `MapDTO`, categories and a tombstone view. `MapEditorWindow.BuildInspectorColumn` dispatches to concrete terrain, folder, spawn, operations, map-object, prop, turntable, track and tombstone inspectors. | The inspected dispatcher offers no documented registration call for an external type. Reflection or method patching is not evidence that arbitrary inspector sections can be integrated reliably. |
| Graph edits | `GraphEditor.NodeDidChange` is an event and `OnGraphNodeDidChange` invokes it. `DeleteNodeInternal` calls `Graph.RemoveSegment` for incident segments and `Graph.RemoveNode`; `DeleteSegmentInternal` calls `Graph.RemoveSegment`. Both register undo actions. | A node change notification is not proof that every segment deletion, property edit, geometry edit, undo and redo produces a complete notification. Capture before/after graph state or inspect additional graph callbacks before relying on coverage. |
| Refresh after native undo activity | `MapEditorController.OnEnable` subscribes to `UndoManager.DidChange`. `OnUndoManagerChanged` refreshes gizmo state, reconciles enabled content, marks the outline stale, and rebuilds the window when undoing or redoing. | It is a broad change signal, not a typed change set. Its timing, grouping, preview-drag behavior and coverage for all graph mutations need tests. |
| Existing warnings | `Track.TrackMarker.OnEnable` checks location validity, emits a `MessageLog.Warning` when invalid, and otherwise registers a named location with the graph. `MapEditorController.DeleteSelection` presents returned delete warnings as a toast. `MapEditorWindow.BuildLayerWarnings` displays `ActiveMapDefinition.MapLayerWarnings`. | These are different warning sources. None proves a continuously updated, exhaustive list of broken references or a registration point for custom warning rows. Initial warnings miss valid but misplaced markers and independent objects. |
| Native preview and undo | `MapEditor` exposes `PerformUndoable`, grouping, `Undo`, `Redo` and `Save`; `GraphEditor` registers undo for native deletion. The editor owns its selection and DTO inspectors. | Those methods do not prove that an arbitrary scene `Transform`, marker registration or another mod's state participates in undo or saved map data. A diagnostic-only view avoids asserting such coverage. |

The [previous position analysis](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/PositionControl.md) identifies a scene location board without `TrackMarker` or `TrackRelativePosition`. The [inventory observations](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/FinalObservations.md) report a marker whose segment still resolved after moving track while its board remained in the old position. Thus a useful inventory must include independent scene objects and valid references with changed spatial relationships, not just missing-marker warnings. Proximity indicates a candidate for review, not a proven dependency or error.

## Bounded empirical questions

These experiments are not production implementation tasks. Use a disposable editor map and record build hash and observations without modifying normal saves or existing mods.

1. **Editor lifetime and diagnostic view.** Does a DLL lifecycle callback find the controller at editor entry, and can a separate view remain usable until exit? Observe entry, close, re-entry and mod disable; record callback order, controller identity, view visibility and cleanup. This tests the route, not support for a native inspector extension.
2. **Scene inventory and focus.** Can representative marker-backed and independent scene objects be enumerated with stable identifiers and game-space positions, including inactive objects? Compare a known marker and the previously identified location board with a read-only hierarchy inventory. Attempt camera focus and record destination after an origin shift. Record omissions and identity collisions.
3. **Edit notification completeness.** Which notifications occur for delete segment, delete node with incident segments, move an endpoint, change segment properties, drag preview, undo and redo? Log `NodeDidChange` and `UndoManager.DidChange` with before/after graph IDs and geometry. Record event ordering and missed or duplicate changes; do not infer complete coverage from event names.
4. **Warning freshness and scope.** In the same disposable map, compare the initial marker warning, delete warnings and layer banner with a fresh inventory after deletion and a same-ID movement. Record whether each is emitted or refreshed and whether it identifies the affected scene object. Include an independent object and a valid but spatially displaced marker.
5. **Preview and undo boundary.** For a single disposable marker-backed object, compare its transform, graph registration, native dirty state and saved JSON before a diagnostic preview, after cancel, undo, save and reload. The result establishes only that tested operation; it cannot establish safety for signals or other dependent components.
