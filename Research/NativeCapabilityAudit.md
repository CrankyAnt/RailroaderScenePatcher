# Native capability and scene ownership audit

Research for [issue 17](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/17), the [support boundary](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/7#issuecomment-6715003887) and [map issue 3](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/3). This audit covers the original inventory, not arbitrary Unity objects. Signals, CTC and interlocking, model changes and mile-value editing are excluded. Restoration means restoring earlier pose, bindings, activity and affected state, not redesigning mileage origins.

## Evidence and limits

The installed `Railroader_Data/Managed/Railroader.dll` has SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`, matching the [0.6.2 lifecycle audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/0f8d3fb69cc362c5a56a22910bdb5a93aa75acc3/Research/SceneLifecycle.md). It does not identify every game asset. The original audit read metadata and method string operands from that assembly without running the game; the continuation records later editor observations separately. The earlier scene inventory and experiments used the same assembly identity, but their asset identities and bounded observations remain as recorded there. Official pages were checked on 2026-11-08; they are mutable and do not establish runtime behavior in this installation.

The [map guide](https://docs.railroadergame.com/modding/map-modding/), retrieved again on 2026-11-08, documents editable track, operations, props, structures, paths and terrain. It lists signs, mileposts, progression and some base-map scenery among editor limitations, and says passenger stops can be defined but are not yet usable in game. The earlier audit recorded a different version of the sign wording; the current documentation and the separate player-sign observation below must not be conflated. The guide says Save writes the mod's `Data/Map.json` and terrain and exit discards unsaved changes. It describes inherited map-data overrides, not general editing of retained scene objects. [Data.rl](https://docs.railroadergame.com/modding/data-rl/) modifies map JSON before deserialization and does not run in the editor. Native support for a map-data object therefore does not establish an edit path for a retained scene counterpart.

## Native routes and sign distinction

Static inspection of `Game.MapEditor.MapEditorCreateMenu.Build` found entries for track nodes, turntables, builtins, structures, paths, props, masks, spawns, areas and folders. No sign-labelled entry occurs in that method. Its method strings are evidence of that menu only, not of every context menu or possible indirect creation route. `MapEditorCreation` has creation methods for track spans, nodes, turntables and map objects. `MapObjectDTO` exposes position, rotation, scale, folder and enabled fields. These metadata names establish available structures, not that a particular scene instance can be selected or saved through them. The prior [editor hook audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/research/issue-4-editor-authoring-hooks/Research/EditorAuthoringHooks.md) identified typed selection and inspector dispatch, without a general scene-object selection path. The [diagnostic observation](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/research/issue-14-editor-diagnostics/Research/EditorDiagnostics.md) demonstrated camera focus separately from native selection in its fixture.

Another native context route exists. Static method string operands identify `UI.ContextMenu.TrackContextMenu.TryShow` with `Place Sign`, and `Game.Mow.PlayerSignPickable.ShowMenu` with `Edit Sign`. `PlayerSignWindow` names Speed and Resume types and Place, Delete, Move and Save actions. `PlayerSign` has kind, text, location, position and rotation fields, with serialization keys in `ToValue` and `TryFromValue`. The later editor observation below confirms that the track context route is available there and distinguishes its state from map-mod data. The editor create menu and player-sign route are distinct inspected classes; neither proves that a retained `TrackMarker` or its visual target is editable. Creating a sign does not establish that it edits or replaces its pre-existing scene counterpart.

## Continuation: native dispatch and later observations

This continuation answers the revised [issue 17](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/17). The earlier matrix preserves the state of the original audit; the later evidence below supersedes its statements that no milepost pair or concrete group-following instance had been identified. The [operation report at b41a6dd](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/ApplicableSceneOperations.md) owns the detailed mutation and restoration observations under issue 18. ### Typed editor boundary

On 2026-11-08 the installed `Railroader.dll` again hashed to `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. Read-only inspection used Mono.Cecil 0.11.6.0 to enumerate metadata, field types and method operands. It found ten `SelectableItem.From*` factories: graph node, segment and turntable; spawn, area and industry DTOs; industry child DTO; map-object DTO; operations `TrackSpanDTO`; and folder. `MapEditorSelection` exposes corresponding typed selections. `MapEditorWindow.BuildInspectorColumn` dispatches terrain, folder, spawn, operations, map-object, turntable, track and tombstone inspectors. `MapEditorCreation.CreateTrackSpan` constructs `Model.Ops.Data.TrackSpanDTO`. The track-span gizmo accepts that DTO even though it reads color constants from `Track.TrackSpan`.

The inspected `MapEditor.Save` calls `MapSerializer.MergeGraphInto` and `MapDataIO.SaveToJson` and `SaveToFile`, with map objects, folders and operations data in its path. This agrees with the [official map guide](https://docs.railroadergame.com/modding/map-modding/) on map-mod `Data/Map.json` ownership. The documented save route does not establish serialization of arbitrary retained Unity scene components. These are internal implementation observations for this build, not an exhaustive proof that no indirect or undocumented native route exists. `TrackAnchorReposer` does use `TrackMarker` and `TrackRelativePosition` for native map-object handling, so component type alone does not prove a retained object is selectable or unselectable.

`MapDTO` declares graph, operations, objects, spawns and folders, plus an extra-sections dictionary. It declares no crossing-controller field. `GradeCrossingController` has its own list of circuit sets; each `CircuitSet` holds `Track.TrackSpan` references named `approachA`, `island` and `approachB`. A read-only scan of fields and method operands in `Game.MapEditor`, `Track.Data` and `Track.Serialization`, including nested types, found no reference to `GradeCrossingController` or `CircuitSet`. This covers the named types and inspected direct references, not reflection, external assemblies, extension data semantics or an uninspected indirect route. Combined with the typed selection, inspector, span factory and save paths, it supports a version-specific gap in the inspected native editor for the retained controller's detection circuit, rather than treating the lack of a click as the only evidence. It does not establish that a new unrelated operations span is wired to that controller.

The local installed `br-industries`, `eastwhittiermowyard`, `Katers-SylvaInterchange`, `Sox's Ela Rework` and `wh-crossover` packs provide additional map-overlay examples. Read-only inspection of their `Definitions.json`, `Data/Map.json` and `Scripts/Data.rl` found map definitions and native graph, operations, object or folder data; Sox also defines a load. Their scripts call `modifyMap` and `map.merge`, and the inspected prop placements refer to existing `rr/` definitions. These examples did not identify a crossing circuit or controller binding. A text search of installed core and bundled asset-pack JSON and Relay files for grade-crossing, crossing-gate, crossing-signal and circuit-set terms also returned no matches. These local files are version-dependent evidence, not a search of bundled binary assets or a guarantee about other mods. No third-party files or assets are reproduced here.

For authoring, the distinction is that the operations span factory and inspector address a map-data DTO, whereas the Bryson Everett controller owns six retained scene `TrackSpan` components in two circuit sets. A native operations span or physical crossing prop is therefore not evidence of changing an existing approach or island endpoint, controller membership, parallel-track detection or detached detection. No such route was found in the inspected paths. A successful custom mutation does not establish a native gap by itself. For the crossing boundary decision, record endpoint changes, adding or removing span components, circuit-set membership and controller ownership separately from equipment placement.

The [official experimental FAQ](https://community.railroadergame.com/t/experimental-faqs-known-issues-planned-improvements/129), checked on 2026-11-08, lists the ability to edit crossings among planned map-editor improvements. It does not specify controller fields or identify the tested instance. The internal paths above supply the narrower build-specific evidence for those fields.

### Native editor crossing and Resume observation

A normal Steam launch without additional arguments opened the disposable `crankyant/native-audit-map` map editor. Its map definition layered `rr/bushnell-whittier` and used `rr/nc-bryson` terrain after correcting the initially missing terrain configuration outside the game. A native spawn named `crossing-focus`, placed at the retained crossing's recorded scene position, allowed native Focus Selection to reach Bryson Everett. The load log identified the core `nc-bryson` terrain. The fixture and its temporary spawn are separate from normal saves and existing mods.

With Select active, no category filter and prior selection cleared, clicking the crossing's crossbuck left `Nothing selected`. Right-click highlighted the equipment but displayed no menu. This is one equipment target and interaction, not proof that every part or indirect route is unavailable. It is consistent with the typed editor and controller evidence above. The observation does not test an edit or save of scene spans or circuit membership.

Right-clicking nearby track in the editor opened a menu with `Place Sign` and `Place Fusee`. `Place Sign` offered Speed and Resume. Selecting Resume and placing it produced a visible green sign. The game log recorded a Resume Speed sign on `S8rj` at `b|7.533474`. The disposable map file's SHA-256 remained `3BF37EF9B150929D282171D974CFC2659DF27414A552ED28C5DAAF88853A227B` and the editor did not mark the map dirty after placement.

As a save control, a native folder was then created and the map was saved. The native save log and map data contained the new folder and the temporary spawn, but no sign section, key, kind or location. The resulting map file SHA-256 was `272EF9388C4CEDFB507673A142792EA10CEBB7B98CA86397C5F3D369FB80E9E6`. Right-clicking the Resume sign opened `Edit Sign` with Resume selected and Cancel, Delete, Move and Save actions. Delete removed the visible sign; the map file hash remained unchanged. These observations show editor-session placement and deletion and a controlled map save that omitted the placed sign. They do not establish Resume persistence in an ordinary save or deletion across a fresh reload.

A second Resume sign was placed after that map save. The operator exited the editor and reloaded the same map in the same game process. The saved folder remained visible in the hierarchy, and the saved spawn remained selectable and focused the crossing. The second green Resume sign was absent at the crossing and nearby track. Because that second sign was placed after the last map save, this is an unsaved editor-world reload observation, not a fresh-process test of a saved Resume sign. The first sign was present during the controlled map save and omitted from the file; it was explicitly deleted before this second placement.

The game was quit after the world reload. The disposable `ModDev/native-audit` folder was removed and a subsequent existence check returned false. Original mods and normal saves were not edited for this continuation.

The historical FUSE passenger entry in the [original scope inventory](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/Scope/ScopeInventory.md) reports a pre-2026-10-27 experimental-release search result, not a captured current fixture, exact binding or owning component. The current official guide's passenger-stop limitation is documentation, not proof of that warning's owner. Do not assign it to the known OpsDTO loader or a retained scene object without additional source evidence. [Recover ownership of unresolved inventory candidates](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/20) owns recovery of the warning and its map/version context and identification of its emitter and affected object. Until then the historical observation cannot establish a current scene repair target. The independently identified OpsDTO cases remain native map-data cases, not an exclusion of passenger objects as a family.

### Remaining native evidence and its owners

The inspected typed editor and serialization paths and the crossing equipment observation support the bounded circuit gap above. A targeted native editor check can identify a route missed by static inspection, but a click on every child span is not required to establish what those paths handle. Save and reload of a retained edit could not be tested through the inspected paths because those paths exposed no retained-edit route. If another route is found, compare its saved map-mod owner and fresh-process reload. Resume player-save and delete/reload persistence remain unobserved, but are not needed to establish the observed map-authoring distinction. Record exactly which menus and dispatch paths were inspected; do not turn that bounded finding into a claim about all possible routes. The candidate-ownership continuation owns the remaining identified passenger and marker ownership questions.

The remaining runtime mutation, consumer, and restoration questions belong to [issue 18](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/18). The circuit editing product boundary belongs to [issue 19](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/19). The static audit does not establish a native map-mod save or reload for any retained scene change.

## Original proposed follow-up evidence

These were the original proposals, retained for provenance. The continuation above and the issue 18 report identify what has since been observed and which issue owns each remaining question:

1. Inspect the native map context menu and any editor sign routes, their exact types and ownership. Create, select, edit, save and reload a native sign, then separately try to select and edit an identified retained scene sign. Compare saved map data, scene identity and resulting registration. Include the Speed and Resume player-sign route only after identifying its actual context and persistence owner.
2. Exercise a concrete marker-backed object with a broken reference and one valid but spatially misplaced object. Separate reference, graph registration, direct pose, track-relative placement and activity. Existing M5pp observations cover only their recorded cases. Capture old and new groups and check explicit disable against group activation if an actual group-following instance exists.
3. Identify a milepost origin and same-prefix dependent. Restore the prior binding, pose and activity and inspect registrations, origin resolution and dependent display without editing mileage values.
4. Inspect the named retained bridge's children, collision and construction relationships before move and disable cases. Check the independent board's mask, culling and floating-origin behavior where not already observed.
5. For the identified protected crossing, repair a selected child span's existing endpoints and separately move or disable equipment. Check both approaches, island occupancy, gates, lights and bell before and after restoration, repeat and reload.
6. Where an original inventory candidate remains unresolved, first identify its owner and applicable relationships; do not turn missing evidence into an exclusion. Compare editor save/reload and ordinary-save application independently. Record build, object identity, original and replacement state, registration and affected consumers.

The original audit made no game or profile changes. The later observations and their disposable fixtures are identified above; the original proposals alone are not runtime results.
