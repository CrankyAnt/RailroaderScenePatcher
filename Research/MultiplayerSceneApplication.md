# Multiplayer scene application

Research for [Investigate host and client scene application including late join](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/31), serving [Choose the compatibility and dependency contract](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/11). This is source analysis, not a multiplayer observation or an implementation specification. The inspected installation is Railroader 0.6.2, build 26335745. On 2026-11-09 `Railroader_Data/Managed/Railroader.dll` had SHA-256 `8E9ACFD583C1DA79655C970773D42F2179E999F62DC36A3C6BC3A7B94C27A91E`. Method names identify the primary source, inspected read-only using Mono.Cecil. The assembly hash does not identify scene bundles. These internal methods are unsupported and may change. Official documentation was retrieved on 2026-11-09 and is not pinned to the installed build.

## Installation and data

The [map guide](https://docs.railroadergame.com/modding/map-modding/) says each player installs a custom map mod, the host sends its mod list, and missing or different required versions block joining. Mods are not downloaded automatically. The [manifest reference](https://docs.railroadergame.com/modding/info-json/) distinguishes default required `unscoped` packs from `optional` packs, which can differ or be absent, and requires dependencies to be present at compatible versions. The [DLL guide](https://docs.railroadergame.com/modding/dll-mods/) requires each installation to enable unsafe DLL mods and restart. The guide says matching DLL pack identifiers and versions does not verify matching code. The [installation guide](https://docs.railroadergame.com/modding/installing-mods/) describes local installation and restart for discovery.

A required patch-bearing pack and required patcher dependency therefore need to be installed and loadable locally on each peer. Manifest agreement does not establish equal patch JSON bytes or equal DLL bytes. The native manifest is not evidence that a patch was read, applied or successfully matched on any peer. A client's disabled unsafe-DLL setting and the exact join outcome for that case are not established by the cited documentation. The product's cross-peer content and failure contract belongs to the compatibility decision, not this report.

## Join, restore and local construction

The official [DLL guide](https://docs.railroadergame.com/modding/dll-mods/) says lifecycle hooks run on each peer that loads the DLL. Once-per-session shared writes need a host check. That rule does not replicate arbitrary Unity objects.

In the inspected assembly, `Network.Client.ClientManager.RequestSnapshotAfterModReconcileAsync` waits for mod reconciliation before requesting the snapshot. `Game.HostManager.HandleMessageAuthenticated` defers a remote client's snapshot request until the host client is active; `SendSnapshotTo` sends a copy of the host snapshot. `UI.Menu.GlobalGameManager.HandleClientDidReceiveSnapshot` loads the selected map when no map is current or the identifier differs. It then calls `StateManager.PopulateFromRemoteSnapshot`, runs world-load scripts and requests active status. The same-map branch can skip `LoadMap`; a repeated callback is not proof of a new scene. Sources: those methods and their compiler-generated async state machines in `Railroader.dll`; [prior lifecycle analysis](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/3e5970722bb278cbbaee003300ada6ce916df702/Research/ApplicableLifecycleStatic.md).

`GlobalGameManager.LoadMap` resolves and activates the local map definition, loads GameUI and the map scene list. `MapLoader.Awake` loads map data and assigns `Track.Graph.Shared`. During scene activation, components can register before `MapDidLoad` and `OnWorldLoad`. `TrackMarker.OnEnable` resolves and registers a valid location or emits its warning immediately. A fixture-specific earlier run observed a guarded repair at this activation point, before `OnWorldLoad`; it does not establish a universal early hook or readiness for every object. [Prior lifecycle analysis](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/3e5970722bb278cbbaee003300ada6ce916df702/Research/ApplicableLifecycleStatic.md); [early repair evidence](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/21d88d1f99545a3b25bdcd7d9476fa54ace4969f/Research/EarlySceneRepair.md).

`Game.Messages.Snapshot` contains map identity and time, cars, switches and property dictionaries among other game state. Its map record has no generic scene transforms, component registrations or crossing circuit definitions. `PopulateFromRemoteSnapshot` restores cars and properties, then calls `RestoreNotifier.NotifyDidRestore`; `GameBehaviour.OnEnable` queues `OnEnableWithProperties` through that notifier. This establishes the inspected initial snapshot path, not a claim that no other message ever affects any scene object. It does not carry an arbitrary patcher's local scene mutations. A late joiner loads its local map when needed, or reconciles the retained local map on the same-map path. Its applicable scene changes must exist locally as well as receiving shared state. Source: `Snapshot`, nested `Snapshot.Map`, `PopulateFromRemoteSnapshot`, `GameBehaviour.OnEnable` and `RestoreNotifier`.

## Operation mechanisms

| Mechanism | Per-peer consequence | Source and limit |
| --- | --- | --- |
| Pose and active state | Apply the intended physical transform or activity to each local scene instance. A logical location change is separate from placement. Local group callbacks can change activity later. | `TrackRelativePosition.TryApply`, `MoveTransform`, `ObserveTrackGroup`; [lifecycle analysis](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/3e5970722bb278cbbaee003300ada6ce916df702/Research/ApplicableLifecycleStatic.md). The snapshot fields do not supply a general scene-transform channel. |
| Marker binding and registration | Bind against each peer's current graph and maintain that graph's named-location registration. A location setter invalidates pose and sends a local event; it does not itself repair the graph index. Apply before registration when that specific path and inputs are ready, or handle the old registration and consumers explicitly. | `TrackMarker.OnEnable`, `OnDisable`, `set_Location`, `Graph.AddNamedLocation` and `RemoveNamedLocation`; [scene lifecycle](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/0f8d3fb69cc362c5a56a22910bdb5a93aa75acc3/Research/SceneLifecycle.md). Earlier activation may precede world-load hooks. |
| Group subscriptions and cached or generated state | Rebind and clean up local observers and dependent state along with local position or geometry. A group subscription or generated mesh is not established by receiving a game property. | `TrackRelativePosition.TryApply`, `ObserveTrackGroup`, `OnDestroy`; [operation batch reports](https://github.com/CrankyAnt/RailroaderScenePatcher/tree/f4e49fc6b2471ba3aeae01945dfedeb9c4fbd60e/Research/SceneOperationBatch). Graph replacement matters because unsubscribe consults the current graph. Do not infer universal regeneration from one object family. |
| Crossing detection | Construct and register spans on each local graph with distinct IDs and attach the intended circuit set to each local controller. Check endpoints, cache and membership. `AddSpan` uses `TryAdd`, whereas removal uses the ID, so conflicting cleanup can remove another registration. | `TrackSpan.OnEnable`, endpoint setters and `Graph.AddSpan`/`RemoveSpan`; `GradeCrossingController.UpdateCircuit`; [crossing construction](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/9495abf1fcef5f3c129a6ebd63a0af8a3c62604a/Research/CrossingConstruction.md). Prior single-process trial demonstrated one topology, not a multiplayer run. |
| Crossing equipment and sound | Construct local equipment under the intended local controller and initialize local lamp and gate observers. The controller creates its own bell player and owns the loaded audio reference. An additional bell needs its own binding and lifetime; cloning a signal does not create it. | `GradeCrossingController.OnEnableWithProperties`, `CreateBellPlayer`, `LoadBellAudio`, `OnDisable`; lamp and gate `OnEnableWithProperties`; [equipment sources and trial](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/9c0403e487c98a0ac422ed67fa103e19d9e94be3/Research/CrossingEquipmentSources.md). A locally added device does not automatically enter the original culler's list. |

The inspected crossing controller starts its own circuit coroutine in `OnEnableWithProperties` and sets its `lights`, `gates` and `bell` keys from computed circuit state. Its method contains no host check. Registered game property objects can participate in the synchronized property mechanism, but the controller's use of a `KeyValueObject` alone does not prove that a particular scene instance registers that object as a shared property object. Do not assume that crossing outputs are replicated merely because the snapshot has a property dictionary. Source: `GradeCrossingController.OnEnableWithProperties`, `LoopCoroutine`, `set_SignalLights`; `StateManager.RegisterPropertyObject`; `RollingStock.Controls.GlobalKeyValueObject.OnEnable`.

## Re-entry, failure and limits

Treat application as belonging to a particular local world, graph and scene instance. Resolve target identities again when these change, and detect an already applied operation on a retained instance. Repeated callbacks must not append duplicate circuit sets, spans, equipment or observers. Remove only owned registrations and additions, restore prior bindings and dependent state where the operation supports restoration, and release observers and audio references with their owners. These are consequences of the inspected local ownership and ID-based removal paths, not a native exactly-once guarantee. A reconnect that retains the same map can take the same-map path, so neither an unconditional second addition nor an assumption of fresh scene construction is justified.

No inspected native path reports a patcher's arbitrary local operation failure to the other peers. A local failure therefore does not establish remote failure, rollback, disconnection or consistency. The [failure decision](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/10#issuecomment-6731647920) requires isolated failures, restoration and continued ordinary play. Unknown JSON-content and format-recovery diagnostics belong only in the editor. Cross-peer consequences remain with the compatibility decision. The source establishes the responsibilities and ordering above, conditional on this build and the relevant loader branch. It does not establish identical JSON contents, a universal pre-registration hook, every instance's property registration, or successful behavior of a future patcher. Multiplayer testing of that implementation is downstream validation, not evidence claimed here. No game was launched and no installation, account setting, save or mod was changed during this investigation.

The snapshot handler calls world-load scripts after the conditional map-load branch on the successful path, including when the same-map branch skips reconstruction. Consequently `OnWorldLoad` can run again against retained objects. Re-entry needs an operation identity and a current world/graph identity, with ownership checks against actual registrations and membership, rather than a process-wide boolean or an assumption that callbacks create fresh objects. Source: `GlobalGameManager.HandleClientDidReceiveSnapshot` and `AssetPackManager.ExecuteMainScriptsOnWorldLoad`.

Stable, collision-free authored span and operation identifiers make local reconciliation reproducible on each peer. The inspected snapshot does not transmit circuit-set or span identity, so this source does not prove that matching span IDs are a native networking requirement. If a separate registered shared property object is used, its registration identifier and keys must address the same shared state across peers; no new shared property is required merely to construct local equipment. The native crossing controller starts its own local detection coroutine without a host check. The DLL guide's host check applies to mod-authored once-per-session shared writes, not to disabling this native local coroutine on clients. The inspected sources do not establish that every crossing's keys are registered for synchronization or require a patcher to write them.
