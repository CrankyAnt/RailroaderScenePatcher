# Map-mod ownership and patch loading

Research for [Identify map-mod ownership and patch-loading entry points](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/6), serving [Define the first usable Railroader Scene Patcher](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/3). Inspected 2026-11-07. This is static evidence, not a live test or a specification.

## Findings

A map definition, a pack, a map layer and the editor's writable document are different identities. A pack is identified by `Info.json`'s `domain/id`, not its directory name. The supported editor opens a Map definition in a `ModDev` pack and saves that pack's map data. The definition can inherit other map definitions without making their packs the authoring owner. Map layers use definition identifiers, topmost first, and the selected map is above its layers. A shared ancestor composes once. Terrain is a separate flat list. Missing layers and cycles fail loading. [Asset packs](https://docs.railroadergame.com/modding/asset-packs/); [map modding](https://docs.railroadergame.com/modding/map-modding/).

The game documents required dependencies in `Info.json`; it refuses to load a mod when a required dependency is absent or incompatible. An installed DLL pack also needs the experimental unsafe DLL setting and a restart. If disabled, the DLL pack itself does not load. The supported `IModContext` gives a DLL its own mod identifier and directory, plus optional dependency checks. It does not document enumeration of other enabled packs or the current editable map. `OnWorldLoad` is a world lifecycle callback, but the documented contract does not establish that it occurs at a safe point for changing pre-existing scene components. [DLL mods](https://docs.railroadergame.com/modding/dll-mods/); [Info.json](https://docs.railroadergame.com/modding/info-json/).

Consequently a dependency cannot discover all enabled dependants' arbitrary JSON using the documented DLL context alone. A dependant's required-dependency declaration activates the dependency, but is not a registration or a callback that hands the dependency the dependant's path. Discovery needs an additional explicit registration mechanism or an unsupported game-internal enumeration. Neither a file name nor a schema is chosen here. Multiple enabled packs may contain candidate data, and enabled status alone does not establish relevance to the selected map. No scene-patch ordering or conflict semantics follow from native map-layer ordering.

## Internal candidates in the inspected build

The installed experimental `Railroader.dll` is assembly version `0.0.0.0`, SHA-256 `8e9acfd583c1da79655c970773d42f2179e999f62dc36a3c6bc3a7b94c27a91e`. The prior [0.6.2 audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/JsonLoaderAudit.md) identifies the installation as 0.6.2. The hash identifies the inspected binary more precisely than the assembly version. Mono.Cecil metadata and IL were inspected read-only; these are implementation details, not supported APIs.

- `Model.Database.AssetPackManager.OrderedPacks` returns `_orderedPacks`. Its nested `PackEntry` exposes `Info`, `Store`, `ScriptLoader` and `Scope`; `AssetPack.Runtime.AssetPackRuntimeStore` exposes `Identifier`, `BasePath` and `Writeable`. These are candidates for enumerating loaded packs and locating their roots, subject to verifying collection membership and timing in the target route. A filesystem scan of `Mods` or `ModDev` alone cannot prove a pack is enabled. Pack roots need not equal the dependency's `IModContext.ModDirectory`.
- `Game.ActiveMapDefinition.Current` stores a typed Map definition and `Identifier` reads that definition's identifier. `Activate` resolves its `MapData` using the definition identifier, resolves terrain and map layers, records `MapDataAbsolutePath`, `MapLayerIdentifiers`, `MapLayerDataPaths`, and records `IsEditTarget`. `Model.Database.AssetPackManager.GetPackBasePathForDefinition(identifier)` looks up the definition entry and returns its store's base path. This is a candidate route from the active editor definition to its pack root, provided the editor target and store are verified and the store is writable. Do not infer ownership merely from `MapDataAbsolutePath`, since its asset reference can resolve in another pack.
- `AssetPackManager.TryResolvePackForEditing` resolves selection for a named pack and can report refusal; `ApplyPackForEditing` applies the resulting recorded and client configurations. `AvailableDevPacks` enumerates filtered discovered packs. Their existence does not prove that the active Map definition belongs to a particular editor pack in every route, nor that a separately loaded installed copy is writable.
- `AssetPackManager.GetDataAssetPath` resolves an asset reference with a contextual definition and looks up the resolved pack. `IAssetPackSource` has `Identifier`, `BasePath` and `IsWriteable`, while `FilesystemAssetPackSource` has `GetModsPath` and `GetModDevPath`. Source roots and individual pack roots must not be conflated.

## Map loading and scene changes

The official map documentation says the editor reads map data without `modifyMap` patches. In normal loading, each pack's `Data.rl` `modifyMap` runs in dependency order against in-memory map JSON before deserialization. The [prior audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/JsonLoaderAudit.md) traces `Game.MapLoader.LoadMapData` to `Track.MapDataLoader.Load`, `Track.Serialization.MapDataIO.LoadComposed`, `Game.MapLoader.MutateMapJson`, and `MapDataScriptManager.ExecuteOnMapData`. `MapDefinition` contains map data and map-layer references, not a scene path. This native JSON path composes map DTOs; it does not supply a proven operation on existing Unity scene components. The selected base scene and graph/map data therefore cannot stand in for the writable mod owner. The [prior save and editor observations](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/4c00445b048adccb6920c238116d1f7e1e915db9/Research/FinalObservations.md) are bounded evidence, not proof of a general hook.

## Remaining empirical checks

These checks require a disposable test setup and were not run in this research. Record build hash, selected definition ID, edit-target flag, loaded pack IDs, store roots and writable flags without publishing user-specific paths.

1. Open two distinct writable map definitions, including one layered over a map in another pack. Compare `Current.Identifier`, definition-store root, data-asset root and editor-selected pack. Expected output is a per-session mapping and an explicit failure when the target cannot be identified or is not writable. This checks ownership, including cross-pack data references.
2. Enable two independent packs and disable a third; include a pack requiring the DLL dependency and one with a missing requirement. Compare `OrderedPacks` and `PackEntry` values with the mod manager's resolved selection in both editor and save routes. Record whether activation and roots match; do not infer scene-patch relevance or order from this test alone.
3. Instrument lifecycle and scene object readiness on fresh load and reload in both editor and save routes. Record callback order, object availability, registration side effects, unload and re-entry. `OnWorldLoad` timing relative to all required scene lifecycle callbacks is not established by the documented name or this static inspection.
4. Test missing, version-incompatible, disabled and unsafe-DLL-blocked dependencies with disposable packs. Record each pack's actual enabled/refusal state and whether its code and data are considered. No claim is made here that declaring a dependency alone discovers or filters arbitrary patch files.

The official pages are first-party current documentation, not a version-pinned copy of the installed build. Internal details can change without notice. This report does not choose a JSON contract, a conflict policy, a patch hook, or a product workflow.
