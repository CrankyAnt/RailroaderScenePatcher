# Editor diagnostic investigation

Research for [issue 14](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/14), serving the [authoring decision](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/8). A diagnostic window, explicit discovery, camera focus and a bounded edit/undo/redo sequence worked in the tested session. The probe does not automatically refresh its displayed snapshot. Its scans and display use the same implementation. Native inspector observations independently check the representative node and its removal, but do not establish a complete inventory.

## Observed sequence

At entry the probe logged controller identity `-780557148` and subscriptions to `GraphEditor.NodeDidChange` and `UndoManager.DidChange`. Scan 1 found active Mjd8 with missing Sozu and `resolved=False`, active M5pp with existing Shuo and moved endpoints, inactive Mpg1 on existing Shp7, and the independent Sylva board. M5pp's game-space board position was approximately `(25201.1465, 622.7342, -778.0820)` and its calculated Shuo point was `(25223.7656, 623.3010, -779.0695)`. In the earlier base scan those values were approximately `(25201.1465, 622.7342, -778.0820)` and `(25203.7656, 623.3010, -779.0695)`. The 20 m X change is consistent with the deliberate fixture, not by itself a general error classifier.

The probe requested camera focus on Shuo end B, node N51l, at `(25227.7383, 623.376, -768.012)` without changing native selection. The parent reports that the native inspector displayed N51l after the node was selected. It displayed the original, moved, undone and redone X values, and the deletion and restoration. The log records the focus request and probe scans but does not capture the native inspector. The earlier Boot02 board-focus observation likewise showed the board while the native inspector reported no selection, according to the operator; its log records the request.

| Step reported by operator | Explicit scan | Recorded result |
| --- | --- | --- |
| Move N51l | 2 | Node X changed from `25227.7383` to `25228.74`; Shuo point changed to `(25224.56, 623.2979, -779.4447)`. |
| Undo move | 3 | Node X and Shuo point returned to the scan 1 values. |
| Redo move | 4 | Node X and Shuo point returned to the moved values. |

| Undo deletion | 8 | Shuo resolved again with the original fixture endpoint and curve point. |

For each of the first three move/undo/redo actions the log recorded one node-change event followed by one undo-manager change event. A further node-change and undo-manager event occurred before the deletion, without a subsequent scan to establish its state. For the deletion and its undo/redo/undo, each logged two node-change events followed by one undo-manager change event. Event entries do not carry an operation ID or node ID, so this ordering is a bounded correlation to the operator's sequence, not a complete notification contract. No conclusion is supported for untested segment property edits, drag previews or other object families.

The parent reports screenshots showing the displayed diagnostic snapshot remained stale until explicit rescan. That matches the probe implementation, which logs events without calling `Scan`; the probe log records only explicit snapshots. The parent reports the native inspector independently showed N51l's before, moved, undo and redo positions and the node's deletion and restoration. Those observations check the relevant graph state against the explicit scan; they are not an exhaustive independent scene inventory. The separately implemented SceneProbe also discovered the independent board and its active state in Boot02. Boot03 and Boot04 SceneProbe logs separately report M5pp and a matching named-location registration, but those reads were in separate sessions and do not independently validate every edit step. An authoring design can require an explicit rescan based on this experiment, while automatic refresh remains a design and validation question. A broad undo-manager notification is a candidate trigger, not proof of complete coverage or correct timing.

On exit the probe logged both unsubscriptions, controller `none`, and behaviour destruction. Earlier in the same capture it had entered this fixture, exited, and later attached again with a different controller identity and working scan. After the final edit-session exit and a separate fixture, the same process re-entered the inventory fixture. Controller `-1749754716` subscribed to both callbacks; scan 1 again found missing Sozu, restored shifted Shuo, inactive Mpg1 and the board. The logged instance IDs changed. On application exit both subscriptions were removed and the behaviour was destroyed. The operator reports seven expected warnings and no map save. These observations support bounded session cleanup and re-entry, not absence of every leaked callback or reliable disable/re-enable. The ownership capture also records world unload and mod unload/load around exit. The test did not establish general stable IDs, an exhaustive inventory, native selection of arbitrary scene objects, or all floating-origin cases. In Boot02 the same board's game coordinates stayed approximately stable after a reported origin shift within floating-point rounding.

## Decision and gaps

For issue 8, the evidence supports considering a separate editor diagnostic window with explicit rescan and camera focus, while treating native selection and scene-object discovery as separate functions. This path depends on unsupported internals and the scan covers only named representatives. The test does not establish editing, saving or safe mutation of scene objects.

The bounded discovery and edit sequence have probe logs and independent native-inspector or separate-probe checks for representative state. The supplied screenshot observations support the stale-display finding, but the screenshot files were not present in the inspected evidence folder. Fixture entry, exit and re-entry were observed before the final Boot04 exit. The subsequent same-process fixture re-entry and exit also completed with the original fixture state in the explicit scan. Complete notification coverage, a saved reload of the final edited state and arbitrary-object selection were not demonstrated and must not be implied. A full scene inventory or exhaustive event test is outside the ticket's bounded feasibility question. No game runtime, tracker or shared installation was changed while preparing this report.
