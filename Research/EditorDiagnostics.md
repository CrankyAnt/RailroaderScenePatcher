# Editor diagnostic investigation

Research for [issue 14](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/14), serving the [authoring decision](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/8). A diagnostic window, explicit discovery, camera focus and a bounded edit/undo/redo sequence worked in the tested session. The probe does not automatically refresh its displayed snapshot. Its scans and display use the same implementation, so the logs alone do not independently establish inventory completeness or refresh correctness.

## Observed sequence

At entry the probe logged controller identity `-780557148` and subscriptions to `GraphEditor.NodeDidChange` and `UndoManager.DidChange`. Scan 1 found active Mjd8 with missing Sozu and `resolved=False`, active M5pp with existing Shuo and moved endpoints, inactive Mpg1 on existing Shp7, and the independent Sylva board. M5pp's game-space board position was approximately `(25201.1465, 622.7342, -778.0820)` and its calculated Shuo point was `(25223.7656, 623.3010, -779.0695)`. In the earlier base scan those values were approximately `(25201.1465, 622.7342, -778.0820)` and `(25203.7656, 623.3010, -779.0695)`. The 20 m X change is consistent with the deliberate fixture, not by itself a general error classifier.

The probe requested camera focus on Shuo end B, node N51l, at `(25227.7383, 623.376, -768.012)` without changing native selection. The parent reports that a native node selection was then made for the edit; the log records the focus request but not the selection or viewport result. The earlier Boot02 board-focus observation likewise showed the board while the native inspector reported no selection, according to the operator; its log records the request.

| Step reported by operator | Explicit scan | Recorded result |
| --- | --- | --- |
| Move N51l | 2 | Node X changed from `25227.7383` to `25228.74`; Shuo point changed to `(25224.56, 623.2979, -779.4447)`. |
| Undo move | 3 | Node X and Shuo point returned to the scan 1 values. |
| Redo move | 4 | Node X and Shuo point returned to the moved values. |
| Delete N51l and its connection | 5 | M5pp reported `segmentExists=False` and `resolved=False` for Shuo. |
| Undo deletion | 6 | Shuo resolved again and the scan reported the original fixture endpoint and curve point. |
| Redo deletion | 7 | Shuo was missing again. |
| Undo deletion | 8 | Shuo resolved again with the original fixture endpoint and curve point. |

For each of the first three move/undo/redo actions the log recorded one node-change event followed by one undo-manager change event. A further node-change and undo-manager event occurred before the deletion, without a subsequent scan to establish its state. For the deletion and its undo/redo/undo, each logged two node-change events followed by one undo-manager change event. Event entries do not carry an operation ID or node ID, so this ordering is a bounded correlation to the operator's sequence, not a complete notification contract. No conclusion is supported for untested segment property edits, drag previews or other object families.

The parent reports that the displayed diagnostic snapshot remained stale until explicit rescan. That follows the probe's implementation, which logs events without calling `Scan`; the log records only the resulting explicit snapshots, not screenshots of the stale display. Explicit rescan produced values consistent with the reported operations. An independent fresh inventory after each change was not captured: the displayed data and logged scan are the same read path, and native selection is not an independent full graph comparison. An authoring design can require an explicit rescan based on this experiment, while automatic refresh remains a design and validation question. A broad undo-manager notification is a candidate trigger, not proof of complete coverage or correct timing.

On exit the probe logged both unsubscriptions, controller `none`, and behaviour destruction. Earlier in the same capture it had entered this fixture, exited, and later attached again with a different controller identity and working scan. The final exit has no later fixture entry in this log. These observations support bounded session cleanup and re-entry, not absence of every leaked callback or reliable disable/re-enable. The ownership capture also records world unload and mod unload/load around exit. The test did not establish general stable IDs, an exhaustive inventory, native selection of arbitrary scene objects, or all floating-origin cases. In Boot02 the same board's game coordinates stayed approximately stable after a reported origin shift within floating-point rounding.

## Decision and gaps

For issue 8, the evidence supports considering a separate editor diagnostic window with explicit rescan and camera focus, while treating native selection and scene-object discovery as separate functions. This path depends on unsupported internals and the scan covers only named representatives. The test does not establish editing, saving or safe mutation of scene objects.

The ticket's specific sample and edit sequence have useful evidence, including re-entry and cleanup. Strict closure remains a judgment for the parent: the requested comparison to an independent fresh inventory and a direct, auditable record of the displayed stale state are missing. A standalone reload of the final edited state, complete notification coverage and arbitrary-object selection were not demonstrated and must not be implied. No game runtime, tracker or shared installation was changed while preparing this report.
