# Candidate ownership on the experimental game line

Research for [Recover ownership of unresolved inventory candidates](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/20). This report identifies two retained marker hierarchies and separates a historical passenger warning from current native operations data. It records one read-only marker capture, not mutation or gameplay tests.

These are method paths and captured field links, not a test that either candidate was moved or that culling was restored. ## Ownership and decision consequences

The two captured roots are members of the loaded map-manager scene, with the listed components and no map-object spawner component on their captured ancestors or subtrees. Combined with the [typed editor and serializer audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/8d3bfc0/Research/NativeCapabilityAudit.md), this supports treating these instances as retained scene candidates for identity and authoring analysis. It does not prove their original asset serialization provenance, rule out an indirect DTO association, or establish a native map-mod save route. A component type or matching marker ID alone is not proof of a native DTO owner.

For [target identity](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/9), use the scene identity, full path, marker ID, type and binding together and validate uniqueness and registration per load. For [modder authoring](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/8), the captured retained roots and typed serializer boundary leave inherited-scene authoring unestablished. For the [operation investigation](https://github.com/CrankyAnt/RailroaderScenePatcher/issues/18), both candidates have a concrete marker and target relationship suitable for a separately scoped applicability investigation. Capture, registration and field references do not prove safe rebind, movement, group behavior, restoration, persistence, or yard and station gameplay effects. Mkwd's culler adds a distinct renderer-state dependency; Mi4f's recorded hierarchy does not contain that component. No claim of absent world consumers follows from the bounded scan.

## Probe and limits

The independently authored `CandidateProbe/` uses the lifecycle and explicit GUI capture pattern in [ApplicableProbe](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/b41a6dda255accf2de1949414b35ea37f4b8d63c/Research/ApplicableProbe/ApplicableProbe.cs). It reads marker fields, ancestor and subtree components, track-relative target subtrees, graph registrations and direct loaded-scene field references. Target subtrees are capped at 256 nodes with truncation logged. It does not mutate the scene or save. The capture is a point-in-time observation; it does not establish behavior across reloads or identify consumers outside that scan.

The successful build used the installed game assemblies and emitted no warnings. The executed source file SHA-256 is `CE06364095E53DD3888F26C2A1E8B3FCDE660DFA01F4A3E64FE4684FB55446F5`; the executed DLL SHA-256 is `FE53DB84FED51492C9809152D4B5834498D0152C3C3B72DFCE2D24F8158F7040`. The retained [source](CandidateProbe/CandidateProbe.cs) hashes to `035C3E6CF324F87F88D7DB71642E50C033BA71E5643298765DCAD0B8AC5185EE`. Before publication, exact text comparison verified that replacing CRLF with LF in the executed source yields the retained source, with no other changes. This complies with `.gitattributes`; the capture received the same line-ending normalization. No vendor binary is copied into the probe output.

## Passenger ownership and applicability

The [original passenger warning](https://discord.com/channels/795878618697433097/1275391753129562113/1541491926044516383) was recovered in authenticated Discord search. Its timestamp is 2026-08-24 at 18:58 Europe/Amsterdam. It names FUSE passenger stop `ela`, component `ela-house.ela` and invalid span `Pbhv`. The matching historical [`FusePassengerStopComponent.ResolveBoundSpans`](https://github.com/F-U-S-E-E/FuseDevelopmentGroup/blob/1eeef152ec57066bb7a90e1ef6edb27f6018e690/FUSE/Runtime/API/FusePassengerStopComponent.cs#L229-L269) filters invalid bindings when refreshing the FUSE passenger stop. The historical source's [requirements](https://github.com/F-U-S-E-E/FuseDevelopmentGroup/blob/1eeef152ec57066bb7a90e1ef6edb27f6018e690/README.md) name Railroader 2025.1.x. This previous-version incident is outside the current 0.6.x experimental investigation. It supplies neither a current defect nor a retained-scene repair target; recovering its old package is unnecessary for this investigation. The matching source does not establish the historical installed FUSE version or the original cause.

The current installed `Railroader_Data/StreamingAssets/AssetPacksCore/nc-bryson-terrain/Data/Map.json`, lines 20650-20670, defines industry `ela-house`, component `ela` of kind `PassengerStop`, referencing operations span `ela-station`. Its endpoints are `Sp4e8|b|15.36455` and `Sp4e8|a|30.4624`. The file SHA-256 is `79E157E65BFCAA0B7701C3E3AB8689EC81E8A1F18EF353E63399AA1D1A140C62`. This is a concrete native map-data owner, distinct from historical `Pbhv`. No vendor file is reproduced here.

The inspected native `IndustryDataLoader.CreatePassengerStop` resolves `PassengerStopDTO.trackSpans` through its span lookup and assigns them to the stop. `PassengerStop.FindCars` queries cars on those spans and filters stopped passenger cars. These static paths identify the native passenger consumer, not successful current gameplay. The [native capability audit](https://github.com/CrankyAnt/RailroaderScenePatcher/blob/8d3bfc0005d15e8b0404fc584479bd60f385c4fd/Research/NativeCapabilityAudit.md) identifies the operations DTO editor and save path. `StationAgent.passengerStopId` is a distinct scene-to-operations lookup, not evidence that it owns the historical span. The current [map guide](https://docs.railroadergame.com/modding/map-modding/), checked 2026-11-08, says passenger stops can be defined but are not yet usable in game.

For authoring and identity, use the current operations industry, component and span IDs for this native case. It does not justify a DLL scene repair. No separate current passenger scene target was established, and no family-wide exclusion follows. The operation investigation receives no passenger mutation case from the old warning.
